# Bulletin解析（JSON出力）

指定された処理について、**処理対象までの振る舞いを一本線で追跡するコードリーディング資料**をJSONで作成する。

目的は、関連コードを網羅的に説明することではない。

> **「この振る舞いは、どこから始まり、どのコードを通り、どこへ到達するのか」**

を、実コード上の根拠を確認しながら一本道として追える資料にする。**クラスを追うのではなく、振る舞いを追う。**

## 表記

値の中で Bulletin と書く場合は、すべて **「Bulletin解析」** と書く。キー名 `bulletinEnd` / `bulletinStopped` は変えない。

## 出力ファイル

プロジェクトルート直下に次の形式で作成する。

```text
ngbi-{2桁連番}-{日本語タイトル}.{YYMMDD}.json
```

| 要素 | 決め方 |
| --- | --- |
| `{2桁連番}` | プロジェクトルート直下の `ngbi-[0-9][0-9]-*.json` の最大番号 + 1。該当がなければ `01` |
| `{日本語タイトル}` | 追跡する振る舞いを、クラス名ではなく利用者視点の1文で書く。空白と `/ \ : * ? " < > \|` および `` ` `` は除く |
| `{YYMMDD}` | 作成日（`date +%y%m%d`） |

- `ngbi-01-実験一覧の行を右クリックしてメニューを表示する.260918.json`

連番は次のコマンドで確認する。

```bash
ls ngbi-[0-9][0-9]-*.json 2>/dev/null | sed -E 's/^ngbi-([0-9]{2})-.*/\1/' | sort -n | tail -1
```

## 作業手順

1. **終了地点を確定する** — 指示された「処理内容」がどのコードへの到達を指すのかを決める。
2. **開始地点を特定する** — ボタンクリック、右クリック、入力値変更、`formControl` 変更、`output` イベント、Route遷移、Component初期化、Signal変更、Store Action、外部イベント、APIレスポンスなど。開始地点そのものが不明な場合は、確認できた最上流地点を `index:0` の地点とし、`trigger.接続根拠` にその旨を書く。
3. **接続を実コードで1本ずつ裏取りしながら前進する** — テンプレートのバインド、`emit` の受け手、`dispatch` を監視する Effect、呼び出されるメソッドを grep 等で確認する。推測で経路を繋がない。
4. **本線の地点を確定する** — 地点を発生順に並べ、各地点を配列の1要素にする。
5. **JSONを書く**（下記の構造と整形に従う）。
6. **検証と自己レビューをして修正する**（末尾のチェックリスト）。

## JSON構造

トップレベルは**地点オブジェクトの配列**。処理の発生順に並べる。

```json
[
  {
    "hr": "index:0, --------------------------------------------------",
    "name": "{この地点で起きること}",
    "trigger": {
      "呼び出し元": "ユーザー",
      "イベント": "{利用者の操作}",
      "接続根拠": "{この地点が実行される実コード上の根拠}"
    },
    "implementation": {
      "コンポーネント": "{Class}",
      "メソッド": "{method}",
      "リンク一覧": [
        "code -g {path}:{line}"
      ]
    },
    "componentOverview": {
      "表示内容": "{何を表示するComponentか}",
      "データ受取元": "{Class}",
      "受取データ": ["{データ}", "{データ}"],
      "通知先": "{Class}",
      "通知内容": "{output名}"
    },
    "process": {
      "使用技術": ["{技術}", "{技術}"],
      "コード": "{中心となる1行}",
      "処理内容": "{この地点が担当する処理}"
    },
    "effects": [
      { "影響名": "{変化・再計算・再描画など}" }
    ]
  },
  {
    "hr": "index:1, --------------------------------------------------",
    "name": "{この地点で起きること}",
    "trigger": {
      "呼び出し元インデックス": 0,
      "呼び出し元": "{Class.method()}",
      "イベント": "{output名など}",
      "接続根拠": "(xxx)=\"yyy($event)\""
    },
    "...": "...",
    "bulletinEnd": "{到達点}へ到達。{その先の処理}は対象外"
  }
]
```

### 地点オブジェクト

キーは次の順序で置く。

| キー | 必須 | 内容 |
| --- | --- | --- |
| `hr` | 必須 | 地点番号を兼ねた区切り線。`"index:{番号}, --------------------------------------------------"` の形で書く。番号は0始まりの連番、`, ` の後ろは半角ハイフン50個で固定。`"index"` キーは単体で置かない |
| `name` | 必須 | この地点で起きることを動詞句で書く（例: `行の右クリックを検出`）。クラス名にしない |
| `trigger` | 必須 | この地点が実行される理由 |
| `implementation` | 必須 | この地点のコード位置 |
| `{種別}Overview` | 必須 | 地点の種別ごとの概要。Componentなら `componentOverview` |
| `process` | 必須 | この地点で行う処理 |
| `precondition` | 任意 | 本線より前に準備されている前提で、本線の理解に必要なもの |
| `effects` | 必須 | 影響範囲（NgRx Effect ではない） |
| `bulletinEnd` | 最後の地点のみ | 到達点。追跡不能で止まる場合は代わりに `bulletinStopped` |

### trigger

| キー | 必須 | 内容 |
| --- | --- | --- |
| `呼び出し元インデックス` | `index:0` の地点以外 | 呼び出し元となった地点の `hr` にある番号（数値） |
| `呼び出し元` | 必須 | `ユーザー`、`TableComponent.openContext()`、`TableComponent template` など |
| `イベント` | 必須 | output名、Action名、テンプレートイベント名。直接呼び出しなら `openMenu({x, y})の直接呼び出し` |
| `接続根拠` | 必須 | 前の地点からここへ来る**実コード上の根拠**。バインドは `(rowRightClick)=\"openContextMenu($event)\"` のようにコードのまま書く |

### implementation

| キー | 必須 | 内容 |
| --- | --- | --- |
| `コンポーネント` / `定義` | 必須 | Componentなら `コンポーネント` にクラス名。それ以外は `定義` に Effect・Service のクラス名、または reducer・selector・action の const 名。複数にまたがる場合は `A / B` |
| `メソッド` | メソッドがある場合 | メソッド名（`()` なし）。複数なら `updatePosition / openMenu` |
| `リンク一覧` | メソッドがある場合 | この地点を読むのに必要なコード位置の配列。メソッド定義、そのメソッドが使うメンバー（signal / output / viewChild など）、接続を示すテンプレートのバインドを3個前後 |
| `実装箇所` | メソッドがない場合 | テンプレート上の属性・イベントが実装である地点で使う。`[{ "シンボル": "pContextMenuRow", "リンク": "code -g ..." }]` |

### {種別}Overview

今回の振る舞いに必要な範囲だけを書く。子Componentやメソッドの一覧にしない。

| キー名 | 中のキー |
| --- | --- |
| `componentOverview` | `表示内容` / `この地点の役割`（表示内容だけで役割が伝わらない場合） / `データ受取元` / `受取データ` / `通知先` / `通知内容` |
| `actionOverview` | `dispatch元` / `payload` / `受取先` |
| `effectOverview` | `受取Action` / `RxJSオペレーター` / `呼び出し先` / `成功時dispatch` / `失敗時dispatch` |
| `reducerOverview` | `対象Action` / `変更するState` / `変更内容` |
| `selectorOverview` | `参照State` / `抽出・変換内容` / `利用元` |
| `serviceOverview` | `呼び出し元` / `引数` / `戻り値` / `次の呼び出し先` |
| `apiOverview` | `HTTPメソッド` / `エンドポイント` / `リクエスト` / `レスポンス` / `呼び出し元` |

`通知内容` が output ではない場合は、`outputではなくopenMenu()を直接呼び出す` のように接続方法を書く。

### process

| キー | 必須 | 内容 |
| --- | --- | --- |
| `使用技術` | 必須 | この地点の振る舞いに関わる技術だけを配列で書く（例: `Angular signal`、`viewChild.required`、`PrimeNG p-table`） |
| `処理内容` | 処理が1つの場合 | この地点が処理全体の中で担当することを1文で書く |
| `処理手順` | 処理を順に複数行う場合 | 手順の配列 |
| `コード` | 任意 | この地点の中心となる1行のコード |
| `出力コード` | 任意 | 次の地点へ渡す emit / dispatch / 呼び出しのコードを、`コード` と別に示す場合 |
| `後処理` | 任意 | 主処理の後に行う処理の配列 |
| `{対象}分岐` | 任意 | 本線の理解に必要な分岐。`{ "条件": "結果" }` の形（例: `選択分岐`）。本線でない分岐先は深追いしない |
| `{値}の流れ` | 任意 | 値が層をまたいで形を変える場合に `"A → B → C"` の形で書く（例: `座標の流れ`） |
| `補足` | 任意 | 誤解しやすい点を1文で書く |

### precondition

```json
"precondition": {
  "説明": "{本線より前に何が準備されているか}",
  "経路": [
    "{準備の手順}"
  ],
  "リンク一覧": [
    "code -g {path}:{line}"
  ]
}
```

追跡中に本線外の重要そうな処理を見つけた場合も、必要ならここか `process.補足` に一言で記録するにとどめ、深追いしない。

### effects

| キー | 必須 | 内容 |
| --- | --- | --- |
| `影響名` | 必須 | この地点によって起きる変更・再計算・再描画・再取得・処理担当の移動など |
| `画面変更` | 任意 | 見える表示が変わるなら `true`。変わらないことを明示したい場合は `false` |
| `条件付き` | 任意 | 分岐条件を満たす場合だけ起きるなら `true` |

影響範囲に書いたものを無条件に追跡しない。処理対象へ到達するために必要な場合だけ、次の地点として本線へ昇格させる。

### bulletinEnd / bulletinStopped

最後の地点に到達点を書く。その先に処理があっても、今回の目的外なら追跡しない。

```json
"bulletinEnd": "メニュー表示へ到達。メニュー項目クリック後は対象外"
```

途中でコード上の接続関係が確認できなくなった場合は、推測して先へ進まない。確認できた最後の地点に `bulletinEnd` の代わりに次を置く。

```json
"bulletinStopped": {
  "確認済み": ["FooComponent", "foo.emit()", "BarComponent"],
  "不明": ["foo.emit() を受け取る処理"],
  "説明": "次の処理への接続を実コード上で確認できないため、推測で補完せず追跡を停止"
}
```

## 値の書き方

- **リンクは `code -g {プロジェクトルートからの相対パス}:{行}` で書く。** 先頭に `./` を付けず、`#L` 形式は使わない。
  - 例: `"code -g src/app/webapp-common/shared/ui-components/data/table/table.component.ts:421"`
- 行番号は `grep -n` 等で実コードと一致することを確認してから書く。
- `データ受取元` / `受取データ` / `通知先` / `通知内容` などは、1つなら文字列、複数なら配列にする。
- 確認できない値は `"不明"` と書く。推測で埋めず、キーを省いて不明を隠さない。
- 任意キーは該当しなければ省略する。`null` や空文字は入れない。
- 文字列中のダブルクォートは `\"` でエスケープする。
- 値は常体の短い文で書く。コードは転載せず、中心となる1行だけを `コード` / `出力コード` / `接続根拠` に入れる。

## 整形

見本と同じく、読みやすさを優先して整形する。`JSON.stringify(data, null, 2)` のような一括整形はしない。

- インデントは半角スペース2つ。
- 短い文字列の配列（`使用技術`、`受取データ`、`通知内容` など）は1行で `["a", "b"]` と書く。
- `リンク一覧`、`処理手順`、`経路`、`後処理`、`実装箇所` は1要素1行にする。
- `effects` の要素は、キーが `影響名` だけなら1行で `{ "影響名": "..." }` と書き、複数キーなら展開する。

## 追跡ルール

### 本線だけを追う

関連コードを全部調査しない。常に **「今回追っている振る舞いの一本線はどこか」** を基準にする。

- 対象Componentが多数の子Componentを持っていても、今回の処理に関係しないものは追跡しない。
- Serviceに多数のメソッドがあっても、今回呼ばれるメソッドだけを追跡する。
- Effectに複数Actionの処理があっても、今回のActionに関係する処理だけを追跡する。

### 実コードで確認できた経路だけを書く

`ユーザー操作 → Template → Component → output → 親Component → Store Action → Effect → Service → API` は一例にすぎない。実際のコードをこの形へ当てはめない。

### 上方向へ戻ってよい

子Componentから親へ `output()` される場合など、一時的にComponent階層を上へ戻ってよい。**実際の処理方向**に従って地点を並べ、Componentツリーの上下関係と処理の進行方向を混同しない。

## 検証

作成したファイルに対して次を実行する。

```bash
# JSON構文
python3 -m json.tool {file} > /dev/null && echo "json ok"

# リンク先の実在と行内容（各行の内容が意図したコードか目視で確認する）
grep -oE 'code -g [^"]+:[0-9]+' {file} | sort -u | while read -r _ _ loc; do
  f=${loc%:*}; l=${loc##*:}
  printf '%s  ' "$loc"
  if [ -f "$f" ]; then sed -n "${l}p" "$f" | sed 's/^[[:space:]]*//' | cut -c1-80; else echo MISSING; fi
done
```

## 完成時の自己レビュー

ファイル作成後、必ず次を確認し、問題があれば修正してから完成とする。

- [ ] ファイル名が `ngbi-{2桁連番}-{日本語タイトル}.{YYMMDD}.json` で、連番が既存と重複していないか
- [ ] JSONとして構文エラーがないか
- [ ] `hr` の `index:{番号}` が0からの連番で、`呼び出し元インデックス` が実在する地点を指しているか
- [ ] 各地点の `trigger.接続根拠` に、前の地点からここへ来る実コード上の根拠が書かれているか
- [ ] リンクがすべて `code -g パス:行` 形式で、ファイルが実在し、行番号が実コードと一致しているか
- [ ] 関係ない処理を深追いしていないか（Overview が子Componentやメソッドの一覧になっていないか）
- [ ] 推測を事実として記載していないか
- [ ] 最後の地点に `bulletinEnd`（または `bulletinStopped`）があり、指定された処理対象へ到達しているか
- [ ] 値の中の表記が「Bulletin解析」になっているか
