段の区切りは、答えている問いで分かれている。
1〜2 が「何を」、3〜4 が「どう作ったか」、5〜6 が「何を入力にしているか」、
7〜9 が「何が出てくるか」、10〜11 が「何をもって良しとするか」、12 が「その後どうするか」である。

### 読み終えたときに説明できるはずのこと

要件（01）の各項目が、どの構成要素（04）で実現され、どの方式（03）で作られ、
どの Dataset（10・21）を入力に、どのモデル（20）を生み、どの基準（23・33）で出荷され、
誰が運用する（40）か。この鎖を1本たどれることが、この順序の目的である。

たどれない箇所が見つかった場合、それは読み落としではなく、文書の側の欠落である可能性がある。
`backlog/` に、着手していないものが着手条件つきで並んでいる（[backlog/00_未解決ストーリー一覧.md](backlog/00_未解決ストーリー一覧.md)）。

### この順序に入れていないもの

* 実際に動かす手順。`_archive/runbooks/` の9本にあり、§5 の表から引く
* 判断の経緯。`_archive/adr/` の10本にあり、03 と 61 から参照している
* セキュリティ・データ管理・プロジェクト管理の各文書。上の鎖をたどるには要らないが、
  その領域に入るときは 50・11〜13・70〜76 を §3 の一覧から引く

### 確かめていないこと

この順序で読んだ人が対応関係を説明できたか、という確認は取れていない。
書いた本人には判定できない。本人は、文書に書いていないことも知っているためである。
確認できる条件と、確認の仕方は [backlog/19_新規参画者の読み通し確認.md](backlog/19_新規参画者の読み通し確認.md) にある。

## 5. `_archive/` の扱い

`_archive/` の資料は更新しない。ADR 10本は意思決定の記録として、runbook 9本は実機で確認した手順として、
書かれた時点の内容のまま残す。新しい体系資料は、判断の経緯や具体的な操作手順を写し取らず、
`_archive/` の該当箇所へリンクする。

例外は、そのまま読むと操作を誤るパスの記述だけである。
併存リポジトリの移動に伴い、`../learn-ClearML` を `../001-learn-ClearML` へ書き換えた
（2026-09-13、runbook 001・004）。判断・手順・数値は書き換えない。

| 種別 | 本数 | 参照のされ方 |
| --- | --- | --- |
| `_archive/adr/` | 10 | 「なぜその方式を選んだか」の根拠。03・61・50・51 から参照する |
| `_archive/runbooks/` | 9 | 「どう操作するか」の手順。40〜44・22・50〜54・57 から参照する |
| `_archive/security/001_20260908_threat_model.md` | 1 | データ分類と信頼境界。02 と 50・53・54・57・58 から参照する |

移設に伴い、コード・設定・CI 内のパス参照（13ファイル）も `docs/_archive/` へ書き換えてある。
`x-plan-改訂/` 配下は履歴として凍結する取り決めのため、`docs/` の旧パスはそのまま残してある。
併存リポジトリのパスだけは、同じ理由で `将来的展望/02_20260912_将来TODO.md` も書き換えた。
