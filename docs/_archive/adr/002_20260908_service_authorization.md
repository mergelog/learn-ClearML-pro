# ADR 002: サービス間の認証・認可の方式

- 状態: 採用
- 日付: 2026-09-08
- 対象: 推論サービス（`services/prediction_api`）、ops-exporter（`services/ops_exporter`）
- 関連: `docs/_archive/security/001_20260908_threat_model.md`、計画書 P1-9

## 背景

推論サービスとops-exporterは、これまで誰でも呼べた。答えるのは予測結果、
提供中のモデル、Queueの滞留、ホストの資源であり、いずれも「このシステムが
いまどうなっているか」を語る。ローカル学習環境であってもこのまま検証環境へ
持っていける形にはならない。

必要なのは次の4つである。

1. 呼び手を特定できること（監査の1行に名前が残る）
2. 呼び手ごとに、できることが違うこと（最小権限）
3. 資格情報を平文で保存せずに済むこと
4. 資格情報を無停止で入れ替えられること

## 決定

**共有シークレット（Bearerトークン）＋役割ベースのアクセス制御**を採る。

- トークンは256ビットの乱数に `stk_` を付けたもの。発行は `pnpm sec:token`
- サービスが設定として持つのは、トークンのSHA-256（fingerprint）だけ
- 1つの呼び手（principal）は、名前・役割・複数のfingerprintを持つ
- 役割は3つ。`predictor`（predict, model:read）、`operator`（model:read,
  metrics:read）、`scraper`（metrics:read）
- 権限は業務の名前で定義し、経路名では定義しない
- 呼び手が設定されていないサービスは**起動しない**
- `/health` だけが無認証。答えるのは「プロセスが動いている」だけである

## 検討した選択肢

### A. 認証しない（現状維持）

ローカルだけなら成立する。しかし「検証環境へ出す直前に認証を足す」形になり、
そのときには経路が増えていて、どこに漏れがあるか分からなくなる。
また、認可の設計はデータの持ち方（誰が何を読めるか）に影響するため、
後付けにすると設計をやり直すことになる。却下。

### B. mTLS（相互TLS）

サービス間認証としては最も強い。呼び手の識別は証明書が担い、盗聴にも強い。

却下の理由は運用の初期費用である。認証局、証明書の発行と配布、失効、更新が
要る。このリポジトリでそれを人手なしに用意することはできず（証明書の発行は
人の作業である）、学習環境で「動かないもの」を作ることになる。
検証環境以降で、前段のTLS終端と合わせて再検討する。

### C. OIDC / JWT（IdP発行のトークン）

呼び手が人であれば妥当。有効期限、失効、属性を発行側で管理できる。

却下の理由は、必要なのが人ではなく機械の呼び手（Prometheus、バッチ、smoke）
であること、そしてIdPの登録が人の作業であること。この計画では
「ユーザ登録など人手が必要な項目はスキップする」方針を採っている。
IdPを置ける環境では、ここで定義した権限をそのままclaimへ写せる形にしてある
（権限が経路名ではなく業務の名前で定義してあるのはそのためである）。

### D. ClearMLの資格情報を流用する

サービスがClearMLの `access_key` / `secret_key` を検証する案。新しい資格情報を
増やさずに済む。

却下。ClearMLの資格情報は全権であり、「予測だけを呼べる呼び手」を作れない。
最小権限という要件を最初から満たせない。

## 決定の理由

- **fingerprintだけを保存する**: 設定の一覧（`.env`、compose、secret manager）が
  漏れても、それだけでは呼べない。認証情報を保存する場所を1つ減らせる
- **役割を3つに絞る**: 役割が増えるほど「どれを渡せばよいか」が曖昧になる。
  いま実在する呼び手（推論の利用者、運用者、Prometheus）に1つずつ対応させ、
  4つ目が要るときは仕事の名前で追加する
- **呼び手ゼロで起動しない**: 空の一覧には「誰も呼べない」と「誰でも呼べる」の
  2つの読みがあり、安全なのは前者だけである。起動を拒否すれば、設定漏れは
  起動時に分かる。開いたまま起動すると、気付くのは事故のときになる
- **`/health` を無認証にする**: プロセスを再起動する側（Docker、将来の
  オーケストレータ）が資格情報を持つと、資格情報の期限切れが再起動ループに
  なる。`/health` はモデルにも数字にも触れず、「動いている」以上を語らない
- **fingerprintを複数持てる**: 入れ替えは「新しいものを足す → 呼び手を移す →
  古いものを消す」の3手で、有効な資格情報が無い瞬間が生じない。
  無停止でできない更新は、結局行われない

## 影響

- 推論サービスとops-exporterは `*_CLIENTS` が無いと起動しない。
  ローカルでは `scripts/security-tokens.sh` が生成し、`backend:up` が渡す
- Prometheusはscrape時にトークンを提示する。`credentials_file` を使い、
  設定ファイル本体には書かない
- 既存のsmokeは資格情報を提示するようになり、併せて「名乗らない呼び出しが
  401」「権限の無い呼び出しが403」を確認する
- 監査ログに `event: access.decision` の行が増える。許可も拒否も記録する

## 見直す条件

次のいずれかが起きたら、この決定を見直す。

- サービスの呼び手が人になる（画面から直接呼ばれる）→ OIDCを再検討
- 検証環境以降でサービス間通信が同一ホストを越える → mTLSを再検討
- 役割が4つを超え、1つの呼び手に複数の役割が要るようになる → 権限の直接付与
