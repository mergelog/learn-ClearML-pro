# ADR 004: 実験設定を環境別に分け、探索は学習用の行だけで行う

- 状態: 採用
- 日付: 2026-09-09
- 対象: `config/experiment/`、`ml/experiment/`、`ml/semiconductor_quality`（設定と推定器）
- 関連: 計画書 P2-12、`docs/_archive/adr/001_20260908_learning_algorithm_choice.md`、
  `docs/_archive/runbooks/003_20260908_model_promotion.md`

## 背景

ここまでのハイパーパラメータの決め方は、`--n-estimators` を手で変えて
学習を回し、ClearMLの画面で見比べる、というものだった。次の3つが欠けている。

- 何を探したか。どの範囲を試したのか、どこで打ち切ったのかが残らない
- 何を良いとしたか。1回の validation の数字を見て人が判断していた
- 誰の予算で走ったか。手元でも本番でも同じ回数・同じ並列数になる

加えて、探索を入れると新しい危険が2つ現れる。

**選定と評価が同じ行を見てしまう。** 探索は数十回モデルを作る。そのたびに
validation を見て良し悪しを決めると、validation は「選定に使い切った行」に
なる。評価ゲートが同じ validation で判定しているので、ゲートは自分が
選んだものを自分で承認することになる。test を使えばもっと悪い。

**しきい値を動かすと、再現性の穴が見える。** 不良かどうかは確率を 0.5 で
切って決めていた。切る位置を動かして最適化すると、確率のわずかな違いが
判定を変える。RandomForest は木を並列に育てており、予測確率を足す順序が
実行ごとに変わるため、同じ種で学習しても下位桁が動いていた。

## 決定

### 1. 探索は学習用の行だけを見る

分割の3つの部分に、それぞれ1つの役目だけを持たせる。

| 部分 | 使う人 | 回数 |
| --- | --- | --- |
| train | 探索（fold分割して交差検証） | 何度でも |
| validation | 評価ゲート | 候補1件につき1回 |
| test | 最終評価 | 1回だけ |

探索は train を `folds` 個に分けて順に測り、その平均で候補を比べる。
validation には触れないので、探索が選んだ設定はゲートにとって初見である。
test は探索からも見えない。

`ml/experiment/trials.py` は train 以外の部分を渡されたら拒否する。
「うっかり」で崩れる決まりにはしない。

### 2. 確率のしきい値は候補ごとに、内側の分割で選ぶ

しきい値は探索の対象にしない。候補（木の本数など）が決まって初めて
「その候補にとっての最適な切り位置」が決まるためである。

各foldの学習側をさらに内側で分割し（`TunedThresholdClassifierCV`）、
そこで目的指標を最大化する位置を選ぶ。採点するfoldの行は使わない。
foldごとに選ばれた位置の**中央値**を、その候補のしきい値として引き継ぐ。
平均ではなく中央値にしたのは、1つのfoldの極端な選択に引きずられないため。

引き継がれたしきい値は `FixedThresholdClassifier` として学習済み
pipelineの中に入る。保存されるファイルがそのまま「その位置で切るモデル」に
なるので、推論サービス側に変更は要らない。

### 3. 森は1つの流れで育てる

`RandomForestClassifier(n_jobs=-1)` をやめ、`n_jobs=1` にした。

並列に育てると予測確率の下位桁が実行ごとに動き、しきい値の選択が変わる。
探索は「同じ設定なら同じ成績」を前提に候補を比べるので、それが崩れると
比較そのものが成り立たない。2,500行では1回あたり1秒に満たない代償である。

### 4. 実験設定は環境別に階層化し、資格情報は入れない

```text
config/experiment/base.yaml         探索の意味（何を変える・何を良しとする・どう判定する）
config/experiment/dev.yaml          予算とQueue
config/experiment/staging.yaml
config/experiment/production.yaml
```

`base` を読んでから環境の1枚を重ねる。環境が変えるのは、ほぼ予算とQueueだけで
ある。既定は `dev`。本番の予算で走らせるには `--environment production` か
`EXPERIMENT_ENVIRONMENT=production` を明示する必要がある。

読み込み時に3つを拒否する。

- 知らないキー（綴り違いが既定値で黙って走るのを防ぐ）
- 資格情報らしき値（W10の検出器をそのまま通す。接続情報は環境変数から読む）
- 各アルゴリズムが読まない設定を探索空間に挙げること

`model_gate.yaml` / `data_quality.yaml` / `security.yaml` は今回の階層化の
対象にしていない。合格基準やデータ契約は環境によって変わるべきものではなく、
変えられる形にするほうが危ない。

### 5. 探索エンジンは Optuna、依存は制御役だけに入れる

計画書が挙げる「早期停止」を実装するため、ClearML同梱の RandomSearch では
なく `OptimizerOptuna` を使う。試行はfoldごとに途中経過を報告し、Optuna が
見込みの無い候補をその場で打ち切る。`minimum_folds` に達するまでは
打ち切らないので、1 foldの不運で候補を捨てることはない。

optuna は `requirements/optimization.txt` にだけ入れる。試行Taskが要るのは
学習と同じ依存だけで、探索を進める側の依存を学習イメージや推論イメージへ
持ち込む理由はない。

### 6. 探索の成果物は「設定」であって「モデル」ではない

探索は勝った設定を Registry へ入れない。`--handoff` で学習Pipelineへ渡し、
Pipelineが train で学習し、validation でゲートにかけ、test で1回だけ
評価して、通ったものだけを candidate として登録する。

登録経路を1本に保つためである。探索が独自にモデルを登録できると、
「ゲートを通っていないモデル」がRegistryに存在しうることになる。

## 結果

- 探索空間・目的指標・予算・判定方法は、探索Taskの Parameters と
  `search_plan` アーティファクトから読める
- 勝った試行のTask、成績、しきい値、引き渡したPipeline Taskが
  探索Taskに残る
- 探索を1件も走らせずに、`--dry-run` で「何を許すつもりか」を先に読める

## 見送ったもの

| 見送り | 理由 |
| --- | --- |
| アルゴリズムそのものの探索 | ADR 001 の比較で決着済み。混ぜると結果をどちらにも帰属できない |
| 探索空間のコマンドライン指定 | 予算と同じく、環境が持つべき設定である。CLIに出すと過去の探索を再現できなくなる |
| 入れ子交差検証（しきい値の完全な内側化を超えて、候補選定まで二重にする） | 計算量が候補数×foldsで増える割に、この規模では選定順位がほぼ変わらない |
| 探索結果からの自動昇格 | 昇格は人の承認を要する決定である（ADR/Runbook 003） |
