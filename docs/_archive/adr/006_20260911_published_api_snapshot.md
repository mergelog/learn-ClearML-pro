# ADR 006: 消費者のいない API は、契約テストではなくスナップショットで守る

- 状態: 採用
- 日付: 2026-09-11
- 対象: `services/prediction_api`（公開している HTTP API）
- 関連: 計画書 W12-5、`docs/_archive/adr/002_20260908_service_authorization.md`、
  `docs/_archive/adr/005_20260911_test_pyramid.md`、`docs/_archive/runbooks/004_20260908_prediction_service.md`

## 背景

W12 の原文は「OpenAPI / JSON Schema による consumer-provider contract test」である。
着手前に消費者を数えたところ、**`prediction_api` には消費者がいなかった。**

| 呼んでいるもの | 実体 |
| --- | --- |
| `apps/web` | 呼んでいない（`features/serving/` は `empty-state` の1つだけ） |
| runbook 004 | `curl` の例が数本 |
| `services/tests` | サービス自身のテスト |

この状態で consumer-provider contract test を書くと、**片側しかいない契約**に
なる。消費者の期待は誰も持っていないので、書けるのは provider の都合を
もう一度書き写したものだけである。写した先が写し元と一致することは確かめられるが、
それは何も守っていない。ADR 005 の規則（下の層で確かめられることを上の層で
確かめない）にも反する。サービスの入出力は `services/tests` の167件が既に見ている。

一方で、消費者がいないことは「変わってよい」ことを意味しない。
runbook の `curl` は動かなくなるし、これから来る消費者は**いま公開されている形**を
前提に書く。守れていないのは形そのものではなく、**形が黙って変わること**である。

## 決定

**FastAPI が生成する OpenAPI 文書を `services/prediction_api/openapi.json` へ
コミットし、コードが生成する文書と一致することをテストで確かめる。**

### 1. 検知は完全一致、分類は説明

差分があれば**どんな差分でも失敗する**。破壊変更かどうかは失敗の**読み方**を
変えるだけで、失敗するかどうかは変えない。

`services/contracts/openapi.py` は文書を「呼び出し側が依存できる部分」
（操作・要求・応答の形）へ縮め、2つを比べて破壊変更と互換の変更に分ける。
この分類は**不完全**である。上下限や enum の狭まりは読まない。

ここで分類のほうを検知に使うと、**読めない種類の変更が緑になる。**
それは W12-1 で見た「走っていないことは、走っていないという理由では表に
出てこない」と同じ形の失敗である。だから完全一致を検知に使い、分類は
「呼び出し側が壊れるかどうか」を人が判断するための材料として添える。
分類できない差分は「差分を読むこと」と書いて出す。

### 2. 破壊の定義は、送る側と読む側で逆向きになる

| 変更 | 要求（送る側） | 応答（読む側） |
| --- | --- | --- |
| 値が増えた | 必須なら破壊 / 任意なら互換 | 互換 |
| 値が無くなった | 破壊 | 破壊 |
| 任意 → 必須 | 破壊 | 互換（保証が強くなる） |
| 必須 → 任意 | 互換 | **破壊**（読み手が nil を見る） |
| 型が変わった | 破壊 | 破壊 |
| 操作・応答ステータスが無くなった | 破壊 | 破壊 |

`confidence: number \| null` のような省略可能な値は、型を `null|number` と
して持つ。`null` を落として `number` として扱うと、読み手が落ちる変更が
互換に見えてしまうためである。

### 3. 置き場所は `services` 単体の層、新しいゲートは作らない

ADR 005 の層でいうと `services-unit` である。新しい層は要らない。

新しい npm script のゲートにもしなかった。ゲートにすると `ci.yml` へ写す
必要が生まれ、`ci:parity` の対象が1つ増える。`services:test` の中に置けば、
`verify:python` と CI の python ジョブが既に走らせている。
**検証を増やすために、走らせる場所を増やさない。**

更新は `pnpm run serving:openapi:update` の1本だけを用意した。
文書はコードから導かれるので、この命令は何も決めない。決めるのは差分を
見たレビューである。

### 4. 文書を作るのに資格情報は要らない

サービスは呼び出し側の宣言が無いと起動を拒む（ADR 002）。文書の中身は
呼び出し側が誰かに依存しないので、**資格情報を1つも持たない呼び出し側**を
1件だけ宣言してアプリを組み立てる。組み立てには足り、誰も認証できない。

## 検討したが採らなかった案

### consumer-provider contract test（pact など）を先に入れる

消費者が現れたときに最も効く形だが、いま書くと provider の写経になる。
`openapi.json` は consumer-driven へ育てる素材としてそのまま使える
（消費者側のクライアントをここから生成する、など）。

### 破壊変更のときだけ失敗させる

互換の変更（エンドポイントの追加など）で更新を強制されないのは楽だが、
**分類が読めない変更が黙って通る**。公開しているAPIの差分は、破壊か
どうかに関わらずレビューで見られるべきものである。

### スナップショットの完全一致だけにして、分類を書かない

失敗はするが、「呼び出し側が壊れるのか、エンドポイントが1つ増えただけなのか」を
毎回 472 行の JSON から読み取ることになる。**壊れる変更が、壊れない変更に
埋もれる。** 分類は検知のためではなく、この読み取りのためにある。

### `/metrics` も文書へ載せる

`include_in_schema=False` のままにした。Prometheus が読むのは OpenAPI では
なく exposition format であり、載せても消費者の役に立たない。

## 影響

- `prediction_api` の入出力を変えると `services:test` が落ちる。意図した
  変更なら `pnpm run serving:openapi:update` を走らせ、**差分をレビューに載せる**
- `services/prediction_api/openapi.json` が「このサービスは何を受け取り、
  何を答えるか」の回答になる。これまではハンドラを読むしかなかった
- `services/contracts/` は `prediction_api` に限らない置き場所として作った。
  `ops_exporter` が API を公開するようになったら同じ形で守れる

## 未決

- 制約（上下限・パターン）と enum の狭まりを分類できるようにするか。
  いまは「分類できない差分」として出る。実害（誤読）が出てから決める
- 消費者が現れたとき、`openapi.json` からクライアントを生成するか、
  consumer-driven な契約へ移すか。W12 の範囲では決めない
