# ADR 009: 自作共有層の切り出しと、いま動かさない3つの判断

- 状態: 採用
- 日付: 2026-09-12
- 対象: `src/app/shared/**`（自作分）、`libs/` の新設、`@defer`、zoneless
- 関連: `docs/_archive/adr/003_20260908_angular_boundaries_and_strict.md`（凍結領域）、
  `docs/_archive/adr/005_20260911_test_pyramid.md`（テストの層）、
  `docs/_archive/adr/007_20260912_angular_feature_composition.md`（feature の組み立て方）、
  `README.md`（「ディレクトリ構成」）、
  `x-plan-改訂/00_プラン.md` §6（Stage P の狙い）

## 背景

自作 feature が2本になった（`quality-pipeline` / `data-catalog`）。

1本しか無いあいだは、共有層を育てるか・`libs/` を切るか・`@defer` を入れるか・
zoneless へ動くかを**決められなかった**。共有するものが1つも無い状態で
「共有層の設計」を書くと、それは設計ではなく想像になる。そのため旧プランでは
これらを D レーン（トリガー待ち）へ置き、条件だけ先に決めてあった。

2本目が出たことでトリガーの一部が実際に引かれた。この文書は、その4つを
**実測して判定した記録**である。うち1つは動かし、3つは動かさない。

**動かさないことを決めるのも設計である。** 理由を書かずに放置すると、
半年後に同じ議論をゼロから始めることになる。

## 決定

### 1. 失敗の文言づくりだけを `shared/` へ寄せる（旧 D-3）

`shared/clearml/clearml-failure.ts` を新設し、2つの Effects から同じものを消した。

**寄せた理由は行数ではない。** ADR 007 は「失敗は state に載せ、文言は Effects で
決める」と決めている。その文言の作り方が feature ごとに割れると、同じ失敗が画面に
よって違う言い方をする。**方針の実体が2つあるものは方針ではない。**

寄せられる状態であることは実測で確かめた。2つの実装は註釈を除いて完全に同一で、
`describe` / `describeHttpFailure` / `UNEXPLAINED_FAILURE` の3つがそのまま重なった。

### 2. lineage の読み取りは寄せない（旧 D-3 の残り）

§4.3 で「2箇所目が出たら寄せる候補」としていた Dataset 版数の読み取りは、
**見比べた結果 寄せない**。

| | `quality-pipeline` | `data-catalog` |
| --- | --- | --- |
| 読む場所 | `hyperparams.Dataset.dataset_version` | 同左 **と** `runtime.version` |
| 向き | 実行が使った版数を出す（順方向だけ） | 版数から実行を引く・実行から版数を出す（両方向） |
| 共有できる実体 | 定数2つ（`'Dataset'` / `'dataset_version'`）と1行の参照 | 同左＋ `runtime` 側 |

寄せない理由は2つある。

- **共有できるのは ClearML の語彙そのものである。** `'Dataset'` という区画名も
  `runtime.version` という置き場所も ClearML 側の事実で、これを共有層へ上げると
  「ClearML の語彙は `data-access` の内側に留める」という両 feature 共通の決めを
  こちら側から破ることになる。どの層が ClearML を知っているかが曖昧になる
- **同じに見えて同じではない。** 片方は順方向の1行、もう片方は両方向で、
  逆引き側は API の問い合わせ条件（`runtime.version`）としても同じ文字列を使う。
  いま寄せると、**次に ClearML 側の置き場所が変わったときに、両方の feature の
  都合を1つの関数で背負うことになる**

**重複は「同じ文字列があること」ではなく「同じ判断が2つあること」を指す。**
失敗の文言は判断で、版数の置き場所は事実である。寄せたのは前者だけである。

### 3. `libs/` は切らない（旧 D-5）

旧プランで決めた3つのトリガーを実測した。**1つも引かれていない。**

| トリガー | 実測（2026-09-12） | 引かれたか |
| --- | --- | --- |
| ① 2本目のデプロイ単位 | 配信するのは `Angular Web` の1つだけ。`services/` は Python で別の配信物であり、コードを共有していない | 否 |
| ② `shared/` が自作100ファイル超 | 自作分は2ファイル（`clearml-failure.ts` + spec）。`shared/` 全体でも12ファイル | 否 |
| ③ feature の所有権が分かれる | 分かれていない | 否 |

`libs/` を切ると、ビルド構成・パス別名・テストの層の宣言・境界検査の対象が
それぞれ1段深くなる。**いま払う費用に対して、得られるのは「将来やりやすい」だけ**で、
その将来が来る兆候が3つとも出ていない。

**次に見直すのは②が近づいたときにする。** ①と③は起きれば分かるが、②は
静かに育つ。`shared/` の自作分が増えたら、この表を数え直す。

### 4. `@defer` は入れない（旧 D-4）

`pnpm run web:build` の実測。

| 測ったもの | 値 | 予算 |
| --- | --- | --- |
| 初期束（raw / 転送見積） | 3.10 MB / 796.21 kB | 警告 3.15 MB・失敗 3.30 MB |
| `data-catalog` の初期束への寄与 | **0**（`loadChildren` で完全に遅延） | － |
| `data-catalog` の遅延 chunk | 4つ・計 約 38 kB（最大 12.9 kB） | `any` 予算は警告 560 kB |

**入れない理由は、入れても下がらないからである。** `@defer` が削れるのは
自作 feature の内側だけで、そこは初期束に 1 byte も乗っていない。最大の chunk も
`any` 予算の 2.3% にすぎない。**測らずに入れていたら、効かない複雑さだけが残った。**

ただし**初期束の余裕は 0.05 MB（1.6%）しかない**。これは凍結領域が積み上げたもので、
自作分を削っても届かない。**削る対象は凍結領域であり、それは ADR 003 の凍結方針と
正面から衝突する。** いまは衝突させない。警告が実際に出た時点で、
「凍結を一部やめる」か「予算を上げる」かの判断をここへ書き足す。

### 5. zoneless へは動かさない（旧 D-1）

3つのトリガーのうち、①は達成済みで、②③は引かれていない。

| トリガー | 実測 | 引かれたか |
| --- | --- | --- |
| ① 自作分が OnPush 相当 | 達成済み。明示的な離脱は全体で1件（`open-dataset-card`）のみ | 達成 |
| ② 追従で `webapp-common` の OnPush 比率が上がる | **この指標は無意味だった**（下記） | 測れない |
| ③ 描画性能の問題が実測される | 出ていない | 否 |

**②が測れないことが、今回いちばんはっきりしたことである。** Angular 22 では
OnPush が既定なので「OnPush 比率」はほぼ 100% であり、比率を見ても何も分からない。
zoneless で本当に問題になるのは**変更検知が zone 由来の再評価に頼っている箇所**で、
凍結領域（1687ファイル）の実測は次のとおりである。

| 凍結領域で zone に依存しうるもの | ファイル数 |
| --- | --- |
| `.subscribe(` で直接購読している | 129 |
| `setTimeout` / `setInterval` を使っている | 83 |
| `detectChanges()` / `markForCheck()` を呼んでいる | 94 |
| `NgZone` を直接参照している | 7（`runOutsideAngular` / `zone.run` が 12 箇所） |

**動かさない理由は、費用が自作分ではなく凍結領域に出るからである。** 自作分は
すでに zoneless 相当で、`.subscribe(` も `detectChanges()` も `setTimeout` も
`async` パイプも 0 件である（読むのは `selectSignal` と `toSignal` と `input()` だけ）。
つまり移行で検証が要るのは上の 300 弱のファイルであって、こちらの書き方ではない。

**②のトリガーを差し替える。** 「OnPush 比率が上がったら」ではなく、
**「`webapp-common` の `.subscribe(` 依存が実際に減ったとき」**にする。
比率ではなく、zoneless で壊れる書き方そのものを数える。

## 影響

- `shared/` に自作コードが入ったので、ゲートの受け皿を2つ足した。
  **feature を足すときと同じ手順である**（Stage N-0 と同じ取りこぼし方をする）
  - `tsconfig.strict.json` の `include` に `src/app/shared/clearml/**/*.ts`
  - `test-pyramid.json` の `web-unit` の `include` と、`web-unit-vendor` の
    `exclude` の両方に `src/app/shared/clearml/**/*.spec.ts`
- 失敗の文言のテストは共有層に1つだけになった（8ケース）。両 feature の
  Effects の spec は「失敗が action になること」を見ており、文言そのものは見ない
- `libs/` / `@defer` / zoneless は**再評価の条件つきで閉じた**。条件を満たさない
  うちは議論を再開しない。満たしたらこの文書へ追記する

## 代案と、採らなかった理由

- **`describe` を寄せずに置いておく**: 2つが別々に直る余地を残すことになる。
  ADR 007 が方針として決めている以上、実体は1つでなければならない。採らない
- **`shared/` ではなく `webapp-common/` へ置く**: ClearML 追従時にベンダー差分と
  混ざって判別できなくなる（README のルール1）。採らない
- **lineage の読み取りも一緒に寄せる**: ClearML の語彙が共有層へ漏れる。
  `data-access` の内側に留めるという両 feature 共通の決めと衝突する。採らない
- **`libs/` を先に切っておく**: 将来の移行費用を前払いする形になるが、
  トリガーが3つとも引かれていない以上、その将来が来る根拠が無い。採らない
- **初期束を下げるために凍結領域へ `@defer` を入れる**: 凍結の約束を、
  予算という理由で崩すことになる。警告が実際に出るまでやらない。採らない
