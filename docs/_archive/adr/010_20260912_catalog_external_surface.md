# ADR 010: 台帳の外への出口は「参照URL」と「JSON 書き出し」の2つにする

- 状態: 採用
- 日付: 2026-09-12
- 対象: `apps/web/src/app/features/data-catalog`（外向きの面）
- 関連: 計画書 `x-plan-改訂/00_プラン.md` §1.1 / §5、
  `docs/_archive/adr/006_20260911_published_api_snapshot.md`（公開した形の守り方）、
  `docs/_archive/adr/002_20260908_service_authorization.md`（サービスの認可）、
  `docs/_archive/adr/005_20260911_test_pyramid.md`（層）、
  `docs/_archive/adr/009_20260912_shared_layer_and_deferred_decisions.md`（`libs/` を切らない判断）

## 背景

Stage N で台帳（`data-catalog`）ができ、資産（Dataset / Model / Run）を
1つの語彙 `CatalogAsset` で横断して引けるようになった。計画書 §1.1 の順序
どおり、ここで初めて「外へ渡す」ものが定まる。

計画書 §5 が挙げた候補は3つである。

| 候補 | 中身 |
| --- | --- |
| E-a | 一覧・詳細の CSV / JSON エクスポート |
| E-b | 検索条件つき参照URL |
| E-c | カタログ参照の HTTP API（`services/` 側に置く） |

制約は先に決まっている。

- **出すのは `CatalogAsset` であって、ClearML API の応答そのものではない**（§5）。
  生の応答を出すと、ClearML 追従で外部が壊れる
- P-3 で `libs/` を切らないと決めたので、置き場所は `apps/web` の中か
  `services/` 側かの二択である（ADR 009）
- 出口を守る流儀は ADR 006 が既に持っている。**新しい流儀を作らない**

そして ADR 006 が残した教訓がここへそのまま効く。**消費者のいない公開口を
作ると、片側しかいない契約になる。** `prediction_api` のときに数えたのと
同じことを、今回も先に数えた。

| 出口の候補 | いま実在する消費者 |
| --- | --- |
| E-b 参照URL | **いる**。画面の利用者が URL を渡し合う。N-5 で実体ができている |
| E-a 書き出し | **いる**。台帳の中身を、この画面を持たない相手（報告・棚卸し）へ渡す |
| E-c HTTP API | **いない**。呼ぶプログラムは1つも無い |

## 決定

**外への出口は E-b（参照URL）と E-a（書き出し）の2つにする。E-c は採らない。**

### 1. E-b は「すでに在るもの」を公開契約として固定するだけにする

N-5 のクエリ同期（`data-catalog.query.ts` / `QUERY_KEYS`）が、
そのまま外向きの入口である。**実装は足さない。** 足すのは、
それが外向きの約束であるという明示と、黙って変わらないための検査だけである。

固定するのは次のものである。

- 一覧の経路 `/data-catalog` と詳細の経路 `/data-catalog/:kind/:id`
- クエリの鍵（`q` / `kind` / `project` / `tag` / `from` / `to`）
- 複数値の区切り（`,`）と日付の書式（`YYYY-MM-DD`）
- URL に現れる種別の語（`dataset` / `model` / `run`）

`QUERY_KEYS` の註釈には既に「外向きの名前である」と書いてあった。
**註釈は検査ではない。** 書いてあることと守られていることの差を埋めるのが
この決定である。

### 2. E-a は JSON だけにする。CSV は出さない

書き出す文書は、資産の並びではなく**封筒**である。

```text
catalog / version / exportedAt / reference / filter / truncated / count / assets
```

`assets` は `CatalogAsset` そのもの（7項目）である。封筒が持つのは
「どの条件で引いたか（`filter`）」「その条件で開けるURL（`reference`）」
「上限で打ち切られたか（`truncated`）」の3つで、これは**画面が黙らないと
決めたことを、ファイルになっても黙らないため**にある。

一覧は上限50件で打ち切る（`CATALOG_PAGE_SIZE`）。打ち切りを画面では
注記で言っている。同じものをファイルにして渡したとき、注記は付いてこない。
**打ち切られた台帳は、台帳ではなく抜粋である。** 抜粋を台帳として渡さない
ために、封筒が自分で `truncated` を名乗る。

CSV を出さないのはこのためである。CSV には封筒を入れる場所が無い。
先頭にコメント行を置けば表計算が1行目を列名として読まなくなり、
別ファイルにすれば渡す途中で必ず離れる。加えて CSV は
`tags`（並び）と `updatedAt`（`null` を許す）の2つを必ず嘘にする。
空欄は「タグが無い」と「タグを出していない」を、
また「更新されていない」と「いつ更新されたか分からない」を区別しない。

**表計算で開きたいという要求そのものは正当である。** それが実際に出てから、
封筒を落とす代わりに何を保証しなくなるのかを書いて足す（§未決）。

`reference` を封筒へ入れることで、E-a と E-b は同じ1つの条件を指す。
**ファイルを受け取った人が、そのファイルを作った画面へ戻れる。**

### 3. E-c（HTTP API）は採らない

呼ぶプログラムがいない。この状態で `services/` 側に口を開けると、次の2つを
同時に抱えることになる。

1. **ClearML の読み取りが2言語に重複する。** 種別の対応付け、`data_processing`
   の判定、lineage の置き場所（Task の `runtime.version` と hyperparams の
   `Dataset/dataset_version`）は、いま TypeScript の adapter にしかない。
   Python 側へ写せば、ADR 009 で「寄せない」と決めた**事実の読み取り**が、
   言語をまたいで2つになる
2. **消費者の期待が無いまま形が決まる。** ADR 006 が `prediction_api` で
   見たとおり、そこで書けるのは provider の写経である

**作らないことの記録として、いつ作るかを書いておく。**
次のいずれかが起きたら E-c を再検討する。

| # | トリガー | 測り方 |
| --- | --- | --- |
| ① | 画面を持たない呼び手が実在する（バッチ・他システム・通知） | 呼びたいものの名前が1つ挙がること |
| ② | 書き出した JSON を人手で加工して定期的に取り込んでいる | その手順が runbook に書かれること |
| ③ | 台帳の読み取りを Python 側が必要とする（seed / 点検の道具） | `tools/` から同じ問い合わせが必要になること |

③ が先に来た場合、置き場所は `services/` ではなく `tools/` である。
**呼び手が中にいるものを、外向きの API として作らない。**

### 4. 検査は ADR 006 の形に倣う。完全一致で検知し、分類は説明に使う

公開している面（§1 の URL と §2 の書き出し）を1つの文書
`data-catalog.surface.published.json` としてコミットし、コードが組み立てる
面と**完全一致すること**を単体テストで確かめる。差分があれば、
それがどんな差分でも失敗する。

分類（壊れる変更か、互換の変更か）は失敗の**読み方**を変えるだけで、
失敗するかどうかは変えない。理由は ADR 006 §1 と同じで、分類を検知に使うと
**読めない種類の変更が緑になる**。

読み手の側から見た分類にする（ADR 006 §2 の「応答」列と同じ向き）。

| 変更 | 扱い |
| --- | --- |
| 鍵・値・語が無くなった | 破壊（持っている URL とファイルが意味を失う） |
| 値が変わった（`q` → `query` など） | 破壊 |
| 語が末尾に増えた | 互換 |
| 並びの途中に入った・順序が変わった | 破壊（並びを位置で読む相手が居る） |
| 鍵が増えた | 互換 |

ADR 006 と1点だけ違えたのは**更新の手順**である。`openapi.json` は
472行あり、生成の命令（`serving:openapi:update`）が要った。この文書は
40行ほどで、失敗したテストが「いま公開されている面」をそのまま出す。
**新しい npm script もゲートも作らない**（ADR 006 §3 と同じ理由。
`ci:parity` の対象を増やさない）。差分をレビューに載せることは変わらない。

置き場所は `web-unit`（ADR 005）。既存の層に載る。

### 5. 認可は増やさない。新しい経路を作らないから増えない

E-b も E-a も**画面の中で完結する**。参照URL は画面の経路そのもので、
書き出しはブラウザが手元で組み立てる。ClearML への問い合わせは
一覧・詳細と同じもので、**新しい問い合わせ経路が1本も増えない。**

したがって ADR 002 の principal / role を増やす必要が無い。
台帳が見せてよいものは、画面が見せてよいものと同じである。

E-c を採っていれば、ここに「台帳を読めるだけの役割」が1つ要った。
**役割を増やさずに済んだのは、外へ出す口をブラウザの中に留めたためである。**

## 検討したが採らなかった案

### 3つとも作る

E-c を含めると、いない消費者のために ClearML 読み取りの二重実装と役割の追加を
同時に抱える。ADR 006 で「片側しかいない契約」を作らないと決めた直後に、
同じものを作ることになる。

### 書き出しを ClearML へ問い合わせ直して全件出す

打ち切り（`truncated`）を出さずに済む。採らなかったのは、
「画面に見えているもの」と「ファイルに入るもの」が食い違うためである。
食い違うと、渡した相手と画面を見ている人が違うものを見て話すことになる。
**書き出しは、いま見えているものの写しである。** 全件が要るなら、
それは §3 の E-c トリガー①であって、書き出しの改良ではない。

### 参照URLに版を付ける（`/v1/data-catalog`）

URL の形を後から変えられるようにする案。採らなかったのは、
版が付いているのは**変える予定があるとき**だけ意味を持つからである。
いま変える予定は無く、付ければ画面の経路にも版が現れる。
形が変わるときは、変わったこと自体が §4 の検査で失敗する。

### 書き出しを Effects と action にする

state が変わらない。`CatalogExportDocument` は state から導かれる純粋な形で、
遷移の記録が要らない（ADR 007 §2 の分担でいえば selector 側である）。
action にすると、reducer が何も変えない action が1つ増える。

## 影響

- `data-catalog.query.ts` / `data-catalog.consts.ts` の URL 語彙と、
  `data-catalog.export.ts` の封筒・列を変えると `web:test` が落ちる。
  意図した変更なら `data-catalog.surface.published.json` を失敗が出した内容へ
  直し、**差分をレビューに載せる**
- `data-catalog.surface.published.json` が「台帳は外へ何を約束しているか」の
  回答になる。これまでは註釈（`QUERY_KEYS` の「外向きの名前である」）しか無かった
- 台帳の画面から書き出したファイルは、それ自身が条件と打ち切りを名乗る。
  受け取った側は `reference` で元の画面へ戻れる
- **E-c を作らなかったことがトリガー付きで記録される。** 次に「API が要る」と
  言われたとき、議論をやり直さずに①②③のどれが起きたかを見る

## 未決

- 表計算で開きたいという要求が実際に出たときの形。CSV を足すなら、
  封筒を落とす代わりに何を保証しなくなるのかをここへ書き足す
- 書き出しに詳細（`CatalogAssetDetail` / lineage）を含めるか。いまは一覧だけである。
  詳細1件を渡す用途は参照URL（E-b）で足りているので、要求が出てから決める
