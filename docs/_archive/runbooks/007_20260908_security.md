## 呼び手に資格情報を発行する

```bash
pnpm sec:token -- --name batch-scoring --role predictor
```

役割は3つ。

| 役割 | できること | 典型的な呼び手 |
| --- | --- | --- |
| `predictor` | `/predict`、`/ready` | 予測を使う側、smoke |
| `operator` | `/ready`、`/metrics` | 運用者、障害対応 |
| `scraper` | `/metrics` | Prometheus |

出力のうち、

- **トークン**は呼び手へ渡す。**保存されないので、この1回しか見られない**
- **`name:role:fingerprint` の行**は、サービスの `PREDICTION_API_CLIENTS` か
  `OPS_EXPORTER_CLIENTS` へ足す（区切りは `;`）

fingerprintは秘密ではない。トークンだけが秘密である。

## 資格情報を入れ替える（無停止）

止まる時間を作らずに入れ替える。順番を守ること。

1. 新しいトークンを発行する（上記）
2. その呼び手の行に、**新しいfingerprintを足す**（古いものは消さない）

   ```text
   batch-scoring:predictor:<古いfingerprint>,<新しいfingerprint>
   ```

3. サービスを再起動して、新旧どちらでも通る状態にする

   ```bash
   pnpm serving:up
   ```

4. 呼び手側を新しいトークンへ差し替える
5. 監査ログで、古いfingerprintが使われていないことを確かめる

   ```bash
   docker logs learn01-clearml-prediction-api-1 2>&1 \
     | grep '"credential":"<古いfingerprintの先頭8文字>"' | tail
   ```

6. 古いfingerprintを消し、再起動する

漏えいが分かっている場合は、この順序を守らずに **先に古いものを消す**。
使われているかどうかより、使えなくすることが先である。

## ローカルの資格情報を作り直す

```bash
pnpm sec:tokens -- --rotate
pnpm serving:up
pnpm ops:up
```

`.generated/security/clients.env` が作り直され、古いトークンは無効になる。
手元のシェルに `curl` 用の値を控えていた場合は、そちらも取り直す。

## 401 が返る

「誰か分からない」である。次の順で見る。

```bash
# ヘッダを付け忘れていないか
curl -i http://localhost:8090/ready

# ローカルのトークンを確かめる（表示はするが、貼り付けて共有しない）
. .generated/security/clients.env
curl -s -H "Authorization: Bearer ${LOCAL_PREDICTOR_TOKEN}" http://localhost:8090/ready
```

- ヘッダの形式は `Authorization: Bearer <token>`。他の方式は「名乗っていない」
  として扱われる
- `pnpm sec:tokens -- --rotate` を実行した後は、古いトークンは401になる
- サービスが再起動していない場合、設定へ足したfingerprintはまだ効いていない

## 403 が返る

「誰かは分かるが、それは許されていない」である。トークンは正しい。

```bash
# 監査ログが、どの役割で何を求めて断られたかを言う
docker logs learn01-clearml-prediction-api-1 2>&1 | grep insufficient_role | tail -3
```

必要なのは、役割の変更である。トークンを取り直しても変わらない。
その呼び手が本当にその権限を要るのかを先に決めてから、
新しい役割で発行し直す（入れ替えの手順に従う）。

## サービスが起動しない: no caller may use this service

呼び手が1つも設定されていない。開いたまま起動するより安全側に倒している。

```bash
# ローカルなら、生成し直して起動する
pnpm sec:tokens
pnpm serving:up

# コンテナへ実際に渡っているかを見る
docker inspect learn01-clearml-prediction-api-1 \
  --format '{{range .Config.Env}}{{println .}}{{end}}' | grep CLIENTS | cut -c1-80
```

`pnpm serving:start` / `pnpm ops:start`（コンテナではなくホストで起動）は
[scripts/service-run.sh](../../../scripts/service-run.sh) を経由し、同じ生成物から
資格情報を読む。既に環境変数が設定されている場合は、そちらを優先する
（検証環境以降で secret manager から渡すため）。

## Prometheus の対象が down になる

`/metrics` は `metrics:read` を要求する。Prometheusはトークンをファイルから読む。

```bash
# 対象の状態と、直近の失敗理由
curl -s "http://localhost:9090/api/v1/targets?state=active" \
  | grep -o '"job":"[^"]*","[^}]*"health":"[^"]*"'

# Prometheusが読むファイルが在るか
ls -l .generated/security/prometheus-token
```

- ファイルが無い、または権限が `600` の場合、コンテナ内の `nobody` が読めない。
  `pnpm sec:tokens` を実行し直す（`644` で置き直される）
- `pnpm sec:tokens -- --rotate` の後は Prometheus の再起動が要る。
  ファイルは差し替わるが、Prometheusは起動時に読む

  ```bash
  pnpm ops:up
  ```

## 秘密を書いてしまった

**順序が重要である。消すより先に、無効にする。**
書かれた資格情報は、ファイルを消しても漏えいしたままである。

1. その資格情報を無効にする
   - サービスのトークン: 該当のfingerprintを設定から消して再起動
   - ClearMLの資格情報: ClearML Webの Settings から作り直し、`clearml.conf` を更新
2. どこまで広がったかを調べる

   ```bash
   pnpm sec:scan                      # 追跡されているファイル
   pnpm sec:scan:paths apps/web/build # ビルド生成物
   pnpm sec:scan:clearml -- --limit 50  # Taskのパラメータとログ
   ```

3. 記録から消す。コミット済みなら履歴の書き換えが要る（ユーザの作業）
4. 検出できなかった場合は、規則を足す（`ml/security/secrets.py`）。
   「今回は特別」で終えると、次も検出できない

## 学習が「credential を記録しようとした」で止まる

Task Parametersへ記録する直前の検査が止めている。記録されてからでは、
ClearML Serverを読める全員に見えている状態になるため、実行を止めている。

```text
task parameters/Execution would record a credential, and was not written:
- task parameters/Execution:1: issued-token: ...
```

コマンドラインや設定に資格情報が入っている。渡し方を環境変数へ変える。
それが誤検知である場合は、その値の形を確かめたうえで
`config/security.yaml` に理由付きの除外を書く（理由の無い除外は読み込みで拒否される）。

## 脆弱性でリリースが止まった

```bash
pnpm sec:sbom     # 何でできているか
pnpm sec:audit    # 既知の脆弱性を問い合わせる（ネットワークが要る）
pnpm sec:gate     # 出してよいかを決める
```

止まったときの選択肢は3つ。上から順に検討する。

1. **上げる**: `requirements/*.in` か `package.json` を直し、lockを作り直す
   （`pnpm py:lock`）。`fixed in` に出ている版数が目安
2. **使うのをやめる**: その依存が本当に要るかを見直す
3. **期限付きで受け入れる**: `config/supply_chain.yaml` の `exemptions` に、
   IDと理由と期限を書く。期限を過ぎると、除外ではなく「期限切れ」として
   再び止まる

```yaml
release_gate:
  exemptions:
    - id: GHSA-xxxx-xxxx-xxxx
      reason: 修正版が未公開。該当経路は呼んでいない（services/… で確認）
      until: 2026-10-31
```

`unknown`（深刻度未評価）は既定では止めない。報告には出るので、
`pnpm sec:audit` の出力を見ること。

## 誰が何をしたかを調べる

許可も拒否も、1行1JSONで記録している。

```bash
# 直近の判断
docker logs learn01-clearml-prediction-api-1 2>&1 | grep access.decision | tail -20

# 1人の呼び手を追う
docker logs learn01-clearml-prediction-api-1 2>&1 \
  | grep '"principal":"batch-scoring"'

# 1件の呼び出しを、予測の行まで辿る
docker logs learn01-clearml-prediction-api-1 2>&1 | grep '"correlation_id":"<id>"'
```

記録される項目。

| 項目 | 意味 |
| --- | --- |
| `principal` | 呼び手の名前。名乗らなかった場合は `anonymous` |
| `role` | その呼び手の役割 |
| `permission` | 何を求めたか |
| `outcome` | `allowed` / `missing_credential` / `unknown_credential` / `insufficient_role` |
| `endpoint` / `method` | どの経路か |
| `credential` | fingerprintの先頭8文字。トークンは記録しない |
| `correlation_id` | 同じ呼び出しの他の行と繋がる |
