# 脅威モデルとデータ分類

対象は、このリポジトリが動かすもの全体である。ClearML Server、学習Agent、
Pipeline、推論サービス、監視、Angular Web、CI、およびそれらが扱うデータを含む。

この資料が答えるのは3つだけである。

1. 何を守るのか（データ分類）
2. 誰から守るのか（信頼境界と脅威）
3. いま何がされていて、何がされていないのか（対策と残存リスク）

環境ごとに答えが変わるため、開発（ローカル）・検証（staging）・本番の3つを
分けて書く。いま実在するのは開発だけで、残る2つは「そこへ持っていくときに
何が要るか」を先に決めておくためにある。

## 1. データ分類

| 区分 | 例 | 扱い |
| --- | --- | --- |
| 公開 | コード、設計資料、依存の版数、SBOM | 制限なし |
| 内部 | 学習の指標、Task・Pipelineの実行履歴、監視の数字、モデルのメタデータ | 権限のある者だけが読む。外部へ出さない |
| 機密 | 半導体の測定データ（本番相当）、学習済みモデルの重み | 権限のある者だけが読む。持ち出しは記録する |
| 秘密 | ClearMLの資格情報、サービスの資格情報、TLS秘密鍵 | 平文で保存しない。記録に残さない。漏えいしたら必ず更新する |

このリポジトリのデータは合成データであり、区分としては内部にあたる。
本番の測定データを同じ経路へ流す場合、区分は機密へ上がり、保存時暗号化と
アクセス記録が前提になる（第5節）。

## 2. 信頼境界

```text
[ブラウザ]              [開発者の端末]            [他システム]
    |                        |                        |
    | HTTP                   | pnpm / CLI             | HTTP + Bearer
    v                        v                        v
+-------------------------------------------------------------+
| ホスト（WSL2 / 単一マシン）                                  |
|                                                              |
|  Angular Web ---- ClearML API (8008) ---- ClearML Server     |
|                        |                    |  Elasticsearch |
|                        |                    |  MongoDB       |
|                        |                    |  Redis         |
|                        v                                     |
|                  Queue / Agent ----> 学習Task ----> Model     |
|                        |                              |      |
|                        v                              v      |
|                  ops-exporter (8091)         prediction-api  |
|                        |                       (8090)        |
|                        +--------> Prometheus ---> Grafana    |
+-------------------------------------------------------------+
```

境界は4つある。

1. **ホストの外と中**: いまはループバック（`BIND_ADDRESS`）で仕切っている。
   ClearMLの3ポート（8008 / 8080 / 8081）だけは家庭内LANからの利用を想定して
   公開したままで、これは意図した例外である（第5節の残存リスク）
2. **サービスとその呼び手**: 推論サービスとops-exporterは資格情報と役割で
   仕切る。`/health` だけが例外で、これは「プロセスが生きているか」しか
   答えない（資格情報の期限切れが再起動ループになるのを避けるため）
3. **コンテナとホスト**: Agentは作業ツリーを読み取り専用で受け取り、
   非rootで動く。書けるのは自分のキャッシュ用ボリュームだけ
4. **リポジトリと外部**: 依存はlockで固定し、SBOMを書き出し、脆弱性は
   リリースゲートで判断する

## 3. 脅威と、いまの対策

STRIDEの語をそのまま使わず、「起こると何が失われるか」で並べる。

### 3-1. 秘密の持ち出し

| 脅威 | いまの対策 |
| --- | --- |
| 資格情報がコミットされる | `pnpm sec:scan`（追跡ファイル全走査）。`pnpm verify` とCIに入っており、見つかれば失敗する |
| 資格情報がTask ParametersやTaskログに残る | 記録する直前に検査し、含んでいれば**記録せずに実行を止める**（`ml/semiconductor_quality/clearml_tracking.py`）。既にあるものは `pnpm sec:scan:clearml` で探す |
| 資格情報がビルド生成物に混ざる | `pnpm sec:scan:paths <dir>`。Angularの生成物については既知の問題がある（第5節） |
| 設定の一覧から資格情報が読める | サービスが持つのはSHA-256のfingerprintだけで、トークンそのものは持たない。`.env` やcomposeが漏れても、それだけでは呼べない |
| 監査ログから資格情報が読める | 記録するのはfingerprintの先頭8文字だけ。トークンは記録しない |

### 3-2. 権限のない操作

| 脅威 | いまの対策 |
| --- | --- |
| 誰でも推論を呼べる | `predict` 権限を要求。役割 `predictor` のみが持つ |
| 誰でも「いま何が提供されているか」を読める | `/ready` は `model:read` を要求 |
| 誰でもシステムの状態（Queue滞留、資源、失敗率）を読める | `/metrics` は `metrics:read` を要求。Prometheusは `scraper`（数字だけ）で読む |
| 権限を持つ者が別の仕事もできてしまう | 役割は最小権限。`operator` は予測できず、`predictor` は数字を読めない。組み合わせは `services/tests/security/test_authorization.py` の表で固定している |
| 「誰が何をしたか」が残らない | 許可・拒否のすべてを1行1JSONで記録する（`event: access.decision`） |

### 3-3. 供給網

| 脅威 | いまの対策 |
| --- | --- |
| 依存が実行のたびに変わる | `requirements/*.txt` と `pnpm-lock.yaml` で固定。CIがlockと宣言の一致を確認する |
| 既知の脆弱性を含んだまま出す | `pnpm sec:sbom` → `pnpm sec:audit` → `pnpm sec:gate`。criticalは通さない |
| ベースイメージの脆弱性 | ベースイメージはdigestで固定。CIでTrivyがイメージを走査し、同じゲートへ渡す |
| 何を使っているか分からなくなる | SBOM（CycloneDX）を成果物として書き出す |

### 3-4. なりすまし・盗聴

| 脅威 | いまの対策 |
| --- | --- |
| 資格情報が通信路から盗まれる | ローカルはループバックのみ。ホストの外へ出す場合はTLS（`PREDICTION_TLS_*`）か前段での終端が前提 |
| 資格情報が使い回される | 1つの呼び手に1つの資格情報。同じfingerprintを2者に配ると起動時に拒否される（呼び出しを誰の行為か特定できなくなるため） |
| 漏えいした資格情報が使われ続ける | 1つの呼び手が複数のfingerprintを持てるため、無停止で入れ替えられる（runbook 007） |

## 4. 環境ごとの前提

| | 開発（いま） | 検証（staging） | 本番 |
| --- | --- | --- | --- |
| データ | 合成データ（内部） | 匿名化した実データ（内部） | 実データ（機密） |
| 資格情報の出所 | `.generated/security/clients.env`（生成物・gitignore） | secret manager | secret manager |
| 資格情報の更新 | 手動（`--rotate`） | 定期 + 事故時 | 定期 + 事故時。更新は無停止 |
| 通信 | ループバックの平文 | 前段でTLS終端 | 前段でTLS終端。内部通信もTLS |
| ElasticsearchのSecurity | 無効（ローカルのみ・内部ネットワーク） | 有効 | 有効 |
| 保存時暗号化 | 無し（ホストのディスク次第） | ボリューム暗号化 | ボリューム暗号化 + 鍵管理 |
| Grafana | 匿名Viewer（ループバック） | 認証必須 | 認証必須 + 役割 |
| 監査ログ | プロセスの標準出力 | 収集して保持 | 収集して保持 + 改変不可 |

## 5. 残存リスク（判断のうえで受け入れているもの）

1. **Angularの生成物にClearMLの資格情報が入る**
   `apps/web/src/credentials.json` は持ち込んだClearML Webアプリが実行時に読む
   ファイルで、ビルド生成物 `apps/web/build/browser/credentials.json` にそのまま
   写る。ブラウザへ配るものに資格情報が含まれる、という構造的な問題である。
   `pnpm sec:scan:paths apps/web/build` はこれを検出する。
   ローカルでの緩和は次のとおり。ファイルはgitignoreされ、リポジトリには入らない。
   webは開発者自身の端末で動かす。生成物を配布しない。
   本番相当へ持っていく場合は、ブラウザへ資格情報を配らない認証方式
   （ClearML Server側のログイン、または前段でのトークン発行）へ替える必要がある。
   これはW11（Angular品質）以降で扱う。

2. **ClearMLの3ポートが家庭内LANへ公開されている**
   8008 / 8080 / 8081 は、別端末のブラウザから使う運用のために公開したままにして
   ある。ここにはRBACが無く、`clearml.conf` の資格情報を持つ者が全権を持つ。
   同一LANの信頼を前提にした受け入れであり、LANの外へは出していない。

3. **Elasticsearchのsecurityが無効**
   `xpack.security.enabled: "false"`。Composeの内部ネットワーク（`internal: true`）
   にのみ接続しており、ホストへポートを公開していない。ClearML Serverのコンテナ
   からだけ到達できる。検証環境以降では有効化する。

4. **保存時暗号化が無い**
   Dataset、モデル、MongoDB、Elasticsearchはホストのファイルシステム上に平文で
   置かれる。ホストのディスク暗号化に依存しており、これは環境側の設定である
   （このリポジトリからは制御できない）。

5. **深刻度未評価の助言はリリースを止めない**
   `config/supply_chain.yaml` の `unknown: report`。評価が付くまで数日かかる
   ことがあり、そこで止めるとゲートを迂回する習慣ができるため。報告には出る。

## 6. 攻撃者から見た最短経路（優先度の根拠）

1. `clearml.conf` を読む → ClearMLの全権を得る（Dataset・Model・Taskの改変）
2. `apps/web/build` の生成物を得る → 同じ資格情報を得る（残存リスク1）
3. 推論サービスの資格情報を得る → 予測を呼べる。モデルの版数が分かる
4. 監視の資格情報を得る → システムの構成と負荷が分かる

1と2が最も価値が高く、どちらも「秘密の持ち出し」である。だからW10の中心を
RBACではなく秘密の検出と非記録に置いている。
