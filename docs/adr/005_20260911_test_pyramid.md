# ADR 005: どの層で何を確かめるかを決め、宣言と実態のずれをゲートで見る

- 状態: 採用
- 日付: 2026-09-11
- 対象: リポジトリ全体のテスト（`ml` / `services` / `tools` / `apps/web` / `scripts`）
- 関連: 計画書 W12-3、`docs/adr/003_20260908_angular_boundaries_and_strict.md`、
  `.github/workflows/ci.yml`、`test-pyramid.json`

## 背景

W12-1 と W12-2 で、**手元にある検証が CI で必ず走る**状態になった。
それまでは `services/tests` の133件（認可13件を含む）と `web:contract` が
CI から落ちたまま、CI は緑であり続けていた。

土台が出来たので、次に足すのは failure test・contract test・smoke E2E・a11y・
負荷試験である。ここで先に決めておかないと困ることが1つある。
**同じ判断を2つの層で確かめてしまうこと**である。

たとえば「評価スコアを小数3桁で表示する」は、presentational の単体テストでも
E2E でも確かめられる。両方に書くと、桁を変えたときに2か所が落ちる。
片方を直せば緑になるので、**遅いほう（E2E）だけが残り、速いほうが消える**。
これを何度か繰り返すと、単体テストが薄く E2E が厚いという逆の形になる。

着手前の実測は次のとおりである（件数は `pnpm test:pyramid:report` が出す）。

| 層 | ファイル | ケース |
| --- | ---: | ---: |
| ゲート自身（`scripts/tests`） | 3 | 32 |
| `ml/tests` | 38 | 813 |
| `services/tests` | 9 | 133 |
| `tools/tests` | 5 | 69 |
| `apps/web` 単体（自作） | 11 | 162 |
| `apps/web` 単体（取り込み） | 50 | 111 |
| E2E（Playwright） | 3 | 18 |

形としては既にピラミッドになっている。**これから崩れる**のを止めたい。

## 決定

**層ごとに「何を確かめるか」と「何を確かめないか」を宣言し、
宣言と実際の置き場所が合っていることをゲートで見る。**

宣言は `test-pyramid.json`、検査は `scripts/test-pyramid.mjs`
（`pnpm run test:pyramid`）に置く。`verify:web` の `ci:parity` の次で走る。

### 1. 層と、その層が引き受けるもの

| 層 | 確かめる | 確かめない |
| --- | --- | --- |
| ゲート自身 | 検査スクリプトが落とすべきものを落とすこと | 製品の挙動。ここが緑でも製品について何も分からない |
| `ml` 単体 | 学習・評価・昇格・drift の**判断**（しきい値・境界・失敗時にどちらへ倒すか） | ClearML Server との実通信、Agent 上での実行、精度そのもの |
| `services` 単体 | `prediction_api` / `ops_exporter` の入出力・認可・失敗応答 | 画面からの利用、実モデル成果物、負荷特性 |
| `tools` 単体 | CLI の判断（何を見つけ、何で止めるか） | 外部データベースへの実問い合わせ、イメージの実走査 |
| Angular 単体（自作） | 表示判断・container と state の結線・変換・reducer / effects の遷移 | 実 HTTP、ルーティング、ビルドの成立 |
| Angular 単体（取り込み） | 取り込んだコードの回帰の網 | 自分たちの判断。ここへ新しいテストを足さない |
| E2E | 画面が起動し、route から操作・表示までが**縦に繋がる**こと | 業務ルールの網羅 |

**規則は1つ。下の層で確かめられることを、上の層で確かめない。**
分岐が1つ増えたときに足すのは単体テストであって、E2E ではない。
E2E が答えるのは「繋がっているか」だけである。

### 2. E2E にだけ上限を置く

E2E は **30件**を上限とする（現在18件）。W12-6 の smoke E2E と W12-7 の a11y で
それぞれ5件程度を見込んだ数である。超えたときに失敗するので、
そこで「その確認は本当にこの層でなければできないのか」を見直すことになる。

上限を他の層に置かないのは、下の層は**増えて困らない**ためである。
ピラミッドが崩れるのは上が太るときだけで、それは件数に出る。

### 3. すべてのテストが、いずれか1つの層に属すること

ゲートはリポジトリ全体から `test_*.py` / `*.spec.ts` / `*.test.mjs` などを集め、
宣言した層に照らす。**未分類**（決めていない場所に置かれた）と
**二重所属**（層の境界が重なっている）を失敗にする。

「新しい種類のテストを足すときに、置き場所を先に決める」を強制する形である。
決め忘れたまま足すと、CI が赤くなって気付く。

### 4. 件数は静的に数える

Python は `def test_` で始まる行、TypeScript / mjs は `it(` `test(` で始まる行を
1件と数える。`describe` や `beforeEach` は数えない。

実行して数えるほうが正確だが、そのためには全層を走らせることになり、
このゲートが `verify` の先頭近くで軽く回れなくなる。着手時に実測と突き合わせ、
813 / 133 / 69 / 273 / 18 / 32 がいずれも一致することを確かめた。
parameterized test を使い始めると、ここはずれる。**ずれたら数え方を直す**。

## 検討したが採らなかった案

### 文章だけで定義する（README に節を足して終わる）

W12-1 で分かったことと同じ理由で採らない。**宣言と実態のずれは、ずれたという
理由では表に出てこない。** 実際、`ci.yml` の冒頭には「手元と同じコマンドを
同じ順序で実行する」と書いてあり、その状態で3件が落ちていた。

### 層の件数の比率をゲートにする（例: 単体 : E2E を 20:1 以上に保つ）

比率は下の層を足しても上の層を足しても動く。
**E2E を1件増やしたいときに、無関係な単体テストを増やせば通る。**
守りたいのは比率ではなく「上の層で確かめるものの種類」なので、
上限を絶対値で置いて、超えたときに見直す形にした。

### テスト名や配置から重複を機械検出する

「同じ判断を2つの層で確かめている」ことを直接検出できれば一番よいが、
判断が同じかどうかはテスト名からは分からない。
いま置けるのは「境界がはっきりしていること」までである。

## 影響

- テストを足す前に、どの層に置くかを決めることになる。決め忘れは CI で落ちる
- 新しい層（負荷試験 k6 など）を足すときは `test-pyramid.json` に宣言を書く。
  W12-8 で k6 を足すときが最初の機会になる
- glob の解釈を `scripts/lib/glob.mjs` へ寄せた。依存境界（ADR 003）と
  `strict` の範囲判定も同じ実装を使う。3か所で違う意味にならないようにするため
