# ADR 008: 台帳からのメタデータ編集（楽観更新をしない・二重編集を防がない）

- 状態: 採用
- 日付: 2026-09-12
- 対象: `apps/web/src/app/features/data-catalog`（tags と description の書き込み）
- 関連: 計画書 Stage N-8、`docs/adr/007_20260912_angular_feature_composition.md`、
  `x-plan-改訂/00_プラン.md` §4.4

## 背景

データカタログは **`apps/web` の自作分で初めてサーバの状態を書き換える画面**である。
`quality-pipeline` の起動・停止は ClearML への操作であって、台帳そのものの編集ではない。

書き込みが入ると、それまで無かった2つの問いが生まれる。

1. **失敗したときに、画面の表示をどう戻すか**
2. **同じ資産が2箇所（台帳と既存の Dataset / Model 画面）から編集できてしまうことを、どう扱うか**

この2つを決めずに「とりあえず楽観更新」で入れると、**台帳が嘘をつく**。
台帳が嘘をつくと、台帳である意味が消える。「いま何があるか」を答えられないなら、
ClearML の画面を直接見たほうが正しい。

## 決定

### 1. 楽観更新をしない。サーバが受け付けてから state に反映する

押した直後に画面の値を変えない。`saveMetadata` は `saving: true` を立てるだけで、
`detail` も `assets` も触らない。値が変わるのは `metadataSaved` を受けたときだけである。

```text
save を押す → saving: true（表示は変わらない）
   → ClearML が受け付けた   → metadataSaved → 表示が変わる
   → ClearML が受け付けない → saveFailed   → 表示は元のまま・理由を出す
```

**巻き戻しの処理が要らないのが、この形の要点である。** 楽観更新を採ると、
失敗時に「押す前の値」をどこかに持っておいて戻すことになる。その退避した値は、
失敗が来るまでの間に別の経路（読み直し）で古くなりうる。戻した結果が
サーバとも画面ともずれた第三の値になる壊れ方は、再現も説明も難しい。

代償は、押してから表示が変わるまでに1往復ぶんの間があることである。
tags と description の編集は**頻度が低く、結果を確認したい操作**なので、
この間は許容する。1秒を惜しむ種類の操作ではない。

### 2. 「変えなかった」を成功として扱わない

ClearML は存在しない ID への更新でも 200 を返し、`updated: 0` で
「何も変えなかった」と言う。`DataCatalogApiService.updateMetadata` は
`updated !== 1` を例外にする。

これをやらないと、**消された資産への編集が成功として画面に残る**。
画面には新しい値が出ているのに、ClearML にはその資産自体が無い、という状態になる。

### 3. 二重編集は防がない。防げないことを画面に書く

同じ資産は、台帳からも既存の Dataset / Model 画面からも編集できる。
これを防ぐ手立ては、この構成では取れない。

- ClearML の `tasks.update` / `models.update` に**楽観ロック（版数の突き合わせ）が無い**。
  後から届いた更新が黙って勝つ
- 既存画面は凍結領域であり、そちらへロックの仕組みを足さない（ADR 003）

**採るのは「防ぐ」ではなく「隠さない」である。**

1. 編集欄に「この資産は ClearML 側の画面からも編集できる。他の人が変えた
   可能性があるなら、編集前に読み直すこと」と**常に書いておく**
2. 保存に成功したら、**その資産をもう一度読み直す**（`reloadAfterSave`）。
   自分の変更が他人の変更を上書きしていた場合、その結果が画面に出る
3. 読み直した値は**入力欄へ書き戻す**。手元の入力が古い値のまま残ると、
   次に保存したときにその古い値でもう一度上書きしてしまう

3 が無いと、警告文だけがあって実際には上書きが続く。**文言と挙動は対で決める。**

### 4. 書き込むのは tags と description だけにする

名前・プロジェクト・状態は ClearML 側の実体が決めるものであって、
台帳が上書きしてよいものではない。`updateMetadata` は他のフィールドを送らない。

台帳は**横断して引くための層**であり、実体の所有者ではない。
所有者でないものが実体の同一性（名前・所属）を書き換えられると、
ClearML 側の画面と突き合わせる手掛かりが台帳の操作で失われる。

## 影響

- 失敗時の表示は E2E ではなく単体テストで確かめられる（ADR 007 と同じ形）。
  `data-catalog.reducer.spec.ts` が「押しても表示は変わらない」を固定している
- 保存のたびに読み取りが1回増える。編集の頻度が低いので、この往復は問題にならない
- 将来 ClearML 側に版数つきの更新が入ったら、決定 3 は見直す。そのときは
  **「防がない」をやめて「弾く」に変えられる**。文言もそのとき一緒に消す

## 代案と、採らなかった理由

- **楽観更新して失敗時に巻き戻す**: 巻き戻しの値が古くなる経路があり、
  サーバとも画面とも違う第三の値になりうる。台帳が嘘をつく形なので採らない
- **台帳からの編集をやめる（閲覧専用にする）**: tags は台帳の絞り込みの軸そのもので、
  引けるようにするには付けられなければ意味がない。採らない
- **台帳側でロックを持つ（編集中フラグ）**: 既存画面はそのフラグを知らないので、
  台帳から見えるところだけが守られる。**守られていないものを守られているように
  見せる**のが最も悪い。採らない
- **編集の競合を検出するために毎回 `last_update` を突き合わせる**: 読み取りと
  更新の間は依然として開いており、競合の窓を狭めるだけで閉じられない。
  仕組みとして中途半端なので、いまは採らない（ClearML 側が版数を受けるように
  なったら再検討する）
