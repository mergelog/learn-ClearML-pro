## 何を作らないと決めたか

台帳の内容を `services/` 側から HTTP で読める口を開けること。

台帳の外への出口は、参照 URL（画面をその条件で開ける URL）と JSON の書き出しの2つに限ってある。
3つ目として HTTP API を作らない。

## なぜ作らないか

呼ぶプログラムがいない。この状態で口を開けると、次の2つを同時に抱えることになる。

ClearML の読み取りが2言語に重複する。種別の対応付け、`data_processing` の判定、
lineage の置き場所は、現在 TypeScript の adapter にしかない。Python 側へ写せば、
同じ事実の読み取りが言語をまたいで2つになる。

消費者の期待が無いまま形が決まる。片側しかいない契約は、provider の写しにしかならない。

## 再検討する条件

次のいずれかが起きたとき。

| # | 条件 | 測り方 |
| --- | --- | --- |
| ① | 画面を持たない呼び手が実在する（バッチ・他システム・通知） | 呼びたいものの名前が1つ挙がること |
| ② | 書き出した JSON を人手で加工して定期的に取り込んでいる | その手順が運用手順に書かれること |
| ③ | 台帳の読み取りを Python 側が必要とする | `tools/` から同じ問い合わせが必要になること |

③ が先に来た場合、置き場所は `services/` ではなく `tools/` である。
呼び手が中にいるものを、外向きの API として作らない。
