# BL-18: ClearML upstream を追跡しておらず、更新の影響範囲を検討できない

| 項目 | 内容 |
| --- | --- |
| 種別 | 実装＋文書 |
| 状態 | 一部着手（2026-09-13） |
| 起票日 | 2026-09-12 |

## 何が起きているか

71（リスク登録簿）の R-01・R-02 は、どちらも検知方法の欄が「検知手段なし」である。
`x-plan-改訂/_old/20_ドキュメント作成プラン.md` §17 の完了条件「ClearML upstream 更新時の影響範囲を検討できる」が
未チェックのまま残っているのはこのためである。

`Angular Web` は ClearML Web の fork であり、そこへ自作の feature を足してある。
upstream に更新が入ったことを知る手段が現在は無い。fork 元のリポジトリを remote として登録しておらず、
版を突き合わせる検査も走っていない。`package.json` の `version` は `2.5.0` だが、
この値が fork した時点の upstream の版と一致するという確認は取っていない。

影響範囲を検討できないのは、差分を取る相手が手元に無いからである。
upstream の更新が自作分と競合するかどうかは、更新の中身を見なければ決まらない。
更新を見る手段が無い状態では、競合の有無も、取り込みの可否も判断できない。

01（要件定義書）§6 と 03（方式設計書）§6 も、取り込み方式が未決であると記している。

## 解決とみなす状態

次の3つが揃うこと。

* upstream を追跡する手段がある（remote の登録、または版の突き合わせ検査のいずれか）
* 71 の R-01・R-02 の検知方法の欄に、実際に走る手段が書いてある
* upstream の更新を取り込むときの手順が 03（方式設計書）に書いてある

手順には、自作 feature と upstream の変更が同じファイルに触れた場合の扱いを含める。

## 着手の条件

無し。remote の登録だけならいつでも着手できる。

ただし、取り込み手順まで決めるには、一度実際に upstream の更新を取り込んでみる必要がある。
競合がどの粒度で起きるかを見ないまま手順を書くと、机上の手順になる。

## 2026-09-13 に入れたもの

「解決とみなす状態」の3つのうち、2つを満たした。

* fork 元を remote `upstream`（`https://github.com/clearml/clearml-web.git`）として登録した
* `upstream.json` に、最後に確認した commit・版・日付を記録した
* `scripts/upstream-status.mjs`（`pnpm upstream:status`）が、記録と upstream の `master` を比べる。
  CI の `upstream` ジョブが変更のたびに呼ぶ
* 71 の R-01・R-02 の検知方法の欄を、この検査の名前に書き換えた
* 03 §4.15 に取り込み方式を書いた

突き合わせて分かったことは3つある。

1. fork 元は tag `v2.5` 系列である。upstream の2481ファイルのうち2435本が手元と同一で、
   34本を手元で変更してあり、12本は手元に無い
2. commit は1つに絞れない。tag `v2.5`・branch `v2.5`・`master` を分ける4ファイルは、
   手元で変更してあるか、手元に無いかのどちらかである
3. 版数では更新を検知できない。upstream の `master` は tag `v2.5` の4つ先にあるが、
   `package.json` の `version` はどちらも `2.5.0` である。
   4つの中身は依存の更新と脆弱性の修正で、`src/test.ts`・`pnpm-lock.yaml`・
   `pnpm-workspace.yaml`・`package.json` に触れている

3つ目のため、検査は版数ではなく commit を見る形にした。

## なお残るもの

取り込み手順（03 §4.15）が未検証である。一度も取り込んでいない。
競合がどの粒度で起きるかは、34本のうちどれに触れる更新が来るかで決まる。

20 §17 の完了条件「ClearML upstream 更新時の影響範囲を検討できる」にチェックは付けない。
影響範囲を挙げられる状態にはなったが、挙げた範囲が正しいかは、1回取り込むまで分からない。
