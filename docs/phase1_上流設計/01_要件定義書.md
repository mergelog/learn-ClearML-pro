## 1. 目的

この文書は、本プロジェクトが何を実現するものかを定める。どの方式で実現するかは 03 が、
どの品質水準を求めるかは 02 が持つ。

ClearML そのものの説明はここでは扱わない。ClearML を土台にして本プロジェクトが何を足したのかを書く。

## 2. 適用範囲

対象は、このリポジトリが持つ次の5つである。

| 範囲 | 実体 |
| --- | --- |
| 学習・評価・昇格の処理 | `ml/` |
| 推論と監視中継のサービス | `services/` |
| 種まきと検査の道具 | `tools/` |
| 画面 | `apps/web/`（取り込んだ ClearML Web と、その上の自作 feature 2本） |
| 実行基盤の定義 | `infra/`, `config/`, `scripts/` |

ClearML Server 自体（apiserver / fileserver / webserver / Elasticsearch / MongoDB / Redis）は、
公式イメージをそのまま使う。その内部仕様は対象外である。

## 3. 前提

単一の開発端末（WSL2）で、Docker Compose により全プロセスを起動する。
利用者は開発者1名であり、その1名が開発・運用・判断のすべてを兼ねる。

同一ホスト上に併存する別プロジェクト `../001-learn-ClearML` とポート 8008 / 8080 / 8081 を共有するため、
両者を同時に起動できない。

## 4. 定義

### 4.1 背景と解決する課題

ClearML は実験の記録・Dataset の版管理・Agent による実行を単体で提供する。
それでも、次の3つは ClearML を起動しただけでは満たされない。

第一に、学習の結果が良いかどうかを誰かが目で見て決める状態が残る。実行が終わったことと、
そのモデルを使ってよいことは別の事実であり、後者を判断する基準が要る。

第二に、モデルがどのデータから来たのかを一画面で辿れない。ClearML では Dataset・Model・Task が
別々の画面に分かれており、「このモデルはどのデータで学習したのか」に答えるには画面を往復する。

第三に、再現に必要な情報が揃わない。Task が記録するのは測った値と設定であり、
どのコード・どのイメージ・誰の実行がそれを生んだかは、記録させなければ残らない。

本プロジェクトは、この3つを埋めるものとして作られている。

### 4.2 システムの目的

半導体の製造工程で測った値から、その製品が不良（`fail`）になるかを判定する分類器を題材として、
データの登録から学習・評価・昇格・配備・監視・rollback までを一続きに扱える基盤を構築する。

題材としての分類精度そのものは目的ではない。データは合成であり（4.6 節）、
実在の工程を判定する用途には使えない。

### 4.3 対象ユーザー

| 役割 | いまの担い手 | 何をするか |
| --- | --- | --- |
| データ登録者 | 開発者 | Dataset の版を作り、品質条件を満たすか判定する |
| 実験者 | 開発者 | 学習・Pipeline・ハイパーパラメータ探索を実行し、結果を比較する |
| 承認者 | 開発者 | 評価ゲートを通ったモデルを staging・production へ昇格する |
| 運用者 | 開発者 | 推論サービスを配備し、警報に対応し、必要なら rollback する |
| 台帳の閲覧者 | 開発者 | 資産の来歴を追い、メタデータを編集し、参照用に書き出す |

4つの役割を1人が兼ねている。権限の対応は `../phase6_セキュリティガバナンス/52_権限マトリクス.md` が持つが、そこでも人ではなく経路で表を作っている。

### 4.4 主な利用シナリオ

```text
Dataset の版を作る
  → 品質条件を満たすか判定する（ml:data check）
  → 学習する（ml:train）／ Pipeline で通す（ml:pipeline）
  → 設定を探索する（ml:experiment）
  → 評価ゲートを通す（候補モデルとして登録）
  → staging・production へ昇格する（ml:model promote）
  → 推論サービスを配備する（serving:up）
  → 監視する（ops:up、Prometheus / Alertmanager / Grafana）
  → drift を検知する（ml:data drift）
  → rollback する（ml:model rollback）
```

この筋書き全体を一続きに演じた記録は、まだ作られていない（`../backlog/02_通し台本が無い.md`）。

### 4.6 対象データ

学習に使うのは、`tools/semiconductor_seed` が生成した合成データである。実在の製造データではない。

| Dataset | 版 | 行数 | 内容 |
| --- | --- | --- | --- |
| `semiconductor-quality-data` | 1.0.0 | 1,200 | 基本の合成測定値 |
| `semiconductor-quality-data` | 2.0.0 | 2,500 | 装置ごとの効果と雑音を調整し、行数を増やしたもの |

列の意味・型・値域は 10 が持つ。

### 4.7 外部システムとの関係

外部と通信するのは2箇所だけである。

`tools/supply_chain` は OSV の脆弱性データベースへ問い合わせる。これが唯一、実行にネットワークを要する処理である。

`apps/web` は ClearML Server の HTTP API を呼ぶ。これはホスト内の通信であり、外部のサービスではない。

それ以外の処理は、すべて同一ホスト内で完結する。

### 4.8 ClearML 標準機能と独自機能の境界

ClearML が提供し、本プロジェクトがそのまま使うもの。

* Dataset の版管理と取得
* Task としての実行記録、Parameter と指標の記録
* Queue と Agent による遠隔実行
* Pipeline の制御（Task を複製して Parameter を書き換える仕組み）
* Output Model の保管と、tag・metadata による検索
* Web UI の既存画面（実験・モデル・Queue など）

本プロジェクトが足したもの。

| 追加 | 実体 | なぜ足したか |
| --- | --- | --- |
| データ品質の判定 | `ml/data_quality` | 列が揃っていることと、学習に使ってよいことは別である |
| 評価ゲート | `ml/model_lifecycle/gate.py` | 実行の完了と、モデルの合格を別の事実として扱う |
| 段階と昇格の記録 | `ml/model_lifecycle` | いま何が production かを、一覧から答えられるようにする |
| 来歴の記録 | `ml/semiconductor_quality/provenance.py` | どのコード・イメージ・誰の実行かを Task に残す |
| 推論サービス | `services/prediction_api` | production のモデルを HTTP で呼べるようにする |
| 学習側の監視中継 | `services/ops_exporter` | Queue・Agent・Task は自分で HTTP に答えないため |
| 資産台帳の画面 | `apps/web` の `/data-catalog` | Dataset・Model・Run を1つの語彙で辿れるようにする |
| 品質パイプラインの画面 | `apps/web` の `/quality-pipeline` | Pipeline の各ステップの状態を1画面で見る |
| 秘密と供給網の検査 | `tools/security`, `tools/supply_chain` | 記録された内容と依存が、公開してよい状態かを検査する |

取り込んだ ClearML Web（`apps/web/src/app/webapp-common/**` と既存 feature）は凍結領域として扱い、
新しい判断を足さない（ADR 003）。自作分は `features/quality-pipeline`、`features/data-catalog`、
`shared/clearml` の3つに限られる。

### 4.9 対象範囲と対象外範囲

対象範囲は 4.5 の機能要件と、それを動かす実行基盤である。

対象外は次のとおりで、それぞれ理由がある。

| 対象外 | 理由 |
| --- | --- |
| 複数人での同時利用、利用者ごとの権限分離 | 利用者が1名であり、分離すべき相手がいない |
| 本番環境での運用 | 単一ホスト上の学習環境であり、冗長化も無停止更新も持たない |
| IaC（W14） | Compose 以上の基盤定義を扱わない判断が出ている |
| チーム標準（W15） | 60番台として整備対象ではあるが、Stage 2 では対象外のまま止まっている |
| コスト管理（W16） | 課金の対象となる資源を使っていない |
| ClearML Server 本体の改修 | 公式イメージをそのまま使う |
| 実データの取り扱い | データは合成であり、実在の製造データを受け入れる経路を持たない |
| カタログ参照の HTTP API | 消費者が現れていない（ADR 010。`../backlog/03_カタログ参照API.md`） |

対象外は削除ではなく保留である。判断が変わる条件は `../backlog/` の各ストーリーが持つ。
