## 1. 目的

この文書は、本システムに求める品質水準を定める。何を実現するかは 01 が持つ。

数値目標は、実測または設定ファイルに根拠があるものだけを目標として書く。
根拠の無い数値は目標として置かず、「未確定」または「本学習環境では保証対象外」と記す。
この区別は 20・22 の実測欄にも同じ形で現れる。

## 2. 適用範囲

対象は 01 §2 と同じである。ClearML Server 本体の品質特性（Elasticsearch の可用性など）は対象外とする。

## 3. 前提

単一ホスト・単一利用者・Docker Compose による起動を前提とする。
冗長化された構成、負荷分散、無停止更新のいずれも持たない。

この前提により、可用性・障害復旧・キャパシティの多くの項目は「保証対象外」となる。
対象外と書くのは、要求しないという判断であって、考えなかったという意味ではない。

## 4. 定義

### 4.1 性能

| 項目 | 要求 | 根拠 |
| --- | --- | --- |
| 推論の応答時間 | p95 が 1秒未満（30日の95%の時間） | `../_archive/runbooks/006` の SLI/SLO 表。学習環境として控えめに置いた値であり、利用側と合意した値ではない |

| 探索の所要時間 | 環境ごとの予算で上限を与える | `config/experiment/{dev,staging,production}.yaml` |

### 4.2 同時利用

| 項目 | 要求 |
| --- | --- |
| 同時利用者数 | 1。複数利用は保証対象外である |

| 項目 | 要求 | 根拠 |
| --- | --- | --- |

SLO は破ってはいけない線ではなく、破ったら手を止めて直す線として扱う。

### 4.5 セキュリティ

#### 認証

サービスを呼ぶ側は、要求にトークンを添える。サービスはトークンを保存せず、SHA-256 の指紋だけを保持する。
設定ファイルが漏れても、それ自体では呼び出せない。

発行されるトークンには `stk_` の接頭辞が付く。漏れた資格情報を検索できるようにするためであり、
この接頭辞は秘密検査の規則 `issued-token` が見る形でもある。

#### 認可

権限は、経路ではなく行為（`predict`、指標の読み取り）で表す。役割は権限の集合であり、呼び手には役割を与える。
判断の方式は ADR 002 が持つ。

拒否は2種類を区別する。401 は誰か分からないこと、403 は誰か分かったうえで許していないことを意味する。

#### 監査

認可の判断はログに残る。誰が、どの役割で、何を求めて断られたかを後から読める
（`../_archive/runbooks/007`）。記録する項目と、保持期間・改竄対策が未確定であることは
`../phase6_セキュリティガバナンス/53_監査ログ設計.md` が扱う。

#### 秘密の取り扱い

| 対象 | 方針 |
| --- | --- |
| ClearML の資格情報 | `./clearml.conf`（git 管理外）にのみ置く。環境変数から読み、Task Parameter には記録しない |
| 発行したトークン | 指紋のみ保存する。平文はその場で一度だけ表示する |
| 検査の対象 | 追跡下のファイル、生成物、Task が記録した Parameter・コンソール出力・環境 |
| 除外 | 理由付きでのみ認める。理由の無い除外は読み込みで拒否される（`config/security.yaml`） |

#### 供給網

SBOM を lock から生成し、OSV へ問い合わせ、その結果でリリース可否を決める。
`critical` で停止し、`high` 以下と深刻度不明は報告に留める（`config/supply_chain.yaml`）。
学習環境で毎回赤くしないための線引きであり、本番相当の環境では `high` も停止側へ動かす。

例外には理由と期限を書く。期限を過ぎた行は除外ではなく期限切れとして扱われ、ゲートは停止する。

### 4.6 ログ

すべてのログ行を1つの JSON オブジェクトとして出力する。要求ごとに相関 ID を付け、
1つの要求に属する行をまとめて追えるようにする（`ml/observability/logging.py`）。

ログの保存先・ローテーション・保持期間は未確定である。現在は各コンテナの標準出力に出るだけで、
集約する仕組みを持たない。

### 4.7 バックアップ・リストア・データ保持

現状、定期バックアップの仕組みは無い。状態は Docker の名前付きボリューム
（`clearml-elasticsearch`、`clearml-mongo-db`、`clearml-files`、`prometheus-data` ほか）にあり、
これらを保全する手順は未定義である。

| 項目 | 状態 |
| --- | --- |
| バックアップ | 未確定。取得手順・頻度・保存先のいずれも決めていない |
| リストア | 未確定。復旧できることを確認していない |
| データ保持期間 | Prometheus のみ 7日。ClearML 側の Dataset・Task・Model・Artifact は無期限 |
| 削除の方針 | 期限で消さず、容量の逼迫時に人が消す。消してはならないものは 12 §4.3 |

`docker volume prune` と `docker system prune --volumes` は、停止中の併存プロジェクトのボリュームを
消すため実行しない。これは運用上の制約であり、バックアップの代わりではない。

### 4.9 保守性

| 項目 | 要求 | 確認手段 |
| --- | --- | --- |
| 静的解析 | Python は ruff・mypy を全体に通す | `pnpm py:lint`, `py:typecheck` |
| 型の厳格化 | Angular は移行済み範囲で strict を維持し、範囲外を増やさない | `pnpm web:typecheck:strict` |
| lint の負債 | 既存の指摘件数を上限として固定し、増加を検出する | `pnpm web:lint:baseline` |
| 依存の方向 | feature 間の直接参照と、生成 API への境界外アクセスを検出する | `pnpm web:boundaries` |
| テストの層 | 宣言した層と実際の置き場所の食い違いを検出する | `pnpm test:pyramid` |
| CI との一致 | ローカルの検査と CI の内容が食い違わないことを検出する | `pnpm ci:parity` |
| 公開 API の変化 | OpenAPI の意味のある変化を検出する | `pnpm web:contract` |

### 4.10 拡張性

単一ホストを前提とするため、水平方向の拡張は保証対象外である。
Agent の台数を増やすことは Compose の定義で可能だが、確認していない。

将来の拡張として条件付きで保留している判断が4つある（`libs/` の分離、zoneless、`@defer`、
カタログ参照の HTTP API）。それぞれ再検討の条件が決まっており、`../backlog/` が持つ。

### 4.11 移植性

WSL2 上の Docker に依存する箇所がある。

| 箇所 | 依存 |
| --- | --- |
| node-exporter | WSL2 のルートが shared / slave でないため `rslave` を付けられない |
| Elasticsearch | ディスク watermark を 500mb に固定している |
| Agent と各サービス | `network_mode: host` を使い、ホストの公開ポートと同じ URL で ClearML を見る |

Linux ホストへ移す場合、これらの設定を見直す必要がある。他の OS での動作は確認していない。

### 4.12 可観測性

推論サービスは、要求数（結果別）、応答時間の分布、予測ラベルの分布を公開する。
平均ではなく分布を測るのは、平均が裾を隠すためである。

学習側は自分で HTTP に答えないため、`ops_exporter` が ClearML に問い合わせて中継する。
読み取り専用であり、監視対象を変更する経路を持たない。

警報は11種類あり、いずれも対応手順へのリンクを持つ。

| 深刻度 | 警報 |
| --- | --- |
| critical | `PredictionServiceDown`(2m), `PredictionServiceHasNoModel`(2m), `PredictionErrorRateHigh`(5%超・5m), `ClearmlUnreachable`(5m), `QueueUnattended`(10m) |
| warning | `PredictionLatencyHigh`(10m), `PredictionDistributionShifted`(30m), `QueueBacklogGrowing`(5件超・30m), `PipelineFailuresRecurring`(3件超・15m), `HostDiskFillingUp`(空き10%未満・15m), `HostMemoryExhausted`(空き10%未満・15m) |

ClearML へ到達できないことは、0 ではなく到達不能として報告する。
Queue の深さ 0 と「サーバが答えなかった」は逆の事実であり、後者を 0 として扱うと警報が沈黙する。

通知先は未確定である。Alertmanager は起動しているが、外部への通知経路を設定していない。
