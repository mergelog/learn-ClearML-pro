## 1. 目的

この文書は、01 が定めた機能をどの技術方式で実現するかを定める。
どのプロセスがどこで動くかは 04 が、コードをどこに置くかは 61 が持つ。

採用理由が ADR にある項目は、理由を書き写さずリンクする。

## 2. 適用範囲

`apps/web`・`ml`・`services`・`tools`・`infra`・`config` の方式を対象とする。
ClearML Server 内部の方式は対象外である。

## 3. 前提

ClearML Server は公式イメージをそのまま使う。本プロジェクトは、その SDK と HTTP API の利用者である。

## 4. 定義

### 4.1 責務の分担

| 層 | 実体 | 担うもの | 担わないもの |
| --- | --- | --- | --- |
| 画面（自作） | `apps/web/src/app/features/{quality-pipeline,data-catalog}` | 利用者の操作と表示 | 判断・計算・保存 |
| 画面（取り込み） | `apps/web/src/app/webapp-common/**` と既存 feature | ClearML Web の既存機能 | 新しい判断（凍結領域。ADR 003） |
| ClearML Web Server | `webserver` コンテナ | 公式 UI の配信 | 本プロジェクトの独自画面 |
| ClearML API Server | `apiserver` コンテナ | Task・Dataset・Model・Queue の保管と検索 | 学習の良し悪しの判断 |
| ClearML File Server | `fileserver` コンテナ | Artifact とモデル本体の保管 | 内容の検証 |
| 学習側 | `ml/` | データ品質の判定、学習、評価、ゲート、昇格の判断 | HTTP の応答 |
| サービス側 | `services/` | 推論の応答、監視のための中継 | 学習、モデルの選定 |
| 道具 | `tools/` | 種まき、秘密の検査、供給網の検査、在庫の確認 | 製品の実行経路 |

判断を `ml/` に閉じ、`services/` を薄く保つのは、判断を ClearML Server 無しで確かめられるようにするためである。

### 4.2 ClearML SDK との境界

SDK を呼ぶモジュールを、用途ごとに1つに限る。他のモジュールは SDK を知らないので、
サーバを起動せずに動かせる。

| 用途 | SDK を呼ぶ唯一の場所 |
| --- | --- |
| 学習 | `ml/semiconductor_quality/clearml_tracking.py` |
| Pipeline のステップ | `ml/pipeline/steps.py` |
| Pipeline の制御 | `ml/pipeline/controller.py` |
| 探索 | `ml/experiment/optimizer.py` |
| モデルの段階管理 | `ml/model_lifecycle/registry.py` |
| 推論のモデル取得 | `services/prediction_api/model_source.py` |
| 監視の読み取り | `services/ops_exporter/clearml_source.py` |
| 秘密検査の対象取得 | `tools/security/clearml_tasks.py` |

この規約の一般形は 61 が持つ。

### 4.3 API 通信方式

#### 画面から ClearML へ

画面は ClearML の HTTP API を、取り込み時に生成された API クライアント
（`src/app/business-logic/**`）経由で呼ぶ。自作 feature がそれに触れてよいのは境界ファイルだけで、
`*-api.service.ts` と `*.adapter.ts`（およびその spec）に限られる。
`pnpm web:boundaries` がこの規則を検査する。

ClearML の語彙（`Task`、`data_processing`、`hyperparams`、`meta.result_msg`）は adapter の内側に留める。
そこから外に現れていれば、adapter の漏れである。

#### サービスの公開 API

`services/prediction_api` は FastAPI で HTTP を提供する。OpenAPI 文書はコードから導出されるため、
文書そのものは常に正しい。問題になるのは変化に誰も気付かないことなので、
消費者との契約テストではなく、公開している形のスナップショットを突き合わせる（ADR 006）。

`pnpm web:contract` が、操作の有無・受け取る形・返す形の変化だけを見る。
説明文やキーの順序が動いても検出しない。

### 4.4 認証方式

| 経路 | 方式 |
| --- | --- |
| 画面 → ClearML | ClearML 自身の認証。`./clearml.conf` の資格情報を使う |
| 呼び手 → 推論サービス / ops-exporter | 要求にトークンを添える。サービスは SHA-256 の指紋だけを保持する |
| Prometheus → 各 exporter | 発行済みトークンを `.generated/security` 経由で渡す |
| Agent → ClearML | 開発者と同じ `./clearml.conf` を読み取り専用で渡す |

トークンは発行時に一度だけ表示する。保存場所は無く、無くしたら再発行する。

### 4.5 認可方式

権限は行為で表し、経路では表さない。役割は権限の集合で、呼び手には役割を与える。
経路は必要な権限を宣言し（`Depends(requires(Permission.PREDICT))`）、検査そのものは書かない。

拒否は 401 と 403 を区別する。401 は資格情報が無いか誰のものでもないこと、
403 は誰か分かったうえで許していないことを意味する。判断の理由は ADR 002 が持つ。

### 4.6 状態管理方式

自作 feature は NgRx の feature state を持ち、経路に入ったときだけ登録する。
アプリ全体へ登録しないのは、その画面を開かない利用者にとって存在しないほうが正しいためで、
どの state がどこで生まれるかも経路の定義を見れば分かる（ADR 007）。

state・Effects・API 境界の provider は、一覧と詳細が共有する親の経路に置く。
子の経路ごとに置くと、詳細へ移った時点で state が作り直され、戻ったときに一覧を引き直すことになる。

| 道具 | 使う場所 |
| --- | --- |
| NgRx Store | feature の state。`provideState` で経路に登録する |
| NgRx Effects | 取得と副作用。`provideEffects` で同じ経路に登録する |
| Signals | container が `selectSignal` で state を読み、入力として子へ渡す |
| RxJS | Effects の内側。component では使わない |

store に触れるのは feature ごとに container 1つだけである。presentational component は store を知らず、
入力と出力だけで組み立てられる。

zoneless への移行は行っていない。判断と再検討の条件は ADR 009 が持つ。

### 4.7 エラーハンドリング

ClearML API の失敗は、`shared/clearml/clearml-failure.ts` が画面に出せる1行へ変換する。
これを共有層へ置いているのは行数のためではなく、「失敗は state に載せる」という方針の実体が
1つでなければ方針にならないためである。

どの失敗を state へ載せ、どれを流すかは feature の判断であり、共有層では決めない。

Python 側は、実行前に判定できる誤りをすべて実行前に拒否する。設定の矛盾は ClearML Task を作る前に、
Dataset の破損は学習を始める前に、それぞれ理由を挙げて止まる。
誤りを1件ずつではなくまとめて報告するのは、1回の実行で全部直せるようにするためである。

### 4.8 ロギング方式

1行を1つの JSON オブジェクトとして出力し、要求ごとの相関 ID を全行に付ける。
文脈は処理ごとに持ち、プロセス全体では持たない。

### 4.9 データ保存方式

| 対象 | 保存先 | 形 |
| --- | --- | --- |
| Dataset | ClearML Dataset（File Server） | CSV。版を付けて登録する |
| ステップ間の受け渡し | ClearML Artifact | pickle を使わない。数値列とカテゴリ列を別の配列として保存し、読む側で組み直す |
| モデル | ClearML Output Model | 段階を tag と metadata の両方に書く |
| 実行の記録 | ClearML Task | Parameter・指標・来歴 |
| 監視の時系列 | Prometheus | 7日保持 |

pickle を避けるのは、pickle が書かれた時点のクラスを持ち回るためである。
コードが変われば古い Artifact を読めなくなり、古い Pipeline の1ステップを再実行したいときに、まさにそれが起きる。

### 4.10 Dataset 管理方式

Dataset は ClearML の版管理をそのまま使う。学習は版を指定して取得し、読み取り専用の複製を受け取る。

学習に使ってよいかの判定は、取得とは別の処理として行う。
列が揃っているかは学習入力の検証が、値が学習に適するかは `ml/data_quality` が見る。
後者の条件は `config/data_quality.yaml` にあり、コード側の列定義と読み込み時に突き合わせる。
片方だけに列を足すと、読み込みが失敗する。

版の間の変化は、生の行ではなく測った統計どうしで比較する。
両方の版を手元に持っていなくても比較できる。

### 4.11 Model 管理方式

モデルは同時に1つの段階にしかいない。段階は tag として書き、同じ内容を metadata にも書く。
tag は検索に使い（いま何が production かを一覧から答える）、metadata は経緯を持つ（誰が、いつ、なぜ）。

宣言された遷移だけを許す。候補から staging を飛ばして production へは進めない。
rollback も同じ承認を要する。

推論サービスは、モデル ID を設定として受け取らない。production を持つモデルを引いてくるので、
昇格は設定の書き換えではなくプロセスの再起動で反映される。
例外は障害再現用の `PREDICTION_MODEL_ID` だけである。

### 4.12 Artifact 管理方式

Pipeline の各ステップは別のプロセスで動くため、中間結果をファイルとして受け渡す。
何を書くかを決める場所は `ml/pipeline/artifacts.py` の1つに限る。

ステップは2種類の入力を読む。Parameter は「何をするか」（どの Dataset 版、どの比率、どの設定）で、
Pipeline の制御役が複製した Task に書き込む。Artifact は「前のステップが何を作ったか」である。

### 4.13 外部連携方式

外部への通信は `tools/supply_chain` から OSV への問い合わせだけである。
SBOM は lock から作るので、問い合わせる対象は実際に固定されているものと一致する。

深刻度は助言が持つ CVSS ベクタから計算する。帯だけを返すデータベースは補助として信じ、
何も返さないものは不明として報告する。不明を低と推測しない。

### 4.14 非同期処理方式

学習は2通りで実行できる。`--queue` を付けない場合はその場のプロセスで実行し、
付けた場合は契約と来歴を記録した Task を Agent へ渡して終了する。

Pipeline の制御役は Task を複製して Parameter を書き換え、終了を待つ。
待つ間 Agent を占有するため、ステップ用の Queue とは別の Queue を使う。
同じ Queue に載せると、制御役が待っている間にステップを動かす Agent がいなくなる。

探索も同じ仕組みで、雛形の Task を複製して設定だけを変える。
1つの設定を変えて30回起動するために、30個のコマンドを作らずに済む。

### 4.15 upstream の取り込み方式

`apps/web` は ClearML Web の fork である。fork 元は remote `upstream`
（`https://github.com/clearml/clearml-web.git`）として登録してある。
upstream のリポジトリの根は、こちらの `apps/web/` に対応する。

#### 何を fork したか

2026-09-13 に突き合わせた結果は次のとおりである。upstream の tag `v2.5` が持つ2481ファイルのうち、

| 状態 | 本数 |
| --- | --- |
| 手元と同一 | 2435 |
| 手元で変更してある | 34 |
| 手元に無い | 12 |

fork 元の commit は1つに絞れていない。tag `v2.5`・branch `v2.5`・`master` を分けるファイルは
`package.json`・`pnpm-lock.yaml`・`pnpm-workspace.yaml`・`src/test.ts` の4つで、
最初の1つは手元で変更してあり、残る3つは手元に無いためである。
分かっているのは、内容が `v2.5` 系列と一致し、`v2.4` とは一致しないことまでである。

#### 更新に気付く方法

`pnpm upstream:status`（`scripts/upstream-status.mjs`）が、`upstream.json` に記録した commit と
upstream の `master` を比べる。CI の `upstream` ジョブが変更のたびに呼ぶ。

版数では比べない。着手時点の upstream の `master` は tag `v2.5` の4つ先にあるが、
`package.json` の `version` はどちらも `2.5.0` のままである。版数を見ると、
依存の更新と脆弱性の修正が4回入ったことが何も見えない。

#### 取り込む手順

以下は未検証である。実際に1回取り込むまで、この手順が成り立つ保証は無い（BL-18）。

1. `git fetch upstream`
2. `git diff <upstream.json の recorded.commit> <取り込む commit>` で、触れているファイルを見る
3. 触れているファイルが上の「手元と同一」の2435本に収まるなら、
   `git diff ... | git apply --directory=apps/web` で当てる
4. 「手元で変更してある」34本に触れているなら、その34本は自動で当てない（次項）
5. `pnpm verify` と `pnpm web:e2e` を通す
6. 取り込んでも見送っても、`upstream.json` の `recorded` を進める。
   見送った場合は理由を `note` へ書く

`git merge` や `git subtree` を使わないのは、upstream の履歴をこちらの履歴へ繋いでいないためである。
繋いでいない以上、取り込みは差分を当てる作業であって、合流ではない。

#### 同じファイルに触れた場合

自作分（`features/quality-pipeline`、`features/data-catalog`、`shared/clearml`）は upstream に無い。
そのため競合は起きない。競合しうるのは、上の34本に限られる。

34本の内訳は次のとおりである。

| 区分 | 本数 | 何を変えたか |
| --- | --- | --- |
| ビルドと設定（`angular.json`・`tsconfig*.json`・`package.json`・`eslint.config.js`・`src/index.html`・`src/main.ts` ほか） | 11 | 単体のリポジトリから `apps/web` への移設と、依存の版上げ |
| 起動と経路（`app.ts`・`app.config.ts`・`app.routes.ts`・`app.component.ts`） | 4 | 自作 feature の経路と初期化を足した |
| 自作画面への導線（`side-nav` と、モデル・Dataset の画面の各2本） | 5 | `/quality-pipeline` と `/data-catalog` へのリンクを足した |
| `*.spec.ts` | 9 | 試験の土台を jasmine / karma から vitest へ置き換えた |
| `webapp-common/` の実装 | 5 | 版上げに伴う API の置き換え（`table` は PrimeNG、`dom-service` は Angular）、`report-widgets` に書かれていた資格情報の削除、`experiment-info-execution` の再描画の修正 |

上から3つ目までの20本は、こちらが足したものである。upstream の変更を当てたうえで、足した分を書き戻す。

`*.spec.ts` の9本は、upstream 側の変更をそのまま当てると jasmine へ戻る。当てずに、
変更の趣旨だけを vitest の書き方へ写す。

`webapp-common/` の5本のうち、版上げに伴う置き換えの2本は、upstream が同じ置き換えを
済ませていればこちらの変更を捨てて upstream 側を採る。資格情報を消した1本は、
upstream が書き戻してくる可能性があるため、取り込みのたびに中身を確かめる。
再描画の修正1本は、upstream 側に同じ修正が入っていなければ残す。

判断の順序は、どの区分でも同じである。upstream 側を既定とし、こちらの変更を残す理由が
書ける場合にだけ残す。理由が書けない変更は、残す価値が無いか、記録が失われているかのどちらかである。
