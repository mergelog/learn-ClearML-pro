## 1. 目的

この文書は、何をいつまで残し、何を消してよいかを定める。

11（データライフサイクル）が段の順序を決めるのに対し、この文書は最後の段の入口、
つまり「消してよいか」の判断だけを扱う。

## 2. 適用範囲

対象は ClearML Server が保持するもの（Dataset・Task・Model・Artifact）、監視の時系列、
各プロセスのログ、およびローカルの生成物である。

法令や契約による保存義務は無い。このリポジトリのデータは合成データであり、
規制上の保持要求を持つものを扱っていない（13 と `../phase6_セキュリティガバナンス/58_規制・コンプライアンス適用判定.md` で扱う）。

## 3. 前提

削除を自動で行う仕組みは無い。期限を書いても、それを実行するものがいない。
したがってこの文書は期限ではなく、**消す契機**と**消してはならないもの**を定める。

容量が尽きたときに何が起きるかは、環境の側で決まっている。
ホストのディスクの空きが10%を切ると `HostDiskFillingUp` が鳴り（`infra/observability/alerts.yml`）、
Elasticsearch は空きが 500MB を切った時点で書き込みを拒む（`infra/clearml/compose.yaml`）。
後者に達すると、学習の指標が記録できなくなる。

## 4. 定義

### 4.1 原則

保持期間は設けない。期限で消す代わりに、容量が逼迫したときに人が消す。

この選び方をするのは、いまのデータが再生成できるためである。Dataset は同じ乱数種から
作り直せ、モデルは学習し直せる。失って取り返せないのは、実行そのものの記録
（どの版でどう学習し、何点だったか）だけであり、これは容量を大きく使わない。

実測値や再現できない実行の記録が積み上がった時点で、この原則は見直す（§6）。

### 4.2 対象ごとの扱い

| 対象 | 保持 | 消してよい契機 | 消し方 |
| --- | --- | --- | --- |
| Dataset | 無期限 | §4.3 のどれにも当たらない版だけ | ClearML Web から版を削除 |
| Dataset 版 | 無期限 | 同上 | 同上 |
| Task | 無期限 | 失敗した Task、および §4.3 に当たらない試行 | ClearML Web から削除 |
| Experiment（試行の集合） | 無期限 | 上と同じ。最良試行を生んだ Task は残す | 同上 |
| Model | 無期限 | `archived` の段にあり、rollback の戻り先でもないもの | ClearML Web から削除 |
| Artifact | 親の Task に従う | Task を消すと一緒に消える | Task の削除に伴う |
| Log（コンテナ標準出力） | 未確定 | — | 未確定（§6） |
| Log（ClearML Server） | 無期限 | ボリューム `clearml-logs` の中身 | 未確定（§6） |
| Audit Log | 対象外 | — | 監査ログは独立して保持していない（§4.5） |
| Temporary File | 再生成できる | いつでも | `.generated/` の該当ディレクトリを消す |
| Backup | 存在しない | — | `../backlog/11_バックアップ手順が無い.md` |

### 4.3 消してはならないもの

次のものを消すと、再現できたはずのものが再現できなくなる。

| 対象 | 理由 |
| --- | --- |
| `production` と `candidate` の段にあるモデル | いま提供している、あるいは提供しようとしているもの |
| 直近で `archived` になったモデル | rollback の戻り先である（`ml/model_lifecycle/registry.py`） |
| 上の各モデルを生んだ Task | 学習条件・指標・来歴がここにしか無い |
| その Task が使った Dataset 版 | 版が消えると、同じ入力で学習し直せない |
| 20（モデルカード）と 22（再現性検証書）が識別子で参照しているもの | 文書が指す先が消えると、文書が嘘になる |

モデルから Dataset 版へは、Task の Parameters と lineage の記録で辿れる
（11 §4.4、22）。消す前にこれを辿り、参照されていないことを確かめる。

### 4.4 期限が決まっているもの

| 対象 | 期限 | 根拠 |
| --- | --- | --- |
| 監視の時系列 | 7日 | `--storage.tsdb.retention.time=7d`（`infra/clearml/compose.yaml`） |

7日を超えた指標は消える。性能の長期傾向をこの環境で追うことはできない。
それが要るようになった時点で、保持期間と保存先を決め直す（44 で扱う。未着手）。

### 4.5 監査ログを独立に保持しない理由

監査ログにあたるものは、いま各プロセスの標準出力にしか出ていない
（`../_archive/security/001_20260908_threat_model.md` §4）。収集先も改竄対策も無いため、
「保持期間」を定めても守る場所が無い。

保持方針は、収集の仕組みを決める `../phase6_セキュリティガバナンス/53_監査ログ設計.md` §4.6 で扱う。そこでも未確定のまま残っている。

### 4.6 削除したときに実体まで消えるか

ClearML の削除は、属性の削除とファイルの削除が別である。この環境では非同期削除を
有効にしてあるため、削除された URL は async-delete サービスが実体ごと消す
（`CLEARML__services__async_urls_delete__enabled`）。

この設定を切ると、Web から消えたのに fileserver のディスクは減らない状態になる。
容量を空けるために消したのに空かない、という結果になるため、切らない。

### 4.7 ローカルの生成物

`.generated/` には、生成した CSV、SDK のキャッシュ、監視の設定、
サービスの資格情報が入る。いずれも作り直せる。

ただし資格情報だけは、消すと呼び出し側の設定と食い違う。
消したら `pnpm sec:tokens` で作り直し、呼び手へ配り直す（`../_archive/runbooks/007_20260908_security.md`）。

## 5. 判断事項

| 判断 | 理由 |
| --- | --- |
| 保持期間を定めず、容量を契機にする | 自動削除の仕組みが無い環境で期限を書いても守られず、守られない規定は判断を誤らせるため |
| 消してはならないものを、期間ではなく参照関係で定める | 古いかどうかではなく、いま何かがそれを指しているかが、再現できるかを決めるため |
| 監視の時系列だけ7日で捨てる | 学習環境で長期傾向を追う用途が無く、放置するとディスクを最も早く埋めるため |

## 6. 未決事項

* ログの保存先・ローテーション・保持期間。`docker compose` に logging の指定が無く、
  ホストの Docker 既定に従っている。
* 監査ログの保持期間と改竄対策（`../phase6_セキュリティガバナンス/53_監査ログ設計.md` §6 と同じ項目）。
* 容量が逼迫したときに、どの順で消すかの具体的な手順。現在は判断の基準だけがある。
* 実測値を扱い始めたときの保持期間。再生成できないデータが入った時点で、§4.1 の原則は成立しない。
* バックアップの保持世代。バックアップ自体が無い。
