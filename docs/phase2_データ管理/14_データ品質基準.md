## 1. 目的

この文書は、Dataset を学習に使ってよいかの合否条件を定める。

10（データディクショナリ）が各列の値域を決めるのに対し、この文書は
「その値域に照らして、Dataset 全体をどう判定するか」を決める。

## 2. 適用範囲

対象は Dataset `semiconductor-quality-data` の各版である。
判定はモデルの良し悪しを見ない。モデル側の合否は 23（モデル評価基準。未着手）で扱う。

## 3. 前提

判定は2段ある。生の文字列のまま測る品質契約と、学習の入力に変換できるかを見る
学習入力契約である（11 §4.4）。この文書は主に前者の基準を定め、
後者については拒否される条件だけを挙げる。

閾値は `config/data_quality.yaml` にあり、この文書はその値の意味と
「なぜその値か」を述べる。値そのものを二重に管理しない。

## 4. 定義

### 4.1 合否の基準

| 観点 | 基準 | 超えたとき | 実装 |
| --- | --- | --- | --- |
| 行数 | 100行以上 | 不合格 | `checks.MINIMUM_ROWS` |
| 欠損率 | 全列 0%（1件も許さない） | 不合格 | `NumericExpectation.maximum_missing_share` 既定 0.0 |
| 型不一致 | 数値列に数値として読めない値があれば、欠損として数える | 欠損率の基準で不合格 | `profile._number` |
| 範囲外値 | 各数値列が 10 §4.2 の値域を外れない | 不合格 | `config/data_quality.yaml` の `numeric` |
| 不正値 | `inf` と `NaN` は数値として扱わない | 欠損率の基準で不合格 | 同上 |
| 分散 | どの数値列も行ごとに値が変わる | 不合格 | `_check_numeric` の分散ゼロ検査 |
| カテゴリ値 | 宣言していない値が1件もない | 不合格 | `maximum_unknown_share: 0.0` |
| 重複 | `sample_id` の重複が1件もない | 不合格 | `maximum_duplicate_identifier_share: 0.0` |
| ラベルの偏り | `pass` も `fail` も5%以上 | 不合格 | `labels.minimum_share: 0.05` |

不合格になった判定は、全ての違反を挙げてから終わる。最初の1件で止めない。
1回の実行で直せるものを、何度も実行させないためである。

### 4.2 閾値の根拠

**欠損 0%** は、欠損を意味として受け取る経路が無いことによる。
学習入力契約が欠損値をそのまま拒否するため、品質契約でこれを許しても先へ進めない（10 §4.5）。

**未知カテゴリ 0%** は、増設した装置を宣言してから流す運用を強制するためである。
宣言していない装置の行で学習すると、モデルが一度も見たことのない装置について判定することになる。

**ラベル 5%** は、不良がほとんど無い Dataset を弾くための下限である。
`fail` が 1% しか無ければ、「全て `pass`」と答えるモデルが正解率 99% を取る。
不良を見つけられないモデルを高得点にしないために、下から抑える。

**分散ゼロ** は、範囲の検査では見つからない故障を捕まえる。
センサが上限に張り付いた列は、値域には収まるが、学習の入力としては存在しないのと同じである。

**100行** は、指標が出ても意味を持たない大きさを弾くための下限である。
これは経験的な線であり、測って決めた値ではない（§6）。

### 4.3 学習入力契約が拒否するもの

品質契約を通っても、次に当たると学習は始まらない（`ml/semiconductor_quality/dataset.py`）。

| 条件 | 理由 |
| --- | --- |
| 列の過不足 | 契約と食い違う Dataset を、黙って一部だけ使わないため |
| 数値に変換できない値 | 変換できない値を代表値で埋めると、埋めた事実が消えるため |
| 契約外のラベル | 2値分類の答えとして扱えないため |
| いずれかのラベルが3行未満 | train / validation / test の3つに層化して割れないため |

### 4.4 Schema 変更

列の一覧は2か所にある。`ml/semiconductor_quality/domain.py` と `config/data_quality.yaml` である。
この2つが食い違うと、契約の読み込み自体が失敗する（`ml/data_quality/contract.py`）。

片方にだけ列を足したときに起きるのは、追加した列が黙って検査されない状態である。
読み込みで止めることで、その状態を作れないようにしている。

列を増やすときは、両方を同じコミットで変える。

### 4.5 データ分布の変化

分布は合否を決めない。前の版と比べて、どれだけ動いたかを測って報告する。

| 対象 | 測り方 | 閾値 |
| --- | --- | --- |
| 数値列 | 平均の移動量を、前の版の標準偏差で割る | 0.5 |
| カテゴリ列 | 分布を一致させるのに動かす必要のある割合（差の絶対値の総和の半分） | 0.2 |
| ラベル | 同上 | 0.1 |

数値列を標準偏差で割るのは、温度と正規化済みセンサに同じ閾値を使うためである。
ラベルの閾値だけ厳しいのは、`fail` の割合が変わると「良い」の意味そのものが変わるためである。

閾値を超えても Pipeline は止まらない。Task に `data-drift` のタグと警告が残り、
その Dataset で学習してよいかを人が決める（`ml/pipeline/steps.py`）。
止めない理由は、動いたデータも学習に使う価値があるためで、
避けたいのは「動いたことに気付かないまま学習すること」だけである。

### 4.6 外れ値を検査しない理由

値域の中にある外れ値は検査していない。

現 Dataset は正規分布から生成した合成データであり、分布の裾を外れ値として弾いても
除かれるのは正常な値である（10 §4.4）。実データを受け入れるときは、
どの値を外れ値とみなすかを工程側の知識から決める必要がある（§6）。

### 4.7 Dataset の採用基準

次の3つを満たしたとき、その版を学習に使ってよい。

1. 品質契約に合格している（`pnpm ml:data check -- --dataset-version <版>` が終了コード0）。
2. 学習入力契約に合格している（Pipeline の validate ステップが通る）。
3. 前の版があるなら、比較の結果を見たうえで使うと判断している。

3番目は自動では判定できない。閾値を超えた列について、それが工程の変化なのか
取得の誤りなのかは、数字だけでは決まらないためである。

### 4.8 判定を実行する場面

| 場面 | 実行するもの |
| --- | --- |
| 登録前のローカル CSV | `pnpm ml:data check -- --csv <path>` |
| 登録済みの版 | `pnpm ml:data check -- --dataset-version <版>` |
| 学習の実行時 | Pipeline の validate ステップ（自動） |
| 版の比較 | `pnpm ml:data drift -- --dataset-version <版> --against <前の版>` |

終了コードは、合格が0、不合格が1、使い方の誤りが2である（`ml/data_quality/cli.py`）。
比較は、閾値を超えた列があれば1を返す。

## 5. 判断事項

| 判断 | 理由 |
| --- | --- |
| 値域を「物理的にありうるか」で決め、いまの Dataset が収まる範囲にしない | 狭くすると、正常な製造条件の変化で学習が止まるため |
| 分布の変化を合否にしない | 動いたデータにも学習の価値があり、止めるべきなのは気付かずに学習することだけであるため |
| 違反を1件目で止めず全て挙げる | 直して再実行する回数を減らすため |
| 閾値をコードではなく YAML に置く | 工程の変化に応じて変えるのは、配備を伴わない操作であるべきだから |

## 6. 未決事項

* 最小行数 100 の根拠。経験的な線であり、学習曲線から決めた値ではない。
* 外れ値の定義。実データを扱うまで決められない。
* 比較の閾値（0.5 / 0.2 / 0.1）の根拠。既定値のまま使っており、
  この Dataset で調整した結果ではない。
* 実測の記録。各版がこの基準をどの余裕で通ったかは残していない（`../backlog/10_実測欄が空のまま.md`）。
