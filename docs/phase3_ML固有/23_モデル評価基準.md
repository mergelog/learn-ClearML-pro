## 1. 目的

この文書は、学習したモデルを何で測り、どの値なら次の段階へ進めてよいかを定める。

モデルカード（20）は、ある1つのモデルが何者かを記す。この文書は、任意のモデルに当てはめる判定の規則を記す。
両者に同じ指標が現れるが、20 が記すのは実測値、この文書が記すのは合否の線である。

## 2. 適用範囲

対象は `semiconductor-quality-classifier` の学習実行が出す評価である。

Dataset の合否は 14 が定める。この文書はモデルだけを扱う。

## 3. 前提

不良（`fail`）はデータのおよそ38%を占める（21 §4.3）。実工程よりはるかに高い。
以下の基準値は、この題材の中で置いた値であり、利用側と合意したものではない。

## 4. 定義

### 4.1 何を測るか

評価は `ml/semiconductor_quality/evaluate.py` が行い、4つの指標と混同行列を出す。
正例は `fail` である。precision・recall・F1 は `fail` について測り、多数派の `pass` については測らない。

| 指標 | 何を表すか | 何のために見るか |
| --- | --- | --- |
| recall | 実際の不良のうち、不良と判定できた割合 | 見逃しの少なさ。不良を見逃した製品はそのまま出荷される |
| precision | 不良と判定したもののうち、実際に不良だった割合 | 過検出の少なさ。良品を不良と言えば再検査の手間が増える |
| f1 | recall と precision の調和平均 | 両者の釣り合い。片方だけを上げた極端なモデルを弾く |
| accuracy | 全体の正解率 | 参考。合否には使わない |
| 混同行列 | 4区分の件数 | どちらの向きに誤っているかを見る。ラベルの順序はデータ契約に従う |

accuracy を合否に使わない理由は、不良が一部しかないデータでは「全部良品」と答えるモデルが
高い accuracy を得るためである。いまの Dataset の不良率は38%なので、そのモデルでも accuracy は0.62になる。

### 4.2 どの部分で測るか

3つの部分は役割が重ならない（21 §4.6）。

| 部分 | 誰が使うか |
| --- | --- |
| train の内側（5分割） | 探索が候補設定を採点する |
| validation | 評価ゲートが候補モデルとして登録してよいかを判定する |
| test | 選び終えたモデルを1回だけ測る。最終評価 |

評価ゲートが validation を見て test を見ないのは、test を選定に使うと、選んだ結果を確かめるものが
残らなくなるためである。`ml/semiconductor_quality/evaluate.py` は test の予測を1度しか行わない。

学習実行が報告するのは validation と test の2つである。train に対する指標は報告しない。

### 4.3 baseline

比較の基準は2つ置く。

| baseline | 内容 | 期待される値 |
| --- | --- | --- |
| 多数派 | すべて `pass` と答える | recall 0、precision 0、f1 0、accuracy 約0.62 |
| 全件不良 | すべて `fail` と答える | recall 1、precision 約0.38、f1 約0.55、accuracy 約0.38 |

この2つは実装しておらず、上の値は不良率38%から計算したものである。

多数派 baseline は recall が0になるので、recall を基準に置けば自動的に落ちる。
全件不良 baseline は recall が1になるので、recall だけを基準にすると通ってしまう。
f1 を併せて見るのは、この後者を止めるためである。

過去の実行との比較は、同じ Dataset 版で測ったものどうしに限る。版が違えば雑音の大きさが違い、
指標が動いた理由を設定の差に帰属できない（21 §4.5）。

### 4.4 採用基準

候補モデル（`candidate`）として登録してよい最低条件を、`config/model_gate.yaml` が持つ。

| 項目 | 値 |
| --- | --- |
| 判定に使う部分 | validation |
| recall の下限 | 0.55 |
| f1 の下限 | 0.65 |

判定は `ml/model_lifecycle/gate.py` が行う。ファイルに書かれた指標だけを見るので、
指標を増やすのはこのファイルの編集であり、コードの変更ではない。次の Pipeline 実行から適用され、配備も要らない。

基準を変えたときは、なぜ変えたかをコミットメッセージに残す。

### 4.5 不採用の条件

次のいずれかに当たれば、そのモデルは候補として登録しない。

| 条件 | 理由 |
| --- | --- |
| validation の recall が 0.55 未満 | 見逃しが多すぎる |
| validation の f1 が 0.65 未満 | recall と precision の釣り合いが取れていない |
| 基準が名指す指標を実行が報告していない | 数値が無いことは、品質の証拠にならない |
| validation の結果が読めない形で残っている | 同上 |

3つ目と4つ目を不合格として扱うのは `ml/model_lifecycle/gate.py` の決めである。
報告されていない指標を判定不能として通すと、指標を出さない実行がすべて通ることになる。

判定の結果は、通っても通らなくても、理由の文とともに Model の metadata に残る
（`gate_split` / `gate_passed` / `gate_detail`）。

### 4.6 探索が使う目的関数

探索（`ml/experiment`）は f1 を最大化する（`config/experiment/base.yaml`）。
評価ゲートと同じ指標を目的に置くのは、探索が選んだ設定がゲートで落ちる事態を減らすためである。

探索は候補1件を train の内側の5分割で採点し、その平均で比較する。
1回の分割で測ると、その分割で強かった設定を選ぶことになる。

探索は不良と判定する確率の閾値も動かすが、閾値は各分割の学習側だけを使った内側の分割で決める。
採点する側の答えを見ずに閾値を決めるためである。既定の学習は閾値を動かさず 0.5 で切る。

### 4.7 退行の判定

同じ Dataset 版で、直前に `production` にあったモデルと比べて指標が下がったとき、
どこから退行と呼ぶかは決めていない。

いま実装されているのは絶対値の下限だけで、前のモデルとの相対比較は行っていない。
昇格は人が要求し、`ml/model_lifecycle` が宣言された遷移だけを許す。前のモデルより悪いモデルを
`production` へ上げようとしても、それ自体は止まらない。

退行を機械が止めるには、比較の対象（どの Model を「前」とするか）と、許容する低下幅を決める必要がある。
どちらも未決である（§6）。

## 5. 判断事項

| 判断 | 記録 |
| --- | --- |
| `fail` を正例とする | `ml/semiconductor_quality/evaluate.py`。不良を見つけられないモデルは役に立たない |
| accuracy を合否に使わない | `config/model_gate.yaml` の注記 |
| ゲートを validation で判定する | `ml/model_lifecycle/gate.py`。test を選定に使わないため |
| 報告されていない指標を不合格とする | 同上 |
| 基準をコードでなくファイルに置く | 基準の変更は運用上の決定であり、配備を伴わないほうがよいため |
| 探索の目的を f1 にする | `config/experiment/base.yaml`。ゲートと揃えるため |
| 閾値を探索の内側でだけ動かす | `../_archive/adr/004_20260909_experiment_settings_and_search.md` |

## 6. 未決事項

* 基準値 0.55 / 0.65 の根拠。学習環境として置いた値であり、見逃しと過検出のどちらがどれだけ高くつくかを利用側と詰めていない。実務では、この費用の比から基準を決める。
* 退行の判定（§4.7）。比較対象と許容する低下幅の両方が未定である。
* baseline を実装して測るかどうか。現在の値は不良率からの計算である。
* `staging` と `production` へ昇格するときの追加条件。いまは `candidate` の条件しか無い。
* 実測値。学習を1回も実行していないため、いまの基準を実際のモデルが満たすかは確かめていない（`../backlog/10_実測欄が空のまま.md`）。
