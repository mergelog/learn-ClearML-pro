## 1. 目的

この文書は、モデルが誤った判定を出し続ける事態をどう防ぎ、起きたときにどう気付くかを整理する。

扱うのは、モデルに固有の危険である。プロジェクト全体の危険は 71（リスク登録簿、未着手）が持ち、
そこから本書を参照する。

## 2. 適用範囲

対象は `semiconductor-quality-classifier` の学習・評価・昇格・提供の各段である。

ClearML Server の障害、ディスク枯渇、資格情報の流出は運用側の危険であり、ここでは扱わない。

## 3. 前提

学習データは合成である（21 §3）。したがって、データドリフトもコンセプトドリフトも、
現在の環境では実際には起こらない。以下に書くのは、手当てがどこまで用意してあるかと、
実データに移したときに何が効かなくなるかである。

現時点で学習を1回も実行していないため、ここに挙げる手当てのうち、実機で確かめたのは
runbook に記録のある範囲に限られる。

## 4. 定義

### 4.1 危険の一覧

影響度と発生確率は、実データを扱う運用に移した場合の見立てである。現在の学習環境での確率ではない。

| ID | 危険 | 影響度 | 確率 | 主な手当て |
| --- | --- | --- | --- | --- |
| R-01 | 過学習 | 中 | 中 | 3分割と交差検証（§4.2） |
| R-02 | データリーク | 大 | 中 | 分割の役割分離（§4.3） |
| R-03 | データドリフト | 中 | 大 | 版間の比較と予測分布の監視（§4.4） |
| R-04 | コンセプトドリフト | 大 | 中 | 未対応（§4.5） |
| R-05 | Dataset の品質低下 | 中 | 中 | 学習前の品質判定（§4.6） |
| R-06 | 学習データの汚染 | 大 | 小 | 部分的（§4.7） |
| R-07 | 誤ったモデルの配布 | 大 | 小 | 評価ゲートと段階遷移（§4.8） |
| R-08 | どのモデルが動いているか分からない | 中 | 中 | 応答がモデルを名乗る（§4.9） |
| R-09 | 再現できない | 中 | 中 | 来歴の記録（§4.10） |
| R-10 | 推論の性能低下 | 中 | 中 | 応答時間と失敗率の監視（§4.11） |

### 4.2 過学習（R-01）

学習用の行に当てはまりすぎ、見たことのない行で外す状態である。

train・validation・test を分け、探索は train をさらに5分割して平均で比較する（23 §4.2）。
1回の分割で測ると、その分割で強かった設定を選ぶことになる。

残る穴が2つある。探索の範囲に `min_samples_leaf` と `max_depth` が入っているので、
複雑さを抑える方向へ動く余地はあるが、目的関数が f1 の最大化だけなので、複雑さそのものに罰は無い。
また、train と validation の指標の開きを見る手立てが無い。学習実行は train の指標を報告しないためである
（`ml/semiconductor_quality/evaluate.py`）。

### 4.3 データリーク（R-02）

答えを知っている情報が、知らないはずの場面へ漏れる状態である。3つの経路を塞いである。

| 経路 | 手当て |
| --- | --- |
| test を設定の選定に使う | 評価ゲートは validation だけを見る。test は最終評価で1回だけ予測する |
| 探索が validation や test を覗く | 探索は train の内側の分割だけを使う（ADR 004） |
| 閾値の調整が採点する側の答えを見る | 閾値は各分割の学習側だけを使った内側の分割で決める |

塞いでいない経路もある。前処理の当てはめは学習用の行だけで行う必要があるが、
その分離が崩れていないことを確かめる検査は無い。また、`sample_id` は特徴量に含めないが、
同一製品の行が複数の部分に分かれて入る事態は、生成器が1行1製品で作るために起きない。
実データでは起こりうる（§6）。

### 4.4 データドリフト（R-03）

入力の分布が学習時から離れる状態である。2か所で見る。

Dataset 側は `pnpm ml:data drift` が2つの版の統計を比べる（`ml/data_quality/drift.py`）。
数値列は平均の移動を前の版の標準偏差で割った値で測り、既定の閾値は 0.5 である。
カテゴリ列は分布の移動量で測り、閾値は 0.2、ラベルの割合は 0.1 とする。
統計どうしを比べるので、両方の版を手元に置いていなくても比較できる。

提供側は予測ラベルの分布を見る。学習時の不良率と、いま返している不良率の差が20ポイントを超えた状態が
30分続くと `PredictionDistributionShifted` が鳴る（`infra/observability/alerts.yml`）。
30分の継続を条件にするのは、短時間の偏りが普通に起きるためである。

どちらも入力そのものの分布ではなく、統計または出力を見ている。提供時の入力を Dataset として
蓄積していないので、実際に届いている値の分布を後から測ることはできない（§6）。

### 4.5 コンセプトドリフト（R-04）

入力の分布は変わらないのに、入力と正解の対応が変わる状態である。工程の変更や検査基準の見直しで起こる。

対応していない。検出には提供後の正解が要るが、推論の応答に対する正解を回収する経路が無い。
予測分布の監視（§4.4）は、入力が変わらずに正解だけが変わった場合には動かない。

実データを扱うなら、検査結果を後から突き合わせて、モデルの判定と実際の判定のずれを測る仕組みが要る。

### 4.6 Dataset の品質低下（R-05）

列が揃っていても学習に使うべきでない Dataset を、学習の前に止める。
値域外・未知のカテゴリ・ラベルの偏り・識別子の重複を見る。条件は 14 が定める。

判定は Pipeline の1段目にあり、落ちればそこで止まる。手で `pnpm ml:train` を実行する経路では、
学習入力契約（列と型）は見るが、この品質判定は通らない。

### 4.7 学習データの汚染（R-06）

意図的または偶発的に、誤ったラベルや作為的な行が Dataset へ混ざる状態である。

現在の手当ては部分的である。品質判定は統計として見えるおかしさ（未知の装置、ラベルの極端な偏り、
識別子の重複）を止める。Dataset の版は ClearML が持ち、親子で連なるので、いつ何が加わったかは辿れる。

止められないものもある。ラベルだけを少数入れ替えるような改変は、統計を動かさないため通る。
Dataset の内容に対する署名やチェックサムの照合は行っていない。

### 4.8 誤ったモデルの配布（R-07）

基準を満たさないモデル、または意図しないモデルが提供される状態である。3段で止める。

| 段 | 内容 |
| --- | --- |
| 評価ゲート | validation の recall と f1 が基準を下回れば `candidate` として登録しない（23 §4.4） |
| 段階遷移 | 宣言された遷移だけを許す。段階を飛ばして上げられない（`ml/model_lifecycle/domain.py`） |
| 提供の条件 | 推論サービスは `production` のモデルだけを読み込む。それ以外の段階を指されると拒否する（`services/prediction_api/domain.py`） |

`production` は排他である。昇格は、いま `production` にあるモデルを同じ操作で降ろす。
2つのモデルが同時に `production` にある瞬間は作らない。降りたモデルには、何に置き換えられたかが残る。

段階・決めた人・時刻・理由は metadata に書き、段階は tag にも書く。
tag は ClearML が検索の対象にするので、「いま production はどれか」を一覧から答えられる。

### 4.9 モデルの取り違え（R-08）

どのモデルが判定を返したのか分からなくなる状態である。

推論の応答は必ずモデルを名乗る（`services/prediction_api/schemas.py`）。
応答を見れば、どのモデルのどの段階が返したかが分かる。
提供できるモデルが無ければ `prediction_model_loaded` が 0 になり、2分で `PredictionServiceHasNoModel` が鳴る。

版の表し方は段階であり、連番ではない（20 §4.1）。同じ段階を過去に持っていたモデルを区別するには
metadata の昇格履歴を見る必要がある。

### 4.10 再現できない（R-09）

ある Task が出した結果を、後から同じ条件で作り直せない状態である。

来歴（コミット、イメージ、実行者、環境、Dataset 版、乱数の種、パラメータ）を Task に記録する。
何を記録し、何が記録されていても再現が成立しないかは 22 が持つ。

### 4.11 推論の性能低下（R-10）

判定の質ではなく、応答の速さと成否が悪化する状態である。

95パーセンタイルが1秒を超えた状態が10分続くと `PredictionLatencyHigh`、
サービス側の失敗率が5%を超えた状態が5分続くと `PredictionErrorRateHigh` が鳴る。
入力の誤り（4xx）を失敗率に含めないのは、呼び出し側の不具合でこちらが起こされないようにするためである。

### 4.12 いま塞いでいないもの

| 事項 | 現状 |
| --- | --- |
| コンセプトドリフト | 検出の手立てが無い（§4.5） |
| 提供時の入力の分布 | 蓄積していないため、後から測れない |
| 退行（前のモデルより悪いモデルの昇格） | 絶対値の下限だけで、相対比較が無い（23 §4.7） |
| train と validation の指標の開き | 学習実行が train の指標を報告しない |
| Dataset の改ざん | 統計に現れない改変は通る（§4.7） |

## 5. 判断事項

| 判断 | 記録 |
| --- | --- |
| 評価ゲートを validation で判定する | `ml/model_lifecycle/gate.py`、23 §4.2 |
| `production` を排他にし、昇格と降格を同じ操作で行う | `ml/model_lifecycle/registry.py` |
| 段階を tag と metadata の両方に書く | 同上。tag は「いまの状態」、metadata は「そうなった経緯」 |
| 提供するのは `production` だけとする | `services/prediction_api/domain.py` |
| drift の閾値を 0.5 / 0.2 / 0.1 とする | `ml/data_quality/drift.py`。実測に基づく値ではない |
| 予測分布の監視を30分継続の条件にする | `infra/observability/alerts.yml`。短時間の偏りは普通に起きるため |

## 6. 未決事項

* 提供後の正解を回収する経路。これが無い限り、コンセプトドリフトは検出できない。
* 提供時の入力を Dataset として蓄積するかどうか。蓄積すれば実際の入力分布を測れるが、保持期間と PII の判断が要る。
* 前処理の当てはめが学習用の行だけで行われていることを確かめる検査。
* 実データで同一製品の複数行が別々の部分へ入る事態の扱い。生成器では起きないが、実データでは起こりうる。
* drift の閾値の根拠。実測ではなく、置いた値である。
* 退行の判定（23 §4.7）。
* 各危険の Owner。現在は単独開発のため、すべて同一人物である。
