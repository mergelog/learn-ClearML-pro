## 1. 目的

この文書は、何をどの層で確かめ、いつ実行するかを定める。
合格条件そのものは 32 が持つ。個々のケースは 31 が持つ。

層の定義は `test-pyramid.json` にあり、その宣言と実際のテストの置き場所は
`pnpm test:pyramid` が突き合わせる。この文書は宣言を読み解いたものであり、宣言の写しではない。

## 2. 適用範囲

`ml` / `services` / `tools` / `Angular Web` / `scripts` のテストと、
検査スクリプト（lint・境界・型・契約・秘密・供給網）を対象とする。

## 3. 前提

テストの実行に ClearML Server を必要としない。SDK を呼ぶモジュールは層ごとに1つへ寄せてあり、
テストではそれを差し替える。実サーバとの通信を確かめるのは runbook の実機手順であって、
自動テストではない。

## 4. 定義

### 4.1 層と、その層が答える問い

| 層 | 実行 | 何を確かめるか | 確かめないこと |
| --- | --- | --- | --- |
| ゲート自身 | `pnpm web:gates:test` | 検査スクリプトが、落とすべきものを実際に落とすこと | 製品コードの挙動 |
| 学習・評価の単体 | `pnpm ml:test` | しきい値・境界値・失敗時にどちらへ倒すか。ClearML SDK は差し替える | 実サーバとの通信、Agent 上の実行、学習の精度そのもの |
| サービスの単体 | `pnpm services:test` | 入出力・認可・失敗応答の形。HTTP 層まで含めて呼ぶ。公開 OpenAPI の変化もここで見る | 画面からの利用、実際のモデル成果物、負荷特性 |
| 道具の単体 | `pnpm tools:test` | seed / security / supply_chain / data_status の判断。何を見つけ、何で止めるか | 外部データベースへの実問い合わせ、イメージの実走査 |
| Angular の単体（自作） | `pnpm web:test` | 表示判断、container と state の結線、data-access の変換、reducer / effects の遷移 | 実 HTTP、ルーティング、本番ビルドの成立 |
| Angular の単体（取り込み） | `pnpm web:test` | ClearML Web が持っていたテスト。回帰の網としてそのまま走らせる | 自分たちの判断。ここへ新しいテストを足さない |
| E2E | `pnpm web:e2e` | 画面が起動し、経路から操作・表示まで縦に繋がること。API 応答は fixture が差し替える | 業務ルールの網羅 |

### 4.2 現在の規模

`pnpm test:pyramid:report` の出力である（2026-09-12 時点）。

| 層 | ファイル | ケース | 上限 |
| --- | --- | --- | --- |
| ゲート自身 | 7 | 62 | — |
| 学習・評価の単体 | 38 | 820 | — |
| サービスの単体 | 11 | 169 | — |
| 道具の単体 | 5 | 80 | — |
| Angular の単体（自作） | 28 | 319 | — |
| Angular の単体（取り込み） | 50 | 111 | — |
| E2E | 6 | 29 | 30 |

E2E だけに上限がある。残り1件しかないため、E2E を足したくなったときは、
まず下の層でやるべきことを上げていないかを疑う（ADR 005）。

### 4.3 層に当てはまらない検査

テストと同じ扱いで実行するが、ケース数では数えないものがある。

| 検査 | 実行 | 何を守るか |
| --- | --- | --- |
| Python の lint | `pnpm py:lint` | ruff の指摘を0に保つ |
| Python の型 | `pnpm py:typecheck` | mypy を通す |
| カバレッジ | `pnpm py:coverage` | `ml` / `services` / `tools` の分岐網羅が 80% を下回らない |
| ESLint の負債 | `pnpm web:lint:baseline` | 既存の指摘件数を上限として固定し、増加を検出する |
| 依存の方向 | `pnpm web:boundaries` | feature 間の直接参照と、生成 API への境界外アクセス |
| 型の厳格化 | `pnpm web:typecheck:strict` | 移行済み範囲が strict を通り続けること |
| 公開 API の形 | `pnpm web:contract` | OpenAPI の意味のある変化（操作・受け取る形・返す形） |
| CI との一致 | `pnpm ci:parity` | ローカルの検査と CI の内容が食い違わないこと |
| 層の宣言との一致 | `pnpm test:pyramid` | 宣言した層と実際の置き場所 |
| 秘密の混入 | `pnpm sec:scan` | 追跡下のファイルに資格情報の形が無いこと |
| 生成物の秘密 | `pnpm web:scan:build` | ビルド成果物に資格情報が写っていないこと |

カバレッジの 80% は床であって目標ではない。導入時点の実測が 82% であり、
そこを割る変更を止めるために置いてある。

### 4.4 Dataset の検証

Dataset には2種類の検証がある。片方はデータの形を、もう片方は学習に使えるかを見る。

| 検証 | 実行 | 落ちる条件 |
| --- | --- | --- |
| 学習入力の検証 | 学習の一部として常に走る | 列の過不足、数値に変換できない値、契約外のラベル、ラベルごとの行数が3未満 |
| データ品質の判定 | `pnpm ml:data check` | 値域外、未知のカテゴリ、ラベル比率が 5% 未満、識別子の重複 |
| 版の比較 | `pnpm ml:data drift` | 落ちない。何が動いたかを報告する |

品質の判定は Pipeline の中でも自動的に行われ、条件を満たさない Dataset では学習が始まらない。

### 4.5 モデルの検証

| 検証 | 実行 | 判定 |
| --- | --- | --- |
| 評価ゲート | Pipeline の一部として走る | validation の recall ≥ 0.55 かつ f1 ≥ 0.65 |
| 段階の遷移 | `pnpm ml:model promote` / `rollback` | 宣言された遷移のみ。承認者と理由が空なら拒否 |

ゲートの判定そのもの（境界値、どちらへ倒すか）は、学習・評価の単体層が確かめる。

### 4.6 性能テスト

推論サービスに対して `pnpm serving:load` で負荷を掛ける（k6）。既定は10 VU・30秒。

| 閾値 | 値 | 出所 |
| --- | --- | --- |
| 応答時間 | p95 < 1000 ms | `services/perf/prediction_api.js` |
| 失敗率 | 5% 未満 | 同上 |
| 応答の形 | 全件が期待する形であること | 同上 |

この2つの数値は SLO（02 §4.1・§4.4）と同じ値である。
同じであることを `scripts/tests/perf-thresholds.test.mjs` が確かめている。

負荷試験は CI では実行しない。実行には推論サービスの起動が要る。

### 4.7 セキュリティテスト

| 対象 | 実行 | 内容 |
| --- | --- | --- |
| リポジトリ | `pnpm sec:scan` | 追跡下のファイルから資格情報の形を探す |
| 生成物 | `pnpm sec:scan:paths` | 追跡外の成果物を指定して探す |
| Task の記録 | `pnpm sec:scan:clearml` | Parameter・コンソール出力・Agent が記録した環境 |
| 依存 | `pnpm sec:sbom` → `pnpm sec:audit` | lock から SBOM を作り、OSV へ問い合わせる |
| イメージ | Trivy（CI のみ） | ベースイメージと OS パッケージ |
| 可否の判定 | `pnpm sec:gate` | 走査器の報告を読み、critical があれば停止する |

認可の挙動（401 と 403 の区別、権限の不足）はサービスの単体層が確かめる。

### 4.8 回帰テスト

回帰は、専用のテスト群ではなく次の3つで見る。

取り込んだ Angular のテストをそのまま走らせること。既存の指摘件数と依存の方向を固定して
増加を検出すること。公開 API の形をスナップショットとして突き合わせること。

振れるテストは、直す前に数える（`pnpm test:flaky`）。手順は `../_archive/runbooks/009` にある。

### 4.9 実施タイミング

| 契機 | 実行するもの |
| --- | --- |
| 変更中（手元） | 触った範囲に対応する単体層 |
| 変更を終えたとき（手元） | `pnpm verify`（Python 一式 → Web 一式 → 秘密検査） |
| CI（push / PR） | Python ジョブ、Angular ジョブ、E2E ジョブ、秘密検査ジョブ、供給網ジョブ |
| モデルを昇格する前 | 評価ゲートの通過、Dataset の品質判定 |
| 配備の前 | `pnpm serving:smoke`、必要なら `pnpm serving:load` |
| 監視を変えたとき | `pnpm ops:smoke` |

`pnpm verify` と CI の内容は同じでなければならず、その一致を `pnpm ci:parity` が検査する。

### 4.10 テスト環境

| 層 | 必要なもの |
| --- | --- |
| 単体（すべて） | 言語処理系のみ。ClearML Server も Docker も要らない |
| E2E | Angular のビルドと Playwright のブラウザ。API 応答は fixture |
| 負荷 | 推論サービスの起動と k6 |
| 供給網の audit | ネットワーク（OSV への問い合わせ） |
| 実機確認（runbook） | Compose 一式。併存プロジェクトを先に停止する |

### 4.11 実施責任

開発者1名がすべてを実施する。役割を分けた実施体制は対象外である（01 §4.9）。

CI は GitHub Actions で自動実行される。手元の `pnpm verify` と同じ内容を通すため、
どちらか一方だけが緑になることはない。
