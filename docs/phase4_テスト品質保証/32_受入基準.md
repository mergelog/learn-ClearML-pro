## 1. 目的

この文書は、何をもって合格とするかを定める。何をどの層で確かめるかは 30 が持つ。
リリースしてよいかの判定は 33 が持ち、この文書はその入力になる。

合格条件は、実行できる検査に紐付いたものだけを条件として書く。
人が見て判断するしかない項目は、そう明示する。

## 2. 適用範囲

変更を受け入れるかどうかの判断を対象とする。対象は次の3種類の変更である。

| 種別 | 例 |
| --- | --- |
| コードの変更 | `ml` / `services` / `tools` / `Angular Web` / `scripts` |
| 設定の変更 | `config/**`、`infra/**` |
| モデルの受け入れ | 学習の結果を候補として認めるかどうか |

文書だけの変更（`docs/**`）は、どのゲートの対象でもない。§4.9 で扱う。

## 3. 前提

すべての検査は、手元で `pnpm verify` として、CI で同じ内容として実行できる。
両者の一致は `pnpm ci:parity` が検査するため、一方だけが緑になることはない。

## 4. 定義

### 4.1 機能

| 条件 | 判定 |
| --- | --- |
| 変更した範囲に対応する単体テストが通る | `pnpm ml:test` / `services:test` / `tools:test` / `web:test` |
| 層の宣言と置き場所が一致する | `pnpm test:pyramid` |
| 新しい判断にテストがある | 人が見て判断する。ゲートは持たない |

新しい判断とは、しきい値・分岐・失敗時にどちらへ倒すかを決めた箇所を指す。
それを足したときにテストが増えていなければ、受け入れない。

### 4.2 UI

| 条件 | 判定 |
| --- | --- |
| 自作 feature の単体テストが通る | `pnpm web:test` |
| 画面が起動し、経路から操作・表示まで繋がる | `pnpm web:e2e` |
| E2E の件数が上限を超えない | `pnpm test:pyramid`（上限30、現在29） |
| 本番ビルドが成立する | `pnpm web:build` |
| ビルド成果物に資格情報が写っていない | `pnpm web:scan:build` |
| 初期バンドルが上限を超えない | 人が見て判断する。現在 3.10 MB、余裕 1.6% |
| 見た目の確認 | 人が見て判断する。自動判定は持たない |

### 4.3 API

| 条件 | 判定 |
| --- | --- |
| 入出力・認可・失敗応答の形が期待どおり | `pnpm services:test` |
| 公開している OpenAPI が黙って変わっていない | `pnpm web:contract` |
| 変えた場合、スナップショットが更新され差分がレビューに含まれる | `pnpm serving:openapi:update` を実行したうえで、人が差分を見る |

公開 API の変更は、それ自体が不合格ではない。更新せずに変えたことが不合格である。

### 4.4 性能

| 条件 | 判定 |
| --- | --- |
| 推論の p95 応答時間が 1000 ms 未満 | `pnpm serving:load`（k6） |
| 推論の失敗率が 5% 未満 | 同上 |
| 応答の形が全件正しい | 同上 |

既定の負荷は10 VU・30秒である。この条件は SLO と同じ値であり、
同一であることを `scripts/tests/perf-thresholds.test.mjs` が確かめている。

同時要求数の合格条件は未確定である（02 §4.2）。

### 4.5 セキュリティ

| 条件 | 判定 |
| --- | --- |
| 追跡下のファイルに資格情報が無い | `pnpm sec:scan` |
| Task の記録に資格情報が無い | `pnpm sec:scan:clearml` |
| 依存に critical の脆弱性が無い | `pnpm sec:gate` |
| 除外に理由と期限がある | `pnpm sec:gate`（期限切れは停止する） |
| 認可の判断が変わっていない | `pnpm services:test` |

`high` 以下と深刻度不明は報告に留め、停止しない。この線引きは学習環境としての判断であり、
本番相当の環境では `high` も停止側へ動かす（02 §4.5）。

### 4.6 データ品質

Dataset を新しく登録した場合、または既存の版を学習に使う場合の条件である。

| 条件 | 判定 |
| --- | --- |
| 全数値列が値域に収まる | `pnpm ml:data check` |
| 未知のカテゴリが1件も無い | 同上 |
| どちらのラベルも 5% 以上ある | 同上 |
| 識別子の重複が1件も無い | 同上 |
| 列の定義と値域の宣言が一致する | 読み込み時に自動で突き合わせる |

前の版から何が変わったかは `pnpm ml:data drift` が報告する。これは合否を出さない。
変化の大きさをどこで不合格とするかは未確定である。

### 4.7 モデルの精度

| 条件 | 判定 |
| --- | --- |
| validation の recall ≥ 0.55 | 評価ゲート（`config/model_gate.yaml`） |
| validation の f1 ≥ 0.65 | 同上 |
| test の指標が記録されている | Task の指標 |

test の指標に合格条件は置かない。test はモデルを選んだ後の最終確認に一度だけ使うものであり、
そこに基準を置くと選定に使うことになる。

accuracy は基準にしない（20 §4.5）。

### 4.8 再現性

| 条件 | 判定 |
| --- | --- |
| Task に Dataset 版・設定・種が記録されている | 自動。記録なしでは実行できない |
| Task に来歴（コミット・イメージ・実行者・Queue）が記録されている | 自動。取れない項目は `unknown` になる |
| `git_working_tree` が `clean` である | 人が見て判断する。`dirty` の実行は再現できない |

`dirty` の実行を禁止してはいない。それを昇格の対象にしないという判断である。

### 4.9 文書

| 条件 | 判定 |
| --- | --- |
| 実装を変えたとき、対応する文書が同じ変更に含まれる | 人が見て判断する |
| 存在しない文書へリンクしていない | 人が見て判断する |
| 未確定の事項を推測で埋めていない | 人が見て判断する |

文書はどのゲートの対象でもないため、ここは人の判断に依存する。
その弱さは既知であり、`../backlog/12_文書と実装の乖離.md` にある。

### 4.10 不具合の扱い

| 種別 | 受け入れ条件 |
| --- | --- |
| Critical（データを失う、資格情報が漏れる、production のモデルが誤る） | 0件。1件でもあれば受け入れない |
| High（主要な機能が使えない、警報が鳴らない） | 期限と対応方針を決めたうえでのみ受け入れる |
| Medium / Low | 記録したうえで受け入れてよい |
| Known Issue | 現象・影響・回避方法・再検討の条件を書いて残す |

不具合を記録する場所は、現在 `../backlog/` だけである。
課題管理表（72）は未着手であり、種別の運用はそこで定める。

### 4.11 まとめ

上の条件のうち、自動で判定できるものは `pnpm verify` が一度に実行する。

```text
verify
  ├ verify:python   py:lint → py:typecheck → py:coverage
  ├ verify:web      web:gates:test → ci:parity → test:pyramid → web:lint:baseline
  │                 → web:boundaries → web:contract → web:typecheck:strict
  │                 → web:test → web:e2e:typecheck → web:build → web:scan:build
  └ verify:security sec:scan
```

`verify` に含まれないのは、E2E の実行・負荷試験・供給網の audit と gate・
Dataset の品質判定・評価ゲートである。前の3つは CI が、後の2つは実行時に判定する。

## 5. 判断事項

| 判断 | 理由 |
| --- | --- |
| test に合格条件を置かない | 選定に使うと、独立した最終評価が残らない |
| カバレッジ 80% を床として扱う | 導入時の実測 82% を割る変更を止めるためであり、目標値ではない |
| `high` の脆弱性で停止しない | 学習環境で毎回赤い状態を作ると、ゲートを迂回する習慣ができる |
| 文書にゲートを設けない | `docs/**` を検査対象にしていない。代わりに受け入れ時の判断項目として置く |
