## 1. 目的

この文書は、出してよいかどうかを判定するための確認項目を定める。
個々の合否条件は 32 が持ち、この文書はそれを「出す」という行為の単位でまとめ直したものである。

32 が変更1件ごとの受け入れを見るのに対し、この文書は出す直前に一度だけ通す確認を扱う。

## 2. 適用範囲

本プロジェクトに、外部の利用者へ配布する成果物は無い。出す対象は次の3つであり、
どれを出すかによって確認項目が変わる。

| 種別 | 何が動くか | 出す操作 |
| --- | --- | --- |
| R1 モデルの昇格 | production 段階のモデルが入れ替わり、推論サービスの答えが変わる | `pnpm ml:model promote` |
| R2 推論サービスの配備 | イメージを差し替えてコンテナを入れ替える | `pnpm serving:build` → `pnpm serving:up` |
| R3 画面の配備 | Angular のビルド成果物を差し替える | `pnpm web:build` |

ClearML Server 自体の版上げ（現在 `clearml/server:2.4.0`）は、この文書では扱わない。
基盤の変更であり、判定の枠組みが違う（40番台・43、いずれも未着手）。

## 3. 前提

版の記録は git のタグではなく ClearML 側にある。現在タグは1つも無く、
リリース番号を振る運用も無い。R1 はモデルの版、R2 と R3 はイメージのタグ（現在 `0.1.0`）で識別する。

自動判定できる項目は `pnpm verify` に含まれる。含まれない項目は、実行する人が明示的に走らせる。

## 4. 定義

### 4.1 確認項目の一覧

○ は必須、— は対象外である。「判定」は、何を見て判断するかである。

| # | 項目 | 判定 | R1 | R2 | R3 |
| --- | --- | --- | --- | --- | --- |
| 1 | 必須テストが通る | `pnpm verify` と CI の5ジョブ | ○ | ○ | ○ |
| 2 | E2E が通る | `pnpm web:e2e`（29件） | — | — | ○ |
| 3 | Critical 不具合が0件 | 人が判断（§4.3） | ○ | ○ | ○ |
| 4 | High 不具合の扱いが決まっている | 人が判断（§4.3） | ○ | ○ | ○ |
| 5 | Dataset の品質判定が通っている | `pnpm ml:data check` | ○ | — | — |
| 6 | 評価ゲートを通過している | Pipeline 内の判定。Task の記録 | ○ | — | — |
| 7 | Dataset の版が特定できる | モデルの `dataset_id` / `dataset_version` | ○ | ○ | — |
| 8 | モデルの版と段階が特定できる | 段階タグ。production は1件だけ | ○ | ○ | — |
| 9 | 再現に要る記録が揃っている | Task の来歴。`git_working_tree` が clean | ○ | — | — |
| 10 | 切り戻しの手段がある | R1 は `pnpm ml:model rollback`。R2・R3 は§4.5 | ○ | △ | △ |
| 11 | SBOM を生成してある | `pnpm sec:sbom` | — | ○ | ○ |
| 12 | Security ゲートを通過している | `pnpm sec:gate`、`pnpm sec:scan` | — | ○ | ○ |
| 13 | 配備後の疎通を確認した | `pnpm serving:smoke`（6項目） | — | ○ | — |
| 14 | 成果物に資格情報が写っていない | `pnpm web:scan:build` | — | ○ | ○ |
| 15 | 移行の要否を確認した | §4.6 | ○ | ○ | ○ |
| 16 | Backup を取得した | 手段が無い（§4.4） | — | — | — |
| 17 | Restore を確認した | 手段が無い（§4.4） | — | — | — |
| 18 | License を確認した | 手段が無い（§4.7） | — | — | — |
| 19 | Release Note を作成した | 運用が無い（§4.8） | — | — | — |

△ は、手段はあるが確認していないものである。16・17・18・19 を — にしている理由は、
それぞれの節に書く。対象外にしたのは項目が不要だからではなく、
いま判定に使える手段が無いためである。

### 4.2 必須テスト（項目1・2）

手元の `pnpm verify` と CI の内容は一致しており、その一致は `pnpm ci:parity` が検査する。
したがって「必須テストが通る」は、CI の5ジョブ（python / web / e2e / security / supply-chain）が
すべて緑であることと同じである。

`verify` に含まれないのは E2E の実行・負荷試験・供給網の audit と gate である。
E2E と供給網は CI の専用ジョブが受け持つため、手元で出すときだけ明示的に走らせる。

2026-09-12 時点の実行結果は 31 §4.10 にある。1590件すべてが Pass である。

### 4.3 不具合（項目3・4）

種別の定義は 32 §4.10 にある。判定に使える一覧は現在 `../backlog/` だけであり、
種別も期限も持たない。したがってこの2項目は人の判断に依存する。

課題管理表（72、未着手）が出来た時点で、この項目は「その表に Critical が0件であること」へ
置き換える。

### 4.4 Backup と Restore（項目16・17）

取得の手段も復旧の手段も無い。状態は Docker の名前付きボリューム3つ
（`clearml-mongo-db` / `clearml-elasticsearch` / `clearml-files`）にあり、
取得・保存・復旧のいずれについても手順が無い（`../backlog/11_バックアップ手順が無い.md`）。

このため、この2項目を必須にすると、どのリリースも判定を通せない。
確認できないものを「確認した」と書くよりも、手段が無いことを残す。

手順が出来た時点で、R1 と R2 を ○ に変える。確かめていない復旧手順を ○ にはしない。

### 4.5 切り戻し（項目10）

R1 は `pnpm ml:model rollback` がある。production が置き換えた前のモデルを production へ戻す。
承認者と理由が空なら拒否される（31 §4.4）。

R2 と R3 は、compose のイメージを前のタグへ戻すことで成立する。イメージは
`${PREDICTION_API_IMAGE:-stackup/semiconductor-prediction-api:0.1.0}` のように
既定値を持つ変数で指定してあり、版を固定してある。ただしタグを1つしか作っていないため、
戻す先が存在するかを確かめたことがない。ここを △ にしている理由である。

### 4.6 移行（項目15）

本プロジェクトが所有するスキーマは2つある。どちらもコードの中の宣言であり、
移行スクリプトは持たない。

| 対象 | 宣言の場所 | 変えたときに起きること |
| --- | --- | --- |
| Dataset の列 | `ml/semiconductor_quality/domain.py` | 品質基準の宣言（`config/data_quality.yaml`）と食い違うと、読み込みで拒否される |
| 公開 API の形 | `services/prediction_api` | スナップショットと食い違うと `pnpm web:contract` が落ちる |

どちらも、既に保存されたデータを書き換える必要は生じない。過去の Dataset 版は
その版のまま残り、新しい列を要求する学習はその版を読めない。これは移行ではなく
版の不一致であり、不一致は読み込み時に止まる。

ClearML Server が持つ索引の移行はこの文書の対象外である（§2）。

### 4.7 License（項目18）

依存の一覧は SBOM として生成できるが、ライセンスの欄を持たない（`tools/supply_chain/sbom.py`）。
このため、依存のライセンスを機械的に確認する手段が無い。

OSS ライセンス台帳（`../phase6_セキュリティガバナンス/55_OSSライセンス台帳.md`）は、台帳の形と確認の順序を
定めたが、全件の列挙には至っていない。SBOM がライセンス欄を持った時点で、この項目を ○ に変える。
ClearML Web を fork して取り込んでいるため、取り込み範囲のライセンス条件の確認は
台帳の作成時に必要になる。

### 4.8 Release Note（項目19）

リリース番号を振る運用が無く、git のタグも1つも無い。出したことを記録する場所も無い。

リリース履歴（77、未着手）が出来た時点で、この項目を ○ に変える。
それまでは、出したことはコミットの履歴にのみ残る。

### 4.9 判定の記録

判定した結果を残す場所は、現在無い。R1 については昇格の要求に承認者と理由が必須であり、
モデルの metadata（`promoted_by` / `promoted_at` / `promotion_reason`）として残る。
R2 と R3 には対応するものが無い。

## 5. 判断事項

| 判断 | 理由 |
| --- | --- |
| 「リリース」を3つの種別に分ける | 配布物が無く、出す対象ごとに確認すべきものが違う |
| 手段の無い項目を必須にしない | 必須にすると、通せない判定を毎回迂回することになる |
| 手段の無い項目を削除もしない | 何が欠けているかが判定表から消えると、欠けていること自体を忘れる |
| 切り戻しを △ に留める | 手段はあるが、戻す先が存在するかを確かめていない |
