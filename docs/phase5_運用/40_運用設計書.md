## 1. 目的

この文書は、動いているものを動かし続けるために誰が何をするかを定める。

操作そのものの手順は `../_archive/runbooks/` の9本にあり、ここへ写し取らない。
9本を一続きに演じる筋書きは `45_通し台本.md` が持つ。
この文書が持つのは、運用の単位（何と何をまとめて起動・停止するか）、
定常の作業とその契機、そしてどの作業がどの runbook に対応するかの対応表である。

障害が起きたあとの進め方は 42、データを失ったあとの復旧は 43、
資源が尽きる前の見積りは 44 が持つ。この文書は、そのいずれでもない平常時を扱う。

## 2. 適用範囲

対象は、単一ホスト上で `infra/clearml/compose.yaml` が起動する15サービスと、
ホスト側で動く Angular の開発サーバである。

対象外は次の3つである。

| 対象外 | 理由 |
| --- | --- |
| ClearML Server の版上げ | 手順を定めていない。現在 `clearml/server:2.4.0` に固定してある |
| ホスト OS とDocker 自体の保守 | 開発端末（WSL2）の管理であり、本システムの運用ではない |
| 外部利用者への配布・告知 | 配布物と外部利用者が存在しない（01 §4 の対象範囲） |

## 3. 前提

運用者は開発者1人であり、交代も引き継ぎも発生しない。当番制、オンコール、
承認者と実施者の分離は、いずれも実在しないため設計しない。

このホストには併存する別プロジェクト（`../001-learn-ClearML`、Compose プロジェクト名
`stackup-clearml`）があり、ポート 8008 / 8080 / 8081 を共有する。同時には起動できない。
切り替えるときは、先に相手側を停止する。

Compose のプロジェクト名は `learn01-clearml` である。`docker` を直接使うときは、
コンテナ名とボリューム名がこの接頭辞を持つことを確認してから操作する。

## 4. 定義

### 4.1 運用の単位

15サービスは、役割で4つの群に分かれる。

| 群 | サービス | 停止したときに止まること |
| --- | --- | --- |
| 基盤 | apiserver, fileserver, webserver, async-delete, elasticsearch, mongo, redis | すべて。他の3群は基盤に依存する |
| 学習 | training-agent, pipeline-agent | Queue に入れた Task が実行されない。投入自体は成功する |
| 推論 | prediction-api | 判定の要求に答えられない。学習と記録は続く |
| 監視 | ops-exporter, prometheus, alertmanager, grafana, node-exporter | 何も止まらない。異常に気付けなくなる |

群を分けて起動できるのは、学習と推論の停止を互いに波及させないためである。
モデルを入れ替える間、推論だけを止めて学習を続けられる。

起動はすべて `scripts/backend-up.sh` を通る。引数を渡すとそのサービス（と依存先）だけ、
渡さなければ15サービスすべてを起動する。`package.json` の別名は3つある。

| 別名 | 起動するもの |
| --- | --- |
| `pnpm agent:up` | training-agent。pipeline-agent は含まない |
| `pnpm serving:up` | prediction-api |
| `pnpm ops:up` | ops-exporter, prometheus, alertmanager, grafana |

pipeline-agent と node-exporter を名指しで起動する別名は無い。
どちらも `pnpm backend:up`（引数なし）で上がる。Pipeline を動かすときは、
`pnpm agent:up` だけでは制御役がいないため、Task が Queue に溜まったまま進まない。

### 4.2 起動・停止・再起動

```bash
pnpm backend:up                  # 15サービス全部。初回は Elasticsearch の起動を30秒ほど待つ
pnpm backend:up apiserver        # 名指しすると、そのサービスと依存先だけ
pnpm backend:status              # どのサービスが上がっているか
pnpm backend:down                # 全群を停止する。ボリュームは消えない
```

この薄い層が起動のたびに行うのは次の3つで、いずれも起動時にしか決められない。

1. Agent と推論サービスへ渡すイメージの digest を、`docker image inspect` から取る
2. Prometheus の設定を、`.env` のポートを埋めて `.generated/observability/` へ書き出す
3. サービスを呼んでよい者の資格情報を `.generated/security/clients.env` から読み込む

したがって、`docker compose up` を直接呼ぶと、監視が古いポートを見続けるか、
サービスが呼び手不在として起動を拒否する。起動は必ず pnpm スクリプト経由で行う。

個々のサービスの再起動は Compose を直接使う。設定を変えずにプロセスだけを
入れ替えるときの操作であり、上の3つは再計算されない。

```bash
docker compose -f infra/clearml/compose.yaml restart prediction-api
```

全サービスに `restart: unless-stopped` が付いている。ホストの再起動後、
明示的に停止したものを除いて自動的に戻る。

### 4.3 定常の確認

定期実行の仕組みは無い。次の3つは、起動直後と、何かを変えた直後に人が走らせる。

| 確認 | 操作 | 何を見るか |
| --- | --- | --- |
| 推論が提供できているか | `pnpm serving:smoke` | 6項目の疎通。どのモデルで答えているかを含む |
| 監視が対象を見えているか | `pnpm ops:smoke` | 対象の健康ではなく、スクレイプの成否 |
| 学習側のデータの状態 | `pnpm backend:data:status` | Project・Dataset・Task の件数 |

`ops:smoke` が対象の健康を見ないのは、監視が落ちたときのダッシュボードが
「静かな日」と見分けられないためである。詳細は `../_archive/runbooks/006`。

### 4.4 ログ

ログは各コンテナの標準出力にあり、集約も保存もしていない（02 §4.6）。
`docker compose logs` が届く範囲だけが読める範囲である。

```bash
pnpm backend:logs                # 全サービスを追う
pnpm agent:logs                  # 学習 Agent
pnpm serving:logs                # 推論サービス
pnpm ops:logs                    # 監視4サービス
```

推論サービスと学習コードのログは1行1 JSON で、`correlation_id` を持つ
（`ml/observability/logging.py`）。呼び出し側が受け取った `X-Correlation-Id` から、
1件の要求に属する行だけを取り出せる。

ClearML Server 自身のログは、コンテナの標準出力とボリューム `clearml-logs` の
両方にある。後者はローテーションも削除もしていない。

### 4.5 ディスク

先に尽きるのはディスクである。Elasticsearch は空きが逼迫すると索引を
読み取り専用へ切り替えるため、症状は「学習が失敗する」「画面に記録が出ない」の形で
現れ、原因がディスクだとは見えない。

`HostDiskFillingUp`（空き10%未満が15分）が鳴る前に減らせるのは、順に
古い Task の成果物、`.generated/` の生成物、未使用の Docker イメージである。

```bash
docker image prune               # 停止中のコンテナは消さない
```

`docker volume prune` と `docker system prune --volumes` は使わない。
このホストには併存プロジェクトの停止中ボリュームが同居しており、まとめて消える。
何を消してよいかは 12 §4.3 が持つ。容量の推移と見積りは 44 が持つ。

### 4.6 データストア

Mongo・Elasticsearch・Redis へ直接つなぐ運用は持たない。3つとも
`backend` ネットワーク（`internal: true`）にあり、ホストへポートを公開していない。
状態を読むのも変えるのも ClearML の API 経由に限る。

| ストア | 持っているもの | 触る経路 |
| --- | --- | --- |
| mongo | Task・Model・Dataset・Queue の実体 | ClearML API（画面、SDK、`pnpm ml:*`） |
| elasticsearch | 指標とコンソール出力 | 同上 |
| redis | Agent と Queue の一時状態 | 触らない |

直接つなぐ経路を用意していないのは、ClearML が3つの間で整合を保っているためである。
片方だけを書き換えると、画面には出るが取得できない記録が生まれる。

`async-delete` サービスは、削除された Task の成果物を fileserver から遅れて消す。
削除が画面に反映されてもディスクがすぐには空かないのは、このためである。

### 4.7 Dataset

| 作業 | 操作 | 手順 |
| --- | --- | --- |
| 中身を測る | `pnpm ml:data profile` | `../_archive/runbooks/005` §1 |
| 学習に使ってよいか判断する | `pnpm ml:data check` | 同 §2 |
| 版の間の差を見る | `pnpm ml:data drift -- --against <版>` | 同 §3 |
| 由来を追う | Task の `lineage` アーティファクトを読む | 同 §5 |
| 新しい版を作る | `pnpm seed:semiconductor:dataset` | 現在の Dataset は合成データであり、生成し直せる |

合否の条件は `config/data_quality.yaml` にあり、編集すれば次の実行から効く。
基準そのものは 14 が定める。

### 4.8 Artifact

Artifact の生成は Pipeline の各ステップが行い、人が個別に作る運用は無い。
運用として行うのは、容量が逼迫したときに古い Task ごと消すことだけである。

消してはならないものが 12 §4.3 にある。production 段階のモデルが参照する
`model_weights` と、その評価に使った `evaluation` は、モデルが現役である限り消さない。

### 4.9 モデル

```bash
pnpm ml:model status             # どのモデルがどの段階にいるか
pnpm ml:model promote            # staging / production へ上げる。承認者と理由が必須
pnpm ml:model rollback           # 直前の production へ戻す
```

段階は candidate → staging → production の順にしか進めず、candidate から
production へは飛べない。評価ゲートを通らなかったモデルは登録されない。
根拠と操作は `../_archive/runbooks/003`、出してよいかの判定は 33 が持つ。

推論サービスは起動時に1回だけ Registry を読む。昇格しただけでは切り替わらず、
反映には再起動が要る。

```bash
pnpm ml:model promote -- --model-id <id> --to production --approved-by <名前> --reason <理由>
docker compose -f infra/clearml/compose.yaml restart prediction-api
pnpm serving:smoke
```

### 4.10 バックアップとリストア

取得の手順も仕組みも無い（02 §4.7、`../backlog/11_バックアップ手順が無い.md`）。
この文書は、無いものを手順として書かない。

現在あるのは「消さない」という制約だけである。これは誤って消すことを避けるもので、
失ったものを取り戻す手段ではない。何を失うと何が起きるかは 43 §4.2 に整理する。

### 4.11 障害への入口

症状から手順を引くのは `../_archive/runbooks/006` §症状別の手順である。
警報11種類はいずれも annotation に runbook の該当節を持っており、
鳴った通知から直接たどれる。

警報が鳴っていない、または症状が11種類のどれでもない場合の進め方は 42 が持つ。

### 4.12 作業と担当の対応

担当はすべて開発者1人である。列として残すのは、複数人になった時点で
埋めるべき場所を示すためである。

| 作業 | 契機 | 実施 | 記録の残り先 |
| --- | --- | --- | --- |
| 起動・停止 | 作業の開始と終了、併存プロジェクトとの切り替え | 開発者 | 残らない |
| 疎通の確認 | 起動直後、配備直後 | 開発者 | 残らない |
| Dataset の品質判定 | 新しい版を作ったとき | 開発者 | Task の `data_quality` |
| モデルの昇格 | 評価ゲートを通過したとき | 開発者 | モデルの metadata |
| 容量の確認 | `HostDiskFillingUp` が鳴ったとき | 開発者 | 残らない |
| 障害対応 | 警報、または症状 | 開発者 | postmortem（`../_archive/runbooks/006` の様式） |

「残らない」と書いた3つは、実施したことを後から確かめられない。
複数人での運用へ移す場合は、ここが最初に埋めるべき欠落である。

## 5. 判断事項

| 判断 | 理由 |
| --- | --- |
| 起動を pnpm スクリプトに限る | digest・監視設定・資格情報の3つは起動時にしか決まらず、Compose を直接呼ぶと欠ける |
| 群を4つに分ける | 学習と推論の停止を互いに波及させず、モデル入れ替え中も学習を続けられる |
| データストアへ直接つなぐ経路を作らない | ClearML が3ストアの整合を保っており、片方だけの変更は取得できない記録を生む |
| 当番・承認体制を設計しない | 運用者が1人であり、実在しない体制を書くと手順が守られない前提になる |
| 定期実行の仕組みを持たない | 常時稼働しておらず、停止中に走る定期処理は誤検知しか生まない |
