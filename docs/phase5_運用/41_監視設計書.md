## 1. 目的

この文書は、何を測り、どの値を異常とみなし、そのとき誰を呼ぶかを定める。

測定の実装は `infra/observability/` の4ファイルにあり、症状から引く手順は
`../_archive/runbooks/006` にある。この文書が持つのは、その両者の間にある設計の根拠、
すなわち「なぜその指標を選び、なぜその閾値なのか」と、測れていない範囲である。

## 2. 適用範囲

対象は、推論サービス・学習側（Queue・Agent・Task）・ホストの資源・監視自身の4つである。

対象外は次の3つで、いずれも測る手段を持たない。

| 対象外 | 理由 |
| --- | --- |
| Angular 画面の可用性と表示速度 | 開発サーバであり、常時稼働していない |
| ClearML Server 内部（Mongo・Elasticsearch・Redis・fileserver）の状態 | `backend` ネットワークに閉じており、exporter を置いていない |
| コンテナ単位の資源使用 | ホスト単位でのみ測る（§5） |

## 3. 前提

すべてのプロセスが単一ホスト上に1つずつあり、冗長化していない。したがって
監視の目的は、切り離しや切り替えの判断ではなく、壊れたことに人が気付くことである。

Prometheus の保持は7日である（`--storage.tsdb.retention.time=7d`）。
30日を窓とする SLO を、時系列から直接は検算できない。

通知の宛先は設定していない。Alertmanager は動いており、警報は経路の末端まで届くが、
そこから先へ出ていかない。気付く手段は Grafana と Prometheus の画面である。

## 4. 定義

### 4.1 測る仕組み

```text
[推論]  prediction-api ──/metrics──┐
                                    │
[学習]  ClearML ──ops-exporter──────┼──▶ Prometheus ──▶ Alertmanager
        (Queue/Agent/Task)          │         │
                                    │         └──▶ Grafana
[資源]  ホスト ──node-exporter──────┘
```

学習側は HTTP を話さない。Queue も Agent も Task も、誰かが問い合わせなければ
状態が分からない。`ops-exporter` がその役を負う。ClearML に対して読み取りしか行わず、
監視の側から監視対象を変える経路は持たない。

`/metrics` は推論サービスと ops-exporter のどちらも `metrics:read` を要求する。
Prometheus は資格情報をファイル（`.generated/security/prometheus-token`）から読む。
設定ファイルへ直接書くと Prometheus の設定 API から読めてしまうためである。

スクレイプ間隔は4対象とも15秒である。推論の応答が秒未満で、Pipeline が分単位で進む。
これより短くしても分かることは増えず、長くすると落ちてから気付くまでが目に見えて延びる。

### 4.2 SLI と SLO

| SLI | SLO | 破ったときに鳴るもの |
| --- | --- | --- |
| 推論の可用性：`unavailable` でない応答の割合 | 30日で 99% | `PredictionErrorRateHigh` |
| 推論の応答性：p95 応答時間 | 30日の95%の時間で1秒未満 | `PredictionLatencyHigh` |
| 学習の到達性：Queue に入れた Task が実行される割合 | 30日で 99% | `QueueUnattended` |
| データの健全性：品質条件を満たさない Dataset で学習しない | 0件 | `PipelineFailuresRecurring` |

この4つの値は、利用側と合意したものではない。利用側が存在せず、
学習環境として控えめに置いた値である（02 §4.1・§4.4）。

SLO は破ってはいけない線ではなく、破ったら手を止めて直す線として扱う。
余裕を使い切ったら、新しい機能より先に安定させる。

### 4.3 測っているもの

| 指標 | 出どころ | これが無いと見えないこと |
| --- | --- | --- |
| `prediction_requests_total{outcome}` | 推論 | 失敗率。`unavailable`（5xx）と `invalid`（4xx）を分けてある |
| `prediction_request_seconds_bucket` | 推論 | 応答の遅さ。分位で見る |
| `predictions_total{label}` | 推論 | モデルが全部 `pass` と答え始めたこと |
| `prediction_model_loaded` | 推論 | 起動したが提供できるモデルを持っていない状態 |
| `predicted_failure_share` / `training_failure_share` | 推論 | 予測の drift。壊れていないのに世界が変わった状態 |
| `clearml_queue_pending_tasks` / `clearml_queue_workers` | 学習 | 待ちがあって Agent が0という、放置すると永久に捌けない状態 |
| `clearml_tasks_failed_recent` / `clearml_tasks_completed_recent` | 学習 | 毎回失敗する Pipeline。滞留としては見えない |
| `clearml_reachable` | 学習 | 監視が対象を読めているかどうか |
| `node_filesystem_avail_bytes` / `node_memory_MemAvailable_bytes` | ホスト | 残りの資源。尽きると症状は3か所に同時に出る |
| `node_cpu_seconds_total` | ホスト | 学習中に他が遅くなる理由。警報は置かない（§4.4） |
| `up{job=...}` | Prometheus | 監視そのものの生存 |

CPU だけは、集めていても警報を持たない。逼迫しても止まらず、学習が遅くなるだけだからである。
Grafana の「ホストの資源」で、遅さの原因を確かめるときに見る。

3つの選択に理由がある。

失敗率で `unavailable` と `invalid` を分けているのは、混ぜると呼び出し側の入力の誤りで
こちらが起こされるためである。4xx は、こちらが正しく拒否した結果である。

応答時間を平均ではなく分位で測るのは、平均が遅い一部を隠すためである。

`clearml_reachable` を独立させているのは、Queue の深さ 0 と「サーバが答えなかった」が
逆の事実だからである。後者を 0 として扱うと、最も知りたいときに警報が沈黙する。

### 4.4 警報

段階は critical と warning の2つだけにしてある。増やすと、どれが人を呼んでよいものか
判断できなくなる。critical は手を止めて見るもの、warning は今日のうちに見るものである。

すべての規則に `for` を付けてある。1回の観測で鳴る規則は一過性のゆらぎで鳴り続け、
やがて読まれなくなる。

| 警報 | 段階 | 条件 | 継続 |
| --- | --- | --- | --- |
| `PredictionServiceDown` | critical | スクレイプできない | 2分 |
| `PredictionServiceHasNoModel` | critical | `prediction_model_loaded == 0` | 2分 |
| `PredictionErrorRateHigh` | critical | サービス側の失敗が5%超 | 5分 |
| `ClearmlUnreachable` | critical | `clearml_reachable == 0` | 5分 |
| `QueueUnattended` | critical | 待ちがあり、Agent が0 | 10分 |
| `PredictionLatencyHigh` | warning | p95 が1秒超 | 10分 |
| `PredictionDistributionShifted` | warning | 学習時と不良率が20ポイント以上違う | 30分 |
| `QueueBacklogGrowing` | warning | 待ちが5件超 | 30分 |
| `PipelineFailuresRecurring` | warning | 直近30分で3件以上失敗 | 15分 |
| `HostDiskFillingUp` | warning | 空きが10%未満 | 15分 |
| `HostMemoryExhausted` | warning | 空きが10%未満 | 15分 |

`PredictionServiceDown` が鳴っている間、同じ `job` の warning と critical は抑止する。
サービスが落ちていれば応答が遅いことも失敗率が高いことも当然であり、
原因ではなく結果の警報で人を呼ばない。

各規則の annotation には runbook の該当節へのリンクが入っている。
通知を見た人が、対応手順を探すところから始めなくて済むようにするためである。

閾値のうち、実測に基づくものは1つも無い。p95 1秒は §4.2 と同じく置いた値であり、
空き10%は Elasticsearch がディスク逼迫時に索引を読み取り専用へ切り替える前に
気付くための余裕として決めた。20ポイントと5件と3件は、いずれも根拠を持たない初期値である。

### 4.5 通知

| 経路 | 状態 |
| --- | --- |
| まとめ方 | 同じ警報名・Queue・プロジェクトを1通にまとめる。`group_wait` は critical 10秒、warning 30秒 |
| 鳴らし直し | critical は1時間ごと、warning は4時間ごと |
| 宛先 | 無い。receiver は名前だけがあり、中身が空である |

宛先を持たないのは、学習環境に届け先（メール、チャット、呼び出し）が実在しないためである。
受け口の形だけを残してあり、実運用では receiver の中身を差し替える。

この結果として、いま警報に気付く手段は人が画面を見ることに限られる。
常時稼働していないため、見ていない間に鳴って止まった警報は残らない。

### 4.6 見る場所

| URL | 何が見えるか |
| --- | --- |
| <http://localhost:3000> | Grafana。ダッシュボード「Semiconductor quality — serving and training」の8枚 |
| <http://localhost:9090> | Prometheus。生の値と、鳴っている警報 |
| <http://localhost:9093> | Alertmanager。まとめられた警報 |

Grafana は匿名で閲覧でき、権限は Viewer に固定してある。待ち受けを
ループバックへ寄せたうえでの判断であり、このホストの外からは開けない。

監視が対象を取れているかは `pnpm ops:smoke` で確かめる。対象が健康かどうかは見ない。
監視が落ちるとダッシュボードは空になり、それは「静かな日」と区別が付かないためである。

### 4.7 測れていない範囲

| 測れていないもの | 起きうること |
| --- | --- |
| Mongo・Elasticsearch・Redis の状態 | ディスク逼迫で索引が読み取り専用になっても、症状としてしか見えない |
| fileserver の容量と応答 | Artifact を取得できないことに、取得を試みるまで気付けない |
| 画面（Angular）の可用性 | 画面だけが壊れていることに気付けない |
| ログの内容 | 集約していないため、エラーの発生を件数として見られない |
| 監視の停止そのもの | Prometheus が落ちると、落ちたことを知らせるものがいない |
| 7日より前の推移 | SLO の30日窓を時系列から検算できない |

最後の2つは、監視を二重にしないと解けない。単一ホストで完結させる設計の帰結であり、
現在の構成のままでは解決しない。

## 5. 判断事項

| 判断 | 理由 |
| --- | --- |
| 段階を2つに限る | 段階が増えるほど、どれが人を呼んでよいものか判断できなくなる |
| すべての規則に `for` を付ける | 1回の観測で鳴る規則は、ゆらぎで鳴り続けて読まれなくなる |
| ホスト単位で資源を測る | 学習・推論・監視が同じホストに載っており、先に尽きるのはホストの側である。コンテナ別の内訳が要るようになったら cAdvisor を足す |
| exporter を読み取り専用にする | 監視から対象を変えられると、監視が障害の原因になりうる |
| 結果の警報を抑止する | 1つの障害で複数の通知が出ると、次から読まれなくなる |
| 閾値を実測から決めていない | 実運用の負荷が存在せず、測っても意味のある値にならない。置いた値であることを明記して残す |
