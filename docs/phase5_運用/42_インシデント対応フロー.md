## 1. 目的

この文書は、異常に気付いてから終わったと判断するまでの進め方を定める。

症状ごとの操作は `../_archive/runbooks/006` §症状別の手順が持ち、平常時の運用は 40 が持つ。
この文書が扱うのは、その手順に入る前と出たあと、すなわち深刻度をどう決め、
どこで手順を離れて調べ始め、何を残して終えるかである。

データを失った場合の復旧は 43 が持つ。この文書は、データが残っている障害を扱う。

## 2. 適用範囲

対象は、41 が定める警報11種類と、警報にならない症状（画面が出ない、
学習が進まない、答えが明らかにおかしい）である。

体制に関する次の3つは対象外とする。運用者が開発者1人であり、実在しないためである。

| 対象外 | 理由 |
| --- | --- |
| オンコールと当番 | 常時稼働しておらず、呼び出される人がいない |
| 組織へのエスカレーション | 上位者も別チームも存在しない |
| 利用者への告知 | 外部利用者が存在しない |

実在しない体制を書くと、守られない前提の上に手順が乗る。複数人での運用へ移すときに
何を決めるべきかは §4.7 に残す。

## 3. 前提

推論・学習・監視・画面のすべてが単一ホスト上にあり、切り離す先も切り替える先も無い。
したがって対応は、影響を他へ逃がすことではなく、原因を直すことに限られる。

通知の宛先が無いため（41 §4.5）、検知は人が画面を見たときに起きる。
見ていない時間帯に起きて自然に収まった障害は、記録に残らない。

Prometheus の保持は7日である。8日前の障害は、時系列からは追えない。

## 4. 定義

### 4.1 深刻度

| 深刻度 | 定義 | 例 | 対応の始め方 |
| --- | --- | --- | --- |
| S1 | 記録を失った、または失いつつある | ボリュームの破損、ディスクの枯渇が進行中 | 直ちに書き込みを止める。43 へ移る |
| S2 | 提供している機能が動かない | 推論が応答しない、提供できるモデルが無い、Queue が捌けない | 手を止めて対応する |
| S3 | 動いてはいるが正しさが疑わしい | 予測の分布が学習時から離れた、Task が繰り返し失敗する | その日のうちに調べる |
| S4 | 動作に影響しない | 監視の一部が欠けた、ログに読めない行がある | 次の作業の合間に直す |

41 の警報は、critical が S2、warning が S3 に対応する。対応しないのは
`HostDiskFillingUp` で、これは進行すると S1 になる唯一の warning である。
空きが10%を切った時点では動いているが、尽きた時点で Elasticsearch が
索引を読み取り専用にし、記録が書けなくなる。

深刻度は、原因ではなく失われているもので決める。同じ「推論が応答しない」でも、
モデルが未昇格なら S2、ボリュームが壊れて読めないなら S1 である。

### 4.2 検知

| 経路 | 気付けるもの | 気付けないもの |
| --- | --- | --- |
| Grafana / Prometheus を人が見る | 41 の警報11種類 | 見ていない間に起きて収まったもの |
| `pnpm serving:smoke` / `ops:smoke` | 疎通と、監視が対象を取れているか | 実行していない間の状態 |
| 作業中に症状として出会う | 画面が出ない、学習が進まない | — |

検知の時刻は記録しない。障害の始まりとして使えるのは Prometheus の時系列であり、
気付いた時刻ではない。postmortem の時系列には、両方を分けて書く。

### 4.3 初動

最初にすることは、原因を探すことではなく、**何が失われているかを確定させること**である。
深刻度がこれで決まり、以降の進め方が変わる。

```bash
pnpm backend:status              # どのサービスが上がっているか
df -h /                          # S1 かどうかの分かれ目
pnpm ml:model status             # production のモデルが1つあるか
```

ディスクの空きを最初に見るのは、尽きかけているときに調査そのものが
（ログの書き込み、コンテナの再作成によって）事態を進めるためである。
空きが無いときは、調べるより先に空ける。

推論が止まっている間、判定の要求は失敗する。要求元が再送するかどうかは
こちらでは決められない。答えを返さないことは、誤った答えを返すことより安全である。

### 4.4 切り分け

症状が 41 の警報のいずれかなら、annotation が指す runbook 006 の節へ入る。
11種類はすべて対応する節を持っており、そこで終わることが多い。

手順を離れて調べるのは、次の3つのいずれかに当たったときである。

1. runbook の手順を実行しても症状が変わらない
2. 症状が複数の群（学習・推論・監視）に同時に出ている
3. 記録そのものが読めない

2 と 3 は、上の層を疑う合図である。個々のサービスの不調が3か所に同時に出ることは
起きにくく、ホストの資源か、ClearML Server 側の共通の状態を先に見る。

```bash
docker compose -f infra/clearml/compose.yaml logs --tail 100 apiserver
curl -s -o /dev/null -w '%{http_code}\n' http://localhost:8008/debug.ping
```

推論サービスのログは1行1 JSON で `correlation_id` を持つ。呼び出し側が受け取った
`X-Correlation-Id` が分かれば、1件の要求に属する行だけを取り出せる。

### 4.5 暫定対応と復旧

暫定対応として許すのは、次の2つに限る。いずれも元へ戻せる。

| 暫定対応 | 使う場面 | 戻し方 |
| --- | --- | --- |
| モデルの rollback | 昇格したモデルが原因と分かった | 原因を直して昇格し直す |
| サービスの停止 | 誤った答えを返し続けている | 原因を直して起動する |

`config/data_quality.yaml` の基準を緩めて Dataset を通すこと、
Playwright の `retries` を上げること、警報を沈黙させることは、暫定対応に含めない。
どれも症状を消すだけで、次に同じことが起きたときに検知が働かなくなる。

復旧したと判断する条件は、症状が消えたことではなく、確認が通ることである。

| 群 | 復旧の確認 |
| --- | --- |
| 推論 | `pnpm serving:smoke`（6項目）が通る |
| 学習 | Queue へ投入した Task が最後まで進む |
| 監視 | `pnpm ops:smoke` が通る |
| 画面 | `pnpm web:e2e` が通る |

### 4.6 恒久対応と postmortem

S1 と S2 は、終わったあとに記録を残す。S3 と S4 は、直した内容がコミットに残れば足りる。

様式は `../_archive/runbooks/006` §障害の記録にある。書くのは、何が起きたかと、
なぜそれが起こりうる状態だったかの2つである。人の過失を原因として書かない。
同じ状態が残っていれば、別の人が同じことをする。

記録の置き場所は現在決まっていない。72（課題管理表、未着手）が出来るまでは
`../backlog/` に置き、着手条件つきのストーリーとして残す。

恒久対応として検討するのは次の順である。

1. 同じことが起きたときに、より早く気付けるようにする（警報の追加）
2. 同じことが起きないようにする（検査の追加、既定値の変更）
3. 起きても影響が小さくなるようにする（構成の変更）

1 を 2 より先に置くのは、原因が分からないまま構成を変えると、直ったかどうかを
確かめられないためである。

### 4.7 複数人での運用へ移すときに決めること

いま決めていないのは、対応する人が1人しかいないために決めようがない事項である。
複数人になった時点で、次の4つが必要になる。

| 決めること | いま代わりになっているもの |
| --- | --- |
| 誰が最初に見るか（当番） | 気付いた人が対応する |
| どこまでで人を呼ぶか（エスカレーションの基準） | 呼ぶ相手がいない |
| 対応中の状況をどこへ書くか | 書いていない |
| 誰が終わりを宣言するか | 確認が通った時点で終わる |

## 5. 判断事項

| 判断 | 理由 |
| --- | --- |
| 深刻度を失われているもので決める | 原因で決めると、原因が分かるまで深刻度が決まらない |
| 初動でディスクを最初に見る | 空きが尽きかけているとき、調査自体が事態を進める |
| 体制に関する項目を対象外にする | 実在しない体制を書くと、守られない前提の上に手順が乗る |
| 基準を緩めることを暫定対応に含めない | 症状が消え、次に同じことが起きたときの検知も消える |
| 復旧を確認の通過で判断する | 症状が消えたことは、直ったことと同じではない |
| 警報の追加を構成の変更より先に置く | 原因が分からないまま構成を変えると、直ったかを確かめられない |
