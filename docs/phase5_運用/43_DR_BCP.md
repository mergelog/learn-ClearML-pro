## 1. 目的

この文書は、状態を失ったときに何を取り戻せて何を取り戻せないかを確定させる。

バックアップの仕組みは無い（02 §4.7）。したがってこの文書は、取得と復旧の手順を
定めるものではない。定めるのは、失われうるものの一覧、そのうち作り直せるものと
作り直せないものの区別、作り直しの手順、そしてバックアップが必要になる条件である。

平常時の運用は 40、データが残っている障害の進め方は 42 が持つ。

## 2. 適用範囲

対象は、`infra/clearml/compose.yaml` が定義する13の Docker ボリュームと、
作業ツリーのうち git の管理外にあるファイルである。

対象外は次の2つである。

| 対象外 | 理由 |
| --- | --- |
| 事業継続（BCP）としての代替手段 | 停止しても止まる業務が無い。学習環境であり、依存している利用者がいない |
| 別拠点・別ホストへの切り替え | 切り替える先が存在しない |

BCP の名を残すのは、項目が不要だからではなく、いま置く対象が無いためである。
この構成を実務へ持ち出すときに、最初に埋める欄として残す。

## 3. 前提

すべての状態が1台のホストの1つのディスク上にある。ホストが失われれば、
ボリュームも作業ツリーも同時に失われる。片方だけが残る故障を想定できない。

git の remote は無い。コミット済みのコードも、このホストの外には存在しない。

現在の Dataset は合成データであり、生成側が固定の乱数種（既定 `20260904`、
`SEMICONDUCTOR_RANDOM_SEED` で変更できる）を使う。同じ種と同じ依存の版であれば
同じ行が得られるはずだが、生成し直して一致することは確認していない。

## 4. 定義

### 4.1 何を失うか

| ボリューム | 内容 | 2026-09-12 の容量 | 失ったときに起きること |
| --- | --- | --- | --- |
| `clearml-mongo-db` | Task・Model・Dataset・Queue の実体 | 233.9 MB | 実験とモデルの一切を失う |
| `clearml-files` | Artifact とモデル本体 | 112 MB | 学習済みモデルを取得できなくなる |
| `clearml-elasticsearch` | 指標とコンソール出力 | 6.5 MB | 実験の記録が読めなくなる |
| `clearml-config` / `clearml-logs` | サーバの設定とログ | 0 B / 135 kB | 設定を作り直す |
| `clearml-agent-home` | Agent ごとの実行環境と pip キャッシュ | 1.3 GB | 再構築に時間がかかる。記録は失わない |
| `prediction-api-cache` / `ops-exporter-cache` | SDK のキャッシュ | 3.2 MB / 0 B | 同上 |
| `prometheus-data` | 時系列（7日） | 18.0 MB | 直近の推移を失う |
| `alertmanager-data` | 警報の状態 | 0 B | 沈黙の設定を失う |
| `grafana-data` | ダッシュボードの状態 | 49.9 MB | provisioning から作り直せる |
| `clearml-redis` / `clearml-mongo-config` | Agent と Queue の一時状態、Mongo の構成 | 1.2 kB / 0 B | 実害が無い。起動時に作り直される |

git の管理外にあるファイルは次の3つである。どれも大きくないが、
影響の及ぶ先が違う。

| ファイル | 内容 | 作り直せるか |
| --- | --- | --- |
| `clearml.conf` | ClearML への接続先と資格情報 | 作り直せる。画面で新しい資格情報を発行する |
| `.generated/security/` | 呼び手のトークン | `scripts/security-tokens.sh` が作り直す。ただし発行済みのトークンを配った先があれば、そちらも入れ替わる |
| `.env` | ポートとイメージの指定 | 既定値で動く。変更していれば失う |

### 4.2 取り戻せるものと取り戻せないもの

ボリュームの一覧より重要なのは、**そこに入っているものが作り直せるかどうか**である。

| 資産 | 作り直す手段 | 取り戻せないもの |
| --- | --- | --- |
| Dataset | `pnpm seed:semiconductor:dataset`。合成データであり、固定の乱数種から生成する | 生成し直した Dataset の ID は別物になる。旧 ID を指す来歴の鎖が切れる |
| モデル | 学習し直す。Pipeline は Dataset の版と設定から再実行できる | 学習に使った時刻、Task ID、Model ID。22 の再現性の記録が指す先 |
| 評価の結果 | 再評価する | 過去に測った値そのもの。基準の妥当性を後から検証する材料 |
| 実験の指標・ログ | 取り戻せない | すべて |
| 昇格の記録（承認者・理由・日時） | 取り戻せない | すべて |
| コードと設定 | git から戻す（コミット済みの範囲） | 未コミットの変更 |
| 監視の時系列 | 取り戻せない | 7日分 |

したがって、いま失って本当に困るのは**実行の記録**である。データとモデルは作り直せるが、
「いつ、何を使って、誰が何を判断したか」は作り直せない。

この区別が、バックアップに着手する条件を決める（§4.6）。

### 4.3 故障ごとの扱い

| 故障 | 影響 | いまできること |
| --- | --- | --- |
| サービスの停止（プロセスの異常終了） | 一時的。`restart: unless-stopped` で戻る | 42 の手順。データは失われない |
| ホストの再起動 | 一時的 | 明示的に停止したもの以外は自動で戻る |
| Mongo の破損 | 実験とモデルの一切 | 無い。§4.4 の再構築で作り直す |
| Elasticsearch の破損 | 指標とコンソール出力 | 無い。Mongo が無事なら Task の一覧は残り、中身が空になる |
| Artifact の消失（`clearml-files`） | モデル本体と成果物 | 無い。Task の記録は残るため、何を失ったかは分かる |
| Dataset の消失 | 学習の入力 | 生成し直す。ID は別物になる |
| モデルの消失 | production の提供 | 学習し直す。推論サービスは起動しなくなる（`no model is marked production`） |
| ディスクの故障 | すべて | 無い。git remote も無いため、コードも失う |
| 設定の破損（`clearml.conf`） | 接続と認証 | 画面から資格情報を発行し直す |
| 誤った削除（`docker volume prune` 等） | 対象のボリューム | 無い。実行しないという制約だけがある |

Elasticsearch の破損だけは、進行する形で起きうる。ディスクの空きが尽きると
索引が読み取り専用に切り替わり、書き込みだけが静かに失われる。
`HostDiskFillingUp` が鳴った時点は、まだこの故障の手前である（42 §4.1）。

### 4.4 全てを失ったあとの再構築

バックアップからの復旧ではなく、ゼロからの再構築である。所要時間は測っていない。

```bash
pnpm py:setup                    # Python 環境
pnpm backend:up                  # 基盤。Elasticsearch の起動を待つ
pnpm web:credentials             # clearml.conf を作る（画面で資格情報を発行する）
pnpm seed:semiconductor:dataset  # Dataset を生成し直す
pnpm agent:build
pnpm backend:up training-agent pipeline-agent   # Pipeline には制御役の Agent も要る
pnpm ml:pipeline -- --dataset-version <版>   # 学習からモデルの登録まで
pnpm ml:model promote -- --model-id <id> --to staging --approved-by <名前> --reason <理由>
pnpm ml:model promote -- --model-id <id> --to production --approved-by <名前> --reason <理由>
pnpm serving:build && pnpm serving:up
pnpm ops:up && pnpm ops:smoke
```

この手順は通しで実行していない（`../backlog/02_通し台本が無い.md`）。
個々の段は runbook で確認してあるが、続けて走らせたときに繋がることは確かめていない。

再構築の結果は、失う前と同じではない。Dataset ID も Task ID も Model ID も変わり、
過去の実行を指す記録（22 の再現性の記録、モデルの来歴）は、指す先を失ったまま残る。

### 4.5 RPO と RTO

| 項目 | 値 | 理由 |
| --- | --- | --- |
| RPO | 置けない | バックアップが無く、復旧点が存在しない。失う量は「最後に取った時点から」ではなく「すべて」である |
| RTO | 未確定 | §4.4 を通しで実行していないため、所要時間を測っていない |

目標値を推定で書かない。バックアップを持たない構成で RPO を数値で書くと、
その時点まで戻れるという誤った期待を作る。

### 4.6 バックアップに着手する条件

いま着手していないのは、費用がかかるからではなく、失って困るものがまだ小さいためである。
次のいずれかが起きた時点で、条件が満たされる。

1. 実測値（性能、負荷、学習時間）が記録として積み上がったとき
2. 再現できない実行の記録が生まれたとき。外部から取り込んだ Dataset がその代表である
3. 昇格の判断の履歴が、判断の根拠として参照されるようになったとき
4. 複数人が同じ ClearML Server を使うようになったとき

着手するときに決めるのは、取得の対象（少なくとも `clearml-mongo-db`・`clearml-files`・
`clearml-elasticsearch` の3つ）、頻度、保存先、そして**取ったものから実際に戻せることを
一度確かめる手順**である。確かめていない復旧手順は、手順が無いのとあまり変わらない。

### 4.7 復旧の確認

復旧したかどうかは、サービスが上がったことではなく、次の4つが通ることで判断する。

| 確認 | 何を確かめるか |
| --- | --- |
| `pnpm backend:status` | 15サービスが上がっている |
| `pnpm backend:data:status` | Project・Dataset・Task が読める |
| `pnpm serving:smoke` | production のモデルで答えられる |
| `pnpm ops:smoke` | 監視が対象を取れている |

## 5. 判断事項

| 判断 | 理由 |
| --- | --- |
| RPO を数値で置かない | 復旧点が存在しない構成で数値を書くと、戻れるという誤った期待を作る |
| バックアップの手順を先に書かない | 実行して確かめていない手順は、あることが害になる |
| 失うものを資産ごとに区別する | ボリュームの一覧では、作り直せるものと作り直せないものが混ざって見える |
| BCP の枠だけを残す | 止まる業務が無いのは現在の条件であり、枠を消すと実務へ持ち出すときに欠落が見えない |
| 再構築後に ID が変わることを明記する | 同じ状態に戻ったと誤解すると、過去の記録を根拠に使ってしまう |
