## 1. 目的

この文書は、何がどれだけ増えると足りなくなるかを定める。

いま測れる値は、ディスクの使用量と、その内訳としてのボリュームの容量である。
1件あたりの増え方は測っていない。したがってこの文書が置くのは、将来の需要予測ではなく、
現在の実測値、増え方を決めている要因、そして先に尽きるものの順序である。

容量が逼迫したときに何を消してよいかは 12 が、消すための操作は 40 §4.5 が持つ。

## 2. 適用範囲

対象は、単一ホストのディスク・メモリ・CPU と、それらを消費する13のボリューム、
および同時に走る Job の数である。

ネットワーク帯域は対象外とする。すべての通信がホスト内で完結し、
外部との定常的な通信が無い。

## 3. 前提

学習・推論・監視・画面のすべてが同じホストに載っている。資源は共有であり、
どれか1つの増加が他のすべてに影響する。

このホストには併存プロジェクト（`stackup-clearml`）のボリュームが同居しており、
ディスクの使用量にはそちらの分も含まれる。同時には起動しないため、
メモリと CPU は競合しない。

以下の実測値は 2026-09-12 に取得した。`docker system df -v` と `df -h /` による。

## 4. 定義

### 4.1 現在の使用量

| 区分 | 使用量 |
| --- | --- |
| ホストのディスク | 1,007 GB のうち 132 GB 使用（13%）、824 GB 空き |
| 本プロジェクトのボリューム合計 | 約 1.7 GB |
| Docker イメージ | 約 7 GB（ClearML Server 1.02 GB、Elasticsearch 1.39 GB、Mongo 910 MB、Grafana 746 MB ほか） |

ボリュームの内訳は次のとおりである。

| ボリューム | 容量 | 増え方を決めるもの |
| --- | --- | --- |
| `clearml-agent-home` | 1.3 GB | Task ごとの実行環境と pip キャッシュ。要求の版が変わるたびに積む |
| `clearml-mongo-db` | 233.9 MB | Task・Model・Dataset の件数 |
| `clearml-files` | 112 MB | Artifact とモデル本体の合計 |
| `grafana-data` | 49.9 MB | ほぼ増えない |
| `prometheus-data` | 18.0 MB | 7日で頭打ちになる |
| `clearml-elasticsearch` | 6.5 MB | 指標の点数とコンソール出力の行数 |
| `prediction-api-cache` | 3.2 MB | 提供したモデルの数 |
| `clearml-logs` | 135 kB | サーバの稼働時間。削除もローテーションもしていない |
| その他5つ | 0 B 前後 | — |

いちばん大きいのが記録ではなくキャッシュ（`clearml-agent-home`）であることが、
現在の段階を示している。実験の記録より、実験を動かすための環境のほうが大きい。

### 4.2 増え方を決めているもの

| 対象 | 現在 | 何が増やすか | 上限 |
| --- | --- | --- | --- |
| Dataset の行数 | 1,200（1.0.0）／2,500（2.0.0） | 生成側の指定。合成データである | 無い |
| Dataset の版数 | 2 | 版を作るたびに1つ。上書きはしない | 無い |
| Task 数 | 未計測 | 学習・Pipeline・探索の実行回数。探索は1回で試行 Task を複数作る | 無い |
| Artifact 容量 | 合計 112 MB | Pipeline 1回につき `split`・`model_weights`・報告3種 | 無い |
| Model 数 | 未計測 | 評価ゲートを通過した実行の数。通らなかったものは登録されない | 無い |
| ログ容量 | 135 kB | サーバの稼働時間 | 無い |
| DB 容量 | 233.9 MB | Task・Model・Dataset の件数 | 無い |
| File Server 容量 | 112 MB に含まれる | Artifact と同じ | 無い |
| 監視の時系列 | 18.0 MB | 7日で頭打ち | `--storage.tsdb.retention.time=7d` |

期限で消す仕組みを持つのは Prometheus だけである。他はすべて無期限に残り、
容量の逼迫を契機に人が消す（12 §4.1）。

Task 数と Model 数を未計測としているのは、この文書を書いた時点で
ClearML Server を停止しており、`pnpm backend:data:status` を実行できないためである。
推定値を置かない。

### 4.3 何が先に尽きるか

ディスク、メモリ、CPU の順で逼迫する。

ディスクは 824 GB 空いており、いまの増え方では当面尽きない。ただし尽きたときの
壊れ方が他と違う。Elasticsearch は空きが逼迫すると索引を読み取り専用へ切り替えるため、
症状は「学習が失敗する」「画面に記録が出ない」の形で、原因から離れた場所に出る。
`HostDiskFillingUp`（空き10%未満・15分）は、この切り替えの手前で鳴らしている。

メモリは、逼迫すると最も大きいプロセスから落ちる。Elasticsearch に 2 GB
（`ES_JAVA_OPTS`）、Mongo に 2 GB（`wiredTigerCacheSizeGB`）を割り当ててあり、
これに学習 Task の作業領域が加わる。OOM killer が選ぶのは最も大きいプロセスであって、
最も重要でないプロセスではない。`HostMemoryExhausted` で気付く。

CPU は、警報を持たない。学習は分単位で進み、遅くなっても止まらないためである。

### 4.4 同時に走る Job の数

| 種別 | 同時実行数 | 決めているもの |
| --- | --- | --- |
| 学習 Task | 1 | Queue `semiconductor-training` を聞く Agent が1台 |
| Pipeline の制御 | 1 | Queue `semiconductor-pipeline` を聞く Agent が1台 |
| 推論の要求 | 未確定 | 上限を決めていない。負荷を掛ける手段（`scripts/load-test.sh`）はある |
| 利用者 | 1 | 複数利用は保証対象外（02 §4.2） |

Agent を2台に分け、Queue も分けてあるのは、Pipeline の制御役がステップの終了を
待つ間 Agent を占有するためである。同じ Queue に載せると、制御役が待っている間に
ステップを動かす Agent がいなくなり、自分の完了を自分で待ち続ける。

学習の同時実行を増やすには Agent を増やす。ただし2台目以降は同じホストの
CPU とメモリを分け合うため、所要時間は台数に比例して短くならない。

### 4.5 増設が必要になる条件

現在の構成で足りなくなるのは、次のいずれかが起きたときである。

| 条件 | 先に足りなくなるもの | 対処 |
| --- | --- | --- |
| Dataset が実データに替わり、行数が数十万規模になる | メモリ（学習時に全行を載せる） | 学習を分割するか、ホストを増やす |
| 探索の試行数を増やす | 時間。次いで `clearml-agent-home` | Agent を増やす。Queue の割り当てを見直す |
| 実験の記録を消さずに数千 Task まで積む | `clearml-mongo-db` と `clearml-elasticsearch` | 保持期間を決める（12） |
| 推論を複数の呼び手が常時使う | CPU。RandomForest は推論が重い | モデルを選び直す（`../_archive/adr/001`） |
| 監視の保持を30日へ延ばす | `prometheus-data`（現在の約4倍） | 許容できる。ディスクに余裕がある |

どれも現在は起きていない。起きた時点で測り直す。

### 4.6 測り方

```bash
df -h /                                              # ホストのディスク
docker system df -v | grep learn01-clearml           # ボリュームの内訳
pnpm backend:data:status                             # Project・Dataset・Task の件数
curl -s http://localhost:9100/metrics | grep -E 'node_filesystem_avail_bytes|node_memory_MemAvailable_bytes'
```

定期実行はしない。常時稼働しておらず、停止中に走る測定は空の値を積む。
測る契機は、`HostDiskFillingUp` が鳴ったときと、この文書を更新するときである。

## 5. 判断事項

| 判断 | 理由 |
| --- | --- |
| 需要予測を置かない | 利用者が1人で、増え方を決めているのは生成側の指定である。外から来る負荷が無い |
| 1件あたりの容量を推定しない | Task 件数を測れない状態で割り算をすると、根拠のない単価が独り歩きする |
| 定期の測定を持たない | 常時稼働しておらず、停止中の測定は意味のある値にならない |
| CPU に警報を置かない | 遅くなっても止まらない。止まる資源から順に見る |
| 保持期間を Prometheus 以外に設けない | 消してよいものの基準（12）が先に要る。期限だけ決めると、消してはならないものが消える |

## 6. 未決事項

* Task 数・Model 数・1実行あたりの Artifact 容量の実測
* 推論の同時要求数の上限。`scripts/load-test.sh` の結果から決める
* Dataset・Task・Artifact の保持期間（12 §4.1 と連動する）
* `clearml-logs` と `clearml-agent-home` の肥大への対処
* 学習を複数同時に走らせる必要が生じたときの Agent の台数
