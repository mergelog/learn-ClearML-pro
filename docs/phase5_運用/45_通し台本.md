## 1. 目的

この文書は、`../_archive/runbooks/` の9本を一続きに演じる筋書きを置く。

runbook は部品ごとに独立しており、1本ずつは異常系まで書いてある。
足りないのは「新しいデータが来てから、それが production に載り、
問題が起きて戻るまで」を一本の線として辿る経路である。

手順は書き写さない。各段が持つのは、どの runbook へ行くか、何をもって次へ進んでよいか、
そのときどこを見るか、の3つだけである。手順を写せば二重管理になり、必ずずれる（64 §4.9）。

## 2. 適用範囲

対象は、Dataset の受け入れからモデルの切り戻しまでの8段である。

対象外は、初回の環境構築（`README.初期化方法.md`）、画面そのものの操作、
そして実データを受け入れる場合の経路（01 §6 の未決事項）である。

## 3. 前提

`pnpm backend:up` と `pnpm agent:up` でスタックが動いていること。
併存リポジトリ `../001-learn-ClearML` を停止してあること。ポート 8008 / 8080 / 8081 を共有する。

資格情報は `clearml.conf` が持ち、`scripts/clearml-run.sh` が環境変数を剥がしてから実行する
（`../_archive/runbooks/007_20260908_security.md`）。

## 4. 定義

### 4.1 段の並び

```text
新しいデータが来た
  → 1. 品質判定（005）
  → 2. 学習（002）
  → 3. 探索（008）
  → 4. Pipeline で候補を登録（002）
  → 5. 昇格（003）
  → 6. 配備（004）
  → 7. ドリフト検知（005・006）
  → 8. rollback（003）
  → 9. postmortem（006）
```

段の前提として `../_archive/runbooks/001_20260908_queue_and_agent.md`（Queue と Agent）があり、
全段を通じて `../_archive/runbooks/007_20260908_security.md`（資格情報）が効く。
検証中にテストが揺れた場合は `../_archive/runbooks/009_20260912_flaky_tests.md` へ抜ける。
この3本を加えて9本になる。

### 4.2 各段の合否と観測点

| 段 | runbook | 次へ進んでよい条件 | 観測点 |
| --- | --- | --- | --- |
| 1. 品質判定 | [005](../_archive/runbooks/005_20260908_data_quality.md) §2 | 品質契約のすべての期待を満たす。終了コードが 0 | 台帳の `/data-catalog/dataset/:id` で、その版がどこから来たか |
| 2. 学習 | [002](../_archive/runbooks/002_20260908_training_pipeline.md) | Task が `completed`。validation の recall と f1 が `config/model_gate.yaml` の下限以上 | Task の Provenance。`git_working_tree` が `dirty` なら再現できない（22 §4.7） |
| 3. 探索 | [008](../_archive/runbooks/008_20260909_hyperparameter_search.md) | 予算の中で勝った設定が出る。目的関数は train 分割の f1 | 探索 Task の試行一覧。枝刈りされた試行も残る |
| 4. 候補の登録 | [002](../_archive/runbooks/002_20260908_training_pipeline.md) | 5ステップ（validate / preprocess / train / evaluate / register-candidate）がすべて成功し、評価ゲートを通る | 登録されたモデルの `gate_detail` と `evaluate_task_id` |
| 5. 昇格 | [003](../_archive/runbooks/003_20260908_model_promotion.md) §3・§4 | 23 §4.7 の退行判定に触れない。同じ Dataset 版で比較できること | 台帳の `/data-catalog/model/:id` で、昇格するモデルの来歴 |
| 6. 配備 | [004](../_archive/runbooks/004_20260908_prediction_service.md) §5 | `/ready` が新しいモデル名を返す。smoke が通る | 応答の `model_version`。古ければ再起動していない |
| 7. ドリフト検知 | [005](../_archive/runbooks/005_20260908_data_quality.md) §3、[006](../_archive/runbooks/006_20260908_observability.md) | 閾値を超えた列が無い（終了コード 0）。超えたら 8 へ | Prometheus の対象がすべて up であること |
| 8. rollback | [003](../_archive/runbooks/003_20260908_model_promotion.md) §5 | `production` が1つ前のモデルに戻り、サービスがそれを読む | 戻した後の `/ready`。再起動を忘れると古いまま |
| 9. postmortem | [006](../_archive/runbooks/006_20260908_observability.md) §障害の記録 | 時系列・直接の原因・検知の十分さが書けている | 72（課題管理表）への起票 |

各段が失敗したときの分岐は、その段の runbook のトラブルシュートが持つ。
ここには書かない。

### 4.3 台帳を挟む位置

段 1・5・6 は、台帳（`/data-catalog`）を観測点に持つ。
Dataset から候補モデル、載っているモデルまでを同じ画面で辿るためである。

台帳を運用手順そのものへ組み込む作業は済んでいない（`../backlog/01_台帳が運用手順に現れない.md`）。
上の表は、その作業の前に、どの段で台帳を見るかだけを先に置いたものである。

## 5. 判断事項

| 判断 | 理由 |
| --- | --- |
| 手順を書き写さず、runbook へリンクする | 二重管理はずれる。ずれた側がどちらか分からなくなる |
| 合否条件と観測点だけを置く | 段と段の間で何を確かめるかは、どの runbook にも書いていない |
| 探索と Pipeline を別の段に分けた | 探索は設定を決めるだけで、モデルを登録しない |
| 段 9 を文書の作業として残した | 障害が起きていないので、演じる対象が無い |

### 5.1 2026-09-13 に演じた記録

BL-02 は「机上で書いて置くのは趣旨に反する。一度は実機で通す」ことを求めている。
以下は実際に通した結果である。

| 段 | 実行したもの | 結果 |
| --- | --- | --- |
| 1 | `ml:data check --dataset-version 2.0.0` | 合格。すべての期待を満たす |
| 2 | `ml:train -- --dataset-version 2.0.0` を12回 | 既定の種で2回（完全一致）、種 1〜10 で10回。結果は 23 §4.7 |
| 3 | `ml:experiment --dataset-version 2.0.0` | 6試行（うち1つは枝刈り）。勝ち: `n_estimators=100`、`max_depth=16`、`min_samples_leaf=5`、閾値 0.4136、train の f1 0.7819 |
| 4 | `ml:pipeline`（勝ち設定を引き渡し） | 5ステップ成功。候補 `2.0.0-20260912T170306Z-a5c615e4`。validation は recall 0.8105 / f1 0.8021 |
| 5 | `ml:model promote`（candidate → staging → production） | 成功。直前の production（1.0.0 系）は archived へ |
| 6 | `prediction-api` を再起動し `serving:smoke` | `/ready` が新しいモデルを返す。smoke は6項目すべて通過 |
| 7 | `ml:data drift`、`ops:smoke` | 登録済みの 2.0.0 と 1.0.0 の間に閾値超えは無い。故意に温度を +25 した CSV では検知（終了コード 1） |
| 8 | `ml:model rollback` と再起動 | `production` が 1.0.0 系へ戻り、`/ready` もそれを読む |
| 9 | 演じていない | 障害が起きていないため。書く対象が無い |

この日に分かったことが3つある。

第一に、段 6 は昇格だけでは完了しない。昇格した直後の `/ready` は古いモデル名を返し続けた。
プロセスを再起動して初めて新しいモデルに切り替わる。runbook 004 §5 が書いているとおりで、
「Registry は新しいモデルを指しているのにサービスは古いモデルを返す」状態を実際に踏んだ。

第二に、段 5 で 23 §4.7 の退行判定を適用できなかった。
直前の production は Dataset 1.0.0 で測ったモデルで、候補は 2.0.0 で測ってある。
版が違えば雑音の大きさが違い、指標の差を設定の差に帰属できない（23 §4.3）。
比較できないことを理由に、比較せずに昇格した。この扱いは §6 に残す。

第三に、段 6 の前後で、smoke の同じ入力に対する判定が `pass` から `fail` へ変わった。
探索が選んだ確信度の切り方（0.4136）が既定の 0.5 より低いためである。
smoke はラベルを表示するだけで、どちらでも合格とする。
モデルを入れ替えると同じ入力の答えが変わりうることは、この台本の外で誰にも伝わらない。
