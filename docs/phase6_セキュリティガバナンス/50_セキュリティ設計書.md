## 1. 目的

この文書は、何を守り、どの層で守り、どこを守っていないかを定める。

守る対象と脅威の一覧は `../_archive/security/001_20260908_threat_model.md` にあり、
実際の操作手順は `../_archive/runbooks/007_20260908_security.md` にある。この文書が持つのは、
その両者の間にある設計、すなわち対策を3つの層に分けた理由と、層の境目に残る穴である。

50番台の他の文書との責務は次のように分かれる。この文書は方式の全体像だけを持ち、
個別の定義は持たない。

| 文書 | 持つもの |
| --- | --- |
| 51 認証認可設計書 | 呼び手をどう特定し、何を許すかの方式 |
| 52 権限マトリクス | 役割・権限・経路の対応の一覧 |
| 53 監査ログ設計 | 何を記録し、何を記録しないか |
| 54 脆弱性管理方針 | 見つかった脆弱性をどう扱うか |
| 55 OSS ライセンス台帳 | 依存のライセンスと、その義務 |
| 56 SBOM 管理方針 | 構成情報の作り方と残し方 |
| 57 秘密情報管理方針 | 資格情報の置き場所・検出・更新 |
| 58 規制・コンプライアンス適用判定 | どの規制が適用されるかの判定 |

## 2. 適用範囲

対象は、このリポジトリが動かすプロセスとデータのすべてである。ClearML Server、学習 Agent、
Pipeline、推論サービス、ops-exporter、監視、Angular Web、CI、およびそれらが扱う Dataset・Task・
Model・Artifact を含む。

対象外は次の3つである。

| 対象外 | 理由 |
| --- | --- |
| ホスト OS とネットワーク機器の設定 | 環境側の設定であり、このリポジトリから制御できない |
| ClearML Server 内部の実装 | 持ち込んだ第三者の実装であり、変更していない。境界としてのみ扱う（§4.4） |
| 人の運用体制（承認者、当番、教育） | 利用者が1名であり、実在しない体制を定義しない |

## 3. 前提

すべてのプロセスが単一ホスト（WSL2）上で動き、利用者は1名である。したがって、この設計が
守っているのは「他の利用者から守る」ことではなく、「ホストの外から守る」ことと
「記録に残してしまわない」ことである。

学習に使っているデータは合成データであり、区分は内部にあたる
（`../_archive/security/001_20260908_threat_model.md` §1）。実データを同じ経路へ流した時点で
区分は機密へ上がり、この設計の前提が変わる（§6）。

## 4. 定義

### 4.1 対策を3つの層に分ける

対策は、秘密・認可・供給網の3層に分けてある。分ける理由は、守る対象が違うことではなく、
**破られたときに失うものと、気付く手段が違う**ことである。

| 層 | 守るもの | 破られたときに失うもの | 気付く手段 |
| --- | --- | --- | --- |
| 秘密 | 資格情報が記録に残らないこと | ClearML の全権、サービスの呼び出し権 | 走査（`pnpm sec:scan` ほか。57） |
| 認可 | 呼んでよい者だけが呼べること | 予測の呼び出し、システムの状態の読み取り | 監査ログ（53） |
| 供給網 | 何でできているかが分かり、既知の脆弱性を含まないこと | 実行環境そのもの | リリースゲート（54・56） |

3層のうち、このリポジトリが最も重く守っているのは秘密の層である。攻撃者から見た最短経路が
`clearml.conf` とブラウザへ配られる生成物であり、そこを通られると認可の層は迂回される
（`../_archive/security/001_20260908_threat_model.md` §6）。ClearML Server 自体に役割による
制限が無いため、資格情報を得た者は Dataset・Task・Model を改変できる。

### 4.2 秘密の層

方針は2つで、どちらも「書かれないようにする」側にある。

第一に、秘密を保存する場所を減らす。サービスが設定として持つのはトークンの SHA-256 指紋だけであり、
トークンそのものは持たない。設定の一覧が漏れても、それだけでは呼べない。

第二に、書かれてしまった秘密を機械的に見つける。追跡下のファイル、ビルド生成物、Task が記録した
Parameter とコンソール出力の3経路を走査する。学習側はさらに強く、Task Parameter へ記録する直前に
検査し、資格情報を含んでいれば記録せずに実行を止める。記録されてからでは、ClearML Server を
読める全員に見えている状態になるためである。

置き場所・規則・除外・更新の手順は 57 が持つ。

### 4.3 認可の層

権限は、経路名ではなく行為の名前で定義する（`predict`、`model:read`、`metrics:read`）。
経路を移しても権限が黙って移らないようにするためであり、将来 IdP を置いたときに、
同じ定義を claim へ写せる形にするためでもある（ADR 002）。

呼び手が1つも設定されていないサービスは起動しない。空の一覧には「誰も呼べない」と
「誰でも呼べる」の2つの読みがあり、安全なのは前者だけである。

方式は 51、対応の一覧は 52 が持つ。

### 4.4 境界ごとの守り方

境界は4つあり、守り方が異なる。図は
`../_archive/security/001_20260908_threat_model.md` §2 にある。

| 境界 | 守っているもの | 現状 |
| --- | --- | --- |
| ホストの外と中 | 待ち受けアドレス | 自作サービスと監視はループバック（`BIND_ADDRESS` の既定値）。ClearML の3ポートは公開したままで、これは意図した例外である |
| サービスとその呼び手 | トークンと役割 | `/health` のみ無認証（51 §4.5） |
| コンテナとホスト | 実行権限 | Agent は作業ツリーを読み取り専用で受け取り、非 root で動く |
| リポジトリと外部 | lock と SBOM とゲート | 54・56 |

ClearML の3ポート（8008 / 8080 / 8081）は、`infra/clearml/compose.yaml` で待ち受けアドレスを
指定せずに公開している。別端末のブラウザから使う運用のための受け入れであり、同一 LAN の信頼を
前提にしている。ここには役割による制限が無く、`clearml.conf` の資格情報を持つ者が全権を持つ。

### 4.5 守っていないもの

次の項目は、対策を持たない。いずれも実装で塞げるものではなく、環境か運用の側で決まる。

| 守っていないもの | 理由 |
| --- | --- |
| 保存時暗号化 | Dataset・モデル・MongoDB・Elasticsearch はホストのファイルシステム上に平文で置かれる。ホストのディスク暗号化に依存する |
| 通信の暗号化 | ローカルは平文である。推論サービスは TLS の鍵を受け取れる（`PREDICTION_TLS_CERTIFICATE_FILE` / `PREDICTION_TLS_PRIVATE_KEY_FILE`）が、証明書を用意していない |
| ブラウザへ配る資格情報 | 持ち込んだ Angular アプリの構造上の問題であり、認証方式を替えないと解けない（57 §4.6） |
| Elasticsearch の認証 | `xpack.security.enabled: "false"`。Compose の内部ネットワークに閉じており、ホストへポートを公開していない |
| Grafana の認証 | 匿名 Viewer。ループバックのみ |
| 監査ログの改竄対策と保持 | 標準出力に出るだけで、集約も保全もしていない（53 §4.6） |
| 秘密の集中管理 | secret manager を置いていない。平文ファイルから環境変数へ渡す（57 §4.3） |

### 4.6 環境が変わるときに増えるもの

現在実在するのは開発環境だけである。検証・本番相当へ持っていくときに要るものは、環境ごとの
前提として `../_archive/security/001_20260908_threat_model.md` §4 に表がある。この文書では
再掲せず、設計として影響が大きい2点だけを挙げる。

第一に、ブラウザへ資格情報を配る方式は、ホストの外へ公開した時点で成立しない。ClearML Server 側の
ログインか、前段でのトークン発行へ替える必要がある。

第二に、実データを流すと区分が機密へ上がり、保存時暗号化とアクセス記録が前提になる。
どちらも現在は無く、後から足せる性質のものでもない（保存済みのデータは暗号化されない）。

## 5. 判断事項

| 判断 | 理由 | 記録 |
| --- | --- | --- |
| 秘密の層を最も重く守る | 攻撃者から見た最短経路が資格情報であり、そこを通られると認可の層は迂回される | 脅威モデル §6 |
| 共有シークレット＋役割で認可する | mTLS と OIDC は証明書発行と IdP 登録という人の作業を要し、この環境では動かないものになる | ADR 002 |
| 権限を行為の名前で定義する | 経路を移したときに権限が黙って移らないようにする | ADR 002、`ml/security/domain.py` |
| 呼び手ゼロで起動しない | 空の一覧の2つの読みのうち、安全なのは「誰も呼べない」だけである | ADR 002 |
| ClearML の3ポートを公開したままにする | 別端末のブラウザから使う運用を採っている。同一 LAN の信頼を前提にした受け入れ | 脅威モデル §5 |
| 深刻度が critical でないものを止めない | 学習環境で毎回赤い状態を作ると、ゲートを迂回する習慣ができる | `config/supply_chain.yaml`、54 |
| 対策の無い項目を削除しない | 何が欠けているかが表から消えると、欠けていること自体を忘れる | §4.5 |

## 6. 未決事項

* 保存時暗号化をどの層で行うか（ホストのディスク、Docker のボリューム、アプリケーション）
* TLS 証明書の用意と、前段で終端するか自前で終端するか
* ブラウザへ資格情報を配らない認証方式（`../backlog/` に対応する項目は無い）
* 秘密をどこで管理するか（secret manager の選定）
* 監査ログの集約先と保持期間（53 §6）
* 実データを受け入れる条件。区分が機密へ上がったときに要る対策の範囲
