## 1. 目的

この文書は、呼び手をどう特定し、その呼び手に何を許すかの方式を定める。

方式を選んだ理由は `../_archive/adr/002_20260908_service_authorization.md` にあり、発行・更新・
障害時の操作は `../_archive/runbooks/007_20260908_security.md` にある。この文書が持つのは、
実装されている仕組みの構造と、認証を掛けていない範囲である。

役割と権限の対応の一覧は 52 が持つ。この文書は表を1つだけ持ち、それは経路と要求権限の対応である。

## 2. 適用範囲

対象は、自作の2サービス（推論 API、ops-exporter）の認証と認可である。

対象外は次の4つで、いずれも認証の仕組みを自作していない。

| 対象外 | 現状 |
| --- | --- |
| ClearML Server の API と Web | ClearML 自身の資格情報による。役割による制限は無い（§4.6） |
| Angular Web | 認証を持たない。ClearML の資格情報を実行時設定として読む |
| Grafana | 匿名 Viewer。ループバックのみ |
| Prometheus・Alertmanager の画面 | 認証を持たない。ループバックのみ |

## 3. 前提

呼び手はいずれも機械である。推論を求めるバッチと smoke、運用者の `curl`、Prometheus の scrape の
3種類しかなく、画面から直接呼ばれる経路は無い。この前提が変わると方式を見直す（§5）。

利用者は1名であり、人に対する認証は行っていない。ホストに入れる者と、ClearML のすべてを読める者が
一致している（`../phase2_データ管理/13_PII・機密データ台帳.md` §4.7）。

## 4. 定義

### 4.1 3つの概念

認可は、権限・役割・呼び手の3つに分けて表す。定義は `ml/security/domain.py` にある。

| 概念 | 定義 | なぜ分けるか |
| --- | --- | --- |
| 権限（Permission） | 呼び手ができること1つ。行為の名前で表す | 経路を移しても権限が移らない |
| 役割（Role） | 権限の集合 | 呼び手に与えるのは仕事であり、仕事はレビューできる |
| 呼び手（Principal） | 名前・役割・資格情報の指紋の組 | 監査ログに残るのは名前である |

呼び手は資格情報そのものを持たない。したがって、設定ファイルもプロセスのメモリも、
そこから使えるトークンを渡さない。

### 4.2 トークン

トークンは 256 ビットの乱数に `stk_` を付けた文字列である。発行は `pnpm sec:token`、
ローカル一式の生成は `pnpm sec:tokens` が行う。

接頭辞が付いている理由は秘匿ではなく、検索である。乱数列はログの中で見分けが付かないが、
`stk_` で始まる文字列は、このリポジトリの走査器（規則 `issued-token`）でも、外部の走査器でも、
貼り付けを読む人の目でも見つかる。

サービスが保持するのはトークンの SHA-256 指紋だけである。指紋は秘密ではない。

### 4.3 認証の流れ

```text
呼び手                          サービス
  |                                |
  | Authorization: Bearer stk_...  |
  |------------------------------->|
  |                     SHA-256 を計算し、設定の指紋と照合
  |                     照合できたら、その呼び手の役割を得る
  |                     役割が経路の要求権限を含むかを判定
  |                     判定を1行1JSONで記録（53）
  |<-------------------------------|
  |  200 / 401 / 403               |
```

判定は例外ではなく値として返る（`AccessDecision`）。断られた理由を、その後に何も起きなくても
記録に残すためである。

### 4.4 2つの拒否

拒否は2種類を区別する。区別する理由は、読んだ人が取る行動が違うことである。

| 応答 | 意味 | 内訳 | 呼び手が取る行動 |
| --- | --- | --- | --- |
| 401 | 誰か分からない | 資格情報が無い（`missing_credential`）、知らない資格情報（`unknown_credential`） | 有効なトークンを提示する。応答は方式（`WWW-Authenticate: Bearer`）を返す |
| 403 | 誰か分かるが、許していない | 役割に権限が無い（`insufficient_role`） | 役割の変更を要する。同じトークンを再提示しても変わらない |

403 に 401 を返すと、存在しない資格情報の問題を運用者に調べさせることになる。

### 4.5 経路と要求権限

| サービス | 経路 | 要求権限 | 無認証にした理由 |
| --- | --- | --- | --- |
| 推論 API | `POST /predict` | `predict` | — |
| 推論 API | `GET /ready` | `model:read` | — |
| 推論 API | `GET /metrics` | `metrics:read` | — |
| 推論 API | `GET /health` | なし | プロセスを再起動する側が資格情報を持つと、期限切れが再起動ループになる |
| ops-exporter | `GET /metrics` | `metrics:read` | — |
| ops-exporter | `GET /health` | なし | 同上 |

`/health` が答えるのは「プロセスが動いている」だけである。モデルにも数字にも触れない。

経路が権限を宣言する形（`Depends(requires(Permission.PREDICT))`）にしてあり、検査の手順を
経路ごとに書かない。手順を書く形にすると、書き忘れた経路が無認証になる。

### 4.6 ClearML 側の認証と、その帰結

ClearML Server は自身の資格情報（`access_key` / `secret_key`）で認証する。この資格情報は全権であり、
「Dataset を読めるが Model は変えられない」呼び手を作れない。ADR 002 がこの資格情報の流用を
退けた理由もこれである。

したがって、自作サービスの最小権限は ClearML 側には及ばない。`clearml.conf` を読める者は、
Dataset・Task・Model を改変できる。この非対称は設計上の穴として残っており、ClearML Server 側の
機能に依存するため、このリポジトリからは塞げない。

### 4.7 起動時の拒否

`PREDICTION_API_CLIENTS` または `OPS_EXPORTER_CLIENTS` が空のサービスは、起動しない。
設定漏れが起動時に分かる形にしてある。開いたまま起動すると、気付くのは事故のときになる。

ローカルでは `scripts/security-tokens.sh` が3つの呼び手を生成し、`.generated/security/clients.env`
へ書く。`scripts/backend-up.sh` と `scripts/service-run.sh` がそれを読んで渡す。環境変数が既に
設定されている場合はそちらを優先する。検証環境以降で secret manager から渡すためである。

### 4.8 資格情報の更新

1つの呼び手は複数の指紋を持てる。更新は「新しい指紋を足す → 呼び手を移す → 古い指紋を消す」の
3手で、有効な資格情報が無い瞬間が生じない。無停止でできない更新は、結局行われない。

漏えいが分かっている場合は、この順序を守らず先に古い指紋を消す。使われているかどうかより、
使えなくすることが先である。手順は `../_archive/runbooks/007_20260908_security.md` にある。

## 5. 判断事項

| 判断 | 理由 | 記録 |
| --- | --- | --- |
| 共有シークレット（Bearer）を採る | mTLS は証明書の発行・配布・失効、OIDC は IdP への登録という人の作業を要する。呼び手が機械である限り、得られる強度に見合わない | ADR 002 |
| 指紋だけを保存する | 認証情報を保存する場所を1つ減らす。設定の漏えいが、名前と役割の漏えいで済む | ADR 002 |
| 役割を3つに絞る | 実在する呼び手に1つずつ対応させる。役割が増えるほど、どれを渡すべきかが曖昧になる | `ml/security/domain.py` |
| 判定を値として返す | 断られた理由を、その後に何も起きなくても記録するため | `ml/security/domain.py` |
| 権限の直接付与を持たない | 1つの呼び手に複数の役割が要る状況が、まだ生じていない | ADR 002 |

## 6. 未決事項

* 人が呼び手になる場合の方式（ADR 002 は OIDC の再検討を見直し条件としている）
* 役割が4つを超えた場合に、役割を増やすか権限を直接付与するか
* ClearML Server 側の権限分離。ClearML の機能に依存し、現時点では手段が無い
* トークンの有効期限。現在は期限を持たず、更新で無効化するのみである
* Grafana と Angular Web の認証（50 §4.5）
