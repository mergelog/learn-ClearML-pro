## 1. 目的

この文書は、誰が何をできるかを一覧にする。方式は 51 が持ち、ここにあるのは対応の表と、
その表を実装と食い違わせないための手順である。

これは台帳であり、呼び手・役割・経路のいずれかが増えたときに更新する。

## 2. 適用範囲

対象は3つの層である。

| 層 | 表 |
| --- | --- |
| 自作サービスの機械的な呼び手 | §4.1〜§4.3 |
| 人が触る経路 | §4.4 |
| リポジトリと CI | §4.5 |

対象外は、ClearML Server 内部の権限である。役割による制限を持たず、資格情報を持つ者が全権を持つ
（51 §4.6）。したがって「ClearML の権限マトリクス」は作れない。

## 3. 前提

利用者は1名であり、人に対する権限の分離を行っていない。§4.4 の表が区別しているのは人ではなく
経路であり、「ホストに入れる者が何を読めるか」を示している。

## 4. 定義

### 4.1 役割と権限

定義は `ml/security/domain.py` の `ROLE_PERMISSIONS` にあり、組み合わせは
`services/tests/security/test_authorization.py` が固定している。

| 役割 | `predict` | `model:read` | `metrics:read` |
| --- | --- | --- | --- |
| `predictor` | ○ | ○ | — |
| `operator` | — | ○ | ○ |
| `scraper` | — | — | ○ |

`predictor` が `model:read` を持つのは、どのモデルが答えたかが応答の一部であるためである。
監視の数字はその仕事に要らない。`operator` は障害時に提供中のモデルと数字を読むが、予測は
その仕事ではない。`scraper` は Prometheus のための役割で、数字だけを読む。

役割の間に包含関係を作っていない。`operator` は `predictor` の上位ではなく、別の仕事である。

### 4.2 権限と経路

| 権限 | 許す経路 |
| --- | --- |
| `predict` | 推論 API `POST /predict` |
| `model:read` | 推論 API `GET /ready` |
| `metrics:read` | 推論 API `GET /metrics`、ops-exporter `GET /metrics` |
| （権限なし） | 推論 API `GET /health`、ops-exporter `GET /health` |

### 4.3 呼び手と役割

ローカルで生成される呼び手は3つである（`scripts/security-tokens.sh`）。

| 呼び手 | 役割 | 実際に呼ぶもの | 資格情報の置き場所 |
| --- | --- | --- | --- |
| `local-predictor` | `predictor` | `scripts/serving-smoke.sh`、手元の `curl` | `.generated/security/clients.env` |
| `local-operator` | `operator` | `scripts/observability-smoke.sh`、`scripts/serving-smoke.sh` の `/metrics` 確認、障害時の確認 | 同上 |
| `prometheus` | `scraper` | Prometheus の scrape | `.generated/security/prometheus-token`（Prometheus が読む） |

サービスごとに、設定される呼び手が異なる。

| サービス | 設定される呼び手 |
| --- | --- |
| 推論 API（`PREDICTION_API_CLIENTS`） | `local-predictor`、`local-operator`、`prometheus` |
| ops-exporter（`OPS_EXPORTER_CLIENTS`） | `local-operator`、`prometheus` |

ops-exporter に `predictor` を渡していないのは、そのサービスに `predict` 権限で呼べる経路が
無いためである。渡しても何もできないが、渡さないことで「この呼び手はこのサービスを使わない」と
表明できる。

新しい呼び手を足すときは、`pnpm sec:token -- --name <名前> --role <役割>` で発行し、この表に
1行足す。

### 4.4 人が触る経路

| 経路 | 認証 | 読めるもの | 変えられるもの |
| --- | --- | --- | --- |
| ClearML Web（:8080） | なし（ブラウザに配られた資格情報を使う） | Dataset・Task・Model・Artifact のすべて | 同じくすべて |
| ClearML API（:8008） | ClearML の資格情報 | 同上 | 同上 |
| ClearML File Server（:8081） | ClearML の資格情報 | Artifact とモデルの実体 | 同上 |
| 推論 API（:8090） | トークン | 判定結果、提供中のモデル | なし |
| ops-exporter（:8091） | トークン | Queue・Agent・Task の数字 | なし |
| Grafana（:3000） | なし（匿名 Viewer） | 監視の数字 | ダッシュボードの保存はしない |
| Prometheus（:9090）・Alertmanager（:9093） | なし | 時系列と警報 | 警報の抑止（画面から可能） |
| ホストのシェル | ホストのログイン | すべて（ファイル、ボリューム、`clearml.conf`） | すべて |

待ち受けアドレスは一様ではない。推論 API・ops-exporter・監視はループバックで待ち受ける
（`BIND_ADDRESS` の既定値は `127.0.0.1`）。ClearML の3ポートは待ち受けアドレスを指定せずに
公開しており、同一 LAN から到達できる（`infra/clearml/compose.yaml`）。この違いは意図したもので、
理由は 50 §4.4 にある。

表の最後の行が示すとおり、ホストのシェルに入れる者に対する制限は無い。この環境の権限分離は、
ホストの外との間にしか存在しない。

### 4.5 CI と GitHub

| 主体 | 権限 | 根拠 |
| --- | --- | --- |
| CI のワークフロー | リポジトリの読み取りのみ（`permissions: contents: read`） | `.github/workflows/ci.yml` |
| CI から外部への通信 | OSV への問い合わせ、コンテナイメージの取得 | 54 §4.2 |
| CI が残す成果物 | SBOM と脆弱性の報告のみ（30日） | 56 §4.5 |

CI は資格情報を持たない。ClearML へも接続しない（E2E は応答を差し替えて動く）。

### 4.6 権限の棚卸し

呼び手・役割・経路のいずれかが変わると、この表と実装が食い違う。食い違いを見つける手段は
次の3つで、いずれも自動である。

| 手段 | 見つかること |
| --- | --- |
| `services/tests/security/test_authorization.py` | 役割と権限の組み合わせが変わったこと |
| `pnpm sec:tokens`（引数なし） | 設定されている呼び手の名前 |
| 監査ログの `principal` の集計 | 実際に呼んでいる呼び手。表にあって現れないものは、使われていない |

最後の手段は自動ではない。ログが集約されていないため、コンテナのログを人が読む必要がある
（53 §4.6）。使われていない呼び手を消すことが棚卸しであり、それを定期に行う運用は決めていない（§6）。

## 5. 判断事項

| 判断 | 理由 |
| --- | --- |
| 役割に包含関係を作らない | 上位下位にすると「運用者は予測もできる」ことになり、最小権限から外れる |
| ops-exporter に `predictor` を渡さない | 使わない呼び手を渡さないことで、どの呼び手がどのサービスを使うかが設定から読める |
| 人ではなく経路で表を作る | 利用者が1名であり、人を並べても行が1つになる。守っている境界はホストの外との間である |
| ホストのシェルの行を表に残す | この環境の権限分離がどこまでかを、表の中で見えるようにする |
