## 1. 目的

この文書は、誰が何をしたかを後から言えるようにするために、何を記録し、何を記録しないかを定める。

調べ方の手順は `../_archive/runbooks/007_20260908_security.md` の「誰が何をしたかを調べる」に
ある。この文書が持つのは、記録する項目を選んだ理由と、記録が残っていない範囲である。

ログの出力形式そのもの（1行1JSON、相関 ID）は、監査に限らないログ全体の設計であり、
`../phase1_上流設計/02_非機能要件定義書.md` §4.6 と `../phase1_上流設計/03_方式設計書.md` が持つ。

## 2. 適用範囲

対象は、自作サービスが記録する認可の判断と、ClearML 側に残る操作の痕跡である。

対象外は次の2つである。

| 対象外 | 理由 |
| --- | --- |
| ClearML Server が内部に持つ監査機能 | 持ち込んだ実装であり、何を記録しているかを確認していない（§6） |
| ホスト OS のログイン記録 | 環境側の機能である |

## 3. 前提

ログは各プロセスの標準出力に出るだけで、集約する仕組みを持たない。読む手段は
`docker logs` である。プロセスを作り直すと、その前の記録は残らない。

したがって現状の監査ログが答えられるのは、「いま動いているプロセスが起動してから何が起きたか」
までである。

## 4. 定義

### 4.1 認可の判断を記録する

認可の判断は、許可も拒否も1行1JSONで記録する（`services/security/http.py`）。
許可を記録しない監査は「誰が止められたか」に答えるが、「誰がやったか」に答えない。
事故の後に聞かれるのは後者である。

事象の名前は `access.decision` で固定してある。

| 項目 | 意味 | 値の例 |
| --- | --- | --- |
| `event` | 事象の種別 | `access.decision` |
| `principal` | 呼び手の名前。名乗らなかった場合は `anonymous` | `local-predictor` |
| `role` | その呼び手の役割。呼び手が不明なら `none` | `predictor` |
| `permission` | 何を求めたか | `predict` |
| `outcome` | 判断の結果 | `allowed` / `missing_credential` / `unknown_credential` / `insufficient_role` |
| `endpoint` / `method` | どの経路か | `/predict` / `POST` |
| `credential` | 提示された資格情報の指紋の先頭8文字。提示が無ければ項目自体が無い | `3f9c1a07` |
| `correlation_id` | 同じ呼び出しの他の行と繋がる識別子 | — |
| `service` | どのサービスか | `semiconductor-quality-prediction` |

`outcome` が4値に分かれているのは、読んだ人が取る行動が違うためである。資格情報が無いのは
設定されていない呼び手、知らない資格情報は更新の途中か試行、権限不足は与えていない仕事を
求めている呼び手を意味する。

拒否は `warning`、許可は `info` で出る。拒否だけを抜き出せるようにするためである。

### 4.2 記録しないもの

| 記録しないもの | 理由 |
| --- | --- |
| トークンそのもの | 記録した時点で、ログを読める者が呼べるようになる |
| 指紋の全体 | 指紋は秘密ではないが、全体を残す必要が無い。先頭8文字で1つの呼び手を追える |
| 要求の本文（予測の入力値） | 監査の目的は行為の記録であり、入力の内容はそこに要らない |

`credential` の先頭8文字は、1つの呼び手を追うためだけに置いている。これは提示されたものを
名指しできるようにするが、再現はできないようにするための幅である。

### 4.3 記録される他の痕跡

認可の判断以外に、後から誰の行為かを言える記録は次の2つである。どちらも監査のために作った
仕組みではなく、別の目的の記録が結果として残っているものである。

| 痕跡 | どこに残るか | 何が分かるか |
| --- | --- | --- |
| モデルの昇格 | Model の metadata（`promoted_by` / `promoted_at` / `promotion_reason`） | 誰がどの理由で昇格させたか |
| Task の実行 | ClearML の Task（作成者、開始時刻、Parameter、Git commit） | どの資格情報でどの実行が行われたか |

昇格の記録は、昇格の要求に承認者と理由を必須にしているために残る
（`../phase4_テスト品質保証/33_リリース判定基準.md` §4.9）。

### 4.4 記録が無い操作

次の操作は、行われた事実が記録に残らない。いずれも ClearML Web か API を直接使ったときに起きる。

| 操作 | 残らない理由 |
| --- | --- |
| Dataset の削除・Version の作成 | 自作のコードを通らない経路があり、その経路に記録を足せない |
| Model の削除 | 同上 |
| Task の削除・Parameter の書き換え | 同上 |
| ClearML の資格情報の発行 | ClearML Web の Settings で行う |
| モデルの持ち出し（File Server からの取得） | 取得は HTTP の取得であり、記録する仕組みが無い |

最後の行は、データ分類の上では機密（モデルの重み）の持ち出しにあたる。持ち出しを記録するという
方針を `../_archive/security/001_20260908_threat_model.md` §1 が置いているが、手段は無い
（`../phase2_データ管理/13_PII・機密データ台帳.md` §4.3）。

### 4.5 追跡の単位

1つの呼び出しに属する行は、相関 ID で繋がる（`ml/observability/logging.py`）。要求に
`X-Correlation-Id` が無ければ生成し、応答へ返す。呼び手が問題を報告するときに、その ID を
引用できる。

認可の判断の行と、その後の予測の行は同じ相関 ID を持つ。したがって「断られた呼び出し」と
「通って予測した呼び出し」を、同じ単位で追える。

### 4.6 保持と改竄

| 項目 | 現状 |
| --- | --- |
| 保存先 | 各コンテナの標準出力（Docker のログドライバ） |
| 保持期間 | 未確定。Docker の既定に従い、コンテナを作り直すと失われる |
| ローテーション | 設定していない |
| 改竄対策 | 無い。ホストに入れる者がログを消せる |
| 集約 | 無い。サービスごとに別々に読む |

監査ログに求められる性質のうち、「後から変えられないこと」を満たしていない。単一ホストで、
ホストに入れる者が1名で、その1名が調べる側でもあるため、現在の構成では意味のある改竄対策を
置けない。検証環境以降で、収集と保持を分離する（`../_archive/security/001_20260908_threat_model.md` §4）。

## 5. 判断事項

| 判断 | 理由 |
| --- | --- |
| 許可も記録する | 拒否だけの記録は「誰が止められたか」に答えるが、事故の後に聞かれる「誰がやったか」に答えない |
| 拒否の理由を4値に分ける | 読んだ人が取る行動が、資格情報の設定漏れ・更新の未完了・権限の不足で異なる |
| 指紋の先頭8文字だけを残す | 呼び手を追うには足り、提示されたものの再現には足りない |
| 判定を値として返してから記録する | 例外にすると、断られた事実を記録する場所が例外処理の側へ移り、経路ごとに書き忘れる |
| 事象名を `access.decision` に固定する | 文字列で検索する運用（`docker logs` の出力を `grep` する）が唯一の読み方であるため |
| 保持と改竄対策を未確定のまま残す | 単一ホストで調べる側と記録される側が同一人物であり、置いても機能しない |

## 6. 未決事項

* ログの集約先と保持期間（`../phase1_上流設計/02_非機能要件定義書.md` §4.6 と同じ未決事項）
* ClearML Server が内部に持つ監査機能の有無と、その利用可否
* Dataset・Model・Task の変更を記録する手段。自作のコードを通らない経路を塞ぐか、ClearML 側の
  記録に頼るかの判断を含む
* モデルの持ち出しの記録
* 監査ログを改竄不可にする方法（収集の分離、追記専用の保存先）
