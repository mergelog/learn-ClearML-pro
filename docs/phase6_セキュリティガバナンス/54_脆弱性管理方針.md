## 1. 目的

この文書は、依存とコンテナイメージに見つかった脆弱性を、どう見つけ、どう判断し、
いつまでに何をするかを定める。

止まったときの操作は `../_archive/runbooks/007_20260908_security.md` の
「脆弱性でリリースが止まった」にある。この文書が持つのは、止める深刻度の線引きと、
その線を引いた理由、および走査していない範囲である。

構成情報（SBOM）の作り方は 56 が持つ。この文書は、その SBOM を入力として何を判断するかだけを扱う。

## 2. 適用範囲

対象は次の3つである。

| 対象 | 走査するもの | 走査器 |
| --- | --- | --- |
| Python の依存 | `requirements/*.txt`（compile 済みの lock） | OSV |
| Node の依存 | `pnpm-lock.yaml` | OSV |
| 推論サービスのイメージ | ベースイメージと OS のパッケージ | Trivy |

対象外は次の4つである。

| 対象外 | 理由 |
| --- | --- |
| 自作コードの脆弱性 | 静的解析による脆弱性検査を導入していない。lint と型検査は品質のための検査である |
| ClearML Server のイメージ | 持ち込んだイメージを走査していない。CI で作るのは推論サービスのイメージだけである |
| 学習・最適化のイメージ | 同上 |
| 動的な検査（実行中のアプリケーションへの攻撃） | 実施していない（`../phase4_テスト品質保証/30_テスト計画書.md` の Security Test） |

## 3. 前提

依存は lock で固定されている。走査の対象は「いま入っているもの」ではなく「lock が決めているもの」
であり、手元・CI・イメージの中で同じ答えになる。

脆弱性の情報は外部のデータベースに問い合わせて得る。したがってこの検査は、変更の正しさではなく
「今日の世界の状態」を見ている。CI で別のジョブに分けてあるのはそのためで、外部要因で赤くなった
ときに他の検査の結果まで疑わずに済む。

## 4. 定義

### 4.1 見つける、判断する、の分離

見つけるのは走査器で、出してよいかを決めるのはゲートである。走査器は複数あり（OSV と Trivy）、
今後増えうる。判断を1か所に集めておけば、走査器を増やしても決め方は変わらない。

```text
lock ──▶ sbom ──▶ audit（OSV へ問い合わせ）──▶ dependencies.json ──┐
                                                                    ├──▶ gate ──▶ 可否
イメージ ──▶ Trivy ─────────────────────────────▶ image.json ──────┘
```

判断の方針は `config/supply_chain.yaml` にあり、コードの外にある。環境によって線引きを変える
ためである。

### 4.2 深刻度の決め方

OSV が返すのは CVSS のベクタである。ベクタから基本値を計算し、次の帯に落とす
（`tools/supply_chain/domain.py`）。

| 基本値 | 帯 |
| --- | --- |
| 9.0 以上 | `critical` |
| 7.0 以上 | `high` |
| 4.0 以上 | `medium` |
| 0.1 以上 | `low` |
| 情報が無い | `unknown` |

ベクタが無く、データベースが帯だけを返す場合は、その帯を採る。どちらも無い場合は `unknown` に
なる。`unknown` を `low` とみなさないのは、評価されていない助言に「無害」を当てるのが、
唯一確実に誤っている答えだからである。

### 4.3 止める線

| 深刻度 | 現在の扱い | 本番相当での扱い |
| --- | --- | --- |
| `critical` | 停止 | 停止 |
| `high` | 報告のみ | 停止側へ動かす |
| `medium` 以下 | 報告のみ | 報告のみ |
| `unknown` | 報告のみ | 環境の判断で停止側へ動かせる |

`high` 以下を止めないのは、学習環境で毎回赤い状態を作らないためである。毎回止まるゲートは、
迂回する習慣を作る。`unknown` を止めないのも同じ理由で、評価が付くまでに数日かかることがある。

この線引きは設定の1行であり（`config/supply_chain.yaml` の `block`）、環境ごとに変えられる。

### 4.4 問い合わせに失敗したとき

データベースへ到達できない場合、結果は「脆弱性なし」ではなく失敗として扱う
（`tools/supply_chain/osv.py`）。ネットワークが落ちているときに通るゲートは、
必要なときに通ってしまうゲートである。

### 4.5 例外

止まったものを受け入れるときは、`config/supply_chain.yaml` の `exemptions` に ID・理由・期限を
書く。期限を過ぎた行は、除外ではなく期限切れとして報告され、ゲートは再び止まる。

```yaml
release_gate:
  exemptions:
    - id: GHSA-xxxx-xxxx-xxxx
      reason: 修正版が未公開。該当経路は呼んでいない（確認した位置を書く）
      until: 2026-10-31
```

期限を必須にしているのは、日付の無い許可リストが「誰も見返さないものの一覧」になるためである。
現在、例外は0件である。

### 4.6 対応の順序

止まったときの選択肢は3つで、上から順に検討する。

1. 版数を上げる。`requirements/*.in` か `package.json` を直し、lock を作り直す（`pnpm py:lock`）
2. その依存を使うのをやめる
3. 期限付きで受け入れる（§4.5）

3 を選ぶ判断は、該当する経路を実際に呼んでいるかの確認を伴う。呼んでいない経路の助言と、
呼んでいる経路の助言を、同じ理由で受け入れることはできない。

### 4.7 実行のタイミング

| タイミング | 実行するもの | 場所 |
| --- | --- | --- |
| 変更ごと | SBOM 生成 → OSV 問い合わせ → イメージ走査 → ゲート | CI の `supply-chain` ジョブ |
| 手元で確認するとき | `pnpm sec:sbom` → `pnpm sec:audit` → `pnpm sec:gate` | 手動 |
| リリース判定 | ゲートの結果（`../phase4_テスト品質保証/33_リリース判定基準.md` の項目12） | — |

定期実行はしていない。変更が無い期間は走らないため、その間に公表された脆弱性には気付かない。
これは既知の穴である（§6）。

### 4.8 対応期限

深刻度ごとの対応期限（SLA）は定めていない。定めても、守る主体が1名しかおらず、守れなかった
ことを検知する仕組みも無い。実際に効いている期限は例外の `until` だけであり、これは
「受け入れたものを見返す日」を決めている。

`critical` については、期限ではなくゲートが役割を果たす。修正しなければリリースできない。

## 5. 判断事項

| 判断 | 理由 |
| --- | --- |
| 見つける側と判断する側を分ける | 走査器は増えうる。判断が各所に散ると、走査器を足すたびに決め方が増える |
| `critical` だけを止める | 学習環境で毎回赤い状態を作ると、ゲートを迂回する習慣ができる |
| `unknown` を `low` とみなさない | 評価されていない助言に「無害」を当てるのは、確実に誤っている |
| `unknown` を止めない | 評価が付くまで数日かかることがあり、そこで止めると迂回が習慣になる |
| 問い合わせの失敗を失敗として扱う | ネットワークが落ちているときに通るゲートは、必要なときに通る |
| 例外に期限を必須にする | 日付の無い許可リストは、見返されないものの一覧になる |
| SLA を定めない | 守る主体が1名で、守れなかったことを検知する仕組みが無い |

## 6. 未決事項

* 定期実行の有無と周期。変更が無い期間に公表された脆弱性に気付く手段が無い
* ClearML Server・学習・最適化の各イメージを走査するかどうか
* 自作コードに対する静的な脆弱性検査を入れるかどうか
* `high` を停止側へ動かす条件。本番相当の環境へ持っていく時点で判断する
* Trivy の `ignore-unfixed` の扱い。現在は修正未公開のものも報告させている
