## 1. 目的

この文書は、このシステムが何でできているかを記録する方法と、その記録に何が入っていないかを定める。

記録した内容をどう判断するかは 54（脆弱性）と 55（ライセンス）が持つ。この文書は、
入力・形式・生成の条件・保存の4点だけを扱う。

## 2. 適用範囲

対象は、lock ファイルが決めているコンポーネントである。

| 入力 | 生態系 | 状態 |
| --- | --- | --- |
| `requirements/training.txt` | PyPI | 含む |
| `requirements/serving.txt` | PyPI | 含む |
| `requirements/agent.txt` | PyPI | 含む |
| `requirements/dev.txt` | PyPI | 含む |
| `requirements/optimization.txt` | PyPI | **含まない**（§4.2） |
| `pnpm-lock.yaml` | npm | 含む |

対象外は次の3つである。

| 対象外 | どこで補うか |
| --- | --- |
| コンテナイメージの中の OS パッケージ | Trivy がイメージを走査する（54 §4.1） |
| 持ち込んだ Angular アプリに同梱されている第三者ライブラリ（`**/assets/**`） | lock に現れない。55 §4.4 |
| 自作コード | 構成情報の対象ではない |

## 3. 前提

SBOM は lock から作る。実行環境を見て作らない。実行環境を見て作った構成情報は、その1台の
構成を記述したものであり、他の場所で同じ答えにならない。

生成にネットワークは要らない。問い合わせが要るのは脆弱性の照会（54）であり、これは別の手順である。

## 4. 定義

### 4.1 形式

| 項目 | 値 |
| --- | --- |
| 形式 | CycloneDX |
| 仕様の版 | 1.5 |
| 出力先 | `.generated/security/sbom.json`（git 追跡外） |
| 1件あたりの内容 | 種別（`library`）、名前、版数、purl |
| 文書の metadata | 種別（`application`）、名前 `stackup`、版数 `0.1.0` |

CycloneDX を選んだのは、周辺の道具が読む形式であることによる。

生成物は決定的である。並びを固定し、時刻を書かない。同じコミットから2回作れば同じ文書になり、
差分が出たことが依存の変化を意味する。時刻を書くと、2つの文書を比べられなくなる。

文書の metadata にある版数はコードに直接書いてある（`tools/supply_chain/cli.py` の
`PROJECT_VERSION`）。リリース番号を振る運用が無いため（`../phase4_テスト品質保証/33_リリース判定基準.md` §4.8）、
この値はリリースと対応していない。

### 4.2 `optimization.txt` が入っていない

SBOM の入力は4つの `requirements` ファイルであり、`requirements/optimization.txt`（160行）は
含まれていない。ハイパーパラメータ探索に使う依存が、構成情報と脆弱性の照会の両方から
外れている。

これは実装を確認して分かった欠落であり、意図した対象外ではない。入力の一覧に1行足せば直る
（§6）。ここに書いてあるのは、直すまでの間、その範囲が見られていないという事実である。

### 4.3 含まれない情報

| 含まれない情報 | 帰結 |
| --- | --- |
| ライセンス | 依存のライセンスを機械的に確認できない（55 §4.2） |
| 依存の関係（どれがどれを引いているか） | 助言が出たとき、直接依存か推移的依存かを SBOM から言えない |
| ハッシュ（コンポーネントの完全性） | 取得したものが lock の意図と同じかを SBOM から確かめられない |
| 作成者・供給者 | 供給元を辿れない |

いずれも CycloneDX の仕様には項目があり、入れていないのは生成側の実装の範囲である。

### 4.4 生成のタイミング

| タイミング | 手順 |
| --- | --- |
| 変更ごと | CI の `supply-chain` ジョブが最初に生成する |
| 手元で確認するとき | `pnpm sec:sbom` |
| リリース判定 | 項目11「SBOM を生成してある」（`../phase4_テスト品質保証/33_リリース判定基準.md`） |

lock が変わったかどうかを見て生成を省くことはしない。生成は数秒で終わり、条件分岐を入れると
「生成されていないのに前回の結果が残っている」状態を作れてしまう。

### 4.5 保存と保持

| 項目 | 現状 |
| --- | --- |
| 保存先 | `.generated/security/sbom.json`。git では追跡しない |
| CI の成果物 | `sbom.json`・`dependencies.json`・`image.json` の3つ。保持は30日 |
| 版との対応 | 無い。コミットと成果物の対応は CI の実行記録にのみ残る |

`.generated/security/` を丸ごと成果物にすることはしない。同じ場所にローカルの資格情報
（`clients.env`、`prometheus-token`）が置かれるため、丸ごと上げる形にすると、いつかそれを
一緒に公開する。ファイルを名指しで上げている理由はこれである。

30日を過ぎると、そのときの構成が何であったかは lock から作り直すしかない。コミットが残っている
限り作り直せるため、SBOM そのものを長期保存していない。

## 5. 判断事項

| 判断 | 理由 |
| --- | --- |
| lock から作る | 実行環境を見て作った構成情報は、その1台の構成でしかない |
| 時刻を書かない | 同じコミットから同じ文書が出ないと、2つの文書を比べられない |
| 並びを固定する | 同上 |
| CycloneDX を採る | 周辺の道具が読む形式である |
| 生成物を追跡しない | lock から再生成できるものを git に置くと、再生成との食い違いが起きる |
| 成果物をファイル名で指定する | 同じディレクトリにローカルの資格情報が置かれる |
| ライセンス欄を持たない | 生成側の実装の範囲であり、意図した省略ではない（55 §4.2） |
