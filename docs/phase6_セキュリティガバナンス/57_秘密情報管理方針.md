## 1. 目的

この文書は、資格情報をどこに置き、書かれてしまったものをどう見つけ、どう入れ替えるかを定める。

発行・更新・漏えい時の操作は `../_archive/runbooks/007_20260908_security.md` にあり、
どの秘密がどこに在るかの台帳は `../phase2_データ管理/13_PII・機密データ台帳.md` §4.4 にある。
この文書が持つのは、検出の仕組みと、その仕組みが見ていない範囲である。

## 2. 適用範囲

対象は、このリポジトリを動かすために要る資格情報のすべてである。

| 秘密 | 使う側 | 置き場所 |
| --- | --- | --- |
| ClearML の資格情報（`access_key` / `secret_key`） | SDK、Agent、Angular Web | `./clearml.conf`（git 追跡外） |
| ブラウザへ配る ClearML の資格情報 | 持ち込んだ Angular アプリ | `src/credentials.json` とビルド生成物（いずれも git 追跡外） |
| サービスの呼び出しトークン | 推論 API の呼び手、ops-exporter の呼び手 | `.generated/security/clients.env`（git 追跡外） |
| Prometheus のトークン | Prometheus | `.generated/security/prometheus-token`（git 追跡外） |
| TLS の秘密鍵 | 推論サービス | 未使用。環境変数で場所を渡す形だけがある |

対象外は、ホスト OS の資格情報（ログイン、SSH 鍵）である。環境側の管理である。

パスワードは、この構成のどこにも存在しない。ClearML Server は資格情報の対で認証し
（`infra/clearml/compose.yaml` にパスワードの設定は無い）、Grafana は匿名 Viewer を有効にしている。
自作サービスはトークンで認証する。したがって、パスワードの強度・有効期限・再利用に関する方針は
定めない。ClearML Server 側のログインを有効にする場合、その時点で定める（§6）。

## 3. 前提

秘密を平文で保存しないことが原則である。しかし現状は、いずれも平文のファイルに置いてある。
secret manager を置いていないためで、これは学習環境で受け入れている状態である
（`../phase2_データ管理/13_PII・機密データ台帳.md` §4.4）。

補っているのは2つである。どのファイルも git の追跡外にあり、サービス側はトークンを保存せず
SHA-256 の指紋だけを持つ。したがって、漏れうるのは配布元のファイルだけである。

## 4. 定義

### 4.1 置き場所の規則

| 規則 | 対象 |
| --- | --- |
| 追跡しない | `.env`、`clearml.conf`、`.generated/`（`.gitignore`） |
| 環境変数で渡す | サービスへの指紋の一覧（`PREDICTION_API_CLIENTS`、`OPS_EXPORTER_CLIENTS`） |
| ファイルで渡す | Prometheus のトークン（scrape 設定に書かず `credentials_file` で読む） |
| コマンドラインに書かない | 学習の実行。Task Parameter へ記録されるため（§4.4） |

環境変数が既に設定されている場合、生成物より優先する（`scripts/service-run.sh`）。
検証環境以降で secret manager から渡すためである。

### 4.2 検出する3つの経路

走査する場所を3つに分けている。分ける理由は、それぞれ「何が漏れたことになるか」が違うことである
（`tools/security/sources.py`）。

| 経路 | 手順 | 何を見るか | なぜ別扱いか |
| --- | --- | --- | --- |
| リポジトリ | `pnpm sec:scan` | git が追跡しているファイルの全体 | 追跡されているものは、clone した全員が持つ |
| 生成物 | `pnpm sec:scan:paths <dir>` | 指定したディレクトリ | 追跡されていないため指し示す必要がある。ビルドが入れた秘密は、ソースには無い |
| Task の記録 | `pnpm sec:scan:clearml` | Parameter、コンソール出力、Agent が記録した環境（既定で直近50件） | ClearML Server を読める全員に見えており、実行が終わった後も残る |

リポジトリの走査が追跡下のファイルに限られているのは、無視されている `clearml.conf` が、
そのマシンでは意図して本物の資格情報を持つためである。毎回報告すると、走査の結果が読まれなくなる。

### 4.3 検出の規則

規則は8つある（`ml/security/secrets.py`）。

| 規則 | 見つけるもの |
| --- | --- |
| `issued-token` | このリポジトリが発行したトークン（`stk_` で始まる） |
| `private-key` | PEM 形式の秘密鍵の始まり |
| `aws-access-key-id` | AWS のアクセスキー ID |
| `json-web-token` | JWT の形をした文字列 |
| `credential-in-url` | URL に埋め込まれた資格情報 |
| `clearml-credential` | ClearML の資格情報の形 |
| `environment-credential` | 環境変数の形をした資格情報の代入 |
| `named-secret` | 名前が秘密を約束している代入（`password`、`secret` などを含む名前） |

`issued-token` が最初に来るのは、このリポジトリが発行するトークンに `stk_` を付けている理由と
対応している。接頭辞は秘匿の役に立たないが、漏れたものを見つけられる。

### 4.4 記録される直前に止める

学習側は、走査とは別の仕組みを持つ。Task Parameter へ記録する直前に検査し、資格情報を含んで
いれば記録せずに実行を止める（`ml/semiconductor_quality/clearml_tracking.py`）。

止める理由は、記録されてからでは手遅れであることによる。Task Parameter は ClearML Web にも、
Task の複製にも、実行の比較にも現れる。事後に消しても、見た者が居たかどうかは分からない。

### 4.5 除外

誤検知を外すときは、理由を書く。理由の無い除外は読み込みで拒否される
（`config/security.yaml`）。

| 方法 | 使う場面 |
| --- | --- |
| 行に `secret-scan:allow <理由>` と書く | 1行だけを外す。理由が、外された行の隣に残る |
| `config/security.yaml` の `exemptions` に書く | 同じ理由が何行にも並ぶ場合。パスと規則名を指定する |

現在の除外は2件で、どちらも1件ずつ理由が書かれている。持ち込んだ第三者ライブラリの圧縮された
識別子（`**/assets/**`）と、検出器自身のテストに置いた題材（`ml/tests/security/test_secrets.py`）である。
後者は規則を1つずつ挙げてあり、`issued-token` だけはこのファイルでも検出される。

### 4.6 ブラウザへ配られる資格情報

`src/credentials.json` は、持ち込んだ Angular アプリが実行時に読むファイルで、
ビルド生成物 `build/browser/credentials.json` にそのまま写る。ブラウザへ配るものに
資格情報が含まれる、という構造の問題である。

置いている対策は、検出と限定の2つだけである。`pnpm web:scan:build` が生成物を走査し、
CI でも実行される。ファイルは git の追跡外にあり、web は開発者自身の端末で動かし、生成物を
配布しない。

成立している条件は「生成物を配らない」ことだけである。ホストの外へ公開する場合、この構造の
ままでは配れない。認証方式を替える必要があり、それは 50 §6 の未決事項である。

### 4.7 更新

| 対象 | 手順 |
| --- | --- |
| サービスのトークン | 指紋を足す → 呼び手を移す → 古い指紋を消す（51 §4.8） |
| ローカルの一式 | `pnpm sec:tokens -- --rotate`。古いトークンは無効になる。Prometheus は再起動が要る |
| ClearML の資格情報 | ClearML Web の Settings で作り直し、`clearml.conf` を更新する |

定期的な更新は行っていない。周期を決めていないためで、実際に更新されるのは漏えいが分かった
ときだけである（§6）。

### 4.8 書いてしまったとき

順序が決まっている。**消すより先に、無効にする。** 書かれた資格情報は、ファイルを消しても
漏えいしたままである。

1. その資格情報を無効にする
2. どこまで広がったかを調べる（§4.2 の3経路すべて）
3. 記録から消す。コミット済みなら履歴の書き換えが要る
4. 検出できなかった場合は、規則を足す

4 を省くと、次も検出できない。手順の詳細は
`../_archive/runbooks/007_20260908_security.md` の「秘密を書いてしまった」にある。

### 4.9 検出が見ていない範囲

| 見ていない範囲 | 理由 |
| --- | --- |
| git の履歴 | 走査するのは現在の追跡下のファイルであり、過去のコミットは見ない |
| 追跡外のファイル（指定しない限り） | `pnpm sec:scan:paths` で指し示す必要がある |
| 直近50件より前の Task | 既定の上限。全件を読むと、履歴が伸びるほど検査が終わらなくなる |
| ClearML Server の DB の中身 | Task の API を通して読める範囲だけを見る |
| コンテナイメージの中 | 走査していない |
| 新しい形の秘密 | 規則に無い形は見つからない。§4.8 の 4 がこれを補う |

履歴を見ていないことは、過去に混入した秘密が残っている可能性を意味する。現時点でその走査を
行っていない。

## 5. 判断事項

| 判断 | 理由 |
| --- | --- |
| 走査を3経路に分ける | 追跡下・生成物・Task の記録は、漏えいの意味と気付き方が違う |
| リポジトリの走査を追跡下に限る | 無視されている `clearml.conf` を毎回報告すると、結果が読まれなくなる |
| 記録の直前で実行を止める | Task Parameter へ書かれた時点で、ClearML を読める全員に見えている |
| 理由の無い除外を拒否する | 除外は設定ではなく判断である。判断には理由が要る |
| 行単位の除外を用意する | 理由が、外された行の隣に残る |
| 発行トークンに接頭辞を付ける | 秘匿には寄与しないが、漏れたものを検索できる |
| 履歴を走査しない | 現時点で実施しておらず、必要になった時点で1回限りの作業として行う |

## 6. 未決事項

* secret manager の選定と、環境変数へ渡す経路の置き換え
* 定期的な更新の周期。決めていないため、実際には漏えい時にのみ更新される
* git の履歴に対する1回限りの走査
* TLS の秘密鍵の置き場所（証明書を用意する時点で決める）
* ブラウザへ資格情報を配らない認証方式（50 §6）
* コンテナイメージに対する秘密の走査
* ClearML Server 側のログインを有効にする場合のパスワードの方針（§2）
