## 1. 目的

この文書は、コードをどう書くかを定める。どこに置き、依存をどちら向きに流すかは 61 が、
方式の選択理由は 03 が持つ。

規約は2種類ある。設定ファイルとゲートが強制するものと、人が見て守るものである。
前者は設定の所在を、後者は守られているかを何で確かめるかを併記する。
どちらでもない「望ましい書き方」は、守られているかを確かめる手段が無いため、この文書に書かない。

## 2. 適用範囲

対象は自作分に限る。`apps/web` のうち `features/quality-pipeline`、`features/data-catalog`、
`shared/clearml`、`e2e` と、`ml`、`services`、`tools`、`scripts` である。

取り込んだ ClearML Web（`src/app/webapp-common/**`、`business-logic/**`、`features/` のうち取り込み由来のもの）は
凍結領域であり、この規約を適用しない。凍結領域に対して求めるのは、ESLint 違反の件数を増やさないことだけである（ADR 003）。

## 4. 定義

### 4.1 TypeScript の型

`strict` はリポジトリ全体では有効にしていない。取り込んだコードを含めると500件以上の型エラーが出るためで、
移行済みの範囲を `apps/web/tsconfig.strict.json` の `include` が宣言し、その範囲だけを失敗として扱う。
現在の範囲は自作の3領域と `e2e` である。

新しく書くコードは、この範囲の中に置く。範囲外へ新しいコードを足せば、そのコードには `strict` が効かない。

範囲の外でも、`tsconfig.json` に書いた次の4つは常時有効である。

| 設定 | 咎めるもの |
| --- | --- |
| `noImplicitOverride` | `override` を書かない上書き |
| `noImplicitReturns` | 経路によって値を返したり返さなかったりする関数 |
| `noFallthroughCasesInSwitch` | `break` の書き忘れ |
| `strictTemplates`（`angularCompilerOptions`） | テンプレートの型不一致 |

`strict` の範囲を広げるときは `include` へ足す。足した時点で `pnpm web:typecheck:strict` が通らなければ、
その feature はまだ移行できていない。

### 4.2 ESLint が強制するもの

設定は `apps/web/eslint.config.js` にある。自作分に効く規則のうち、意図して置いたものは次のとおりである。

| 規則 | 内容 |
| --- | --- |
| `no-console` / `no-debugger` | 製品コードに残さない |
| `quotes` | シングルクォート。テンプレートリテラルは許す |
| `@angular-eslint/component-selector` | 要素セレクタ。接頭辞 `sm`、kebab-case |
| `@angular-eslint/directive-selector` | 属性セレクタ。接頭辞 `sm`、camelCase |
| `@angular-eslint/prefer-on-push-component-change-detection` | Angular 22 では OnPush が既定のため、咎めるのは `Default` への明示的な離脱だけである |
| `@angular-eslint/template/prefer-control-flow` | テンプレートは `@if` / `@for`。旧制御フローを書かない |
| `@angular-eslint/template/no-any` | テンプレートで `$any()` を使わない |
| `@ngrx/*` | NgRx プラグインの全ルール。ただし `prefer-effect-callback-in-block-statement` だけは切ってある |

最後の1件は唯一の意図的な無効化である。observable を直接返す書き方が全域で使われており、
264件を機械整形するだけの利益が無いという判断による。

凍結領域を含めた違反の総数は `apps/web/eslint-baseline.json` に記録してあり、
`pnpm web:lint:baseline` が基準値を超えた変更を落とす。基準値の更新（`web:lint:baseline:update`）は、
違反を減らしたときに実行する。増やしたときに実行してはならない。

### 4.3 Angular と NgRx の書き方

方式の選択理由は 03 が、feature の構成は 61 が持つ。ここで定めるのは、その中でのコードの形である。

テンプレートとスタイルは別ファイルにする。`templateUrl` と `styleUrls` で参照し、インラインに書かない。

store を読むのは `store.selectSignal()` で、container のフィールドは `protected readonly` にする。
`protected` はテンプレートからだけ使うという意味で、`readonly` は差し替えないという意味である。
依存の受け取りは `inject()` を使い、コンストラクタ引数では受け取らない。

action は createActionGroup で宣言し、「何が起きたか」を名前にする。「次に何をするか」は書かない。
`startRun` は利用者が起動を押したという事実で、`runStarted` は ClearML が受け付けたという事実である。
どちらを受けて何をするかは Effects と reducer が決める。

失敗は成功と同じ数だけ action を持つ。失敗を1つにまとめないのは、「一覧の取得に失敗した」と
「起動に失敗した」で画面の戻し方が違うためである。

Effects では例外を投げず、`catchError` で失敗 action に変換して流す。投げると、その effect は以後
何も受け取らなくなり、画面は「押しても無反応」になる。繰り返し取得する effect には `takeUntil` を付け、
画面を離れたら止める。

### 4.4 命名とファイル名

Angular 側は、feature の中での役割がファイル名から読めるようにする。具体的な一覧は 61 §4.3 にある。
component は `<name>.component.ts`、spec は対象のファイルと同じ場所に `<name>.spec.ts` として置く。

Python 側の命名は ruff の `N`（pep8-naming）が検査する。モジュールとその中の関数は snake_case、
クラスは PascalCase、定数は UPPER_SNAKE_CASE である。

### 4.5 Python の静的解析

設定は `pyproject.toml` にある。`ruff` が lint と import 整形を、`mypy` が型を見る。

1行は100文字までとする。import は `ml` / `services` / `tools` を先頭パッケージとして並べ替え、
親を辿る相対 import（`from ..x import y`）は書かない。

`ruff` の選択規則のうち、設計上の意味を持つものは次の3つである。

| 規則 | 内容 |
| --- | --- |
| `T20` | `print` を製品コードに残さない。標準出力へ書くことが仕事である CLI 入口と `main.py` だけが例外である |
| `PTH` | パス操作は `pathlib` を使う。`os.path` を書かない |
| `DTZ` | tz を持たない `datetime` を作らない |

`mypy` は `strict` である。緩めてあるのは2か所だけで、どちらも理由が設定ファイルに書いてある。
型情報を配布していない外部ライブラリ（`clearml`、`sklearn`、`joblib`）の import と、
`strict` 導入以前から在るテスト（`ml.tests.*`、`tools.tests.*`）である。
後者は一覧を段階的に空にする対象であり、新しく書くテストをこの一覧へ足してはならない。

カバレッジは分岐カバレッジで測り、80%を下回ると失敗する。この値は導入時点の実測82%に対して置いた床であって、
目標値ではない。

### 4.6 註釈と docstring

註釈は、コードが何をしているかではなく、なぜそう書いたかを記す。
読めば分かることを日本語で言い直した註釈は、コードを変えたときに嘘になるだけで、何も守らない。

言語は場所によって分かれている。Python のモジュール・クラス・関数の docstring は英語で、
その中でも、モジュール docstring は「この層が何を引き受け、何を引き受けないか」と、
意図して選んだ設計判断を書く。行内の註釈は日本語で、その行がなぜ必要かを書く。

TypeScript と `scripts/*.mjs` は、JSDoc も行内の註釈も日本語で書く。

設定ファイル（`pyproject.toml`、`eslint.config.js`、`test-pyramid.json`、`config/*.yaml`）にも、
値を選んだ理由を日本語で書く。設定値そのものは差分から読めるが、なぜその値かは書かなければ残らない。

### 4.7 失敗の扱い

画面側では、ClearML API の失敗を `shared/clearml/clearml-failure.ts` で1行の文言に変換し、state に載せる。
変換を feature ごとに書かないのは、「失敗は state に載せる」という方針が feature ごとに割れないようにするためである。

Python 側では、設定の誤りをプロセスの起動時に拒否する。`services/prediction_api/main.py` は
設定を読んで使えなければ起動しない。使えない設定のまま動き始めて、要求が来てから失敗するのを避けるためである。

判断の層（`ml/**` の `checks.py`、`gate.py` など）は例外で流れを止めず、
どの測定値がどう基準を外れたかを値として返す。「データが悪い」とだけ言う報告は、読んだ人が最初からやり直すことになる。

### 4.8 テストの書き方

何をどの層で確かめるかは 30 と `test-pyramid.json` が持つ。ここで定めるのは書き方である。

ファイル名は層ごとに決まっている。Python は `test_*.py`、Angular は `*.spec.ts`、
ゲート自身のテストは `scripts/tests/**/*.test.mjs` である。`pnpm test:pyramid` が、
宣言した層の外に置かれたテストを落とす。

Python は標準の `unittest` で書く。Angular は vitest と `TestBed` で、store は `provideMockStore` に差し替える。
テストは表明の読みやすさを優先し、`ruff` の一部規則（未使用引数、`with` の入れ子）をテスト配下で緩めてある。

各テストファイルの冒頭には、そのテストが何を確かめ、何を確かめないかを日本語の docstring / JSDoc で書く。

### 4.9 整形

`apps/web/.editorconfig` が文字コード（UTF-8）、インデント（空白2）、行末の空白除去、末尾改行を定める。

Prettier は採用していない。引用符は ESLint が見ており、凍結領域を一括整形すると、
取り込み元との差分が読めなくなるためである。自動整形が無い分、行の折り返し位置は人が決める。

### 4.10 検査の一覧

| 規約 | 検査 |
| --- | --- |
| 型（移行済みの範囲、§4.1） | `pnpm web:typecheck:strict` |
| ESLint 規則（§4.2） | `pnpm web:lint` |
| 違反の件数を増やさない（§4.2） | `pnpm web:lint:baseline` |
| Python の lint と import（§4.5） | `pnpm py:lint` |
| Python の型（§4.5） | `pnpm py:typecheck` |
| カバレッジの床（§4.5） | `pnpm py:coverage` |
| テストの置き場所（§4.8） | `pnpm test:pyramid` |
| Angular と NgRx の書き方（§4.3） | 一部のみ（`@ngrx/*` ルール）。container の書き方に自動検査なし |
| 註釈と docstring（§4.6） | 自動検査なし |
| 失敗の扱い（§4.7） | 自動検査なし |

上の検査はすべて `pnpm run verify` に含まれ、CI の各ジョブは同じ script を呼ぶ。
呼び忘れは `pnpm run ci:parity` が落とす。
