## 1. 目的

この文書は、変更を1件ずつ取り込んでよいかを何で判断するかを定める。
まとまった機能を受け入れてよいかは 32 が、リリースしてよいかは 33 が持つ。

判断は2つに分かれる。機械が落とすものと、人が見るものである。
前者を人が読み直しても時間が減るだけなので、この文書の本体は後者の一覧である。

## 2. 適用範囲

自作分のコード変更、`config/**` と `infra/**` の設定変更、`docs/**` の文書変更を対象とする。

凍結領域（ClearML Web の取り込み分）への変更は、§4.6 で別に扱う。

## 3. 前提

本プロジェクトは単独開発であり、変更を書いた人とレビューする人が同じである。
別の人が読む工程は存在しない。この文書が定めるのは、取り込む前に自分で行う点検であり、
複数人になったときにそのままレビュー観点として使える形にしてある。

機械の検査は `pnpm run verify` が手元で、`.github/workflows/ci.yml` が pull request と main への push で走る。
CI は `package.json` の script を呼び、呼び忘れは `pnpm run ci:parity` が落とす。

## 4. 定義

### 4.1 機械が見るもの

次の項目は、人が読んで確かめない。落ちたものを直すだけである。

| 見るもの | 検査 |
| --- | --- |
| 書式・lint 規則、違反の件数 | `web:lint:baseline`、`py:lint` |
| 型 | `web:typecheck:strict`、`py:typecheck`、`web:e2e:typecheck` |
| feature 間の禁止依存 | `web:boundaries` |
| テストの置き場所と層 | `test:pyramid` |
| 画面と Python 側の文字列の一致 | `web:contract` |
| 公開 API の形 | `services/tests`（`openapi.json` との一致） |
| テストの成否とカバレッジの床 | `web:test`、`py:coverage`、`web:e2e` |
| 生成物に資格情報が混じらないこと | `web:scan:build` |
| リポジトリ内の秘密 | `sec:scan` |
| 依存の脆弱性とライセンス | `sec:audit`、`sec:gate` |

CI が緑であることは、取り込む条件であって、取り込んでよい理由ではない。
上の一覧に無いものは、緑でも確かめられていない。

### 4.2 人が見るもの

以下は順に見る。前の項目が通らない変更を、後ろの項目で救わない。

**要件との整合。** その変更が、どの要件・どの未解決ストーリーに対応するものかを言えるか。
言えない変更は、必要だと判断した理由が残らないため、後から消してよいかも判断できなくなる。

**設計との整合。** 61 が定めた配置と依存の向きに従っているか。
従えない事情があるなら、規約を変えるのか、その1件を例外にするのかを決める。
例外にするなら、なぜ例外かをコードの註釈か ADR に残す。`web:boundaries` の既知の違反一覧へ足して済ませない。

**責務の分担。** ClearML の語彙が adapter と Effects の外へ出ていないか。
container 以外が store に触れていないか。判断の層が ClearML SDK を呼んでいないか。
最後の1つに自動検査は無く、守られている状態は「単体テストがサーバ無しで動く」ことで保たれている（61 §4.7）。

**失敗したときの挙動。** 成功経路だけでなく、API が失敗したとき、応答が空のとき、
権限が無いときに何が起きるかを見る。Effects が例外を投げて黙るのは、最も見つけにくい壊れ方である（60 §4.3）。

**テスト。** 変更した判断に対応するテストがあるか。
テストが無い変更を受け入れるのは、その判断が壊れても誰も気付かないことを受け入れるのと同じである。
ただし、下の層で確かめられることを上の層で重ねて確かめない（ADR 005）。

**読みやすさ。** 註釈が、コードの言い換えではなく、なぜそう書いたかを記しているか。
名前が役割を表しているか。変数名や整形の好みは、レビューの対象にしない（§4.5）。

**セキュリティ。** 資格情報がコードと設定と生成物に入っていないか。
新しい入力経路を足したなら、認可の判断がどこにあるか。ログに秘密が出ていないか。
機械の走査は既知の形しか見つけないため、新しい経路は人が見る。

**性能。** 繰り返し取得する処理に停止条件があるか。1件ずつ API を呼ぶ形になっていないか。
数値目標は 02 が「本学習環境では保証対象外」としているため、ここで見るのは水準ではなく形である。

**互換性。** §4.3 で別に扱う。

**文書。** §4.4 で別に扱う。

### 4.3 何を壊すと外へ影響するか

外から見える形を変える変更は、変えたこと自体が記録に残る形にする。

| 変えたもの | 残す形 |
| --- | --- |
| `prediction_api` の HTTP API | `services/prediction_api/openapi.json` を更新し、差分をレビューの対象にする |
| ClearML 上の名前（プロジェクト・Pipeline・Queue・モデル・タグ・ステップ） | 画面と `ml/` の両方を同時に変える。`web:contract` が片側だけの変更を落とす |
| `config/*.yaml` のキー | 設定に無いキーは読み込みが失敗する。運用中の設定ファイルを同時に更新する |
| Dataset の列・型 | 10 と 21 を更新する。既存の Dataset Version は作り直さない |

`openapi.json` の差分は、消費者がいないことを理由に素通ししない。
守っているのは形そのものではなく、形が黙って変わらないことである（ADR 006）。

### 4.4 文書を伴う変更

コードだけを変えて済む変更と、文書を同時に変えなければならない変更を区別する。

| 変更 | 同時に更新する文書 |
| --- | --- |
| 方式・技術選択 | ADR を1本追加する。既存 ADR は書き換えない |
| 配置・依存の規約 | 61 |
| 検査の追加・削除 | 60 §4.10、61 §4.9、30 |
| 運用手順 | 該当する runbook（`_archive/runbooks/`）ではなく、40〜44 のうち該当するもの |
| Dataset・モデルの性質 | 10、20、21 |
| 未解決のまま残すと決めたもの | `docs/backlog/` にストーリーを1本足す |

文書を更新しないまま取り込むと、次に読む人は文書とコードのどちらが正しいか判断できない。
判断できない文書は、無い文書より悪い。

### 4.5 レビューで見ないもの

書き方の好み、行の折り返し位置、命名の語感は指摘しない。
規約（60）に書いていないものは、書いた人の判断に委ねる。
規約に足すべきだと考えたなら、その変更のレビューではなく、60 の変更として提案する。

### 4.6 凍結領域への変更

`webapp-common/**`、`business-logic/**`、取り込み由来の `features/**` へ手を入れる変更は、
入れないという判断を最初に確かめる。自作側で解けないかを見て、解けないときだけ入れる。

入れると決めたときに見るのは3点である。上流の更新を取り込むときに衝突する範囲がどこまでか、
ESLint 違反の件数が増えていないか、そして取り込み元との差分が読める形になっているか。

### 4.7 指摘の扱い

指摘は2つに分ける。取り込みを止めるものと、記録して進めるものである。

止めるのは、§4.2 の要件整合・設計整合・責務の分担・失敗時の挙動・セキュリティ・互換性に関わる指摘である。
これらは、後から直すと直す範囲が広がる。

記録して進めるのは、それ以外である。記録先は `docs/backlog/` で、
着手条件を書いて残す。「あとで直す」とだけ書いた指摘は、着手される条件が無いので、残らないのと同じである。

## 6. 未決事項

* レビュー者が別にいない。この文書が定めるのは自己点検であり、第三者が見た場合に何が変わるかは未検証である
* 承認の記録が残らない。誰がいつ何を見て取り込んだかを追える形になっていない
* pull request を経由せず main へ直接取り込んだ変更に対して、CI は push 時に走るが、取り込みを止める仕組みが無い
* §4.2 の観点のうち、要件整合・責務の分担・失敗時の挙動には自動検査が無い
