## 1. 目的

## 4. 定義

### 4.1 ブランチ

`main` は、いつ取り出しても CI が緑である状態を保つ。ここへ壊れたものを置かない。

作業は `main` から切ったブランチで行う。名前は `work_<YYYYMMDD>` とし、着手した日を入れる。
1本のブランチで扱うのは1つのまとまりに限り、終わったら畳む。長く残したブランチは、
`main` との差が広がるほど取り込む作業が重くなる。

作業ブランチ以外に、次の2つを使ってよい。どちらも `main` から切り、取り込んだら消す。

| 種類 | 名前 | 用途 |
| --- | --- | --- |
| hotfix | `hotfix_<YYYYMMDD>` | 動いているものが壊れていて、次の作業単位を待てないとき |
| 実験 | `spike_<内容>` | 取り込む前提のない試行。取り込むなら書き直して作業ブランチへ載せる |

### 4.2 コミット

1つのコミットには1つの判断を入れる。「動く状態から動く状態へ」の1歩を単位とし、
複数の判断をまとめない。まとめると、後から片方だけを戻せなくなる。

メッセージは `<種別>: <内容>` の形で日本語で書く。種別は次の7つに限る。

| 種別 | 対象 |
| --- | --- |
| `feat` | 外から見える振る舞いの追加 |
| `fix` | 壊れていた振る舞いの修正 |
| `refactor` | 振る舞いを変えない構造の変更 |
| `test` | テストだけの変更 |
| `docs` | 文書だけの変更 |
| `ci` | ワークフローとゲートの変更 |
| `chore` | 依存の更新、設定の整理 |

1行目は何を変えたかを書く。なぜ変えたかは本文に書く。
本文が要るのは、差分を読んでも理由が分からない変更である。理由がコードの註釈か ADR にあるなら、
そちらを指す。

### 4.3 追跡するものとしないもの

追跡しないものは `.gitignore` が定める。資格情報（`.env`、`clearml.conf`）、
依存と仮想環境（`node_modules/`、`.venv/`）、生成物（`.generated/`）、
ローカル設定（`AGENTS.local.md`）である。

生成物のうち、次の4つは意図して追跡する。どれも「生成できるもの」ではなく「前回と比べるためのもの」である。

| ファイル | 比べる対象 |
| --- | --- |
| `services/prediction_api/openapi.json` | 公開している API の形。黙って変わらないために置く（ADR 006） |
| `apps/web/eslint-baseline.json` | lint 違反の件数。増えたときだけ落とすために置く |
| `apps/web/web-boundaries.json` | 既知の依存違反。増えたときだけ落とすために置く |
| `requirements/*.txt` | 解決済みの依存の版数。手元と Agent で同じものを入れるために置く |

秘密がコミットに混じっていないことは `pnpm run sec:scan` が見る。
混じったまま push したときは、削除のコミットを足しても履歴に残るため、
その資格情報を失効させて作り直す（57）。

### 4.4 取り込み

変更は pull request を経由して `main` へ入れる。CI が緑であることを条件とし、
人が見る点検は 62 に従う。

`main` へ直接 push すると CI は走るが、落ちても取り込みは止まらない。
この経路を使うのは、CI の設定そのものを直すときに限る。

取り込み方は squash とし、`main` には作業単位ごとに1つのコミットが並ぶようにする。
作業ブランチの途中経過は、取り込んだ後に読み返す対象にならない。

### 4.5 rebase と衝突

作業ブランチを `main` へ追従させるときは rebase する。`main` を作業ブランチへ merge しない。
取り込む側の履歴が枝分かれで読めなくなるのを避けるためである。

既に共有したコミットを rebase で書き換えない。単独開発の現在は共有そのものが起きていないが、
複数人になった時点でこの制限が効き始める。

凍結領域で衝突したときは、自作側で解けなかったかを先に確かめる（62 §4.6）。
自作分と凍結領域の変更が1つのコミットに混ざっていると、ここで分けられない。
1つのコミットに1つの判断を入れると決めてあるのは（§4.2）、この場面で凍結領域への変更だけを取り出せるようにするためである。

### 4.6 タグとリリース

タグは1つも作っていない。リリース番号を振る運用も無く、出したことを記録する場所も無い（33 §4.8）。
現在、版は git ではなく ClearML 側（モデルの版と段階タグ）と compose のイメージタグが持っている。

タグを使い始めるときは、タグが何を指すかを先に決める。
`apps/web` の版、モデルの版、配備したイメージの版は別々に動くため、
1つのタグで全部を指そうとすると、どれとも一致しない番号ができる。

### 4.7 戻し方

`main` に入った変更を戻すときは、打ち消すコミットを足す。履歴を書き換えない。

配備したものを戻す手順は 43 と 33 §4.5 にある。git の操作だけでは戻らない対象（データベース、
File Server 上の成果物、ClearML 上のモデルの段階）があるためである。

### 4.8 エージェントによる操作

`git add`、`git commit`、`git push` を、コーディングエージェントに実行させない。
これは本リポジトリの `CLAUDE.md` が定める規則であり、ステージング・コミット・送信は人が行う。

何を1つのコミットにするかは §4.2 の判断であり、その判断は差分を見た人が下す。
