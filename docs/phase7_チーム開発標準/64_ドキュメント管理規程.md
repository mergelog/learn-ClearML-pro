## 1. 目的

この文書は、資料をどこに置き、どう名付け、どう更新し、どう畳むかを定める。
何を書くかは各文書が、どのフェーズで何を作るかは `x-plan-改訂/_old/20_ドキュメント作成プラン.md` が持つ。

## 2. 適用範囲

`docs/**` を対象とする。

`x-docs/`（学習用のメモ）、`x-plan-改訂/`（計画と進捗）、`x-QA/`、`x-history/` は対象外である。
これらは作業の過程を残す場所で、別の人が同じことを再現するための資料ではない。
命名の規則（連番の接頭辞）も別に定められている。

## 3. 前提

`docs/**` はどの自動検査の対象でもない。`test-pyramid.json`・`eslint-baseline`・`web-boundaries`・
`ci:parity` のいずれも Markdown を読まない。この規程が守られているかは、人が見る以外に確かめる手段が無い。

## 4. 定義

### 4.1 置き場所

| 場所 | 置くもの |
| --- | --- |
| `docs/phase<N>_<分類>/` | 番号付きの体系資料。Phase ごとに分ける |
| `docs/backlog/` | 着手していないものを、着手条件つきで残したストーリー |
| `docs/_archive/` | 2026-09-12 の体系整備以前の資料。ADR・runbook・脅威モデル |

Phase とフォルダと番号帯の対応は `docs/README.md` が持つ。1本目の文書を作るときに、
そのフェーズのフォルダも作る。空のフォルダを置かない。

### 4.2 ファイル名

体系資料は `<番号>_<内容>.md` とする。接頭辞に日付を付けない。

番号は文書 ID と一対一に対応し、`10_データディクショナリ.md` は DOC-10 である。
番号はフォルダを移しても変えない。文書を跨いだ参照が番号で書かれているためで、
番号を振り直すと、参照している側をすべて直すことになる。

backlog のストーリーは `<番号>_<内容>.md` とし、文書 ID は `DOC-BL-<番号>` とする。
`docs/_archive/` の資料は、書かれた当時の `<番号>_<日付>_<内容>.md` のまま残す。

### 4.3 文書の構成

体系資料は8つの節を持つ。構成は `x-plan-改訂/_old/20_ドキュメント作成プラン.md` §14 が定める。

| 節 | 内容 |
| --- | --- |
| 文書情報 | 文書名・文書ID・Version・Status・作成日・最終更新日・Author・Reviewer |
| 1. 目的 | この文書が何を定めるか。隣の文書が何を持つか |
| 2. 適用範囲 | 対象と対象外 |
| 3. 前提 | 依存する環境・技術・制約 |
| 4. 定義 | 本文 |
| 5. 判断事項 | 設計判断と、その記録（ADR）へのリンク |
| 6. 未決事項 | 確定していないこと。推測で埋めない |
| 7. 関連資料 | コード・設定・ADR・runbook・他の文書 |
| 8. 更新履歴 | Version・日付・内容 |

backlog のストーリーは別の様式を持つ。種別・状態・起票日の表に続けて、
「何が起きているか」「解決とみなす状態」「着手の条件」「関連」を書く。
進捗はここで管理しない。着手すると決めたものは、作業の計画へ移してから始める。

### 4.4 Version と Status

Version は 0.1 から始める。改訂のたびに上げ、更新履歴に1行足し、最終更新日を書き換える。
本文だけを直して更新履歴を足さない更新をしない。差分が git にしか残らなくなるためである。

Status は次の4つを使う。

| Status | 意味 |
| --- | --- |
| ドラフト | 書いたが、実装との突き合わせが済んでいない |
| 確定 | 実装・設定・実行結果と突き合わせた |
| 運用中 | 継続的に更新する台帳。確定という状態を持たない |
| 凍結 | 更新しない。書かれた時点の記録として残す |

現在、体系資料はすべて「ドラフト」である。実装との突き合わせを行った文書から「確定」へ移す。

### 4.5 レビューと承認

文書を取り込んでよいかの判断は 62 に従う。文書だけの変更も、コードの変更と同じ経路で入れる。

現在、Reviewer は全文書で「なし」である。書いた人と読む人が同じであり、
承認の記録が残る形になっていない。複数人になった時点で、文書情報の Reviewer 欄が意味を持つ。

### 4.6 廃止とアーカイブ

役目を終えた文書を消さない。`docs/_archive/` へ移し、Status を「凍結」にする。
消すと、その文書を参照していた側のリンクが切れ、何が書いてあったかも辿れなくなる。

`docs/_archive/` の資料は更新しない。新しい体系資料は、判断の経緯や具体的な操作手順を写し取らず、
`_archive/` の該当箇所へリンクする。写し取ると、写した先と写し元のどちらが正しいか判断できなくなる。

### 4.7 ADR との関係

ADR は「なぜその方式・技術・方針を選んだか」の記録である。設計書の代わりにしない。
設計書が「いまどうなっているか」を書き、ADR が「なぜそう決めたか」を書く。

ADR は書き換えない。決定を変えるときは、新しい ADR を書き、古い ADR の状態を「置き換えられた」にする。
現在の10本は `docs/_archive/adr/` にあり、体系資料の「5. 判断事項」から参照される。

### 4.8 Markdown の書き方

見出しは H1 を1つ（文書名）置き、以下は H2（節）と H3（項）までとする。H4 を使わない。

並ぶ項目が3つ以上あり、各項目が同じ型の情報を持つときは、箇条書きではなく表にする。
構成・依存の向き・データの流れは Mermaid で描く。図は文章の代わりにせず、
図が示す配置と、文章が示す理由を分けて書く。

文書間の参照は、文書番号で書く（「61 が持つ」）。ファイルへのリンクは相対パスで書く。
まだ作っていない文書には、リンクを張らず「（未着手）」と書く。

本文は常体で書き、`~/.claude/skills/japanese-tech-writing/SKILL.md` の規範に従う。
装飾のための太字と絵文字を使わない。

### 4.9 重複の避け方

同じ内容を2か所に書かない。片方を直して片方を直し忘れると、どちらが正しいか分からなくなる。

数値（しきい値、上限、ポート、版数）は、設定ファイルとコードが持つ。
文書がそれを書き写すときは、どのファイルの値かを併記する。併記が無い数値は、
設定を変えた時点で古くなり、それを検出する手段が無い。

### 4.10 検査

自動で確かめるのはリンクの実在だけである。`pnpm docs:links`（`scripts/docs-links.mjs`）が
`docs/**/*.md` の相対リンクを読み、先にファイルが無ければ失敗する。`pnpm verify` の先頭と、
CI の `docs` ジョブで走る。

体系整備で `docs/_archive/` へ移設したとき、13ファイルのパス参照を書き換えたが、
その食い違いを指摘した検査は1つも無かった。この検査はその種類の欠落を止める。

確かめないものは次のとおりである。実装と食い違う記述、書き写した数値の陳腐化、
見出しを指す `#...` の実在、外部 URL の生死は、いずれも人が読んで見つける
（`../backlog/12_文書と実装の乖離.md`）。リンクが繋がっていることは、
書いてある内容が正しいことを意味しない。

### 4.11 `_archive/` を検査対象に含める理由

リンクの検査は `_archive/` も対象にする。凍結の取り決め（`../README.md` §5）は
「書かれた時点の内容のまま残す」ことであって、参照先が動かないことではない。

実際、併存リポジトリの移動に伴って runbook 001・004 のパスを書き換えている。
凍結した資料でも、指す先が消えれば手順は辿れなくなる。除外すれば、
その22本で起きたリンク切れに誰も気付かない。

含めることの代償は、`_archive/` を直す必要が生じうることである。
そのときも直すのはリンクの先だけで、判断・手順・数値は書き換えない。
