## 1. 目的

この文書は、まだ起きていないが起きるとプロジェクトを止める事象を並べ、
それぞれをどう検知し、どう防ぎ、起きたら何をするかを1か所に置く。

既に起きている問題は対象外であり、72 が持つ。
モデルが誤り続ける事態そのものは 24 が、脆弱性の扱いは 54 が、失った状態の復旧は 43 が持つ。
この登録簿は、それらの文書が担当する事象を含めた全体の一覧として、どこを見ればよいかを示す。

## 2. 適用範囲

対象は、本リポジトリの実装・データ・モデル・文書・依存に関わる事象である。

組織上のリスク（要員離脱、予算、契約、納期）は対象外とする。
単独の学習プロジェクトであり、予算も納期も契約も存在しない。実在しない体制を前提にした欄を置かない。

## 3. 前提

評価は3段階（高・中・低）の定性値で行う。発生頻度を測った記録が無く、確率を数値で書く根拠が無い。

検知方法の欄には、実際に走っている検査だけを書く。
検査が無い項目には「検知手段なし」と書き、人が気付く以外に手段が無いことを明示する。

## 4. 定義

### 4.1 評価の基準

| 値 | 発生確率 | 影響度 |
| --- | --- | --- |
| 高 | 現在の作業を続けると起きる | 作業が止まる。または誤った結果を外へ出す |
| 中 | 特定の操作や更新を行うと起きうる | 手戻りが出るが、やり直せる |
| 低 | 現在の構成では起きにくい | 局所的に直せる |

優先度は、発生確率と影響度がともに高いものを A、いずれかが高いものを B、それ以外を C とする。

### 4.3 優先度 A の3件

R-14・R-16・R-18 は、いずれも「気付かないまま進む」形の失敗である。

R-18 はすでに一度起きている。`services/tests` の133件と `web:contract` が落ちたまま CI が緑であり続けた。
走っていない検証は、走っていないという理由では表に出てこない。`pnpm ci:parity` はこの再発を防ぐために足した。

R-14 と R-16 は、起きた時点では誰も困らず、後から外部の条件で問題になる。
どちらも毎回の自動検査を持ち、人の注意力に依存しない形になっている。

### 4.4 検知の範囲が限られる3件

R-01・R-02・R-19 は検査を持つ。ただし、どれも見ている範囲が限られる。R-11 は警報を持つが、
監視スタックを止めている間は誰も見ていない。

R-01 と R-02 は `pnpm upstream:status` が見る。見るのは「fork 元の `master` が、
最後に記録した commit から進んだか」だけである。進んだことは分かるが、
その更新が自作分と競合するかどうかは、差分を読まなければ分からない（03 §4.15）。

R-11 は警報の定義を持つ。ただし Prometheus と Alertmanager は `pnpm ops:up` で起動する構成であり、
起動していない間は残量が減っても誰も気付かない。44 が挙げる実測値も揃っていない。

R-19 は `pnpm docs:links` がリンクの実在だけを見る。リンクが繋がったまま記述が実装と食い違う場合と、
書き写した数値が古くなった場合は、いずれも検査を通る。この範囲は読む以外に確かめる手段が無い（64 §4.10）。

### 4.5 更新の仕方

リスクを足すときは、検知方法を先に決める。
検知方法が「人が気付く」しか書けないものは、そう書く。予防策だけを書いて検知を空にしない。

Status は、監視中・対策済み・未対応・顕在化・終結の5つを使う。
顕在化したリスクは、この登録簿から消さず、Status を変えたうえで 72 へ課題として起こす。

## 5. 判断事項

| 判断 | 理由 |
| --- | --- |
| 確率を定性の3段階にした | 発生頻度の記録が無く、数値の根拠が無い |
| 組織上のリスクを対象外にした | 予算・納期・契約・要員が存在しない |
| 検知手段の無いものを空欄にせず明記した | 空欄は「検討していない」と「手段が無い」を区別できない |

## 6. 未決事項

* R-11 の残量監視。警報はあるが、監視スタックを常時動かす運用になっていない
* R-12・R-13 の予防策。バックアップ手順そのものが無い（BL-11）
* 定期的な見直しの間隔。単独作業のため、見直しの場が無い
