## 1. 目的

この表は、既に起きていて解決を要する問題を記録する。

まだ起きていない事象は 71 が持つ。着手しないと決めたものは `../backlog/` が持つ。
この表が扱うのは、解決すると決めたが、まだ解決していないものである。

## 2. 適用範囲

対象は3種類ある。実装の不具合、文書と実装の食い違い、決まっていないために作業が進まない事項である。

改善の要望は対象外とする。動いているものをよりよくする提案は `../backlog/` へ置く。
この区別は、放置したときに何が起きるかで決める。放置すると誤った結果や誤った記述が残るものが課題である。

## 3. 前提

不具合の記録は、本文書の作成時点で0件である。
`pnpm verify` と CI の5ジョブはすべて通っており、既知の失敗するテストは無い。

ここに並ぶ課題は、各文書の「6. 未決事項」と `../backlog/` から、解決を要すると判断したものである。

## 4. 定義

### 4.1 backlog との役割分担

`../backlog/00_未解決ストーリー一覧.md` は §5 で、この表ができるまで不具合もそちらへ書くほかないと述べている。
本文書ができたことで、次のように分ける。

| 置き場所 | 置くもの | 判断の基準 |
| --- | --- | --- |
| `../backlog/` | 着手しないと決めたもの | 着手の条件が満たされるまで何もしない |
| 72（この表） | 解決すると決めたもの | 次に手を付けるときの対象になる |

同じ事柄が両方に現れることがある。backlog のストーリーを解決すると決めた時点で、
この表へ課題として起こし、backlog 側の状態を「着手」にする。内容は写さず、ID で参照する。

### 4.2 深刻度

| 深刻度 | 意味 | 扱い |
| --- | --- | --- |
| Critical | 誤った結果を外へ出す。または作業が進まない | 他の作業を止めて対応する |
| High | 判断を誤らせる。放置すると影響が広がる | 次の作業単位で対応する |
| Medium | 手戻りが出るが、回避できる | 関連する作業のついでに対応する |
| Low | 気付いた人が直せる | 期限を置かない |

33 §4.1 の #3・#4 は、Critical が0件であること、High の扱いが決まっていることをリリースの条件にしている。
この表の Critical と High は、その判定の入力になる。

### 4.4 状態

| 状態 | 意味 |
| --- | --- |
| 未着手 | 起票したが、手を付けていない |
| 着手 | 対応中 |
| 判断待ち | 自分では決められず、他者の判断を待っている |
| 解決 | 対応が終わり、結果を確認した |
| 取り下げ | 課題ではないと判断した。理由を残す |

解決した課題を表から消さない。同じ問題が再び起きたときに、前回何をしたかを辿れなくなる。

### 4.5 起票の仕方

課題を足すときは、深刻度と対応の内容を同時に書く。
「調査する」だけを対応欄に書かない。何が分かれば解決なのかが決まっていないものは、
未決事項として関連文書の §6 に残し、解決すると決めた時点でここへ移す。

Owner は書かない。全件が同一人物であり、欄を作ると担当が分かれているように読める（73 §4.2）。

## 5. 判断事項

| 判断 | 理由 |
| --- | --- |
| backlog と分ける基準を「解決すると決めたか」に置いた | 種別（実装・文書・確認）で分けると、同じ種別が両方に現れて判断できない |
| Owner 欄を持たない | 単独作業であり、実在しない分担を書かないため |
| 解決した課題を残す | 再発時に前回の対応を辿るため |

## 6. 未決事項

* 課題の起票から解決までの期限。単独作業のため、期限を置く相手がいない
* 不具合が出たときの記録の粒度。まだ1件も起票していない
* 33 のリリース判定と、この表の状態をどう突き合わせるか（手順が無い）
