## 1. 目的

この文書は、主要な作業について誰が実行し、誰が結果に責任を持ち、誰に相談し、誰へ知らせるかを定める。

本プロジェクトの実態は単独作業であり、現時点で全役割が同一人物に集まる。
この文書は、その事実を記録したうえで、複数人になったときに何をどう分けるかを先に決めておく。

## 2. 適用範囲

対象は、70 が分解した作業と、33 が定めるリリースの判定である。

対象外は、実在しない組織上の役割である。承認者・運用担当・セキュリティ担当といった肩書を、
担う人がいない状態で置かない。置くと、承認が行われているかのような記述が残る。

## 3. 前提

本リポジトリの作業者は1名である。git の履歴、全文書の Author 欄、全文書の Reviewer 欄が
それを示している（Reviewer は全文書で「なし」）。

## 4. 定義

### 4.1 記号

| 記号 | 意味 |
| --- | --- |
| R | 実行する |
| A | 結果に責任を持つ。1つの作業に1人だけ置く |
| C | 実行前に相談する |
| I | 実行後に知らせる |

### 4.2 現状

| 作業 | 開発者（単独） | 備考 |
| --- | --- | --- |
| 要件・非機能要件の決定 | R / A | 相談相手はいない |
| 方式・アーキテクチャの決定 | R / A | 判断は ADR に残す |
| 実装 | R / A | |
| レビュー | R / A | 自分の変更を自分で見る（62） |
| テストの作成と実行 | R / A | 合否は `pnpm verify` と CI が出す |
| Dataset の採否 | R / A | 判定は `pnpm ml:data check`（14） |
| モデルの昇格 | R / A | 判定は 23、操作は `pnpm ml:model promote` |
| リリースの判定 | R / A | 33 の確認項目 |
| 運用・障害対応 | R / A | 42 |
| セキュリティの判断 | R / A | 54・57 |
| 文書の作成と承認 | R / A | 承認の記録は残らない（64 §4.5） |

R と A が同一人物である状態は、レビューとリリース判定で効きが弱い。
自分が書いたものを自分で見る限り、見落としは見落としたまま通る。

この弱さを補っているのは人ではなく機械である。`pnpm verify` と CI の5ジョブ、
4つのゲート（`ci:parity`・`test:pyramid`・`eslint-baseline`・`web-boundaries`）は、
書いた人が誰であっても同じ判定を下す。人の承認が無い代わりに、機械の判定を必須にしてある。

### 4.3 機械が担っている判定

| 判定 | 担い手 | 人が覆せるか |
| --- | --- | --- |
| テストが通るか | `pnpm verify`、CI | 覆せない（CI が赤なら取り込まない） |
| 検証が CI から落ちていないか | `pnpm ci:parity` | `package.json` を直せば覆せる |
| テストが意図した層にあるか | `pnpm test:pyramid` | `test-pyramid.json` を直せば覆せる |
| lint の指摘が増えていないか | `pnpm web:lint:baseline` | baseline を更新すれば覆せる |
| 依存の向きが規約どおりか | `pnpm web:boundaries` | 設定を更新すれば覆せる |
| 秘密が混入していないか | `pnpm sec:scan` | 覆せない（検出条件に該当すれば落ちる） |
| 脆弱性とライセンス | `pnpm sec:gate` | 除外を書けば覆せる |

覆せる項目は、覆した記録が git に残る。設定ファイルの差分として現れるため、
なぜ緩めたかを後から問える。この「覆した記録が残る」ことが、単独作業での歯止めになっている。

### 4.4 複数人になったときの割り当て

以下は現在の体制ではない。人が増えたときに、この形から始めるという案である。

| 作業 | 開発者 | レビュア | 運用担当 | データ提供者 |
| --- | --- | --- | --- | --- |
| 実装 | R | C | I | |
| レビュー | I | R / A | | |
| Dataset の採否 | R | C | | A |
| モデルの昇格 | R | C | I | I |
| リリースの判定 | R | C | A | |
| 障害対応 | C | | R / A | I |
| 文書の更新 | R | C / A | I | |

この案で変える点は2つある。レビューの A を書いた本人から外すこと、
リリース判定の A を実装者ではなく運用側へ置くことである。
どちらも、作ることと出してよいと判断することを同じ人が兼ねない形にするためである。

適用するのは、作業者が2名以上になり、かつレビュアが実装内容を追える状態になったときとする。
人数だけ増えて内容を追えない状態で承認の欄を埋めると、承認は形式になる。

## 5. 判断事項

| 判断 | 理由 |
| --- | --- |
| 現状を「全役割が同一人物」と明記した | 実在しない体制を作らないため（プラン §15） |
| 人の承認の代わりに機械の判定を必須にした | 単独作業で第三者の確認が得られないため |
| 複数人向けの割り当てを案として分けた | 現状と混ざると、いま承認が行われているように読める |

* データ提供者に相当する役割の実体。現在の Dataset は自分で生成している（21）
