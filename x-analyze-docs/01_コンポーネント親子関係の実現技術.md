以下、ファイルパスは `src/app` からの相対で書く。

## 調査範囲と数え方

出現数は文字列検索の件数であり、`.spec.ts` を含む。したがって実装で使われている箇所の数とは厳密には一致しない。種類の網羅を目的とし、件数は規模の目安として読む。

コードは大きく 2 つの区画に分かれる。`webapp-common/` は ClearML 由来の共通実装で、入出力の 9 割以上がここにある。`features/` は環境ごとの実装で、共通側を差し替えるか継承するために置かれている。このうち `features/data-catalog/` と `features/quality-pipeline/` は本プロジェクトで追加された画面で、後述するとおり使っている仕組みが共通側より少ない。

## 入力と出力

signal ベースの API が主流で、デコレータ形式が残っている。`input()` が 914 件に対し `@Input()` が 153 件、`output()` が 385 件に対し `@Output()` が 65 件である。両形式が同一ファイル内に同居する例もある（`shared/ui-components/data/table/table.component.ts` は `input()` と `output()` を使いながら、import には `Output` と `EventEmitter` が残っている）。

必須入力は `input.required` が 19 件ある。値の変換は `booleanAttribute` を使った 2 件（`shared/ui-components/overlay/dialog-template/dialog-template.component.ts`）だけで、`alias` 指定は見当たらない。

デコレータ形式が残っている箇所の一部は、setter で受け取って副作用を実行している（`experiments/dumb/experiment-log-info/experiment-log-info.component.ts` の `set logs()` など）。`ngOnChanges` を実装しているファイルは 7 件にとどまる。

双方向束縛は `model()` が 10 件ある。`[(customColumnMode)]`（`experiments/dumb/experiment-header/experiment-header.component.html`）のように、`ngModel` を介さず子のシグナルを直接双方向で結ぶ使い方である。

## コンテンツ投影

`<ng-content>` は 67 件で、うち 41 件が `select` つきである。セレクタの書き方は 3 通りある。

属性セレクタが最も多い（`select="[footer]"`、`select="[header-content]"`、`select="[extended]"`）。クラスセレクタ（`select=".linkToOrigin"`、`select=".uptime"`）と、要素セレクタ（`select="mat-checkbox"`、`select="sm-status-icon-label"`）も使われている。要素セレクタは `shared/ui-components/data/table-card/table-card.component.html` に集まっており、投影される側のコンポーネント名を子側が知っている形になっている。

投影先が空のときの代替表示（fallback content）は使われていない。`<ng-content select="[footer]">` と閉じタグの間に改行が入っている箇所はあるが、中身は空白だけである。

`ngProjectAs` は使われていない。

## テンプレートを渡す

投影では足りない場面、つまり子が描画のたびに文脈（行データや添字）を差し込みたい場面では、テンプレート自体を渡している。この形が本プロジェクトでは 4 通りに分かれる。

### 入力として `TemplateRef` を渡す

親が `<ng-template>` を定義し、その参照を通常の入力として子に渡す。子は `*ngTemplateOutlet` で文脈つきで描画する。

```html
<!-- experiments/experiments.component.html -->
<sm-experiments-table [contextMenuTemplate]="contextMenuExtendedTemplate">
```

```html
<!-- experiments/dumb/experiments-table/experiments-table.component.html -->
<ng-container *ngTemplateOutlet="contextMenuTemplate(); context: {$implicit: contextExperiment()}"></ng-container>
```

受け側は文脈の型まで宣言している（`contextMenuTemplate = input<TemplateRef<{...}>>()`）。`tsconfig.json` で `strictTemplates` が有効なので、この型宣言は親側のテンプレート変数にも効く。

同じ形が `login/login/login.component.ts` の `errorTemplate`、`shared/components/virtual-grid/virtual-grid.component.ts` の `cardTemplate`、`nested-project-view/` の `cardContentTemplateRef` などにある。

### 構造ディレクティブを名前付きスロットにする

`experiments-compare/dumbs/` には、中身が空のディレクティブが 3 つ置かれている。

```typescript
// experiments-compare/dumbs/compare-card-body.directive.ts
@Directive({selector: '[compareCardBody]'})
export class CompareCardBodyDirective {}
```

これを構造ディレクティブとして書くと `<ng-template>` になり、`let experiment` の記法で文脈を受け取れる。

```html
<!-- experiments-compare/containers/experiment-compare-params/experiment-compare-params.component.html -->
<div class="tree-card-body" *compareCardBody="let experiment; let i = index">
```

子は `@ContentChild` にディレクティブを指定し、`read: TemplateRef` で実体をテンプレートとして取り出す。

```typescript
// experiments-compare/dumbs/compare-card-list/compare-card-list.component.ts
@ContentChild(CompareCardBodyDirective, { read: TemplateRef }) bodyTemplate;
```

`<ng-content select>` と違って各スロットに `$implicit` と `index` を渡せる点が、この書き方を選ぶ理由になっている。

### PrimeNG の `pTemplate` を種別で仕分ける

表コンポーネントは、投影された複数のテンプレートを種別ごとに仕分けている。親は `pTemplate` 属性で用途を名乗る。

```html
<!-- experiments/dumb/experiments-table/experiments-table.component.html -->
<ng-template let-col let-experiment="rowData" pTemplate="body">
<ng-template let-experiment="rowData" let-selected="selected" pTemplate="card">
```

子は `contentChildren(PrimeTemplate)` で全部を受け取り、`ngAfterContentInit` で `getType()` の値によって専用のフィールドへ振り分ける（`shared/ui-components/data/table/table.component.ts:334-363`）。振り分け先は body、card、sort-filter、checkbox、cardFilter、footer、rowexpansion の 7 種類で、どれにも当たらないものは body として扱う。

`table.component.ts` はこの 7 種類それぞれについて `TemplateRef<{...}>` の文脈型を宣言している。表を使う側は、`pTemplate="body"` の `<ng-template>` の中で `let-col`、`let-experiment="rowData"` を型つきで受け取ることになる。

### `templateAlias` ディレクティブ

`shared/ui-components/directives/template-alias.directive.ts` は、テンプレートに文字列の別名を付けるディレクティブである。自身の `TemplateRef` をコンストラクタで受け取りつつ、内側の `<ng-template>` も `@ContentChild(TemplateRef)` で保持する二段構えになっている。

## 子を取得する

### `viewChild`

自分のテンプレート内の子を取得して命令的に操作する形が 50 件（デコレータ形式が 31 件）ある。取得対象は `ElementRef`（DOM 寸法の計測やグラフ描画の下地）と、子コンポーネントのインスタンス（`viewChild(ExperimentsTableComponent)`、`viewChild(ExperimentGraphsComponent)` など）に分かれる。`viewChild.required` が 7 件ある。

`experiments/shared/components/experiment-menu/experiment-menu.component.ts` は、自テンプレート内の `<ng-template>` を `viewChild.required` で取り出し、確認ダイアログへ渡している。テンプレートの受け渡しが親子方向だけでなく、ダイアログへの引数としても使われている例である。

### テンプレート参照変数

親のテンプレート内で、子コンポーネントの状態を直接読む形も使われている。

```html
<!-- experiments/dumb/experiment-details/experiment-details.component.html -->
<sm-editable-section #experimentDescriptionSection ...>
<textarea [readOnly]="!experimentDescriptionSection.inEditMode()">
```

同じ子を `viewChild` でも取得している場合がある（同ファイルの `.ts` に `experimentDescriptionSection = viewChild<EditableSectionComponent>(...)`）。テンプレートからは参照変数で、クラスからは `viewChild` で、同じ子に触れている。

### `contentChild`

投影された内容を子側から取得する形は 8 件と少ない。`shared/components/multi-line-tooltip/multi-line-tooltip.component.ts` は `contentChild('TooltipTrigger', {read: TemplateRef})` で、`shared/project-dialog/project-settings/project-settings-dialog.component.ts` は `contentChildren(MatTab)` で、投影された Material のタブを受け取っている。

`@ContentChildren()`（デコレータ形式の複数取得）は使われていない。

### `exportAs` によるディレクティブの公開

`shared/ui-components/directives/hesitate.directive.ts` は `exportAs: 'hesitate'` を宣言している。使う側はテンプレート参照変数でディレクティブの実体を受け取り、同じテンプレート内の別の要素からその状態を読み書きする。

```html
<!-- shared/components/refresh-button/refresh-button.component.html -->
<div (smHesitate)="hesitateMenu.hesitateStatus && showMenu.set(false)">
...
<div #hesitateMenu="hesitate" (smHesitate)="showMenu.set(true); hesitateMenu.hesitateStatus=true">
```

親子ではなく、同一テンプレート上の離れた要素どうしを結ぶ経路である。3 つのテンプレートで使われている。

## 継承によるコンポーネント再利用

`extends` は 151 件ある。このうち親子関係の組み立てに直接関わるのは、`features/` 側が `webapp-common/` 側のコンポーネントを継承して差し替える形である。

```typescript
// features/experiments/containers/experiment-menu-extended/experiment-menu-extended.component.ts
@Component({
  selector: 'sm-experiment-menu-extended',
  templateUrl: '../../../../webapp-common/experiments/shared/components/experiment-menu/experiment-menu.component.html',
  styleUrls: ['../../../../webapp-common/.../experiment-menu.component.scss'],
  imports: [...]
})
export class ExperimentMenuExtendedComponent extends ExperimentMenuComponent {
  contextMenu = computed(() => this as ExperimentMenuComponent);
}
```

クラスを継承したうえで、テンプレートとスタイルは相対パスで共通側のファイルを直接指している。`imports` は継承されないので、共通側テンプレートが使う依存を派生側で列挙し直している。

継承元の共通側テンプレートには `<ng-content select="[extended]">` が置かれており、追加項目の投影口になっている（`experiments/shared/components/experiment-menu/experiment-menu.component.html:136`）。ただし本リポジトリで確認できる範囲では、`[extended]` 属性を付けて何かを投影している箇所はない。投影口だけが用意されている状態である。

同じ形が `ModelMenuExtendedComponent`、`ProjectCardMenuExtendedComponent` にもある。3 つとも `contextMenu` という名前で自分自身を返すメンバを持っている（`computed(() => this as ExperimentMenuComponent)`、`signal(this)`、`get contextMenu() { return this; }`）。これは、派生コンポーネントを `viewChild` で取得した親が、基底クラスの API に型のついた形で到達するための入口である。

```typescript
// experiments/experiments.component.ts:240-241
contextMenuExtended = viewChild.required(ExperimentMenuExtendedComponent);
public contextMenu = computed(() => this.contextMenuExtended().contextMenu());
```

この参照は階層をまたいで連なることがある。`models/models.component.ts:428` は、自分の `viewChild` である表コンポーネントを経由し、その表が持つ `viewChild`（`contextMenuExtended`）をたどり、さらに `contextMenu()` で基底型に落としてメソッドを呼ぶ。`this.table.contextMenuExtended().contextMenu().archiveClicked()` という 3 段の到達である。

継承のもう一つの用途は、抽象基底クラスによる実装共有である。`export abstract class` は 15 件あり、`BaseEntityPageComponent`、`BaseTableView`、`BaseContextMenuComponent`、`PlotlyGraphBaseComponent` などが、画面の骨格や表の選択処理を持っている。これらは親子関係ではなく実装の継承であり、テンプレート上の階層とは独立である。

## DI を使った結び付き

### コンポーネント単位の `providers`

親コンポーネントがサービスを `providers` に置き、子孫がそれを注入して同じ実体を共有する形が使われている。テストとルート定義を除くと 24 件ある。

```typescript
// experiments/containers/experiment-output-log/experiment-output-log.component.ts
providers: [ExperimentOutputLogStore],
```

供給されているものは 3 種類ある。`@ngrx/signals` の `signalStore`（`ExperimentOutputLogStore`、`selectTaskStore`、`ProjectSettingsStore` の 3 つ）、画面固有のサービス（`DagManagerUnsortedService` を 2 画面が供給し、同じコンポーネントが注入している）、そして Material の設定トークン（`MAT_TOOLTIP_DEFAULT_OPTIONS` を `layout/side-nav/side-nav.component.ts` が上書きするなど）である。

`signalStore` は 3 件だけで、状態管理の主体は依然として NgRx Store である。

### ホスト要素上のディレクティブ間注入

同じ要素に付いた別のディレクティブを注入する形が 2 件ある。

```typescript
// shared/ui-components/indicators/tooltip/show-tooltip-if-ellipsis.directive.ts
private matTooltip = inject(TooltipDirective);
```

`smShowTooltipIfEllipsis` は、文字列が省略記号で切れているときだけツールチップを有効にするために、同じ要素の `TooltipDirective` の `disabled` と `message` を書き換えている。`hostDirectives`（Angular のディレクティブ合成 API）は使われておらず、両方のディレクティブを使う側が要素に並べて書く形になっている。

### 祖先のフォームディレクティブを注入

ストレージ認証情報の入力コンポーネント 3 つは、親のフォームを `inject(FormGroupDirective)` で受け取り、そこに自分のコントロール群を組み込んでいる（`settings/storage-credentials/*/`）。入力で `FormGroup` を渡す代わりに DI で祖先をたどる形である。

### `ControlValueAccessor`

`ControlValueAccessor` を実装するコンポーネントが 11 件ある。いずれも `NG_VALUE_ACCESSOR` に `forwardRef` で自分を登録する定型である。親からは `[(ngModel)]` または `formControlName` で値を渡し、子から値の変更が返る。`shared/ui-components/inputs/duration-input/duration-input.base.ts` のように、基底クラス側で実装して派生が継承する形もある。

`@Host()`、`@Self()`、`@SkipSelf()` は使われていない。`@Optional()` は 15 件あるが、いずれも親子関係の解決ではなくトークンの省略可否である。

## 描画位置を動かす仕組み

### `createComponent` による手続き的な生成

`shared/services/dom-service.service.ts` が `createComponent` でコンポーネントを生成し、`ApplicationRef.attachView` でビューツリーに接続したうえで、DOM ノードを `document.body` に追加する。入力値は `Object.assign(componentRef.instance, extraData)` で流し込む形である。

この仕組みの利用者は `shared/directive/append-component-on-top-element.directive.ts` である。ホスト要素の座標を `getBoundingClientRect()` で測り、生成したコンポーネントの `top` と `left` をその中心に合わせ、生成側で発生したクリックやマウス移動をホスト要素へ転送している。親子関係を持たない要素どうしを、座標とイベント転送で結び付けている。

### CDK Portal

`shared/portal/portal.component.ts` は、投影された内容を `*cdkPortal` で保持し、`DomPortalOutlet` を使って `outletId` で指定した id を持つ DOM 要素へ描画し直す。

```html
<!-- experiments-compare/containers/experiment-compare-details/experiment-compare-details.component.html -->
<sm-portal outletId="searchDiff"> ... </sm-portal>
```

受け口は比較画面のヘッダにある空の `<div id="searchDiff">`（`experiments-compare/dumbs/experiment-compare-header/experiment-compare-header.component.html`）である。比較画面の本体が持つ検索 UI を、テンプレート上の階層を変えずにヘッダの位置へ出すために使われている。`afterNextRender` で id 要素を取得する実装なので、受け口の描画が先である必要がある。

`CdkPortalOutlet` は別の用途で 1 箇所使われている。`shared/project-dialog/project-settings/project-settings-dialog.component.ts` は、投影された `MatTab` を `contentChildren` で集め、その `content`（`TemplatePortal`）を `[cdkPortalOutlet]` で描画している。タブの中身を投影で受け取り、描画位置はダイアログ側が決める形である。

### `NgComponentOutlet`

`shared/components/dropdown-object-select/dropdown-object-select.component.html` の 1 箇所だけで、入力で受け取ったコンポーネント型を `*ngComponentOutlet` で描画し、`inputs:` で値を渡している。どのコンポーネントを描画するかを親が決める仕組みだが、使用箇所はこの 1 件である。

## ルーティングによる親子

`<router-outlet>` は 15 箇所にあり、うち 13 箇所は画面本体の中に置かれた入れ子の outlet である（`experiments/experiments.component.html`、`models/models.component.html` など）。一覧画面が子ルートとして詳細パネルを描画する構造になっている。名前付き outlet は使われていない。

ルート定義から子へ渡るものは 3 種類ある。`data` による静的な値（`{search: true}`、`{entityType: ...}`、`{staticBreadcrumb}` など）、`providers` による DI スコープ（`app.routes.ts:89` の `experimentsProviders` など。NgRx の feature state と effects をルート単位で登録している）、`resolve`（`features/workers-and-queues/workers-and-queues.routes.ts` の 1 箇所のみ）である。

`withComponentInputBinding()` は有効化されていない（`app.config.ts`）。したがってルートパラメータが入力に自動束縛されることはなく、受け取りは 2 通りに分かれる。`ngxtension` の `injectParams` / `injectQueryParams` / `injectRouteData`（合わせて 7 ファイル）と、`ActivatedRoute` を直接読む形、あるいは NgRx の router state セレクタである。

`app.config.ts` では `RouteReuseStrategy` に `CustomReuseStrategy` が差し替えられている。ルート遷移時に子コンポーネントが破棄されるか再利用されるかは、この実装に依存する。

## ダイアログ

`MatDialog.open` が 48 箇所、`afterClosed()` が 70 箇所ある。引数は `data` で渡し、`MAT_DIALOG_DATA` を注入して受け取り（70 箇所）、結果は `afterClosed()` の購読で返す。ダイアログはテンプレート上の親子関係を持たないため、この経路が実質的な入出力になっている。

呼び出し元はコンポーネントだけではない。`reports/reports.effects.ts` のように NgRx の Effects からダイアログを開き、その戻り値でアクションを分岐している箇所がある。

## 親子関係を経由しない連携

### NgRx Store

コンポーネント間の値の受け渡しの多くは Store を経由している。`layout/side-nav/side-nav.component.ts` には入力も出力も 1 件もなく、必要な状態はすべて `store.selectSignal(...)` で読んでいる。ヘッダのタブ構成のように、画面側が `HeaderMenuService` 経由で `headerActions.setTabs` を dispatch し、ヘッダ側がそれを select する形もある。親子の線を引かずに結ぶ経路として使われている。

購読の書き方は 3 通りが混在している。テンプレートの `| ngrxPush` パイプ、`store.selectSignal()`、`toSignal(store.select(...))` である。

### ビルド時のファイル差し替え

どの実装が子として使われるかを、ビルド時に切り替える仕組みがある。二段構えである。

一段目は `tsconfig.json` のパスエイリアスで、`~/*` が `src/app/*` を、`@common/*` が `src/app/webapp-common/*` を指す。共通側のコードが `@features/...` を import している箇所が 169 件あり、共通実装が環境別実装に依存する向きになっている。たとえば `webapp-common/workers-and-queues/dumb/queues-table/queues-table.component.ts` は `@features/workers-and-queues/dumb/queues-menu/queues-menu.component` を import する。

二段目は `angular.json` の `fileReplacements` で、本番ビルド時に `src/app/build-specifics/index.ts` を `index.prod.ts` に差し替える。

この 2 つを合わせると、共通コンポーネントが使う子コンポーネントの実体を、共通側のコードを変えずに切り替えられる。前述の「継承による差し替え」（`*-extended` 系）は、この仕組みの上で成り立っている。

## 使われていない仕組み

以下は Angular が提供しているが、本リポジトリでは使用が確認できなかった。既存コードを読むうえで、これらを探す必要はない。

- `hostDirectives`（ディレクティブ合成 API）
- `ngProjectAs`
- `@ContentChildren()`（デコレータ形式。関数形式の `contentChildren()` は 2 件ある）
- `<ng-content>` の代替表示（fallback content）
- 名前付き `<router-outlet>`
- `withComponentInputBinding()`
- `TemplatePortal` / `ComponentPortal` を直接構築する形（`CdkPortal` と `CdkPortalOutlet` は使用あり）
- `@Host()` / `@Self()` / `@SkipSelf()`

## 本プロジェクトで追加された画面について

`features/data-catalog/` と `features/quality-pipeline/` は、上記のうち入力・出力とルーティングしか使っていない。container が `store.selectSignal()` で状態を読んで子へ渡し、子の `output()` を action に変換する形で統一されている（`features/data-catalog/containers/data-catalog-page/data-catalog-page.component.ts`）。テンプレートの受け渡しも投影も継承もコンポーネント単位の `providers` も使われていない。

共通側（`webapp-common/`）の複雑さは ClearML 由来のものであり、本プロジェクトで追加された画面の書き方とは分けて読む必要がある。
