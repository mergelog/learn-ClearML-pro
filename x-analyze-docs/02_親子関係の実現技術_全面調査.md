### 用語

**投影（content projection）** … 親が書いたタグの中身を、子コンポーネントが自分のテンプレートの好きな位置に埋め込んで描画する仕組み。子は中身を知らないまま、置き場所だけを決める。

**`TemplateRef`** … `<ng-template>` として書いた「まだ描画していないテンプレート」への参照。値として受け渡しでき、受け取った側が任意の回数、任意の文脈（行データなど）を差し込んで描画できる。

**DI（依存性注入）** … クラスが必要とする相手を自分で作らず、Angular の注入器から受け取る仕組み。注入器はコンポーネントの階層に沿って親子関係を持つので、親が登録した実体を子孫が受け取れる。

**`ControlValueAccessor`** … 自作コンポーネントを Angular のフォーム部品として扱えるようにする取り決め。実装すると `[(ngModel)]` や `formControlName` で値をやり取りできる。

## 調査範囲と数え方

対象は `src/app` 配下の `.ts` 1500 件、`.html` 321 件である。この中には `webapp-common/clearml-applications/report-widgets/` という別のアプリケーション（`angular.json` 上の `report-widgets` プロジェクト）も含まれる。

出現数は文字列検索の件数で、`.spec.ts` は除外した。したがって実装で使われている箇所の数に近いが、複数行にまたがる宣言などで誤差が出る。種類の網羅を目的とし、件数は規模の目安として読む。

コードは大きく 2 つの区画に分かれる。`webapp-common/` は ClearML 由来の共通実装で 784 ファイル、`features/` は環境ごとの実装で 71 ファイルである。連携の仕組みのほとんどは `webapp-common/` 側にある。`business-logic/` の 608 ファイルは API の型定義とサービスで、コンポーネントを含まない。

## 前提：全コンポーネントが standalone で、大半が OnPush

`@NgModule` は `webapp-common/angular-notifier/src/notifier.module.ts` の 1 件だけで、これは取り込んだ外部ライブラリの名残である。`standalone: false` は 0 件で、339 個のコンポーネントはすべて standalone として書かれている。親が子を使うには、親の `imports` 配列に子のクラスを列挙する。これが 1 番目の仕組みであり、以降のすべての土台になる。

`ChangeDetectionStrategy.OnPush` は 229 件で、全コンポーネントの約 3 分の 2 にあたる。OnPush の子は、入力の参照が変わるか、自身のシグナルが変わるか、自身のテンプレートでイベントが起きたときに再描画される。親から子へ値を渡す書き方が signal 中心になっているのは、この設定と対になっている。

### 入力

signal ベースの `input()` が 906 件、デコレータ形式の `@Input()` が 145 件で、signal 形式が主流である。両形式が同一ファイル内に同居する例もある。必須入力の `input.required` は 18 件ある。

値の変換を指定しているのは `shared/ui-components/overlay/dialog-template/dialog-template.component.ts` の 2 件だけで、いずれも `transform: booleanAttribute` である。

別名の指定は 1 件ある。


デコレータ形式のうち 39 件は setter で受け取り、代入をきっかけに処理を走らせている。`@Input() set logs()`（`experiments/dumb/experiment-log-info/`）のような形である。一方 `ngOnChanges` の実装は 7 件にとどまる。入力の変化に反応する主な手段は、setter と `effect()` に移っている。

### 出力

`output()` が 379 件、`@Output()` が 65 件ある。

出力で値ではなく子自身を渡している箇所が 1 つある。


親（`notifier-container.component.ts`）はこれを受け取ってコンポーネント参照を保持し、後からその子のメソッドを直接呼ぶ。`viewChild` で取得できない動的なリストの要素に対して、子の側から登録させる形である。

### 双方向

`model()` は 10 件ある。テンプレート側の `[( )]` 記法は 34 件で、内訳は `[(ngModel)]` 26 件、`[(selectedIndex)]` 3 件、`[(customColumnMode)]` 2 件、`[(colorPicker)]` 2 件、`[(opened)]` 1 件である。このうち自作コンポーネントの `model()` に対する双方向束縛は `[(customColumnMode)]` の 2 件だけで、残りは Angular Material や外部ライブラリの入出力に対するものである。

## 内容の投影

`<ng-content>` は 39 ファイル・66 箇所にあり、うち 41 箇所が `select` つきである。セレクタの書き方は 3 通りある。

属性セレクタが最も多く、35 箇所・29 種類ある（`[footer]`、`[header-content]`、`[extended]`、`[empty-state]` など）。クラスセレクタは `.linkToOrigin` と `.uptime` の 2 件、要素セレクタは `mat-checkbox`、`sm-status-icon-label`、`sm-experiment-type-icon-label`、`smTooltipTrigger` の 4 件である。要素セレクタは、投影される側のコンポーネント名を子側が知っていることになるので、`shared/ui-components/data/table-card/` と `shared/components/multi-line-tooltip/` に限って使われている。

投影先が空のときの代替表示（fallback content）は使われていない。`ngProjectAs` も使われていない。

```html
  <mat-divider></mat-divider>
}
...
<div #refFixedOptions><ng-content select="[fixedOptions]"></ng-content></div>
```

## テンプレートを渡す

投影では足りない場面、つまり子が描画のたびに行データや添字を差し込みたい場面では、テンプレート自体を渡している。この形が 4 通りに分かれる。

### 入力として `TemplateRef` を渡す

親が `<ng-template>` を定義し、その参照を通常の入力として子に渡す。子は `*ngTemplateOutlet` で文脈つきで描画する。`TemplateRef` を型に持つ入力は 12 件ある。

```html
<!-- experiments/experiments.component.html -->
<sm-experiments-table [contextMenuTemplate]="contextMenuExtendedTemplate">
```

```html
<!-- experiments/dumb/experiments-table/experiments-table.component.html -->
<ng-container *ngTemplateOutlet="contextMenuTemplate(); context: {$implicit: contextExperiment()}"></ng-container>
```

受け側は文脈の型まで宣言している（`contextMenuTemplate = input<TemplateRef<{...}>>()`）。`tsconfig.json` で `strictTemplates` が有効なので、この型宣言は親側のテンプレート変数にも効く。

同じ形が `login/login/login.component.ts` の `errorTemplate`、`shared/components/virtual-grid/virtual-grid.component.ts` の `cardTemplate`、`nested-project-view/` の `cardContentTemplateRef` などにある。

### 無名の `<ng-template>` を投影して拾う

入力を経由せず、子タグの中に `<ng-template>` を 1 つだけ書いて渡す形もある。子は `contentChild(TemplateRef)` で受け取る。

```html
<!-- workers-and-queues/dumb/queue-info/queue-info.component.html:11-31 -->
<sm-simple-table-2 [cols]="experimentsCols" [rowsData]="selectedQueue()?.entries">
  <ng-template let-i="rowIndex" let-row="row">
    ...
  </ng-template>
</sm-simple-table-2>
```

```html
<!-- shared/ui-components/data/simple-table/simple-table.component.html -->
<ng-template [ngTemplateOutlet]="templateRef()"
             [ngTemplateOutletContext]="{$implicit: cols()[i], row: row, rowIndex: i}">
```

入力名を書かずに済む代わりに、渡せるテンプレートは 1 つに限られる。使っているのはこのコンポーネントだけである。

### 空ディレクティブを名前付きスロットにする

テンプレートを複数渡し、それぞれに別の文脈を与えたい場合は、中身が空のディレクティブを目印にしている。`experiments-compare/dumbs/` に 3 つ置かれている。

```typescript
// experiments-compare/dumbs/compare-card-body.directive.ts
@Directive({selector: '[compareCardBody]'})
export class CompareCardBodyDirective {}
```

これを構造ディレクティブとして書くと `<ng-template>` になり、`let experiment` の記法で文脈を受け取れる。

```html
<!-- experiments-compare/containers/experiment-compare-params/experiment-compare-params.component.html -->
<div class="tree-card-body" *compareCardBody="let experiment; let i = index">
```

子は `@ContentChild` にディレクティブを指定し、`read: TemplateRef` で実体をテンプレートとして取り出す。

```typescript
// experiments-compare/dumbs/compare-card-list/compare-card-list.component.ts:39-41
@ContentChild(CompareCardBodyDirective, { read: TemplateRef }) bodyTemplate;
@ContentChild(CompareCardExtraHeaderDirective, { read: TemplateRef }) extraHeaderTemplate;
@ContentChild(CompareCardHeaderDirective, { read: TemplateRef }) headerTemplate;
```

`<ng-content select>` と違って各スロットに `$implicit` と `index` を渡せる点が、この書き方を選ぶ理由になっている。

### PrimeNG の `pTemplate` を種別で仕分ける

表コンポーネントは、投影された複数のテンプレートを種別ごとに仕分けている。親は `pTemplate` 属性で用途を名乗る。

```html
<!-- experiments/dumb/experiments-table/experiments-table.component.html -->
<ng-template let-col let-experiment="rowData" pTemplate="body">
<ng-template let-experiment="rowData" let-selected="selected" pTemplate="card">
```

子は `contentChildren(PrimeTemplate)` で全部を受け取り、`ngAfterContentInit` で `getType()` の値によって専用のフィールドへ振り分ける（`shared/ui-components/data/table/table.component.ts`）。振り分け先は body、card、sort-filter、checkbox、cardFilter、footer、rowexpansion の 7 種類で、どれにも当たらないものは body として扱う。`table.component.ts` はこの 7 種類それぞれについて `TemplateRef<{...}>` の文脈型を宣言している。

なお `shared/ui-components/directives/template-alias.directive.ts` は、テンプレートに文字列の別名を付けるディレクティブで、自身の `TemplateRef` をコンストラクタで受け取りつつ、内側の `<ng-template>` も `@ContentChild(TemplateRef)` で保持する二段構えになっている。

## 子を取り出して操作する

### `viewChild`

自分のテンプレート内の子を取得して命令的に操作する形が 99 件（デコレータ形式が 31 件）ある。複数取得の `viewChildren` は 10 件、`@ViewChildren` は 3 件である。取得対象は `ElementRef`（DOM 寸法の計測やスクロール操作）と、子コンポーネントのインスタンスに分かれる。

`read:` を指定して取得する型を変える書き方が 3 件ある（`viewChild('inlineInput', { read: ElementRef })` など）。

`experiments/shared/components/experiment-menu/experiment-menu.component.ts:138-143` は、自テンプレート内の `<ng-template>` を `viewChild.required<TemplateRef<...>>` で 3 つ取り出し、確認ダイアログへ渡している。テンプレートの受け渡しが親子方向だけでなく、ダイアログへの引数としても使われている。

### `viewChild` の多段連鎖

取得した子の `viewChild` をさらにたどって、孫やひ孫の API を呼ぶ箇所がある。

```typescript
  if (this.editDesc() && this.info()?.experimentDescriptionSection()) {
```

最後の例は、孫コンポーネントの `EventEmitter` を親が新しいインスタンスで置き換えている。購読者ごと差し替えて右クリックメニューを無効化する書き方である。いずれも `effect()` の中に置かれ、`viewChild` がシグナルであることを利用して、子が現れた時点で実行される。

### `contentChild`

投影された内容を子側から取得する形は 8 件ある。内訳は、前節で挙げた `compare-card-list` の 3 件、`template-alias.directive.ts`、`simple-table.component.ts`、`multi-line-tooltip.component.ts` の `contentChild('TooltipTrigger', {read: TemplateRef})`、`table.component.ts` の `contentChildren(PrimeTemplate)`、`project-settings-dialog.component.ts` の `contentChildren(MatTab)` である。`@ContentChildren()`（デコレータ形式の複数取得）は使われていない。

親のテンプレート内で、子コンポーネントの状態を直接読む形も使われている。


自作で `exportAs` を宣言しているのは `shared/ui-components/directives/hesitate.directive.ts`（`exportAs: 'hesitate'`）の 1 つだけで、5 つのテンプレートで使われている。

## 継承による差し替え

`export class X extends Y` は 76 件、`override` は 154 件ある。このうち親子関係の組み立てに直接関わるのは、`features/` 側が `webapp-common/` 側のコンポーネントを継承して差し替える形である。`features/` 配下に 4 つある（`experiment-menu-extended`、`model-menu-extended`、`project-card-menu-extended`、`project-settings-extended`）。

```typescript
// features/models/containers/model-menu-extended/model-menu-extended.component.ts
@Component({
  selector: 'sm-model-menu-extended',
  templateUrl: '../../../../webapp-common/models/containers/model-menu/model-menu.component.html',
  styleUrls: ['../../../../webapp-common/models/containers/model-menu/model-menu.component.scss'],
  imports: [TagsMenuComponent, MatIconModule, ...]
})
export class ModelMenuExtendedComponent extends ModelMenuComponent {
  contextMenu = signal(this);
  override filterTagsByProject = input<boolean>(undefined, { alias: 'tagsFilterByProject' });
}
```

クラスを継承したうえで、テンプレートとスタイルは相対パスで共通側のファイルを直接指している。`imports` は継承されないので、共通側テンプレートが使う依存を派生側で列挙し直している。

継承元の共通側テンプレートには `<ng-content select="[extended]">` が置かれており、追加項目の投影口になっている（`experiments/shared/components/experiment-menu/experiment-menu.component.html`、`models/containers/model-menu/model-menu.component.html`）。ただし本リポジトリで確認できる範囲では、`[extended]` 属性を付けて何かを投影している箇所はない。投影口だけが用意されている状態である。

`experiment-menu-extended`、`model-menu-extended`、`project-card-menu-extended` の 3 つは、`contextMenu` という名前で自分自身を返すメンバを持っている（`computed(() => this as ExperimentMenuComponent)`、`signal(this)`、`get contextMenu() { return this; }`）。これは、派生コンポーネントを `viewChild` で取得した親が、基底クラスの API に型のついた形で到達するための入口である。

```typescript
// experiments/experiments.component.ts:240-241
contextMenuExtended = viewChild.required(ExperimentMenuExtendedComponent);
public contextMenu = computed(() => this.contextMenuExtended().contextMenu());
```

この `contextMenu` は、`ExperimentsComponent` を継承する画面側で `override` される。

```typescript
// pipelines-controller/controllers.component.ts:64
override contextMenu = viewChild.required<ExperimentMenuComponent>(PipelineControllerMenuComponent);
// dataset-version/open-dataset-versions/open-dataset-versions.component.ts:48
override contextMenu = viewChild.required(OpenDatasetVersionMenuComponent);
```

基底クラスが「文脈メニューへの参照」という名前だけを決め、実際にどのコンポーネントを指すかは派生クラスが `viewChild` で決める。基底クラス側のコードは `contextMenu()` を呼ぶだけで、画面ごとに違う子に到達する。

継承のもう一つの用途は、抽象基底クラスによる実装共有である。`export abstract class` は 15 件あり、`BaseEntityPageComponent`、`BaseTableView`、`BaseContextMenuComponent`、`PlotlyGraphBaseComponent` などが画面の骨格や表の選択処理を持っている。これらはテンプレート上の階層とは独立である。

## DI を使った結び付き

### コンポーネント単位の `providers`

親コンポーネントがサービスを `providers` に置き、子孫がそれを注入して同じ実体を共有する形が 25 ファイルにある。供給されているものは 4 種類に分かれる。

`@ngrx/signals` の `signalStore` が 3 件（`ExperimentOutputLogStore`、`selectTaskStore`、`ProjectSettingsStore`）。画面固有のサービスが 3 件（`DagManagerUnsortedService` を 2 画面が、`ThemeService` を `AppComponent` が、`NotifierTimerService` を通知 1 件ごとに供給している）。`NG_VALUE_ACCESSOR` の自己登録が 11 件。Material の設定トークン（`MAT_TOOLTIP_DEFAULT_OPTIONS`、`MAT_DATE_LOCALE`、`MAT_FORM_FIELD_DEFAULT_OPTIONS` など）が残りである。

`signalStore` が 3 件にとどまる一方、状態管理の主体は NgRx Store にある（`dispatch` 1013 件、`store.select` 903 件）。

`viewProviders` は使われていない。

### 同一要素上のディレクティブ間注入

同じ要素に付いた別のディレクティブを注入する形が 2 件ある。

```typescript
// shared/ui-components/indicators/tooltip/show-tooltip-if-ellipsis.directive.ts:11
private matTooltip = inject(TooltipDirective);
// shared/ui-components/directives/ellipsis-middle.directive.ts:15
constructor(private el: ElementRef, private matTooltip: TooltipDirective) {}
```

どちらも、文字列が省略記号で切れているときだけツールチップを有効にするために、同じ要素の `TooltipDirective` の `disabled` を書き換えている。`hostDirectives`（ディレクティブ合成 API）は使われておらず、両方のディレクティブを使う側が要素に並べて書く形になっている。

### 祖先のフォームディレクティブを注入

ストレージ認証情報の入力コンポーネント 3 つは、親のフォームを `inject(FormGroupDirective)` で受け取り、そこに自分のコントロール群を組み込んでいる（`settings/storage-credentials/{aws,azure,google}-storage-credentials/`）。入力で `FormGroup` を渡す代わりに DI で祖先をたどる形である。

### `ControlValueAccessor`

`NG_VALUE_ACCESSOR` に自分を登録しているコンポーネントが 11 ファイルある。いずれも `forwardRef` で自分を指す定型である。親からは `[(ngModel)]` または `formControlName` で値を渡し、子から値の変更が返る。`shared/ui-components/inputs/duration-input/duration-input.base.ts` や `shared/ui-components/template-forms-ui/templateFormSectionBase.ts` のように、基底クラス側で実装して派生が継承する形もある。

### バリデータディレクティブ

`NG_VALIDATORS` または `NG_ASYNC_VALIDATORS` に自分を登録するディレクティブが 15 ファイルある（`shared/ui-components/template-forms-ui/` に集中）。属性として要素に付けると、同じ要素のフォームコントロールに検証が加わる。値も参照も渡さず、DI の多重登録だけで振る舞いを足す経路である。

```typescript
// shared/ui-components/template-forms-ui/unique-name-validator.directive.ts:20
providers: [{provide: NG_VALIDATORS, useExisting: UniqueNameValidatorDirective, multi: true}],
```

`@Host()`、`@Self()`、`@SkipSelf()` は使われていない。`@Optional()` は 15 件あるが、いずれも親子関係の解決ではなくトークンの省略可否である。

### 制御フロー構文

### `@defer`

`@defer` が 10 箇所ある。条件は 2 種類で、`on viewport`（画面内に入ったら描画）が 3 箇所、`when <式>`（式が真になったら描画）が 7 箇所である。グラフ描画と、ログ・プレビューの切り替えに使われている。

```html
<!-- shared/experiment-graphs/experiment-graphs.component.html:122 -->
@defer (on viewport) {
```

### 自作の構造ディレクティブ

`ViewContainerRef` を使って自分で描画を制御しているのは 1 件である。

```typescript
// shared/directives/check-permission.directive.ts
@Input() set smCheckPermission(permission: boolean | string) { ... }
@Input() set smCheckPermissionElse(templateRef: TemplateRef<any>|null) { ... }
```

`*ngIf` と同じ「本体テンプレート＋ `else` テンプレート」の形を自前で組み、判定に Store から読んだユーザー情報を使っている。使用箇所は `layout/header-navbar-tabs/header-navbar-tabs.component.html:8` の 1 つだけである。

## 描画位置を動かす仕組み

### `createComponent` による手続き的な生成

`shared/services/dom-service.service.ts` が `createComponent` でコンポーネントを生成し、`ApplicationRef.attachView` でビューツリーに接続したうえで、DOM ノードを `document.body` に追加する。入力値は `Object.assign(componentRef.instance, extraData)` で流し込む形で、`input()` の仕組みは通らない。

この仕組みの利用者は `shared/directive/append-component-on-top-element.directive.ts` だけで、さらにその利用箇所は `shared/ui-components/inputs/button-toggle/button-toggle.component.html:15` の 1 つだけである。ボタンのリップル効果をホスト要素の中心に重ねるために、座標を `getBoundingClientRect()` で測り、生成したコンポーネントの位置を合わせている。

### CDK Portal

`shared/portal/portal.component.ts` は、投影された内容を `*cdkPortal` で保持し、`DomPortalOutlet` を使って `outletId` で指定した id を持つ DOM 要素へ描画し直す。

```html
<!-- experiments-compare/containers/experiment-compare-details/experiment-compare-details.component.html -->
<sm-portal outletId="searchDiff"> ... </sm-portal>
```

比較画面 3 つ（`experiment-compare-details`、`experiment-compare-params`、`model-compare-details`）が、それぞれ `searchDiff` と `nextDiff` の 2 つを使っており、合計 6 箇所である。受け口は比較画面のヘッダにある空の `<div id="searchDiff">` で、本体が持つ検索 UI をテンプレート上の階層を変えずにヘッダの位置へ出している。`afterNextRender` で id 要素を取得する実装なので、受け口の描画が先である必要がある。

`CdkPortalOutlet` は別の用途で 1 箇所使われている。`shared/project-dialog/project-settings/project-settings-dialog.component.ts` は、投影された `MatTab` を `contentChildren` で集め、その `content`（`TemplatePortal`）を `[cdkPortalOutlet]` で描画している。タブの中身を投影で受け取り、描画位置はダイアログ側が決める形である。

### `NgComponentOutlet`

`shared/components/dropdown-object-select/dropdown-object-select.component.html:58` の 1 箇所だけで、入力で受け取ったコンポーネント型を `*ngComponentOutlet` で描画し、`inputs:` で値を渡している。

```html
<ng-container *ngComponentOutlet="compRef(); inputs: {entity};"></ng-container>
```

どのコンポーネントを描画するかを親が決める仕組みだが、使用箇所はこの 1 件である。

## ルーティング

`<router-outlet>` は 14 箇所にあり、うち 13 箇所は画面本体の中に置かれた入れ子の outlet である（`experiments/experiments.component.html`、`models/models.component.html` など）。一覧画面が子ルートとして詳細パネルを描画する構造になっている。名前付き outlet は使われていない。

ルート定義ファイルは 15 個あり、子へ渡るものは 3 種類ある。`data` による静的な値（`{search: true}`、`{mode: 'details', limit: true}`、`{staticBreadcrumb}` など）、`providers` による DI スコープ（19 箇所。NgRx の feature state と effects をルート単位で登録している）、`resolve`（`features/workers-and-queues/workers-and-queues.routes.ts` の 1 箇所のみ）である。遅延読み込みは `loadComponent` 103 件、`loadChildren` 24 件である。

`withComponentInputBinding()` は有効化されていない（`app.config.ts`）。したがってルートパラメータが入力に自動束縛されることはなく、受け取りは 2 通りに分かれる。`ngxtension` の `injectParams` / `injectQueryParams` / `injectRouteData`（合わせて 7 ファイル）と、`ActivatedRoute` を直接読む形、あるいは NgRx の router state セレクタである。

outlet の `(activate)` を使っている箇所が 1 つある。

```html
<!-- features/experiments/containers/experiment-ouptut/experiment-output.component.html:74 -->
<router-outlet class="output-outlet" (activate)="onActivate($event, scrollContainer)"></router-outlet>
```

ただし受け側（`webapp-common/experiments/containers/experiment-ouptut/base-experiment-output.component.ts:192`）は `scrollContainer.scrollTop = 0` を行うだけで、`$event` で渡る子コンポーネントの実体は使っていない。

`app.config.ts` では `RouteReuseStrategy` に `CustomReuseStrategy` が差し替えられている。ルート遷移時に子コンポーネントが破棄されるか再利用されるかは、この実装に依存する。

## オーバーレイ（ダイアログとメニュー）

ダイアログもメニューも、テンプレート上の親子関係を離れた位置に描画される。この画面群では入出力と同じ規模で使われている。

### ダイアログ

`MatDialog.open` が 48 箇所、`MAT_DIALOG_DATA` の注入が 62 箇所、`afterClosed()` が 70 箇所ある。引数は `data` で渡し、結果は `afterClosed()` の購読で受け取る。呼び出し元はコンポーネントだけではなく、`reports/reports.effects.ts` のように NgRx の Effects から開いて戻り値でアクションを分岐している箇所もある。

### メニュー

`[matMenuTriggerFor]` が 46 箇所、`<mat-menu>` の宣言が 30 箇所、`MatMenuTrigger` を型として扱う箇所が 51 件ある。メニューの中身は親のテンプレートに書き、参照変数でトリガーと結ぶ。

```html
<!-- shared/ui-components/panel/menu/menu.component.html -->
<button #trigger="matMenuTrigger" [matMenuTriggerFor]="menuHandle">
<mat-menu #menuHandle="matMenu">
  <ng-content></ng-content>
  <div #refFixedOptions><ng-content select="[fixedOptions]"></ng-content></div>
</mat-menu>
```

`sm-menu` は `<mat-menu>` の中に投影口を置いており、利用側が投影した内容がメニューの中身になる。投影とオーバーレイが組み合わさった形である。

メニューへ文脈を渡す `[matMenuTriggerData]` が 2 箇所、対応する `<ng-template matMenuContent let-tag="tag">` が 2 箇所ある（`shared/ui-components/tags/tag-color-menu/`）。開くまでメニューの中身を描画せず、開いた時点で文脈つきで描画する仕組みである。

## 親子関係を経由しない連携

### NgRx Store

コンポーネント間の値の受け渡しの多くは Store を経由している。`dispatch` が 1013 箇所、`store.select` が 903 箇所、`selectSignal` が 275 箇所ある。`layout/side-nav/side-nav.component.ts` には入力も出力も 1 件もなく、必要な状態はすべて `store.selectSignal(...)` で読んでいる。ヘッダのタブ構成のように、画面側が `HeaderMenuService` 経由で `headerActions.setTabs` を dispatch し、ヘッダ側がそれを select する形もある。

購読の書き方は 3 通りが混在している。テンプレートの `| ngrxPush` パイプ（345 箇所）、`store.selectSignal()`、`toSignal(store.select(...))` である。

Store から読んだシグナルを子側で書き換え可能にするために、`linkedSignal` が 14 件使われている（`protected model = linkedSignal(() => this.selectedModel())` など）。親から来た値を初期値とし、子の操作で上書きできる局所状態を作る形である。

### iframe と `postMessage`

`webapp-common/clearml-applications/report-widgets/` は、`angular.json` に独立したプロジェクトとして登録された別のアプリケーションである。レポート画面はこれを iframe として埋め込み、`window.postMessage` で連携する。

```typescript
// webapp-common/reports/report/report.component.ts:288
Array.from(window.frames).forEach(frame => frame.postMessage('renderPlot', '*'));
```

送っているのは `themeChanged`、`renderPlot`、`resizePlot` の 3 種類である。逆方向は `report-widgets` 側が `window.top.postMessage(...)` で送り、ホスト側は `app.component.ts:83` の `window.addEventListener('message', ...)` で受けて iframe 要素にクラスを付け外しする。Angular の親子関係の外にある、文書間の連携経路である。

### ドキュメント全体へのイベント購読

`@HostListener('document:...')` や `host: {'(document:keydown)': ...}` が 16 箇所ある。親から子へイベントを伝える代わりに、子が文書全体のイベントを直接購読する形である。`shared/ui-components/panel/menu/menu.component.ts` の `clickOut` のように、自分の外側のクリックを検出してメニューを閉じる用途が多い。

## 環境別実装の差し替え

どの実装が子として使われるかを、ビルド設定で切り替える仕組みが 1 つある。`tsconfig.json` のパスエイリアスで、`~/*` が `src/app/*` を、`@common/*` が `src/app/webapp-common/*` を指す。

```typescript
// webapp-common/workers-and-queues/dumb/queues-table/queues-table.component.ts:29
import {QueuesMenuComponent} from '@features/workers-and-queues/dumb/queues-menu/queues-menu.component';
```

共通側のコードが `@features/...` を import している箇所が 165 件あり、共通実装が環境別実装に依存する向きになっている。`~` の解決先を差し替えれば、共通側のコードを変えずに子コンポーネントの実体を入れ替えられる。前述の `*-extended` 系の継承は、この仕組みの上で成り立っている。ただし本リポジトリの `tsconfig.json` には `~/*` の候補が 1 つしか書かれていないので、実際の差し替えは起きていない。

`angular.json` の `fileReplacements` も本番ビルド時に 2 つのファイルを差し替えるが、対象は `src/environments/environment.ts` と `src/app/build-specifics/index.ts` で、後者の中身は `@ngrx/store-devtools` の provider だけである。コンポーネントの差し替えには関与していない。
