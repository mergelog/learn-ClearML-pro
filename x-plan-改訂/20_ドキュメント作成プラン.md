# ClearMLベース学習プロジェクト ドキュメント整備指示書

## 1. 目的

本プロジェクトは、ClearMLをベースとしたデータ管理・ML基盤を題材に、実務プロジェクトに近い設計・開発・テスト・運用・ガバナンス体系を構築することを目的とする。

既存のADR、runbook、SBOM、audit、gate、x-plan等は維持しつつ、不足している上流設計、データ管理、ML固有管理、テスト、運用、ガバナンス、チーム標準、プロジェクト管理のドキュメントを追加する。

単に文書数を増やすことを目的としない。

各ドキュメントは以下を満たすこと。

* 実装・運用と対応している
* 他ドキュメントとの責務が明確である
* 重複を極力避ける
* 実際のコード・設定・スクリプト・ClearML構成から確認できる内容を優先する
* 不明な内容を推測で確定事項として記載しない
* 学習環境で不要な項目は削除せず「対象外」と理由を明示する
* 将来的に複数人・本番運用へ拡張できる構成を意識する
* ADRは意思決定記録として残し、設計書の代替にはしない

---

# 2. 作成方針

## 2.1 既存ドキュメントとの関係

既存資料を確認し、内容が存在する場合は新規文書へ無意味に複製しない。

以下の役割分担を基本とする。

* ADR

  * なぜその方式・技術・方針を選択したか
* 要件定義

  * 何を実現するか
* 非機能要件

  * どの品質水準を要求するか
* 方式設計

  * システム全体をどの方式で実現するか
* 基本設計

  * 外部から見える振る舞い・主要構造
* 詳細設計

  * 実装可能な粒度の内部構造
* Runbook

  * 実際の運用・障害対応手順
* テスト文書

  * 何をどの条件で検証し、何をもって合格とするか
* 管理台帳

  * 継続的に更新される管理情報

既存ADRやrunbookに詳細が存在する場合は、関連文書からリンクする。

---

# 3. 優先順位

以下の順序を基本として整備する。

1. 上流設計
2. データ管理
3. ML固有管理
4. テスト・品質保証
5. 運用
6. セキュリティ・ガバナンス
7. チーム標準

一度に全資料を完成させる必要はない。

Phaseごとにレビューし、既存実装との矛盾を確認してから次へ進む。

# 15. 作成時の禁止事項

以下は禁止する。

* 実装を確認せず推測だけで設計を確定する
* ClearML公式仕様と本プロジェクト独自仕様を混同する
* ADRを設計書の代わりにする
* コードを大量に設計書へコピーする
* 同じ説明を複数資料へ大量に重複させる
* 実在しない運用体制を作る
* 学習環境なのに大企業向け運用を無理に適用する
* 不要な規制対応を「対応済み」と記載する
* 数値根拠のないSLOや性能目標を事実として記載する
* 不明事項を推測で埋める

不明事項は以下のように明記する。

> 未確定。実装または運用要件確認後に決定する。

# 16. ドキュメント作成時の調査優先順位

記載内容を決める際は以下の順序で確認する。

1. 現在のソースコード
2. 現在の設定ファイル
3. 現在のDocker / Infrastructure構成
4. 現在のテスト
5. 既存ADR
6. 既存runbook
7. 既存スクリプト
8. ClearML公式仕様
9. Angular / NgRx等の公式仕様
10. 一般的なベストプラクティス

一般論より実際のプロジェクトを優先する。

# 17. 完了条件

ドキュメント整備全体の完了条件は、単純なファイル作成完了ではない。

最低限、以下を満たすこと。

* [ ] 要件から実装まで追跡できる
* [ ] Datasetの意味を第三者が理解できる
* [ ] ML実験を再現できる
* [ ] Model採用理由を説明できる
* [ ] API・Angular・ClearML間の責務を説明できる
* [ ] テスト合格条件を説明できる
* [ ] リリース可否を判断できる
* [ ] 障害発生時の基本対応を説明できる
* [ ] Security上の主要リスクを説明できる
* [ ] ClearML upstream更新時の影響範囲を検討できる
* [ ] 新規参画者が資料を読んで主要構成を理解できる
* [ ] 文書と実装に重大な矛盾がない

最終的には、

**要件 → 設計 → Angular/API実装 → Dataset/Task/Model → テスト → リリース → 運用**

を一連の流れとして説明できる状態を完成形とする。

# 18. 文章規範

本プランで作成する日本語文書は、`~/.claude/skills/japanese-tech-writing/SKILL.md` の規範に従って執筆する。テンプレート（§14）が文書の骨格を定めるのに対し、この規範は本文の書き方を定める。

特に本プランと関わりが深いのは次の項目である。

* 段落は一つの話題だけを扱い、段落の先頭で前の段落との論理関係を示す
* 本文内の根拠で確定していない事項を断定形で書かない。推量・未確認を表す述語はそのまま残す（§15「不明事項を推測で埋める」と同じ方向の規範である）
* 区別すべき対象を一括りにしない。因果を主張するときは、その機構を一文で示す
* 空句を書かない。「重要なのは〜である」「包括的に」「正面から扱う」「不可欠」などは、論点を増やさずに体裁だけを整える
* 翻訳調の比喩と擬人化を避ける。「データが語る」「この問いは開かれている」ではなく、「データから分かる」「未解決である」と書く
* 見出しは、その節が答える問いか、扱う対象を指す名詞句にする

推敲時は、書き上げた文書をこの規範で点検してから完成とする。
