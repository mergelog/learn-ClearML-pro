## 1. 何を作るか

> **このプロダクトは「データを管理すること」を目的に置く。**
> 学習・評価・昇格・推論はその周りの手続きであり、**中心にあるのは資産（Dataset /
> Model / Run）の台帳**である。台帳が正しく引けることが、外部へ機能を提供する前提になる。

いま欠けているのはその台帳そのものである。ClearML の画面は
**Dataset は Dataset の画面、Model は Model の画面**と縦に割れていて、
「このモデルはどのデータから来たのか」を一画面で答える場所が無い。

本プランは **`data-catalog` という自作 feature を新設**し、
資産を1つの語彙で横断して引ける状態を作る。

### 1.1 「外部への提供」との関係

外部提供（エクスポート、参照用URL、外部連携API）は**カタログの出口**であって、
カタログ無しに先へ出すものが無い。だから順序は動かせない。

```text
  管理（Stage N）            出口（Stage E）
  資産を1つの語彙で引ける  →  引けたものを外へ渡せる
```

Stage E は Stage N-6 まで通ってから形を決める（§5）。
**先に出口だけ作らない。** 出すものが定まっていない状態のエクスポートは、
APIの応答をそのまま垂れ流すことになり、後から形を変えられなくなる。

### 1.2 やらないこと

- ClearML の Dataset / Model 画面を置き換えること。**カタログは横断の入口であり、詳細は既存画面へ渡す**
- ベンダー由来コード（`webapp-common`・取り込み済み feature）の全面的な整理
- ML アルゴリズム側の変更

## 2. 現在地

| 項目 | 実測（2026-09-12） |
| --- | --- |
| 自作 feature | `features/quality-pipeline` の**1本だけ** |
| 自作 feature の構成 | `data-access`（api.service + adapter）/ `state`（NgRx feature）/ `containers` / `components` / `.routes.ts` で feature 局所 provider |
| 凍結領域 | `webapp-common`（1687ファイル）とベンダー feature。`eslint-baseline` / `web-boundaries` の `knownViolations` で既存違反だけ許す |
| ゲート | `verify:web` / `ci:parity` / `test:pyramid` / `web:boundaries` / `web:lint:baseline` / `web:typecheck:strict` / `web:contract` |
| テスト | Angular 単体 270（自作 quality-pipeline のみ）・E2E 27（うち a11y 4） |
| 判断の記録 | ADR 003（境界と strict）/ ADR 005（テスト層）/ ADR 007（feature 構成） |

**重要なのは、ゲートが「自作コードの置き場所」をファイル名で名指ししていることである。**

| ファイル | 名指ししている内容 |
| --- | --- |
| `apps/web/tsconfig.strict.json` | `include` に `src/app/features/quality-pipeline/**` |
| `test-pyramid.json` | `web-unit` 層の `include` に `features/quality-pipeline/**/*.spec.ts` |
| `apps/web/web-boundaries.json` | feature 間 import と生成API境界のルール |

つまり **feature を1本足すことは、これら3つを足すことと同義**である。
足し忘れると、新しいコードだけが strict 検査もテスト層の勘定も外れる。
この取りこぼしを防ぐことが Stage N-0 の役割になる。

## 3. 全体の順序

```text
Stage N  データカタログ（自作 feature 新設）      ← いまここ
   │     N-0 受け皿 → N-1..N-3 土台 → N-4..N-8 画面 → N-9 導線 → N-10 検証
   ↓
Stage K  既存 ClearML feature への最小改造（Stage N と同時進行）
   │     導線と相互リンクだけ。改造した凍結領域ファイルは記録する
   ↓
Stage P  ベストプラクティス点検（Stage N の実装を材料に）
   │     2本目の feature が出て初めて判定できるものが多い
   ↓
Stage E  外部への提供口（N-6 完了がトリガー）
```

### なぜこの順か

1. **N-0 を最初に置くのは、ゲートの受け皿が無いまま書き始めると検査されないコードが育つから。** 後から include を足すと、そのとき初めて大量の違反が出る
2. **K は N と同時。** 導線（side-nav）が無いと N-4 以降を人が見られない
3. **P は N の後。** `shared/` を育てるか、`libs/` を切るかは、**2本目の feature が実在してから**でないと机上の話になる（旧 D-3 / D-5 のトリガーがまさにこれ）
4. **E は最後。** §1.1 の通り

## 4. Stage N — データカタログ

### 4.1 何を1つの語彙にするか（N-1）

ClearML 側の実体は3つに分かれている。

| 画面で見せたいもの | ClearML の実体 | 取得元 |
| --- | --- | --- |
| データセット | `data_processing` タイプの Task と、それを束ねるプロジェクト | `ApiProjectsService` / `ApiTasksService` |
| モデル | Model | `ApiModelsService` |
| 実行 | Task | `ApiTasksService` |

これを **`CatalogAsset` という1つの型**へ寄せる。共通で持つのは
「種別・名前・所属プロジェクト・更新日時・タグ・状態・元の実体へのID」だけである。

**種別ごとの固有情報を共通型へ入れない。** 入れると型が3つの実体の和集合になり、
どのフィールドがいつ埋まるのかを誰も言えなくなる。固有情報は詳細（N-6）で
種別ごとに取りに行く。

ClearML の語彙（Task、hyperparams、`data_processing`）は
`data-access` の内側に留める。`quality-pipeline` で既に採った形（`quality-pipeline.model.ts`
の冒頭コメントに書かれている方針）をそのまま踏襲する。

### 4.2 一覧と検索（N-4 / N-5）

一覧は**サーバ側で絞る**。`getAllEx` 系はページングと条件指定を持っているので、
全件を取って手元で `filter` しない。手元で絞ると、件数が増えたときに
「画面が重い」ではなく「途中までしか無い」という形で壊れる。

検索条件は **URL のクエリパラメータへ載せる**。
理由は3つあり、どれも外部提供（Stage E）の前提になる。

1. 絞り込んだ状態を人に渡せる
2. 再読み込みで消えない
3. **「この条件で引いたもの」が URL として名前を持つ**ので、後から
   同じ条件を API として開く判断ができる

### 4.3 lineage（N-7）

`Dataset → 学習 Run → Model` を辿って見せる。
ClearML では Model が生成元 Task を持ち、Task が使った Dataset 版数を
hyperparams に持つ（`quality-pipeline.adapter.ts` の `DATASET_SECTION` /
`DATASET_VERSION_PARAMETER` が既に同じ場所を読んでいる）。

**この読み方は `quality-pipeline` と重複する。** 2箇所目が出るということは、
旧 D-3（`shared/` を自作共有層として育てる）のトリガーが引かれたということである。
判断は P-2 で行う。**先回りして移さない。** N-7 の時点では catalog 側に
書き、P-2 で 2箇所を見比べてから寄せる。

### 4.4 メタデータ編集（N-8）

tags と description の更新。**書き込みを持つのはこの画面が初めてになる**
（`quality-pipeline` の起動・停止は ClearML への操作であって、台帳の編集ではない）。

- 失敗したときに画面の表示が真実からずれないこと
- 同じ資産を2箇所（カタログと既存 Dataset 画面）から編集できてしまうこと

この2つをどう扱うかを N-8 の着手時に決め、ADR へ残す。
**「とりあえず楽観更新」で入れない。** 台帳が嘘をつくと、台帳である意味が消える。

## 5. Stage E — 外部への提供口（N-6 完了で形を決める）

いま決めているのは**順序と原則だけ**である。具体は N-6 まで通ってから書く。

原則

- **出すのは `CatalogAsset`（画面用の形）であって、ClearML API の応答そのものではない。** 生の応答を外へ出すと、ClearML 追従で外部が壊れる
- 出口を増やすときは `services/prediction_api` が採った形（`openapi.json` をコミットして差分を検査する・ADR 006）に倣う。**新しい流儀を作らない**
- 認可の判断は既存の仕組み（`services/security`・ADR 002）に乗せる

候補（どれを採るかは未決）

| 候補 | 中身 |
| --- | --- |
| E-a | 一覧・詳細の CSV / JSON エクスポート |
| E-b | 検索条件つき参照 URL（N-5 のクエリ同期がそのまま外部の入口になる） |
| E-c | カタログ参照の HTTP API（`services/` 側に置く） |

## 6. Stage P — ベストプラクティス点検

**新しいゲートは作らない。** 既存のゲートに新 feature を載せ、
載せた結果として出てくる判断だけを扱う。

| ID | 見るもの | なぜ今か |
| --- | --- | --- |
| P-1 | ADR 007（feature 構成）に新 feature が沿っているか。沿えなかった点は ADR を直す | 2本目で初めて「規約」かどうかが分かる。1本しか無いものは規約ではなく実例である |
| P-2 | 旧 D-3。`shared/` へ寄せるもの（§4.3 の lineage 読み取りなど） | **2箇所目が実在してから**寄せる |
| P-3 | 旧 D-5。`libs/` を切るか | トリガー①②③（`_old` 参照）のうち②が近づく。**現時点の判定は「まだ切らない」** と予想するが、実測してから書く |
| P-4 | 旧 D-4。`@defer` と初期表示バジェット | feature が1本増えればバンドルは増える。`web:scan:build` の実測で判断する |
| P-5 | 旧 D-1。zoneless | `stackup` 側のトリガーを再評価する。凍結領域の都合で動かないなら、**動かない理由を書いて閉じる** |
| P-6 | lint と baseline | 自作分は baseline に入れず直す（旧 B-3 で決めた運用）。`@ngrx/eslint-plugin` のルールが新 state に効いているか |
| P-7 | `test-pyramid.json` / `ci:parity` | 新テストが宣言した層に収まっているか。E2E の上限30件に触れる（現在27件・N-10 で+2〜3件） |

**E2E は上限30件に近い。** N-10 で足すのは smoke 1本と a11y 1本に絞る。
上限を上げたくなったら、それは「E2E でしか確かめられないことが増えた」のではなく
「下の層でやるべきことを上げている」可能性をまず疑う（ADR 005）。

## 7. 進め方

1. **1項目ずつ閉じる。** 閉じるとは「変更した」ではなく「検証が緑になった」
2. **証跡は `01_チェックリスト.md` の末尾へ追記する。** 理由はこの資料へ
3. **判断が分かれたものは ADR へ。** README には形を、ADR には理由を書く（ADR 007 で決めた分担）
4. 凍結領域（`webapp-common`・ベンダー feature）へ手を入れたときは、
   **例外として記録する**。記録の無い改造が増えると、凍結領域という約束が意味を失う
