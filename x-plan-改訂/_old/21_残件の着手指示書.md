## 9.2 BL-18：upstream の追跡

fork 元（`https://github.com/clearml/clearml-web.git`）を remote `upstream` として登録した。

突き合わせて分かったことが3つある。

1. fork 元は tag `v2.5` 系列である。upstream の2481ファイルのうち2435本が手元と同一で、
   34本を手元で変更してあり、12本は手元に無い
2. commit は1つに絞れない。tag `v2.5`・branch `v2.5`・`master` を分ける4ファイルは、
   手元で変更してあるか、手元に無いかのどちらかである
3. **版数では更新を検知できない**。upstream の `master` は tag `v2.5` の4つ先にあるが、
   `package.json` の `version` はどちらも `2.5.0` である。
   4つの中身は依存の更新と脆弱性の修正である

3つ目のため、§3.2 が挙げた「版の突き合わせ」ではなく commit の突き合わせにした。
`upstream.json` に最後に確認した commit を記録し、`scripts/upstream-status.mjs`
（`pnpm upstream:status`）がそれと upstream の `master` を比べる。
CI の `upstream` ジョブが変更のたびに呼ぶ。

追跡の頻度は「変更のたび」になったので、71 §6 の残課題から外した。
71 の R-01・R-02 の検知方法もこの検査の名前へ書き換えた。

取り込み手順は 03 §4.15 に書いた。手元で変更してある34本の内訳と、
upstream の変更と衝突したときにどちらを採るかを含む。
§3.3 のとおり、この手順は未検証である。その旨を 03 §6・01 §6・74 §6 に残した。

### BL-16 の測定

同一条件の繰り返しでは振れ幅が出ない。乱数種が分割と推定器の両方へ渡り、
学習に外部の状態が入らないためである。そこで種だけを変えた10回を併せて測った。

| 指標 | 平均 | 標準偏差 | 幅 |
| --- | --- | --- | --- |
| validation の recall | 0.6968 | 0.0287 | 0.0948 |
| validation の f1 | 0.7630 | 0.0249 | 0.0645 |

これを根拠に 23 §4.7 へ、比較対象・許容する低下幅・退行時の扱いを書いた。
許容幅は、同じ種で測り直す場合 0.02、記録値と比べる場合は recall 0.06 / f1 0.05（標準偏差の2倍）である。

§6.4 が求めた「0.55 / 0.65 を使うなら理由を書く」については、使う理由を 23 §4.7 に書いた。
下限は達成できる値ではなく、下回るモデルを候補にしない線である。引き上げると、
種の違いによる振れが下限に触れる。
