### 4.3 A — 実害があるもの（P0・目安 半日）

#### A-1 / A-2. `stackup` に `provideHttpClient()` が無い

> **【2026-09-10 実測による注記】以下は着手前の仮説であり、原因の見立てが外れていた。**
> 結論（`provideHttpClient(withInterceptorsFromDi())` を足す）は変わらないが、理由が違う。
>
> - **`NullInjectorError` は出ない。** Angular 22 では `HttpClient` / `HttpHandler` /
>   `HttpBackend` が `@Injectable({providedIn: 'root'})` になっており（既定 backend は
>   `FetchBackend`）、`provideHttpClient()` が無くても `HttpClient` は注入できる。
>   下の「一方で HttpClient は確実に必要とされている」以降の危惧は、この点では成り立たない
> - **実害は interceptor 側にあった。** `HttpInterceptorHandler` は chain を
>   `HTTP_INTERCEPTOR_FNS` からしか組み立てず、`HTTP_INTERCEPTORS`（クラス型）を
>   そこへ橋渡しするのは `withInterceptorsFromDi()` だけである。したがって
>   `WebappInterceptor` は一度も動いておらず、`X-Clearml-Client` ヘッダが付かず、
>   401 での `logout()` も走っていなかった
> - つまり下記3の分岐（「出なかった場合は本調査の読み落とし」）に該当するが、
>   **「動いているから良い」ではなく、実際に壊れていた**
>
> 詳細・実測値・再現手順は `apps/web/README.md`「HttpClient と interceptor の提供」と
> `01_チェックリスト.md` の作業証跡（2026-09-10）に置いた。ここには書き写さない。

**測ったこと**

```bash
grep -rn 'provideHttpClient\|HttpClientModule\|withInterceptorsFromDi' apps/web/src/
# → ヒットするのは report-widgets の app.config.ts と 1件の spec のみ。
#    stackup 側（app.config.ts / core/core.providers.ts）には無い。
```

一方で HttpClient は確実に必要とされている。

- `business-logic/api-services/api-requests.service.ts` は `providedIn: 'root'` で
  `HttpClient` を constructor 注入している
- 生成 API サービス（`ApiTasksService` 等）も同様
- `app.config.ts` は `{provide: HTTP_INTERCEPTORS, useClass: WebappInterceptor, multi: true}`
  を登録しているが、`provideHttpClient(withInterceptorsFromDi())` が無いため、
  **仮に HttpClient が別経路で提供されていても、この interceptor は動かない**

**順序を守る。**

1. **A-1: まず再現確認する。** `pnpm run web:start` → DevTools Console に
   `NullInjectorError: No provider for HttpClient` が出るかを見る
2. **A-2（出た場合）**: `app.config.ts` に足す

   ```ts
   import {provideHttpClient, withInterceptorsFromDi} from '@angular/common/http';
   provideHttpClient(withInterceptorsFromDi()),
   ```

   `withInterceptorsFromDi()` を必ず付ける。付けずに `provideHttpClient()` だけだと
   HttpClient は動くが interceptor が黙って無効になる。
   **「動いたように見えて認証ヘッダだけ落ちる」が一番危ない。**
3. **A-2（出なかった場合）**: 本調査の読み落としである。提供元を特定して README に記録し、
   閉じる。**「動いているから良い」で終わらせない。** 次に触った人が壊す

`WebappInterceptor` の functional 化はしない（ベンダー由来。§9）。

#### A-3 / A-4. 自作 feature に `OnPush` が1つも無い

> **【2026-09-10 実測による注記】「無い」のは宣言だけで、挙動は最初から OnPush だった。**
>
> Angular 22 で `ChangeDetectionStrategy` の既定が入れ替わっている。
>
> ```ts
> // @angular/core の型定義
> enum ChangeDetectionStrategy { OnPush = 0, Eager = 1, Default = 1 }
> //   OnPush = 0 に「NOTE: OnPush is enabled by default.」と書かれている
>
> // ɵɵdefineComponent
> onPush: componentDefinition.changeDetection !== ChangeDetectionStrategy.Eager
> //   changeDetection を書かない（undefined）なら onPush: true になる
> ```
>
> つまり **`changeDetection` を省略した component は OnPush** であり、
> 離脱するには `ChangeDetectionStrategy.Default`（= `Eager`）を明示する必要がある。
>
> 実測（`apps/web/src` 全体）
>
> | | 件数 |
> | --- | ---: |
> | `@Component` の総数 | 345 |
> | `ChangeDetectionStrategy.OnPush` を明示 | 235 |
> | `ChangeDetectionStrategy.Default` を明示（＝唯一の離脱） | **1** |
> | 何も書いていない（＝既定の OnPush） | 109 |
>
> 本文の「0/6」「220/314」は**文字列を grep した数**であって、挙動の数ではない。
> 「OnPush が無いので非同期処理のたびに再評価される」という実害の見立ては成り立たない。
> A-3 で加えた宣言は**実行時には no-op** である（意図の明示としてのみ機能する）。
>
> A-4 の確認そのものは有効で、Reactive Forms を持つ `start-run-form` が
> OnPush 下で入力に追従することを実測した。ただしこれは A-3 の前後で変わらない。

`features/quality-pipeline` の6コンポーネントに `OnPush` が付いていない。
`webapp-common` は 220/314 付いており、**自作コードだけが例外になっている**。

なぜ実害か。

- `stackup` は zone.js 上で動く。OnPush が無いと、アプリ内のどこかで
  非同期処理が終わるたびに再評価される
- この feature は `store.selectSignal()` と `input()` だけで組まれている。
  **OnPush 前提の書き方が既にできていて、宣言だけが抜けている**
- **zoneless 化（D-1）の前提条件でもある**

**A-4 の注意**: `start-run-form` は Reactive Forms を持つ。
`form.valid` をテンプレートで直接読んでいると更新が止まる可能性がある。
追加後、**フォームの活性・非活性が入力に追従するかを必ず手で確かめる**。
追従しなければ `toSignal(form.statusChanges)` で signal 化する
（`toSignal` は既に import 済み）。

### 4.4 B — ルールを機械化する（P1・目安 半日）

#### B-1. `@ngrx/eslint-plugin` を接続する

> **【2026-09-10 実施時の判断】** `configs.all`（型情報を要求しない方）で接続した。
> `@ngrx/prefer-effect-callback-in-block-statement` だけは `"off"` のまま残す。
> 264件（うち自作 `quality-pipeline` 7件）が該当するが、`createEffect(() => obs)` を
> `createEffect(() => { return obs; })` に整形するだけで挙動は変わらない。
> 自動修正の出力も読みにくく、注釈の多い effects ファイルを機械整形する価値が無い。
> 以前は同じ1行が「プラグイン未登録で効いていない」状態だったが、接続後は
> **意図して切っている**という意味に変わっている（`eslint.config.js` に理由を併記）。

`package.json` に `@ngrx/eslint-plugin@22.0.0` が**入っているのに**、
`eslint.config.js` にプラグイン登録が**無い**。
`"@ngrx/prefer-effect-callback-in-block-statement": "off"` の1行だけが書かれており、
ESLint 9 以降は未登録プラグインのルールも `off` ならエラーにならないため、
**黙って無視されている**。

NgRx 22 を全面採用し自作 feature も actions / reducer / effects / selectors を持つのに、
`@ngrx/no-dispatch-in-effects` などの典型的な事故を検出する仕組みが無い。

#### B-2. `OnPush` を新規コードで必須にする

> **【2026-09-10 実測による注記】ルールの意味が angular-eslint 22 で変わっている。**
> `prefer-on-push-component-change-detection` はもはや「`OnPush` を書いていない
> component」を咎めない。Angular 22 で OnPush が既定になったため（A-3 の注記）、
> **`ChangeDetectionStrategy.Default` への明示的な離脱だけ**を咎めるルールになった。
> メッセージも "Components should not opt out of the default `OnPush`" である。
> 該当は全体で1件（`webapp-common/datasets/open-dataset-card`）。
>
> したがって「A-3 を先にやらないと自作分が baseline に固定される」という順序の
> 懸念は成立しない。ルール自体は「黙って Default へ落とすことを防ぐ」ゲートとして
> 有効なので `error` で入れる。
> なお `allowExplicitOnPush: false` を指定すると、逆に明示的な `OnPush` を
> 「冗長」として咎めるようになる。A-3 で加えた宣言を残す限り、この指定はしない。

```js
"@angular-eslint/prefer-on-push-component-change-detection": "error",
```

A-3 を人手の注意で維持するのは無理なのでルール化する。
**A-3 を先にやること。** 順序を逆にすると自作分が baseline に取り込まれ、
「既知の負債」として固定されてしまう。

#### B-3. baseline の更新

B-1 / B-2 はベンダーコードで大量に落ちる。既存運用に載せる。

1. 追加して `pnpm run web:lint` で違反数を測る
2. `pnpm run web:lint:baseline:update` で baseline を更新
3. **自作 feature の違反だけは baseline に入れず実際に直す**

#### B-4. テンプレートルールの更新

`use-track-by-function` は `*ngFor` 用のルールで、旧制御フローが0の本リポジトリでは

#### 5.1.2 判断: 足りない行を足すのではなく、ズレの原因を塞ぐ

**`ci.yml` は npm script を呼ぶ形に変える。**

足りない行を足すだけだと、同じズレがまた起きる。script 側に手順が1つ増えるたびに
CI 側へ写し忘れる余地が残り、**「写し忘れても CI は緑になる」**からである。
CI が赤くならない種類の欠落は、誰も気付かない。

ジョブ分割（python / web / security / supply-chain）は**維持する**。分割の理由は
「片方の失敗でもう片方の結果が隠れないように」であって、コマンドを再実装する
ためではない。ジョブを分けたまま、各ジョブが script を呼べばよい。

`requirements` の lock 検証や Trivy 走査など、**手元の `verify` に無いもの**は
CI 固有の手順として残す。ここで揃えたいのは「手元にある検証が CI で必ず走ること」
であって、CI から固有の手順を無くすことではない。

**script を呼ぶ形にするだけでは足りない（着手時に判断を1つ足した）。**
ジョブ分割を保つ以上、CI 側は「どの script を呼ぶか」をステップとして列挙し続ける。
列挙する限り写し忘れの余地は残り、今回の3件がまさにそれだった。

そこで**一致そのものをゲートにする**。`scripts/ci-parity.mjs` が、
`verify:python` / `verify:web` / `verify:security` の各要素が `ci.yml` の担当ジョブで
同じ順序で呼ばれていることを確かめる。落ちていれば失敗する。

検査は**片方向だけ**にする。「`verify` にあって CI に無い」を失敗とし、
その逆（CI 固有の手順）は何も言わない。完全一致を求めると、lock 検証や Trivy を
置く場所が無くなる。

置き場所は `verify:web` の先頭近く（`web:gates:test` の次）にした。検査対象は web に
限らないが、「先に自分を疑う」段に属するゲートであり、`web:gates:test` と同じ理由で
最初に走る必要があるためである。

#### 5.1.3 判断: e2e を CI に載せる

**別ジョブとして載せる。** ビルドと起動で数分かかるため、web ジョブへ足すと
lint や unit の結果が e2e の待ち時間の後ろに隠れる。

`verify:web` にも足すかは別の問題である。`verify:web` は「変更のたびに手元で回す」
想定の速さで作られており、ここへ e2e を入れると回されなくなる。
**手元では `verify:test` を使い、必ず走らせるのは CI の役目**とする。

**実装時に足した判断（2026-09-11 / W12-2）。** 「CI の役目」にすると、`verify` の
外にある検証が1つできる。すると W12-1 で塞いだ穴（CI から落ちても誰も気付かない）が
そこだけ残る。そこで `ci:parity` の `COVERAGE` を、verify の連鎖だけでなく
`web:e2e` のような単体の script も対応先のジョブごと書ける形へ広げ、
`web:e2e` → `e2e` ジョブの対応を固定した。**`verify` の外へ出すことと、
CI から落ちたら失敗することは両立する。**

手元の入口は root の `pnpm run web:e2e`（Playwright だけ）にした。`apps/web` の
`verify:test` は unit と型検査も含むため、e2e だけを見たいときに使いにくい。

これは smoke E2E（縦スライスの自動検証）と axe による a11y 試験の**前提**である。
土台を先に固めないと、以降で足したテストも同じように「走らないまま緑」になる。

#### 5.1.4 判断: contract test は「消費者のいない契約」を書かない

W12 の原文は「OpenAPI / JSON Schema による consumer-provider contract test」だが、
**`prediction_api` には消費者がいない。**
`apps/web` の `features/serving/` は `empty-state` の1つだけで、画面は推論APIを
呼んでいない。いま消費しているのは runbook の curl と `services/tests` だけである。

この状態で consumer-provider contract test を書くと、**片側しかいない契約**の
検査になる。provider 側の都合をもう一度書き写すだけで、破壊変更は検知できない。

**採るのは「`prediction_api` の OpenAPI をスナップショットし、破壊変更を検知する」形。**
`prediction_api` は FastAPI なので OpenAPI は自動生成できる。消費者が不在でも、
**公開しているAPIの形が黙って変わったこと**は検知できる。消費者が現れたときに
consumer-driven な形へ育てられる。

既存の契約検査との関係は次のとおりで、**重複させない**。

| 契約 | いま見ているもの |
| --- | --- |
| Angular の定数 ↔ Python の定数 | `web:contract`（`scripts/pipeline-contract.mjs`）が担当済み |
| Angular ↔ ClearML API | 生成クライアント（`business-logic/`）が担当 |
| **`prediction_api` の公開API** | **W12 で新設する** |

#### 5.1.5 判断: 層は「件数の比率」ではなく「約束」で分ける（2026-09-11 / W12-3）

土台（§5.1.2・§5.1.3）が出来たので、次に足すのは failure test・contract test・
smoke E2E・a11y・負荷である。ここで先に決めないと困るのは**同じ判断を2つの層で
確かめてしまうこと**である。桁の書式を presentational の単体テストと E2E の両方に
書くと、書式を変えたときに2か所が落ちる。片方を直せば緑になるので、
**遅いほう（E2E）だけが残り、速いほうが消える**。

そこで層ごとに「確かめること」と「確かめないこと」を両方宣言した
（`test-pyramid.json`・7層）。規則は1つで、**下の層で確かめられることを
上の層で確かめない**。分岐が1つ増えたときに足すのは単体テストであって E2E ではない。

**比率はゲートにしない。** 「単体 : E2E を 20:1 以上」のような形にすると、
E2E を1件増やしたいときに無関係な単体テストを増やせば通る。守りたいのは比率では
なく上の層で確かめるものの**種類**なので、E2E にだけ絶対値の上限（30件・現在18件）
を置き、超えたときに「その確認は本当にこの層でなければできないのか」を見直す形に
した。下の層は増えて困らないので上限を置かない。

**宣言だけでは §5.1.1 と同じことが起きる。** ずれは、ずれたという理由では表に
出てこない。`pnpm run test:pyramid` が、すべてのテストがいずれか1つの層に属して
いること（未分類・二重所属を失敗）・層が宣言した script が実在すること・上限を
超えていないことを見る。件数は静的に数える（実行して数えると全層を走らせることに
なり、`verify` の先頭で軽く回せない）。判断の記録は
`docs/adr/005_20260911_test_pyramid.md`。

#### 5.1.6 判断: failure test は「失敗するか」ではなく「読めるか」を見る（2026-09-11 / W12-4）

着手前に数えると、失敗に言及するテストは既に 233 件あった。**足りないのは数では
なかった。** 4分類（retry / timeout / API停止 / 破損Artifact）について実装を読むと、
守られていない経路が4つ見つかり、いずれも「失敗はするが、何が起きたか読めない」
種類だった。

- 壊れた重みは `KeyError: 0`、途中で切れた重みは `EOFError` になる。
  ファイル名もモデル名も出ない。`services/prediction_api` と `ml/pipeline` の
  両方で `joblib.load` が素で呼ばれていた
- ClearML が止まっているときだけ、serving の起動が SDK の型のまま落ちていた
  （`_by_id` は包んであり、`_in_production` は包んでいなかった）
- retry するのは `tools/seed_clearml.wait_until_ready` の1か所だけで、無検査だった
- 期限（git 5秒 / readiness 10秒）を確かめるテストが無かった

**このシステムは retry しない。** 失敗は一度で確定させ、再起動で回復させる。
例外は seed の起動待ちだけで、これは `backend:up` の直後という状況が
「最初の失敗が正常」だからである。W12-4 はこの方針を変えていない。

`ml/pipeline/artifacts.py` は同じことを既に丁寧にやっていた（`read_split` /
`read_json`）。**穴は「無い機能」ではなく「揃っていない扱い」として見える。**
既にある良い書き方を基準に読むと見つかる、という形で探した。

運用側から読める必要があるので、修正した失敗の文言は runbook 002 / 004 の
トラブルシュート表にも入れた。

#### 5.1.7 判断: 消費者のいない契約は、スナップショットで守る（2026-09-11 / W12-5）

§5.1.4 で決めたとおり、`prediction_api` の OpenAPI をコミットし、コードが
生成する文書と一致することを `services:test` で確かめる形にした。
実装して分かったのは、**分類を検知に使ってはいけない**ということである。

破壊変更（応答が消えた・要求に必須の値が増えた）と互換の変更（エンドポイントが
増えた）を分けて報告するが、**失敗の判定は文書の完全一致**にした。分類は
上下限や enum の狭まりを読まない。分類のほうを判定に使うと、**読めない種類の
変更が緑になる**。それは §5.1.1 と同じ形の失敗である。
分類は「呼び出し側が壊れるか」を人が読むための材料として添えるだけにした。

破壊の定義が**送る側と読む側で逆向きになる**ことも、書いてみて分かった。
要求の値が「任意 → 必須」になれば送り手が壊れ、応答の値が「必須 → 任意」に
なれば読み手が壊れる。同じ規則を両側へ当てると片方を必ず取りこぼす。

ゲート（新しい npm script）にはしなかった。ゲートにすると `ci.yml` へ写す
必要が生まれ、`ci:parity` の対象が1つ増える。`services:test` の中に置けば
`verify:python` と CI の python ジョブが既に走らせている。
**検証を増やすために、走らせる場所を増やさない。**

判断の記録は `docs/adr/006_20260911_published_api_snapshot.md`。

#### 5.1.8 判断: smoke は「1つの世界」を通す。上の層に値を書かない（2026-09-12 / W12-6）

Dataset登録 → Queue学習 → 比較 → 昇格 → 推論を5件のE2Eで通した。
実装して分かったのは3つである。

**1. 画面ごとのfixtureでは繋がりを確かめられない。** 既存の2つのfixtureは
画面ごとに必要な応答を返す。それでは各画面が「自分用の世界」を見るので、
節目の間で取り違えが起きても全部緑になる。smokeは1つのfixtureが1つの世界を
返し、すべての画面がそれを見る。Dataset版 1.0.0 で学習した実行が比較で並び、
`stage:production` のモデルになり、そのバージョン文字列が提供中として出る。

**2. fixtureは絞り込みを実際に当てる。** `type` / `project` / `id` /
`name`（正規表現）/ 続きの問い合わせ（`scroll_id`）を無視して常に全部返すと、
画面が誤った条件で問い合わせていても気付けない。**応答の形を単純にすると、
テストは画面ではなくfixtureを確かめるものになる。**

**3. 最後の節目は推論そのものではなく、受け渡し点である。** 画面は
`prediction_api` を呼んでいない（§5.1.4 で数えたとおり消費者は runbook 004 の
curl と `services/tests` だけ）。ブラウザから推論には到達できないので、
E2E が言える最後のことは**どのモデルのどのバージョンが提供されるか**である。
それが `prediction_api` の読む `stage:production` のモデルと同じ文字列かを見る。
推論が実際に答えるかは services-unit と `scripts/serving-smoke.sh` の範囲で、
そこを E2E へ持ち上げると backend 起動が前提になり、§5.1.3 で作った
「fixtureだけで走る e2e ジョブ」が壊れる。

比較の節目では**指標の値を見ない**。どちらが良いかの読み方は評価側（ml-unit）と
画面側（web-unit）にあり、ここで見るのは「取り違えずに2つが並ぶか」だけである
（§5.1.5 の規則）。並んだのがその2つかは、行が指す Task の id で見る。
実行はClearMLが毎回同じ名前で作るので、名前では区別できない。

#### 5.1.9 判断: a11y は自作の範囲を0件で固定し、凍結領域は対象にしない（2026-09-12 / W12-7）

axe を画面全体へ当てると、取り込んだ ClearML Web の外枠だけで critical 2 種
（`aria-allowed-attr` / `button-name`）・serious 1 種（`link-name` 7件）・
moderate 2 種が出る。ここで baseline を作ると、**自作の違反が取り込み分の中に
紛れる**。Stage 1-B3 で lint について決めたのと同じ形（自作分は baseline に
入れず直す）を採り、**対象を自作画面の中だけに絞って0件で固定**した。
外枠は `web-boundaries.json` と同じ凍結領域の扱いで、直しても取り込み直しの
たびに消える。

E2E へ置くのは「画面として組み上がったときにだけ分かること」に限る（§5.1.5）。
規則そのもの（属性の付け方・要素の選び方）は lint と単体でも見られるが、
**部品ごとには正しくても重なった結果として名前が消える・キーボードで
辿り着けない**、という壊れ方はここでしか見えない。状態ごとに見るのも同じ理由で、
空の状態と失敗の状態は別の要素で描かれるため、埋まった状態だけを見ると
そこにしか出ない違反を見逃す。

**失敗は規則名と要素まで出す。** 件数だけを比べる形にすると、緑→赤になった
ときに何を直せばよいかが分からない（W12-4 の「読める失敗」と同じ）。

#### 5.1.10 判断: 負荷の期限は新しく決めず、運用が鳴らす値を借りる（2026-09-12 / W12-8）

k6 で `prediction_api` へ負荷を掛ける。ここで最初に要るのは「何秒なら合格か」
だが、**試験のために新しい数字を決めると、運用が鳴らす値と2つになる。**
2つあるものは必ず片方だけが動き、動いたことはずれたという理由では表に出て
こない（§5.1.1 と同じ形）。だから `infra/observability/alerts.yml` が既に
持っている値をそのまま期限にした。

  - 95パーセンタイルが 1 秒（`PredictionLatencyHigh`）
  - サービス側の失敗が 5%（`PredictionErrorRateHigh`）

**ずれを検知する側は、走らせる場所を増やさずに置いた**（§5.1.7）。負荷試験
そのものは backend と推論サービスの起動が要るので `verify` にも CI にも
載せられないが、**数字が一致していることは何も立てずに読める**。
`scripts/tests/perf-thresholds.test.mjs` を gates の層へ置き、
`web:gates:test`（verify と CI の中）で見る。単位が違う（秒とミリ秒）ので、
揃えずに比べて1000倍ずれたまま一致と読まないことも、テストに書いた。

k6 は手元へ入れずに docker イメージで走らせる。入れる道具を1つ増やすと
「その機械にだけ入っている検査」が生まれる。CI には載せないので、
**誰でも同じものを走らせられること**のほうが効く。

見ないことも書いた。モデルの精度、ClearML Server の性能、長時間の耐久。
数分の試験で分かるのは「いま、この配備が期限の内側で答えるか」だけである。

#### 5.1.11 判断: flaky は隠さない。数える道具だけを置く（2026-09-12 / W12-9）

振れるテストへの手当ては、たいてい2つのどちらかになる。隔離（skip /
quarantine）と retry である。**どちらも赤を消す**。赤が消えると直す理由も
消え、残るのは「そのうち見る」だけになる。とくに retry は、振れたテストを
緑にするので**検知そのものを無くす**。このシステムは失敗を一度で確定させる
（§5.1.6）。テストも同じ扱いにし、Playwright の `retries` は 0 のままにした。

置いたのは「同じものを繰り返して、振れるかどうかを数える」道具だけである
（`scripts/flaky.mjs`）。判定の単位はテスト1件にした。走行の成否で数えると、
1件が振れただけで全部が振れたことになり、どれを直せばよいか分からない。
Playwright が既に書いている JUnit XML を読む（報告を新しく作らない）。

**ずっと赤は flaky ではない。** 混ざったものだけを flaky と呼び、常に赤は
「壊れている」として分けて出す。走行ごとに実行された集合が違うことも別に出す。
名前が変わった・途中で落ちて残りが走らなかった、はどちらも「安定している」
とは言えない状態だが、原因も直し方も違う。

対象は E2E に絞った。下の層は時刻・並行・外部を持たない設計なので、そこが
振れるなら flaky ではなく設計の綻びである。CI では走らせない。同じ試験を
5回走らせる分だけ遅くなるだけで、**振れているかどうかは疑いが出てから
数えれば足りる**。

再発防止は運用として書いた（runbook 009）。原因を4つ（時間 / 順序・並行 /
外部 / 実装の非決定性）に分けて読む形にし、**4つ目を最初に疑う**ことを
明記した。振れているのがテストだと決めつけると、製品側の非決定性が
テストの書き換えで隠れる。

#### 5.1.12 判断: ADR は README から起こし、形ではなく理由だけを持つ（2026-09-12 / W12-10）

W11 から持ち越していた4つ（standalone / Signals と NgRx の責務 / lazy route /
error handling）を ADR 007 にした。書くときに効いたのは**分担**である。

`apps/web/README.md` には既に**形**が書いてある（ディレクトリ構成・feature の
標準形・命名・変更検知）。ADR へ形を書き写すと、片方を直したときにもう片方が
古くなる。W12-1 以降ずっと同じことを言っている「宣言が2つあると片方だけが
動く」であり、**文章同士でも同じことが起きる**。

そこで ADR が持つのは理由と代案だけにした。

  - なぜ standalone か（依存が component の中に書いてあること。module 経由だと
    `web-boundaries` の見ている「feature を跨いだ import」を回避できてしまう）
  - なぜ NgRx と Signal の両方か（複数の非同期が同じ state を触るので遷移の
    記録が要る。読む側は Signal に揃える）
  - なぜ provider を lazy route へ置くか（開かない利用者にとっては存在しない
    ほうが正しい。どこで state が生まれるかが route から読める）
  - 失敗をどう扱うか（必ず action へ変換する。重さで分ける。成功したら消す。
    失敗しても直前の結果は消さない）

**失敗の扱いだけは、README に無かった判断である。** 実装には入っていたが
（指標の取得失敗だけ `EMPTY` にする、`meta.result_msg` を出す、状態コード 0 は
通信の説明を出す）、どこにも書かれていなかった。ADR 化の効用は、こういう
**コードにしか無い判断**が1つ見つかることでもある。

## 6. Stage 3 — 読解力の到達度を上げる（学習軸）

### 6.1 何が残ったか

旧チェック表は19項目あったが、**P1〜P3 の16項目は実装台帳 W と同じ作業を
別名で指していた**（§0.1）。統合後、学習軸として固有に残るのは
**「既存 ClearML コードを読む」** 6項目だけである。

これは実装作業ではないので W にも A/B/C にも吸収できない。**ここだけが学習固有。**

| ID | 学習対象 |
| --- | --- |
| P0-0 | 学習ベースラインと安全網（変更前の test / typecheck / build を再現する） |
| P0-1 | Task一覧・詳細（route → API → state → UI を1本 trace する） |
| P0-2 | Queue / Agent（Queue投入から Task status 表示まで） |
| P0-3 | Pipeline（controller、step、失敗経路） |
| P0-4 | Evaluation / Model Registry（model から Task、Dataset、評価へ追跡） |
| P0-5 | Serving（Angular request から model version 付き response まで） |

### 6.2 到達度の判定

```text
Level 1: 読める        主要なファイルと責務を特定できる
Level 2: 説明できる    入力、state遷移、API、失敗経路、出力を図なしで説明できる
Level 3: 壊さず変更できる  仕様変更を小さな差分で実装し、テストを追加し、影響範囲を説明できる
```

**学習済みとみなすのは Level 3。** 完了は日数ではなく Level で判定する。

### 6.3 進め方

**Stage 1 / 2 の順番待ちにしない。** 実装の合間に1項目ずつ回す。
`quality-pipeline` は自作なので読めて当たり前で、**ベンダー feature を読めることが本題**である。

新規に同じ画面を作り直さない。まず既存実装を trace し、
**学習目標を満たす最小の変更**を加える。

## 7. 進め方のルール（Stage 共通）

### 7.1 1機能完成 → 徹底読解 → 小改修

一度に広く実装しない。独立して実行・確認できる小さな完成単位へ分け、次を回す。

```text
1. 対象ユースケースと完了条件を決める
2. 既存の処理経路と変更境界を探す
3. 設計上の選択肢と理由を確認する
4. コーディングエージェントに1機能だけ実装させる
5. diff をファイルごとに読む
6. 処理経路、state遷移、失敗時の動作を自分の言葉で説明する
7. 自分で別の小変更を加える
8. テストを意図的に壊し、原因を確認して直す
9. 学び、設計理由、未解決事項を短く記録する
```

作業量の目安は **Agent 70〜80% / 自分の読解・判断・変更 20〜30%**。

### 7.2 理由を確認せずに採用しない設計判断

- state をどの feature が所有するか
- Classic NgRx / Signals / SignalStore / component local state をどこで使うか
- Effect の責務と配置先
- API model / domain model / view model の変換境界
- polling / retry / timeout / cancel の責務
- Task、Pipeline、Model の ID をどの期間保持するか
- feature 間の依存をどの境界で止めるか

### 7.3 常に Angular へ戻る

ML 側だけを連続して進め、Angular を最後に回さない。
機能を1つ学ぶたびに、対応する ClearML Web の画面と Angular コードへ戻る。
