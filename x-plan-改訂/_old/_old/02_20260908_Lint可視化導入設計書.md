# Lint可視化導入設計書

## 1. 目的

AngularコードのLint違反を、開発者が次の画面で確認できるようにする。

- VS CodeのエディタおよびProblems画面
- GitHub Pull RequestのChecks画面
- GitHub Actionsの実行ログ
- Pull Requestの変更ファイルに付く注釈

既存のLint負債を理由に検査を無効化せず、既存負債を固定したうえで、新規・変更による負債の増加を防止する。

## 2. 背景と現状

2026-09-08時点の状況は次のとおりである。

| 項目 | 現状 |
| --- | --- |
| Lintコマンド | `corepack pnpm web:lint` |
| 対象 | `apps/web/src/**/*.ts`、`apps/web/src/**/*.html` |
| ESLint設定 | `apps/web/eslint.config.js` |
| 既存違反 | 2,871 errors / 56 warnings、合計2,927件 |
| GitHub Actions | test、E2E typecheck、production buildのみ |
| PR上のLint表示 | なし |
| VS Code共通設定 | なし |

全件を直してからCIへ導入する方法では、導入完了まで新しい違反を防げない。そのため、既存違反をベースラインとして管理し、導入時点から増加を検出する。

## 3. 適用範囲

### 3.1 対象

- `apps/web/src/**/*.ts`
- `apps/web/src/**/*.html`
- Angular ESLintおよびTypeScript ESLintの診断
- ローカル、VS Code、GitHub Actions、Pull Requestでの同一ルール利用

### 3.2 対象外

- 既存2,927件の一括修正
- PythonコードのLint導入
- GitHub上での自動修正またはBotによる自動コミット
- Lintルール自体の全面的な見直し

既存負債の解消は、機能変更と分離した品質改善タスクとして段階的に行う。

## 4. 基本方針

1. `apps/web/eslint.config.js`を唯一のLintルール定義とする。
2. ESLintのBulk Suppressionsで既存違反を記録する。
3. ベースラインに存在しない違反は、errorとwarningの両方をCI失敗にする。
4. ローカル、VS Code、CIで同じESLint設定を使用する。
5. CIの診断をGitHub Actionsのannotation形式へ変換し、PR画面から対象箇所へ移動できるようにする。
6. ベースラインの再生成を通常作業にせず、削減方向の更新だけを原則とする。
7. Lintの大量自動修正を機能変更のPull Requestへ混在させない。

## 5. 全体構成

```text
開発中
  VS Code ESLint extension
    └─ apps/web/eslint.config.js
         └─ エディタ上の赤線 / Problems表示

ローカル確認
  corepack pnpm web:lint
    ├─ apps/web/eslint.config.js
    └─ apps/web/eslint-suppressions.json

Pull Request
  GitHub Actions: Quality / Angular lint
    ├─ 同一Lintコマンドを実行
    ├─ 新規違反があればCheckを失敗
    ├─ Actionsログへ診断を出力
    └─ GitHub annotationとしてファイル・行番号を表示
```

## 6. 詳細設計

### 6.1 既存違反のベースライン

ESLintのBulk Suppressionsを使用し、`apps/web/eslint-suppressions.json`へ既存違反を記録してGit管理する。

初回生成の想定コマンドは次のとおりである。

```bash
corepack pnpm --dir apps/web exec eslint \
  "src/**/*.ts" \
  "src/**/*.html" \
  --suppress-all \
  --suppressions-location eslint-suppressions.json
```

運用上の制約は次のとおりとする。

- 初回生成後のベースライン件数が2,927件と一致することを確認する
- 通常の機能開発で`--suppress-all`を実行しない
- 新しい違反をベースラインへ追加してCIを通さない
- 既存違反を修正した場合は`--prune-suppressions`で不要な抑制を削除する
- ベースライン変更時は、Pull Requestで件数の増減と理由を確認する

Bulk Suppressionsはファイルとルール単位の既存件数を管理する。このため、同一ファイル・同一ルールで「既存違反を1件解消し、別の場所へ1件追加する」置換は件数だけでは検出できない。変更行の注釈確認とレビューを併用し、将来は変更行差分との照合を追加検討する。

### 6.2 package scripts

`apps/web/package.json`には用途別の入口を用意する。

| script | 用途 |
| --- | --- |
| `lint` | 開発者がローカルで実行する標準Lint |
| `lint:ci` | CI用。warningを含む未抑制診断を失敗させ、GitHub向け出力を行う |
| `lint:prune` | 解消済みの既存違反をベースラインから除去する |

ルートの`web:lint`は従来どおり`apps/web`の`lint`を呼び出す。検査対象は`angular.json`の現在の対象と一致させ、TypeScriptとAngular templateの両方を含める。

CIでは`--max-warnings 0`を指定し、新規warningも品質ゲートの失敗として扱う。既存抑制が不要になっただけで機能Pull Requestが失敗し続けないよう、通常検査では未使用抑制を許可し、定期的に`lint:prune`で削減する。

### 6.3 VS Code表示

リポジトリ直下に次のWorkspace設定を追加する。

- `.vscode/extensions.json`
  - ESLint extensionを推奨する
- `.vscode/settings.json`
  - ESLintのworking directoryを`apps/web`として解決可能にする
  - TypeScriptとHTMLを検査対象にする
  - 保存時のESLint自動修正は明示操作に限定する

エディタのリアルタイム診断はベースラインを隠すことを目的としない。開発者は既存診断も確認できるが、CIの合否はベースラインとの差分で判定する。

### 6.4 GitHub Actions

`.github/workflows/quality.yml`のAngular jobへ、依存関係のinstall後にLint stepを追加する。

```yaml
- name: Run Angular lint
  run: corepack pnpm --dir apps/web lint:ci
```

表示名は既存の`Angular tests, typecheck, and build`から、検査内容が分かる`Angular lint, tests, typecheck, and build`へ変更する。

Lintを先に実行し、静的に検出できる問題をunit testやbuildより早く返す。既存の`concurrency`設定は維持し、新しいcommitがpushされた場合は古い実行を中止する。

### 6.5 Pull Request注釈

CI専用のESLint formatterをリポジトリ内へ配置し、ESLintの各診断をGitHub Actions workflow commandへ変換する。

formatterの責務は次のとおりである。

- errorを`::error`として出力する
- warningを`::warning`として出力する
- file、line、column、rule ID、messageを含める
- GitHub Actionsの予約文字をescapeする
- 最後にerror数とwarning数のsummaryを出力する
- 診断が0件の場合は余分なannotationを生成しない

formatterにLint判定ロジックは持たせない。判定はESLint、表示変換だけをformatterの責務とする。第三者Actionへの依存を増やさず、依存先の改ざんリスクとversion固定管理を避ける。

Pull Requestでは次の順に確認できるようになる。

1. Checks欄で`Quality / Angular lint, tests, typecheck, and build`の成否を見る
2. 失敗時はannotationから対象ファイルと行へ移動する
3. 詳細が必要な場合はActionsログでrule IDとmessageを見る

### 6.6 Branch protection

CI導入後、GitHubのmain branch protectionまたはRulesetでAngular品質jobをRequired status checkに設定する。

この設定はGitHub管理画面上のリポジトリ設定変更であり、コードだけでは完了しない。リポジトリ管理者が設定し、Lint失敗中のPull Requestを通常の手順ではmergeできないことを確認する。

## 8. テスト設計

| テスト | 操作 | 期待結果 |
| --- | --- | --- |
| baseline | 既存コードを変更せずLint実行 | 成功する |
| TypeScript error | 新規TSファイルに明確な違反を追加 | CI失敗、error annotation表示 |
| TypeScript warning | warningルール違反を追加 | `--max-warnings 0`によりCI失敗 |
| Template error | 新規HTMLにtemplate違反を追加 | CI失敗、HTML行にannotation表示 |
| 既存負債削減 | 既存違反を1件修正してprune | 抑制件数が1件減り、Lint成功 |
| regression | test、E2E typecheck、buildを実行 | すべて成功する |
| branch rule | Lint失敗PRのmergeを試行 | 通常のmerge操作が拒否される |

formatterのunit testでは、複数ファイル、行・列なしの診断、errorとwarning、予約文字を含むmessage、診断0件を確認する。

## 9. 完了条件

以下をすべて満たした時点で導入完了とする。

- ローカルの共通コマンドでベースライン差分Lintを再現できる
- VS CodeでTypeScriptとAngular templateの診断を確認できる
- 新規errorとwarningのいずれでもCIが失敗する
- GitHub PR画面でCheckの成否と対象箇所を確認できる
- 既存2,927件が存在することだけを理由にCIが失敗しない
- ベースラインを増やす操作が通常の開発手順に含まれていない
- 既存負債を修正するとベースラインを削減できる
- Required status checkにより、Lint失敗PRのmergeを防止できる
- unit test、E2E typecheck、production buildへ回帰がない

## 10. 運用ルール

- 新規ファイルはerror / warningともに0件とする
- 既存ファイルを変更しても、ファイル・ルール単位の違反数を増やさない
- 変更行に起因する診断は既存負債として追加しない
- `eslint-disable`は対象rule、最小scope、理由を明記する
- ベースライン増加が必要な例外は、理由、期限、解消担当をPull Requestへ記載し、品質責任者の承認を必要とする
- `lint:prune`による削減は随時受け入れ、負債件数を継続的に減らす
- Lint設定変更は全体件数への影響を計測し、機能変更とは別Pull Requestで扱う

## 12. リスクと対策

| リスク | 対策 |
| --- | --- |
| ベースライン再生成で新規違反が隠れる | 再生成を通常手順から外し、変更理由と件数をレビューする |
| IDEとCIで結果が異なる | Node、pnpm、ESLint versionをリポジトリで固定し、同一configを使う |
| annotationが大量になり見づらい | 既存違反を抑制し、未抑制の新規診断だけを出す |
| formatterがLint判定へ影響する | formatterは表示変換に限定し、終了codeはESLintに委ねる |
| 自動修正が機能diffを汚す | 保存時の一括修正を標準化せず、品質改善PRへ分離する |
| 同一rule内の違反置換を見逃す | 変更行のannotationとレビューを併用し、差分照合を将来拡張とする |
| Required check名変更で保護が外れる | job名を安定させ、変更時にRulesetも同時確認する |
