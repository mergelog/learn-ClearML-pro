# Prettier導入設計書

## 1. 目的

Angularコードの書式を開発者やIDEに依存させず、ローカル、VS Code、CIで一貫させる。

特にAngular HTMLテンプレートの属性配置を統一し、次のような同一行への複数属性記述を自動的に解消する。

```html
<sm-project-card
  [project]="project" (projectCardClicked)="projectCardClicked($event)"
  [hideMenu]="true"
></sm-project-card>
```

整形後は、各属性が1行になることを保証する。

```html
<sm-project-card
  [project]="project"
  (projectCardClicked)="projectCardClicked($event)"
  [hideMenu]="true"
></sm-project-card>
```

## 2. 背景と現状

2026-09-09時点の状況は次のとおりである。

| 項目 | 現状 |
| --- | --- |
| Angular | 22系 |
| package manager | pnpm 10系のworkspace |
| Angular package | `apps/web/package.json` |
| Formatter | 未導入 |
| Linter | ESLint 10 + angular-eslint 22 |
| 基本書式 | `apps/web/.editorconfig`でスペース2文字などを指定 |
| format script | なし |
| CIのformat check | なし |
| VS Code共通設定 | なし |
| Angularソース | TS、HTML、SCSSを合わせて約2,191ファイル |

現在は手作業または各開発者のIDE設定に書式が依存しており、同一ファイル内でもインデントや属性改行にばらつきがある。

## 3. 基本方針

1. Prettierをコード整形専用、ESLintをコード品質検査専用とする。
2. Angular専用Prettierプラグインは追加せず、Prettier内蔵のAngular parserを使用する。
3. Prettierは`apps/web`のdevDependencyとしてexact versionで固定する。
4. Angularソースの属性は`singleAttributePerLine`で1行1属性に統一する。
5. ローカル、VS Code、CIはリポジトリに固定された同じPrettierを使用する。
6. 初回の全体整形は機能変更やLint修正と分離した専用Pull Requestで行う。
7. CIでは自動修正せず、未整形を検出して失敗させる。
8. PythonなどAngular外のコードは今回の適用対象に含めない。

## 4. 責務分離

```text
Prettier
├─ インデント
├─ 改行
├─ セミコロン
├─ クォート
├─ TypeScriptの空白
├─ Angular HTMLテンプレート
└─ SCSS、JSONなどの書式

ESLint + angular-eslint
├─ TypeScriptの問題検出
├─ Angularの推奨事項
├─ Component / Directive規約
├─ Angular templateの問題検出
└─ NgRxなどのコード品質ルール
```

PrettierをESLint内部で実行する`eslint-plugin-prettier`は使用しない。検査結果と整形結果を別コマンドに保ち、障害原因と実行時間を判別しやすくする。

## 5. 適用範囲

### 5.1 対象

- `apps/web/src/**/*.ts`
- `apps/web/src/**/*.html`
- `apps/web/src/**/*.scss`
- `apps/web`直下のJavaScript、TypeScript、JSONなどの設定ファイル
- `apps/web`配下のテストコードとE2Eコード

### 5.2 対象外

- Pythonコード
- ルートのMarkdown資料
- `node_modules`、`build`、`coverage`、`.angular`などの生成物
- vendored asset、minified file、自動生成ファイル
- Prettierで対応していないファイル形式
- 既存ESLint違反の修正
- GitHub Actionsによる自動commit
- pre-commit hookの導入

対象外パスは`.prettierignore`に明記する。`src/assets`などに自作ファイルと外部取得ファイルが混在する場合は、ディレクトリ全体を機械的に除外せず、所有範囲を確認して個別に指定する。

## 6. 依存関係

`apps/web`へ次のdevDependencyを追加する。

```bash
pnpm --dir apps/web add -D --save-exact prettier@3.9.6 eslint-config-prettier
```

| package | 目的 |
| --- | --- |
| `prettier` | TypeScript、Angular HTML、SCSS、JSONなどの整形 |
| `eslint-config-prettier` | Prettierと競合するESLint書式ルールの無効化 |

`pnpm-lock.yaml`も同じPull Requestで更新する。Prettierのversion更新はDependabotなどの通常依存更新とは分離し、更新前後のformat差分を確認する。

## 7. Prettier設定

`apps/web/.prettierrc.json`を追加する。

```json
{
  "singleQuote": true,
  "semi": true,
  "printWidth": 120,
  "tabWidth": 2,
  "bracketSpacing": false,
  "singleAttributePerLine": true
}
```

各設定の意図は次のとおりである。

| option | 値 | 意図 |
| --- | --- | --- |
| `singleQuote` | `true` | 現在のTypeScriptとESLintのクォート方針を維持する |
| `semi` | `true` | 文末セミコロンを明示する |
| `printWidth` | `120` | 大規模Angularコードでの一覧性と折り返しのバランスを取る |
| `tabWidth` | `2` | 既存`.editorconfig`と一致させる |
| `bracketSpacing` | `false` | 現行コードで多数派の`{Component}`形式を維持し、初回差分を抑える |
| `singleAttributePerLine` | `true` | HTML要素とAngular componentの属性を1行1属性にする |

`semi`と`tabWidth`はPrettierの既定値とも一致するが、チームの合意事項として明示する。

`parser`は設定しない。Prettierにファイル拡張子からAngular、TypeScript、SCSSなどを自動判定させる。

## 8. ignore設計

`apps/web/.prettierignore`を追加し、少なくとも次を除外する。

```text
.angular
build
coverage
node_modules
playwright-report
test-results
```

追加で次を調査し、外部取得物または生成物だけを除外する。

- `src/assets`
- `src/app/webapp-common/assets`
- minified JavaScript / CSS
- generated API model
- test fixtureやsnapshot

`.gitignore`任せにせず、Formatterの対象外である理由を`.prettierignore`から判別できる状態にする。

## 9. ESLint連携

`apps/web/eslint.config.js`で`eslint-config-prettier`を読み込み、すべてのESLint設定より後に適用する。

現在明示されている次の書式ルールはPrettierへ責務を移す。

```js
"quotes": ["error", "single", ...]
```

ESLintから書式ルールを削除しても、`.prettierrc.json`の`singleQuote: true`により同じ表現を維持する。

`eslint-config-prettier`適用後に、次を確認する。

- PrettierとESLintを連続実行しても同じ箇所を書き換え続けない
- TypeScript ESLintの品質ルールが無効化されていない
- angular-eslintのtemplate検査が維持されている
- NgRxルールが維持されている

既存Lint負債の扱いとCI可視化は`02_20260908_Lint可視化導入設計書.md`に従う。

## 10. package scripts

`apps/web/package.json`へ次を追加する。

```json
{
  "scripts": {
    "format": "prettier . --write",
    "format:check": "prettier . --check"
  }
}
```

ルートの`package.json`にはworkspace利用者向けの入口を追加する。

```json
{
  "scripts": {
    "web:format": "pnpm --dir apps/web format",
    "web:format:check": "pnpm --dir apps/web format:check"
  }
}
```

用途は次のとおりである。

| command | 用途 |
| --- | --- |
| `corepack pnpm web:format` | Angular対象全体を自動整形する |
| `corepack pnpm web:format:check` | 書き換えずに未整形ファイルを検出する |
| `corepack pnpm web:lint` | ESLintによる品質検査を行う |

## 11. VS Code設定

リポジトリ直下の`.vscode`へ次を追加する。

- `.vscode/extensions.json`
  - `esbenp.prettier-vscode`
  - `dbaeumer.vscode-eslint`
- `.vscode/settings.json`
  - TypeScript、HTML、SCSS、JSONだけにPrettierを指定する
  - 対象言語で保存時formatを有効にする
  - ESLintのworking directoryを`apps/web`にする
  - ESLintの保存時fixは`explicit`にする

リポジトリにはPythonも含まれるため、`editor.defaultFormatter`を全言語共通には指定しない。

現在ルート`.gitignore`は`.vscode/`全体を除外しているため、共有するファイルだけを追跡できるよう、次を例外指定する。

```gitignore
.vscode/*
!.vscode/settings.json
!.vscode/extensions.json
```

保存時処理の順序には依存しない。PrettierとESLintが競合しない設定を前提とし、どちらを先に実行しても最終結果が安定することを確認する。

## 12. CI設計

`.github/workflows/quality.yml`の`web-quality` jobで、依存関係install後にformat checkを追加する。

```yaml
- name: Check Angular formatting
  run: corepack pnpm web:format:check
```

Lint可視化計画の導入後は、Angular品質検査を次の順番にする。

```text
依存関係install
  ↓
Prettier format check
  ↓
Angular lint
  ↓
unit test
  ↓
E2E typecheck
  ↓
production build
```

静的で短時間の検査を先に置き、失敗を早く返す。CIでは`--write`を使用せず、修正は開発者がローカルで行う。

ルートの`verify`にも`web:format:check`と`web:lint`を含め、ローカルの総合検証とCIの検査漏れを防ぐ。

## 14. テスト設計

| テスト | 操作 | 期待結果 |
| --- | --- | --- |
| TypeScript | 未整形TSへ`web:format`を実行 | single quote、semicolon、空白、改行が統一される |
| Angular HTML | 複数属性を同じ行へ記述 | 1行1属性へ整形される |
| Angular control flow | `@if`、`@for`、`@switch`を整形 | parse errorなく構文が維持される |
| SCSS | 未整形SCSSを整形 | 構文を維持して書式だけが変わる |
| ignore | 生成物またはvendor fileを未整形にする | `format`と`format:check`の対象にならない |
| check failure | 対象ファイルを未整形にする | `format:check`がexit code 1で失敗する |
| idempotence | `format`を2回実行 | 2回目に差分が発生しない |
| ESLint compatibility | format後にlintを実行 | 書式ルールとの競合が発生しない |
| regression | test、typecheck、buildを実行 | すべて成功する |
| VS Code | 対象ファイルを保存 | リポジトリ設定と同じ結果になる |
| CI | 未整形commit相当を検査 | format checkでjobが失敗する |

## 15. Pull Request分割

原則として次の単位に分ける。

### PR 1: Prettier基盤と初回整形

- dependencyとlockfile
- Prettier設定とignore
- ESLint競合回避
- package scripts
- Angularコード全体の機械的整形

初回整形を含むため、機能変更、リファクタリング、Lint違反修正を混在させない。

### PR 2: 開発者体験とCI

- VS Code設定
- GitHub Actionsのformat check
- ルート`verify`更新
- 必要な運用文書

Lint可視化計画を同時期に実施する場合、`.vscode`、CI、`verify`の変更競合を避けるため、PR 2はLint可視化PRの後にrebaseして統合する。

## 16. 完了条件

以下をすべて満たした時点で導入完了とする。

- Prettierが`apps/web`のexact devDependencyとして固定されている
- Angular専用Prettierプラグインを追加していない
- TS、Angular HTML、SCSSを同じ設定で整形できる
- Angular HTMLの複数属性が1行1属性へ統一される
- PrettierとESLintが書式上競合しない
- ローカルで`web:format`と`web:format:check`を実行できる
- VS Codeの保存時整形がリポジトリ設定を使用する
- CIが未整形ファイルを検出して失敗する
- CIがlint、test、typecheck、buildを継続して実行する
- 初回全体整形に意味的変更が含まれていない
- 2回連続のformatで結果が変化しない
- Pythonや対象外ファイルの開発環境へ影響しない

## 17. 運用ルール

- Prettierの出力を手作業で崩さない
- 書式だけの議論をコードレビューで繰り返さず、Prettier設定を基準とする
- `prettier-ignore`は生成コードや構文上必要な場合に限定し、理由をコメントまたはPull Requestへ記録する
- Prettier version更新は専用Pull Requestで行い、全体差分を確認する
- 機能Pull Requestへ全体formatを混在させない
- CI失敗を回避するために対象ファイルを`.prettierignore`へ追加しない
- Formatter方針を変更する場合は、個人のIDE設定ではなくリポジトリ設定を更新する

## 19. リスクと対策

| リスク | 対策 |
| --- | --- |
| 初回差分が巨大になる | 専用PRに分離し、意味的変更を禁止する |
| vendorやgenerated fileを書き換える | 所有範囲を調査し`.prettierignore`へ明記する |
| PrettierとESLintが競合する | `eslint-config-prettier`をESLint設定の最後に適用する |
| 開発者ごとに出力が異なる | exact versionとリポジトリ設定を使用する |
| VS Code設定がPythonへ影響する | Formatter指定を対象言語に限定する |
| Angular新構文をparseできない | 導入前に代表構文を検証し、version更新判断を行う |
| CI追加直後に全PRが失敗する | 初回全体整形を先にmergeし、その後CIを必須化する |
| Lint計画と設定変更が競合する | Lint可視化計画と順序を決め、共通ファイルを後続PRで統合する |
