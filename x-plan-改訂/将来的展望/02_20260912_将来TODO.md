## 2. T-2: 9本を貫く通し台本が無い

### 状態

⬜ 未着手（T-1 を先にやると書きやすい）

### 何が起きているか

runbook 9本は**部品ごとに独立**している。1本ずつは異常系まで書かれていて質は高いが、
それらを一続きに演じる筋書きが無い。

想定する筋書き:

```text
新しいデータが来た
  → 品質判定（005）
  → 学習（002）
  → 探索（008）
  → 昇格（003）
  → 配備（004）
  → ドリフト検知（006）
  → rollback（003 §5）
  → postmortem（006）
```

各段の観測点として台帳（T-1）を挟むと、**「いま何を見ているのか」が一本の線になる。**
だから T-1 を先にやるほうが書きやすい。

### 成果物

`docs/runbooks/010_{日付}_{名前}.md` を新規1本。
既存9本へのリンクと、各段の**合否の判定**と**観測点**だけを書く。
**手順そのものを書き写さない**（二重管理になって必ずずれる）。

### 規模

| 項目 | 見積 |
| --- | --- |
| コード変更 | **ゼロ** |
| 文書 | 新規 100〜150行・**既存ファイルは触らない** |
| ゲートへの影響 | 無し |
| 実機確認 | **半日〜1日**。ここが本体 |

### 実機確認が重い理由

`docs/README.md` は「別の人が同じことを再現できるか」を基準にした資料だけを置くと
宣言している。**机上で書いて置くのは趣旨に反する**ので、一度は通す必要がある。

- `../learn-ClearML` を先に `backend:down`（ポート 8008 / 8080 / 8081 が共有・同時起動不可。
  詳細は `AGENTS.local.md`）
- `backend:up` → `agent:up` → seed → 学習 → 昇格 → `serving:up` → `ops:up` を起動しっぱなしにする
- ドリフトと rollback まで演じるなら、**故意に条件を作る手間**が乗る

つまり「修正が大規模」なのではなく、**実行に時間がかかる**種類の作業である。

### 着手の条件

通しで実機を動かせる日を確保できること。
`_old/_old/予定_0915_limitが残る場合は最終日に大規模レビューを実施する` の題材として
噛み合うので、**そこに寄せるのが素直。**
