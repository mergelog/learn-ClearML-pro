## 目的
プロジェクト参画者が最短で理解できる資料を段階的に作成する

作成場所: x-start-docs
ファイル名: {2桁連番}_適切なファイル名.{拡張子}

## 方針
資料を作ること自体を目的にしない。
新規参画者の理解に寄与しない詳細資料は作成しない。

## 基本規約

* 指定がない場合は Markdown で作成する。
* 内容に応じて HTML、Mermaid、シーケンス図、CSV 等を使用してよい。
* 初学者が誤った理解をしないことを最優先する。
* 確認できていない内容を事実として記載しない。
* 判断できない内容は「不明」とする。
* 合理的に推測できても確定できない内容は「推測」であることを明記する。
* 一般的な設計やベストプラクティスを、このプロジェクト固有の仕様として記載しない。
* ディレクトリ名、クラス名、関数名だけから責務を断定しない。
* ライブラリや機能が存在することと、実際に使用されていることを区別する。
* 現在使われている実装、過去の実装、サンプル、試験的コード、未使用コードを可能な限り区別する。
* 業務仕様と、コードから観測できる現在の挙動を混同しない。
* 設計理由をコードの形から推測して事実として記載しない。

## 資料について
- 記載する内容の前提として、冒頭に表形式の「まとめ」を記載する。冒頭であることを間違えないように注意
- ドメイン特有の専門用語を使用する場合で説明不足が懸念される場合、「****とは」の解説を設ける。但し「今理解する必要のある粒度」に留めること。
- 理解できたか確認するテストは不要

## 作成において
- ファイルは1ファイルずつ完成してから次に進む。但し過去に作成したファイルに誤りがある場合の修正は即時対応すること
- 読む人が記憶できないレベルで最初からあれこれ書かない。
  但し、省略した部分はその旨記載して別途既存資料の参照が必要なことを注記する。

## 作成する資料一覧

プロジェクト概要
- [ ] プロジェクト概要をざっくり解説。
- [ ] frentendから関係するバックエンド一覧

前提ドメイン知識
- [ ] ドメインモデルではなく、業務システムとしての企画・概要説明。何をするためのプロジェクトかから始まる
- [ ] 業務システムとしての詳細説明

入り口
- [ ] アーキテクチャ一覧。登場人物別
- [ ] 俯瞰図レベル1作成（インタラクティブなHTML）: 大雑把な全体構成（俯瞰図レベル2の作成も控えているので意識する）
- [ ] 俯瞰図レベル2作成（インタラクティブなHTML）: 大雑把な全体構成で出てきた登場人物ごとの詳細解説。初学者の理解が重くならない程度

環境について
- [ ] 実行環境一覧。登場人物ごとにわかりやすく。本番/テスト/開発 それぞれ

コード解析初級
- [ ] フォルダ構成（説明付きtree構造）
- [ ] ドキュメントがある場所。把握する優先度

frontendコード解析中級（状態管理について）
- [ ] 状態管理の使用している機能と、使用していない機能
- [ ] 状態管理仕組みごとのスコープ（例: @ngrx/store は基本的にアプリ全体で共有するグローバル状態向けで、ローカルな状態には @ngrx/signals となっているか）
- [ ] 状態管理の経路（全体を見渡した場合の基本構造）
- [ ] createAction、createActionGroupの使用率とそれぞれの時期

コード解析その他
- [ ] 層毎の責務一覧。説明資料作成においてどのように「層」を分けるのが適切かから検討する
- [ ] エラー処理のアーキテクチャ

作業履歴からの推測
- [ ] frontendで最近実施した機能改修に関する情報を確認（直近3ヶ月）
- [ ] frentend改修時の、backendとの関わり解説
- [ ] 過去の開発履歴から想定するこのプロジェクトの作業作法
