## まとめ

| 項目 | 内容 |
|---|---|
| 目的 | Angular フロントエンド（`src/app`）の不具合を洗い出し、1件1ファイルで記録する |
| 対象の規模 | コンポーネント339（全352から、§1.2 で対象外にする `features/data-catalog`・`features/quality-pipeline` の13を除いた数）。`.ts` / `.html` は spec を除いて1,818ファイル、うち §1.2 で対象外にする `business-logic/model`・`report-widgets`・`features/data-catalog`・`features/quality-pipeline` を除くと1,174ファイル |
| 探し方 | 横断観点で候補をコードから機械的に拾う方向と、画面ごとに操作して確かめる方向の2本 |

| 調査中の制約 | ソースコードは変更しない。修正は別途指示を受けてから行う |

## 1. 対象と範囲

### 1.1 対象にするもの

`src/app` 配下の `.ts` / `.html` / `.scss` をすべて対象にする。そのうえで、次の部分を重点にする。

| 重点 | 理由 |
|---|---|
| 実験管理画面（一覧・インライン編集・詳細タブ） | 既出の IME 不具合と名前変更の不具合がある。既存資料（ngbi-01・03、x-sequense/01、x-QA/00〜03）で処理の流れを把握済みで、確認を早く回せる |
| 共通 UI 部品（`webapp-common/shared/ui-components`） | インライン編集・テーブル・検索・タグ入力などが全画面で使われており、1件の不具合が多くの画面に出る |
| 上流と中身が違う共通ファイル（実質差分39ファイル） | 書き換えの過程で挙動が変わった可能性がある。内訳は [x-ClearML_公式とカスタマイズ済み比較.md](../x-ClearML_公式とカスタマイズ済み比較.md) §6 のとおりで、Angular 22 / PrimeNG 22 追随は4ファイル、新 feature への導線追加が5ファイル、パス（import・`templateUrl`・`styleUrls` など）の書き換えだけのものが18ファイルなど |
| changeDetection を指定していない109コンポーネント | §3 観点D。すべて上流から来たファイルで、自前で手を入れたのは `experiment-info-execution.component.ts` だけ。上流では Default だったものが、Angular 22 では OnPush として動いている |

上流 ClearML（v2.5）由来の不具合も対象にする。資料には「由来」欄を設けて区別する。由来によって、直す場所（自前で直す、上流に報告する、上流の取り込み時に衝突を覚悟する）が変わるためである。

### 1.2 対象にしないもの

- `business-logic/model` の型定義そのもの（型と API 応答の食い違いは、使う側の不整合として扱う）
- `webapp-common/clearml-applications/report-widgets`（別アプリ。余力があれば最後に見る）
- 自前で追加した画面 `features/data-catalog`・`features/quality-pipeline`（64ファイル）。既存画面に足した導線（サイドナビ・モデル情報ヘッダー・データセット版詳細のリンク、`app.routes.ts` の lazy route）は既存ファイル側の変更なので対象に残す
- バックエンド（ClearML server、Python の `ml/`・`services/`）の不具合。ただし、フロントエンドが API 応答を誤って扱う不具合は対象にする
- `src/app` 内の調査用 `.md`、`_old`
- 4200 側のログイン画面（x-todo.md のとおり、使えない設計）

### 1.3 不具合として数えるもの・数えないもの

数えるものは次の5種類である。

1. 画面の表示・操作が、利用者の意図や UI 上の約束（ボタンの表記、確認ダイアログの文言など）と違う結果になるもの
2. 内部状態の不整合。Store・コンポーネント・URL・サーバのあいだで値が食い違う、同じ処理が二重に走る、購読やタイマーが破棄されずに残る、など。画面に症状が出ていなくても数える
3. 日本語で起きる欠陥。IME 操作、全角文字、空白を含まない長い日本語文字列、日本語を含むファイル名・URL・検索語
4. 操作性の欠陥。キーボードだけで操作できない、フォーカスが失われる、二度押しで二重に実行される、など
5. 利用者の入力した値が、HTML やスクリプトとして解釈される欠陥（§3 観点C）

数えないものは、命名・書式・コメントなど、挙動の差も状態の不整合も伴わない品質上の指摘である。UI の文言が英語であること（多言語化されていないこと）も数えない。日本語を入力・表示したときに壊れるものは数える。

仕様か不具合か判断できないものは、確度「要確認」で登録し、判断をユーザに仰ぐ。

## 2. 確認の方法

### 2.1 確認手段

| 手段 | 使う場面 | やり方 |
|---|---|---|
| 静的解析 | すべての観点 | grep で候補を拾い、呼び出し元と状態の流れを辿って不具合かどうかを確定する |
| 自動の動的確認 | 画面で再現できるもの | Playwright。不具合の再現では、API は既存の `e2e/fixtures` と同じくモックで返すのを基本にし、モックで再現できないものだけ起動中のバックエンド（Compose プロジェクト `learn01-clearml`）を使う。フェーズ0の全ルート巡回は実バックエンドで行う |
| IME の模擬 | 日本語入力の不具合 | ① `isComposing: true` / `keyCode: 229` を持つ `KeyboardEvent` を合成して dispatch し、ハンドラの判定を確かめる ② CDP の `Input.imeSetComposition` / `Input.insertText` で compositionstart〜compositionend を発生させる ③ ②で変換中の状態を作り、そのあいだに①の keydown を dispatch する |
| 実機での確認（ユーザに依頼） | 模擬で決着しない IME の挙動 | Windows の Chrome / Edge と Microsoft IME、macOS の Safari / Chrome と日本語入力。依頼事項は §6 に集める |

②は composition と input のイベントだけを発生させ、keydown を1回も発生させない（Playwright の Chromium で確認済み。①の `keyCode: 229` と `isComposing: true` もそのまま値に入ることを確認済み）。そのため②は、変換中の `(input)`・`ngModel`・DOM の値を確かめる用途に使う。Enter・Esc・Tab・矢印キーの判定は①か③で確かめる。

IME の模擬は、実際の IME と keydown の届き方（compositionend との前後、`key` が `'Enter'` か `'Process'` か）が一致する保証がない。そのため、模擬で再現できたものは確度を「コード上確定」までとし、ブラウザごとの症状は「要実機確認」として残す。Playwright の設定は Chromium だけなので、Safari 固有とされる順序（keydown より先に compositionend が届く。x-QA/02）は模擬できない。

### 2.2 起動と調査データ

- アプリは `ng serve --host 0.0.0.0 --port 4200` で起動する。実バックエンドを使う場合は、先に 8080 の ClearML 標準画面でログインしてから、同じブラウザ・同じホスト名で 4200 を開く（x-todo.md）。Playwright で実バックエンドを使う場合も、同じブラウザコンテキストで先に 8080 にログインする
- バックエンド（Compose プロジェクト `learn01-clearml`）の起動・停止は、ユーザの了承を得てから行う。ポート 8008 / 8080 / 8081 を併存リポジトリ `../001-learn-ClearML` と共有しており、同時には起動できない（AGENTS.local.md）
- 長い日本語名・絵文字・全角空白を含む名前などの調査データは、Playwright のモックで用意するのを基本にする。既存のモックは `page.route('**/service/**')` で API を横取りする形で、対象の画面で使えるのはスモークと Execution タブの分だけである（ほかにデータカタログ・品質パイプラインの分があるが、対象外の画面）。ほかの画面は、必要になった時点でモックを足すか実バックエンドを使う
- 実バックエンドにデータを書き込む必要が出た場合は、調査専用のプロジェクトを作って投入する。投入の前にユーザの了承を得る

### 2.3 由来の判定

由来は次の3区分で記録する。

| 由来 | 判定条件 |
|---|---|
| 上流 | 上流 v2.5 と同じコードで、上流の依存バージョン（Angular 21 系）の挙動を前提にしても同じ症状が出るもの。上流を Angular 21 で起動して確かめるのではなく、コードと Angular 21 の実装から判断する。Angular 21 の実装は `npm pack @angular/core@21.2.22` などで作業用ディレクトリに取得して読む（プロジェクトの `node_modules` は変えない） |
| カスタマイズ | 自前で追加・変更したコードが原因のもの（実質差分39ファイルなど。新 feature 2本は §1.2 で対象外） |
| 版上げ | コードは上流のままだが、Angular 22（Material・CDK を含む）/ NgRx 22 / PrimeNG 22 への更新で挙動が変わったもの（既定の OnPush 化など） |

判定には上流 v2.5 のソースが要る。`upstream` リモートは登録済みだが何も取得していない。比較資料の作成に使った公式ソースは別端末のパス（`/Users/yasu/...`）にあり、この環境からは読めない。そのため、次のどちらで取得するかを着手前にユーザに確認する。

- 第一案：このリポジトリの外へ浅く clone する（`git clone --depth 1 --branch v2.5 https://github.com/clearml/clearml-web.git ../clearml-web-v2.5`）。このリポジトリの `.git` には手を加えない
- 第二案：このリポジトリに浅く fetch する（`git fetch --depth 1 upstream tag v2.5 --no-tags`）。タグと shallow の記録が `.git` に増える

取得しない場合は、比較資料を使って次のように判定する。

- 比較資料 §1 の「カスタマイズ版にしか無い」77ファイル（新 feature 64、`.md` 7、`.ts` 6。新 feature 64 は §1.2 で対象外）と、§5・§6 の分類4〜10で名前が挙がっているファイルは、カスタマイズとする
- それ以外のファイルは、上流と内容が一致するもの（2,262）、エイリアス改名だけが違うもの（§6 分類1、134）、パスの書き換えだけが違うもの（§6 分類2・3、18）のどれかである。分類1〜3はファイル名が資料に無いが、どれも挙動は上流と同じなので、上流のコードとして扱う

## 3. 横断観点

コード全体から候補を拾うための観点である。件数は 2026-09-22 時点の grep の結果で、候補の数であって不具合の数ではない。

### A. キーボード操作と IME

| 見る対象 | 件数 |
|---|---:|
| `(keydown.enter)` | 12 |
| `(keyup.enter)` | 11 |
| `(keyup)` / `(keydown)` / `(keypress)`（キー指定なし） | 19 |
| `(keyup.arrowUp/Down/Left/Right)` | 19 |
| `(keydown.tab)` / `(keydown.shift.tab)` / `(keydown.escape)` | 6 |
| `@HostListener` のキー系 | 8 |
| `fromEvent(..., 'key...')` | 2（うち1件の `select-autocomplete-with-chips` はどこからも使われていない部品） |
| `(input)` | 9 |
| `isComposing` / `composition*` を扱っている箇所 | 0 |

確認すること：

- 変換確定の Enter、変換取消の Esc、変換候補を選ぶ矢印キー、未確定のまま押した Tab で、確定・取消・移動の処理が走るか
- `(keyup)` や `(input)` で検索を実行する箇所が、変換中の文字列（ローマ字や未確定のかな）で API を呼ぶか。debounce の有無も見る
- `document:keydown` などのグローバルなショートカットが、入力欄で文字を打っている最中に反応するか
- Angular Material の部品（`mat-autocomplete` の Enter での候補選択、`matChipInputTokenEnd` の区切りキー、`mat-select` の文字入力による選択）が変換中のキーをどう扱うか。部品側の実装を `node_modules` で確認してから判断する

### B. 文字列の値の扱い

- `trim()` の有無、全角空白（U+3000）、空白だけの名前
- 長さの判定。`length` は UTF-16 の単位で数えるため、絵文字などのサロゲートペアで1文字を2と数える。`maxlength` 属性と `Validators.maxLength` の食い違いも見る
- 最小文字数の検証。入力欄の下限と保存処理の下限が食い違う箇所（既出：実験名は入力欄が2文字以上、保存処理が前後の空白を除いて3文字以上。フェーズ1の06）。日本語は2文字で意味の通る名前（「実験」など）が多いため、下限そのものが仕様として妥当かも要確認の候補にする
- 検索語の扱い。正規表現として API に渡す箇所でエスケープしているか、大文字小文字・全角半角をどう扱うか
- 並び替え。`localeCompare` を使っているか、日本語の並び順
- URL。日本語や記号をクエリパラメータに載せたときのエンコード・デコード（検索語の URL 保存など）
- ファイル名。エクスポート・ダウンロードのファイル名に日本語を含めたとき

grep の起点：`.trim()`、`Validators.(minLength|maxLength|pattern)`、`new RegExp(`、`localeCompare`、`encodeURIComponent`、`.download =`、`Content-Disposition`

### C. 文字列の表示とレイアウト（日本語、HTML として描画される値）

- 空白を含まない長い日本語は改行位置が無いため、テーブルのセル・パンくず・ヘッダー・カード・ツールチップ・ダイアログのタイトルではみ出すか、省略記号（…）が正しく出るか。`white-space` / `word-break` / `overflow-wrap` / `text-overflow` の組み合わせを見る
- 文字数で切り詰めるパイプが、サロゲートペアの途中で切っていないか
- 日時・数値の表示（DatePipe のロケールとタイムゾーン、相対時刻）
- `font-family` に和文フォントの指定が無い場合の字形と行の高さ
- 利用者が付けた名前を HTML として描画する箇所。`[innerHTML]` は14箇所で、プロジェクト名を `breadcrumbsEllipsis` パイプ経由で流し込むもの（`project-card`・`nested-card`・`pipeline-card`）や、名前を文字列連結で埋め込んだ確認ダイアログの本文（`projects-page.component.ts` の削除確認など）がある。`<`・`&` を含む名前の表示が崩れないか、サニタイズを回避する `bypassSecurityTrust*`（`safe` パイプ内の6箇所と、markdown のチートシートの1箇所）に利用者の値が届かないかを見る

### D. 変更検知と描画（Angular 22 で変わった点）

Angular 22 では、changeDetection を指定しないコンポーネントが OnPush として動く。`@angular/core` の実行時のコンポーネント定義が `onPush: componentDefinition.changeDetection !== ChangeDetectionStrategy.Eager` であり、Eager を指定しない限り OnPush になる（[_debug_node-chunk.mjs:10148](../node_modules/@angular/core/fesm2022/_debug_node-chunk.mjs#L10148)。型定義にも `NOTE: OnPush is enabled by default.` とある。`Default` は `Eager` と同じ値の非推奨の別名）。上流が使う Angular 21 系では同じ箇所が `onPush: componentDefinition.changeDetection === ChangeDetectionStrategy.OnPush` であり（21.2.22 で確認）、指定の無いコンポーネントは Default として動いていた。

変更検知の起動方式は上流・現在とも zoneless で、ここは版上げで変わっていない。`app.config.ts` に `provideZoneChangeDetection()` が無く、Angular 21・22 とも `bootstrapApplication` は既定で zoneless になる（zone.js は polyfills で読み込まれているが、変更検知の起動には使われない）。したがって上流の Default のコンポーネントも、どこかで変更検知が起動したときにまとめて検査されていただけで、自分で起動していたわけではない。OnPush になると、自分のビューに印が付かない限り、ほかの箇所で変更検知が起動しても検査されない。

| 区分 | コンポーネント数 |
|---|---:|
| 全体 | 339（対象外の report-widgets の1を含む。対象外の data-catalog・quality-pipeline の13は除く） |
| OnPush を明示 | 229 |
| Eager / Default を明示 | 1（`open-dataset-card`、Default） |
| 指定なし（上流では Default、現在は OnPush） | 109（すべて上流から来たファイル） |

指定の無いコンポーネントのうち、次のものは値が変わっても再描画されない可能性がある。

- signal でも入力でもないフィールドを、`subscribe`・`setTimeout`・Promise のコールバックで書き換え、`markForCheck()` を呼んでいないもの。テンプレートのイベントハンドラの中で同期的に書き換えるものはビューに印が付くので対象外だが、イベントから始めた `subscribe`・`setTimeout` のコールバックでの書き換えは対象に含む
- 入力で受け取ったオブジェクトを、参照を変えずに中身だけ書き換えているもの

実例として、`experiment-info-execution.component.ts` に `markForCheck()` を追加した修正がある（比較資料 §5、タスク切替時に再描画されなかった件）。同じ型を109コンポーネントから探す。

あわせて次も確認する。

- signal を呼ばずに真偽値として評価しているテンプレート（`scrollable && noDataTop` の型。関数そのものは常に truthy になる）。比較資料 §6.1 で上流の潜在バグとして1種類見つかっている
- PrimeNG 22 で signal になったプロパティを、値として読んでいる箇所。比較資料 §6.1 で `table.component.ts` の `first`・`selection`・`wrapperViewChild` を直した跡がある。代入は型検査で落ちるが、真偽値としての評価や `?.` での参照は型検査を通るため、残っていても気付かれない。PrimeNG の UI 部品（`primeng/api`・`primeng/config` 以外）を import している `.ts` は6ファイル（`table.component.ts`・`resizable-column.directive.ts`・`header-navbar-tabs.component.ts` ほか）
- `@for` の `track`。`$index` で track すると、行の並びが変わったときに子コンポーネントの内部状態が別の行に残る（`track $index` は12箇所）
- 開発モードのコンソールに出る警告（NG0100 ExpressionChangedAfterItHasBeenChecked、NG0955 / NG0956 の track 関連）

### E. 購読・タイマー・イベントリスナの破棄

- `subscribe` が `takeUntilDestroyed`・`DestroyRef`・`async` パイプのどれでも解除されていないもの
- `setInterval` / `setTimeout` の clear 漏れ（テーブルの行クリックの250ms 待ちを含む。ngbi-01）
- `addEventListener` と `ResizeObserver` / `IntersectionObserver` の解除漏れ

症状として、画面の出入りを繰り返すと同じ処理や API 呼び出しが増えていく、破棄済みのコンポーネントでエラーが出る、を確かめる。

規模は `.subscribe(` 331箇所、`setTimeout(` 142箇所、`setInterval(` 3箇所、`addEventListener(` 5箇所、Observer の生成3箇所である。`subscribe` は数が多いため、同じ行か直前の `pipe` に `takeUntilDestroyed`・`take(1)`・`first()` があるものを先に機械的に除き、残りを読む。

### F. NgRx の状態の整合

- Effect の `catchError` が外側の `pipe` にあり、1回の失敗で Effect が止まるもの
- `switchMap` / `mergeMap` / `concatMap` / `exhaustMap` の選び方。連続で切り替えたとき、古い応答が新しい状態を上書きしないか
- 楽観更新の失敗時に元に戻しているか。成功後の再取得で値が二度書き換わり、表示がちらつかないか（x-sequense/01 の `updateExperiment` が2回出る流れ）
- 画面を離れたときに状態が初期化されず、前の画面の値が残るもの
- URL と状態の同期。往復して無限に更新されないか、戻るボタンで状態が戻るか
- 同じ feature key の二重登録。`EXPERIMENTS_STORE_KEY` は `experiments.providers.ts`・`experiment-shared.config.ts`・`experiment-routes.ts` の3箇所で `provideState` されており、画面遷移で状態が作り直されないか

### G. フォームと検証

- 検証結果と保存に使う値の食い違い（既出：`form.checkValidity()` は DOM の値、`inlineSaved()` は ngModel の値を見る）
- `<form>` 内の `type` の無い `<button>` が submit として働き、Enter で意図しない送信が起きるもの（既出：インライン編集の✓ボタン）
- 保存中の二度押し、取消時に元の値へ戻るか、未保存の変更がある状態での画面離脱

grep の起点：`<form` 内の `<button`（`type` 属性の有無）、`(ngSubmit)`、`(submit)`、`canDeactivate`

### H. ルーティングと画面遷移

- URL を直接開いたとき・再読み込みしたときに同じ画面が再現されるか
- 戻る・進むで、選択行・タブ・検索条件・スクロール位置が戻るか
- 存在しない ID を開いたときに、404・空の画面・前の値のどれになるか
- 旧パスのリダイレクト（`experiments` → `tasks`、`compare-experiments` → `compare-tasks`）でクエリパラメータが残るか
- （フェーズ0で追加）Angular 22 で Router の `paramsInheritanceStrategy` の既定が `'emptyOnly'` から `'always'` に変わった（[_router-chunk.mjs:1510](../node_modules/@angular/router/fesm2022/_router-chunk.mjs#L1510)。21.2.22 は `|| 'emptyOnly'`）。`app.config.ts` の `withRouterConfig` は指定していないため、子ルートの `params`・`data` に親ルートの値がすべて入るようになった。`route.snapshot.data` / `route.params` を直接読み、キーの有無で分岐している箇所の挙動が変わっていないかを見る。`router.effects.ts` の `getRouterData()` は親から子へ上書きでマージするため、結果は変わらない

### I. HTTP とエラー表示

- `withInterceptorsFromDi()` が無いと `HTTP_INTERCEPTORS` の interceptor が黙って無効になっていた件（比較資料 §7.4）と同じく、DI 経由の仕組みで黙って無効になっているものが他に無いか。なお比較資料はこの件を Angular 22 の変化としているが、`HttpClient` が root で提供され、`withInterceptorsFromDi()` が無ければ `HTTP_INTERCEPTORS` を読まないという既定は Angular 21.2.22 でも同じである。上流の `app.config.ts` がどう interceptor を登録していたかは手元に無く、由来は上流のソースで確かめるまで決めない
- API の失敗時に通知が出るか、読み込み中の表示が消えずに残らないか、セッション切れのときの動き
- 画面を離れたあとに届いた応答が、別の画面の状態を書き換えないか
- （フェーズ0で追加）Angular 22 で `provideHttpClient()` の既定の送信手段が XHR（`HttpXhrBackend`）から fetch（`FetchBackend`）に変わった。21.2.22 は `useExisting: HttpXhrBackend`。fetch はアップロードの進捗を出せず、`reportUploadProgress`（`reportProgress` を含む）を指定すると例外になる（[_module-chunk.mjs:986](../node_modules/@angular/common/fesm2022/_module-chunk.mjs#L986)）。`src/app` で `reportProgress: true` を指定している箇所は0件（生成された API サービスの引数の既定値は false）。ファイルのアップロード（`report.component.ts` の fileserver への `post` など）とダウンロードで、エラー時の応答の扱いが変わっていないかを見る

### J. 操作性とアクセシビリティ

- ダイアログを閉じたあと、インライン編集を終えたあとのフォーカスの位置
- Tab キーの移動順、キーボードだけで届かない操作（hover でしか出ないボタン、右クリックメニューにしかない機能）
- シングルクリックとダブルクリックの判定待ち（テーブルの250ms）による反応の遅れ
- 連打したときの二重実行
- axe による検査。既存の `e2e/accessibility.spec.ts` は対象外の品質パイプラインとデータカタログしか検査しないため、調査用のスクリプトで同じ axe の検査を行う（§7.6）

### K〜Q（フェーズ4で追加）

フェーズ4の見直しで足した観点である。A〜J の結果を見返し、「利用者の値を URL として扱う」「複数の操作・タブ・自動更新が重なる」「表示と保存で参照する ID が分かれる」といった、A〜J のどれにも寄せていなかった筋を分けた。

#### K. 利用者の値を URL・遷移先として扱う箇所

- `window.open(...)`・`location.href = ...`・`a.href = ...` に、利用者が登録した値（デバッグ画像の URL、成果物・モデルの `uri`、リンク）を渡す箇所。テンプレートの `[src]` / `[href]` は Angular が無害化するが、これらは通らない
- 開いた先から `window.opener` でアプリの画面に触れられるか（`noopener` の有無）
- `window.addEventListener('message')` の origin の確認
- grep の起点：`window.open(`、`.href = `、`location.assign`、`addEventListener('message'`

#### L. 選択と一括操作

- チェックで選んだ行が、検索・絞り込み・プロジェクトの切り替えの後も選択に残るか。残った選択に一括操作（アーカイブ・削除）が及ぶか
- 選択中の行の状態（status など）が、自動更新の後も最新か。メニューの有効・無効の判定に古い状態を使っていないか

#### M. 数値と日時の計算

- 日付の範囲フィルタの時差（端末が UTC+9 のときの境界）。URL・サーバとの往復で値がずれないか
- 相対時刻（`timeAgo`）の入力の形式、サーバと端末の時刻のずれ、負の経過時間
- NaN・Infinity・極端に大きい値の表示

#### N. 日本語キーボード配列（JIS）と Mac のショートカット

- `keyCode` / `event.code` / `event.key` のどれでキーを判定しているか。JIS 配列で記号の位置が変わるキー（`+`・`-`・`:`・`@`）の判定
- Mac の Command キー（`metaKey`）を見ているか

#### O. ブラウザ保存（localStorage）の復元と複数タブ

- 保存した状態を読み戻すときの例外処理（`JSON.parse`）、古い形の値が混ざったときの動き
- 同じ利用者が複数のタブを開いているときの、設定・利用者設定の上書き

#### P. 読み取り専用・権限による操作の制限

- サンプル（公開）データ、アーカイブ済み、公開済み（published）のタスク・モデルで、編集の操作が出ていないか
- 読み取り専用の判定（`isReadOnly` と `isExample`）の食い違い

#### Q. 自動更新（ポーリング）と利用者の操作の競合

- 自動更新が、編集中の入力・選択・スクロール位置を上書きしないか
- 自動更新の取り直しが、編集中を除外しているか

## 7. 資料の書き方

### 7.1 ファイルとまとめ方

- 1件1ファイル。ファイル名は `NN_{症状の要約}.md`（2桁連番、登録順）
- 資料の冒頭（件名の直後）に概要の表を置く（§7.2）。各欄は1〜2文で簡潔に書き、詳細は本文に回す
- 同じ症状が複数の箇所で起きるものは1ファイルにまとめ、「同種箇所」の表に列挙する
- 原因が同じでも症状と直し方が違うもの（変換確定の Enter と変換取消の Esc など）は別のファイルにし、互いにリンクする
- コードの箇所は資料からの相対リンクで示す（例：`../src/app/webapp-common/shared/ui-components/inputs/inline-edit/inline-edit.component.html#L36`）
- 再現に使うコード片（Playwright の手順、DevTools で実行するスクリプト）は、各資料の再現手順に載せる
- 確認していない事柄を事実として書かない。確度欄と「検証範囲」に、確認したことと確認していないことを分けて書く

### 7.2 各資料のひな形

````markdown
# {症状を一文で}

| 項目 | 内容 |
|---|---|
| カテゴリー | 画面UI / 処理値 / 状態 / 操作 / セキュリティ（§7.4） |
| 不具合内容 | 何をすると何が起きるか |
| 期待動作 | 本来どうなるべきか |
| 直さないと困ること | 誰が（何が）どう困るか |
| 修正規模 | 長大 / 大 / 中 / 小 / 極小（§7.5） |

| 項目 | 内容 |
|---|---|
| 画面 | 実験管理 > 一覧 > 名前のインライン編集 |
| 観点 | A（IME）など、§3 の記号 |
| 重大度 | S1〜S4 |
| 確度 | 再現済み / コード上確定 / 推測 / 要実機確認 / 要確認 |
| 由来 | 上流 / カスタマイズ / 版上げ |
| 発生条件 | ブラウザ・IME・データの条件 |
| 関連 | 原因が同じ別件へのリンク |

## 症状
## 再現手順
## 期待する動作
## 原因
## 影響範囲と同種箇所
## 対策案
## 検証範囲
````

### 7.3 重大度

| 重大度 | 基準 |
|---|---|
| S1 | 利用者の意図と違う値が保存・削除される。サーバとのあいだに不整合が残る。利用者の入力がスクリプトとして実行される |
| S2 | 機能が使えない。または回避の手段が利用者に分かりにくい |
| S3 | 操作性の欠陥で、回避の手段がある（入力し直す、別の操作で代える） |

### 7.4 カテゴリー

| カテゴリー | 当てはまるもの |
|---|---|
| 画面UI | 表示の崩れ、表示される値や文言の誤り、値が変わっても再描画されない |
| 処理値 | 保存・送信・計算される値の誤り、検証の条件の食い違い |
| 状態 | Store・コンポーネント・URL・サーバのあいだの値の食い違い、処理の二重実行、購読やタイマーの破棄漏れ |
| 操作 | キーボード・IME・フォーカス・クリック判定・二度押しなどで、操作が意図どおりに受け付けられない |
| セキュリティ | 利用者の入力が HTML やスクリプトとして解釈される |

### 7.5 修正規模

対策案（第一案）を実施するときの見積もりである。原因が確定していないものは「未見積」とする。
