## 症状

タスク一覧で、ページ上部の検索を開き、「じっけん」と打ってから変換して「実験」で確定したときの検索（`tasks.get_all_ex` の `_any_.pattern`）は次のとおりである。

| 確定の仕方 | 送られた検索語 | 検索欄の表示 |
|---|---|---|
| 変換中の keydown を送らずに確定（候補のクリックなど） | `じっけん` だけ | 実験 |
| 変換中の Enter（`key: 'Process'`。Windows の Chrome で報告される届き方） | `じっけん` だけ | 実験 |
| 変換中の Enter（`key: 'Enter'`。macOS の Chrome などで報告される届き方） | `じっけん` → `実験` → `実験` | 実験 |

1行目と2行目では、一覧は「じっけん」の検索結果のまま残る。3行目は Enter のハンドラが検索欄の値をそのまま送るため最終的には一致するが、同じ語の検索が2回走る。

変換を取り消す Esc では、それまでに検索していた「調査タスク」も含めて検索欄が空になり、検索条件の無い一覧に戻る。

## 再現手順

実バックエンドの調査用プロジェクト `zz-不具合調査` のタスク一覧で行う（読み取りだけ）。

1. ページ上部の検索アイコンを押して検索欄を開く
2. 日本語入力で「じっけん」と打ち、変換（スペース）の前に 0.3 秒以上止まる。この時点で「じっけん」で検索が走る
3. 変換して「実験」を選び、確定する
4. 検索欄は「実験」、URL の `q` と一覧は「じっけん」のまま

スクリプトは [scripts/p2a-ime-search.spec.ts](./scripts/p2a-ime-search.spec.ts)。変換中の文字列は CDP の `Input.imeSetComposition` で、打鍵ごとの途中経過（`j` → `じ` → … → `じっけん`）を順に置いて作っている。

## 期待する動作

- 変換中は検索を走らせず、確定した時点の文字列で検索する
- 検索欄に表示された語と、一覧の検索条件（URL の `q`）が常に一致する
- 変換中の Esc では、変換だけが取り消され、検索欄の文字列と検索条件は残る

## 原因

[search.component.html:21](../src/app/webapp-common/shared/ui-components/inputs/search/search.component.html#L21) の `(input)` が、変換中の input イベントでも `onValueChange()` を呼び、DOM の値（未確定の文字列を含む）を `value$` に流す。

[search.component.ts:67](../src/app/webapp-common/shared/ui-components/inputs/search/search.component.ts#L67) の購読は、`debounce`（既定 300ms）の後、`filter(val => val.length >= this.minimumChars() || val.length === 0)` で最小文字数に満たない値を捨てる。変換の途中で 300ms 止まると「じっけん」（4文字）が通って検索され、その後に確定した「実験」（2文字）は捨てられる。捨てられた値は再検索されないため、検索欄と検索条件が食い違ったまま残る。

Esc は [search.component.ts:92](../src/app/webapp-common/shared/ui-components/inputs/search/search.component.ts#L92) の `onKeyDown()` が `event.key === 'Escape'` だけを見て `clear()` を呼ぶため、変換中の Esc でも検索欄を空にする。Enter も同じメソッドで `event.key === 'Enter'` だけを見ており、変換確定の Enter で検索を送る（上の表の3行目で2回走る理由）。

最小文字数が3であること自体も、日本語では2文字の語（「実験」「学習」など）で絞り込めないという問題を持つ。英数字でも、`abcd` を検索してから `ab` まで消すと検索は `abcd` のまま残るため、これは IME に限らない上流の設計である。下限の値を変えるかは、[06](./06_実験名の長さの下限が入力欄と保存処理で食い違う.md) と同じく仕様の判断が要る。

## 影響範囲と同種箇所

`sm-search` を使う13のテンプレートのうち、最小文字数が3（既定値を含む）のものは、確定後の語が検索されずに残る症状が出る。

| テンプレート | 最小文字数 | 検索の対象 |
|---|---:|---|
| [common-search](../src/app/webapp-common/common-search/containers/common-search/common-search.component.html)（ページ上部の検索） | 3 | 各一覧の API |
| [global-search-dialog](../src/app/webapp-common/dashboard-search/global-search-dialog/global-search-dialog.component.html)（全体検索） | 3 | 全体検索の API |
| [select-experiments-for-compare](../src/app/webapp-common/experiments-compare/containers/select-experiments-for-compare/select-experiments-for-compare.component.html) | 3（既定） | 比較対象の候補 |
| [select-model-header](../src/app/webapp-common/models/shared/select-model-header/select-model-header.component.html) | 3（既定） | モデルの候補 |

最小文字数が0か1のもの（比較画面・Hyperparameters・Execution の本文表示（`scroll-textarea`）の「次を検索」、メトリクスやメタデータの列選択など）は、確定後の語で検索し直されるため、残る症状は出ない。ただし変換中の文字列での一時的な検索と、変換取消の Esc で検索欄が空になる症状は、13箇所すべてに出る。

`sm-search` 以外にも、`(input)` で API を呼ぶ入力欄がある。プロジェクトの選択欄（[paginated-entity-selector](../src/app/webapp-common/shared/components/paginated-entity-selector/paginated-entity-selector.component.html#L9)・[paginated-project-selector](../src/app/webapp-common/shared/components/paginated-project-selector/paginated-project-selector.component.html#L8)。クローン・移動・プロジェクト作成などのダイアログ）は、変換中の文字列で `projects.get_all_ex` を呼ぶが、Effect が `debounceTime(300)` と `switchMap` で受け、最小文字数も無いため、確定後の語で必ず検索し直される。一時的に変換中の語の候補が出るだけで、食い違いは残らない。

## 対策案

`sm-search` で次の2点を行う。

- `(compositionstart)` / `(compositionend)` で変換中かどうかを持ち、変換中の `(input)` では `value$` に流さない。`compositionend` の時点の値を `value$` に流す
- `onKeyDown()` の先頭で `event.isComposing || event.keyCode === 229` なら何もしない（[01](./01_インライン編集で変換確定のEnterにより編集が終了する.md) の第一案の共通の判定を使う）

変更は `sm-search` の1コンポーネントで完結するため「小」とした。最小文字数の見直しは別の判断として扱う。

## 検証範囲

- 確認したこと：Playwright（Chromium、実バックエンド）で、変換中の文字列を置いて 0.8 秒待つと「じっけん」で `tasks.get_all_ex` が呼ばれること。確定の仕方3通り（keydown なし、`key: 'Process'`、`key: 'Enter'`）での検索語と検索欄の表示。変換中の Esc（`key: 'Escape'`、`isComposing: true`）で検索欄が空になり、検索条件の無い一覧に戻ること
- 確認していないこと：実機の IME での打鍵ごとの input イベントの出方と、確定の Enter の `key`。全体検索・比較対象の選択・モデルの選択の画面上の症状（同じ部品と同じ最小文字数のため同じ症状になると判断した）
- 調べて不具合ではないと判断したこと：検索欄を開いた直後（数十 ms 以内）に Playwright の `keyboard.type` で日本語を打つと、文字が逆順に入ることがあった。アプリのコードは値もカーソルも書き換えておらず（値の setter と `focus()` を記録して確認）、検索欄が開くアニメーションの最中に CDP の `insertText` を送ったときだけ起きるため、試験側の現象と判断した
- 由来：`search.component.*`・`common-search.component.*` は比較資料で上流と一致する
