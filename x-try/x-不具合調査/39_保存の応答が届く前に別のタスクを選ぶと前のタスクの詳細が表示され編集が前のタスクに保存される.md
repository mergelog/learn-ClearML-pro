# 保存の応答が届く前に別のタスクを選ぶと、前のタスクの詳細が表示され、編集が前のタスクに保存される

| 項目 | 内容 |
|---|---|
| カテゴリー | 状態 |
| 不具合内容 | タスク A の名前などを保存し、応答が届く前に一覧でタスク B を選ぶと、応答の後に A の詳細が取り直され、URL・一覧の選択・ID が B のまま、名前と各タブの内容が A になる。この状態で EXECUTION などのセクションを保存すると A に、ヘッダーの名前を保存すると B に送られる |
| 期待動作 | 保存の応答が遅れて届いても、表示中のタスク（B）の詳細は置き換えない。保存の後の取り直しは、保存したタスクが表示中のときだけ行う |
| 直さないと困ること | B を編集しているつもりの変更が A に保存される。画面の部位ごとに保存先が違うため、利用者が気付きにくい |

|---|---|
| 画面 | 実験管理 > 一覧 + 詳細（EXECUTION・CONFIGURATION など、詳細の全タブ） |
| 観点 | F（NgRx の状態の整合）、§4.1「保存中の切替」 |
| 重大度 | S1 |
| 確度 | 再現済み（モック API） |
| 由来 | 上流 |
| 発生条件 | 詳細で保存（名前・説明・タグ、または各セクションの SAVE）をしてから、`tasks.update` / `tasks.edit` の応答が届く前に一覧で別のタスクを選ぶ。応答が遅い環境ほど起きやすい |

## 症状

モック API で `tasks.update` の応答を2秒遅らせ、詳細ヘッダーで Task A の名前を `Task A renamed` にして Enter を押した直後に、一覧で Task B を選んだ。

| 時点 | URL | ヘッダーの名前 | ID チップ | Store の詳細（`infoData`・`selectedExperiment`） |
|---|---|---|---|---|
| 応答の前 | `…/tasks/task-b/execution` | Task B | task-b | task-b |
| 応答の後 | `…/tasks/task-b/execution` | Task A renamed | task-b | **task-a** |

応答の後、EXECUTION の REPOSITORY などの表示も A の値になり、一覧の選択は B のまま残る。自動更新でも戻らない（下記の原因）。

この状態で続けて操作したときの送り先：

| 操作 | 画面上の値 | 送られた要求 |
|---|---|---|
| EXECUTION の CONTAINER の IMAGE を書き換えて SAVE | 編集前の値は `image-task-a` | `tasks.edit` の `task: task-a` |
| ヘッダーの名前を書き換えて Enter | 編集前の値は `Task A renamed` | `tasks.update` の `task: task-b` |

保存の応答を待ってから B を選んだ場合（対照）は、B の詳細が表示される。

## 再現手順

1. 下書きのタスクの詳細（EXECUTION）を開く
2. ヘッダーの名前を書き換えて Enter を押す
3. 応答が届く前に、左の一覧で別のタスクを選ぶ
4. 応答が届くと、選んだタスクの URL のまま、ヘッダーの名前と EXECUTION の内容が 2 のタスクのものに置き換わる
5. このまま EXECUTION のセクションを編集して SAVE すると、2 のタスクに保存される

Playwright の再現は [scripts/p4-save-then-switch.spec.ts](./scripts/p4-save-then-switch.spec.ts)。モック API で `tasks.update` を2秒遅らせる。

## 原因

名前などの保存は `updateExperimentDetails$` が受ける。選択中のタスクを `concatLatestFrom` で action が届いた時点に読み（[common-experiments-info.effects.ts:454](../src/app/webapp-common/experiments/effects/common-experiments-info.effects.ts#L454)）、応答の後に次を返す。

- `experimentUpdatedSuccessfully({id: A})`（[同:464](../src/app/webapp-common/experiments/effects/common-experiments-info.effects.ts#L464)）
- 保存時点の選択が A なので `updateExperimentInfoData`（[同:466](../src/app/webapp-common/experiments/effects/common-experiments-info.effects.ts#L466)）。reducer は ID を見ずに、現在の `selectedExperiment`・`infoData`（この時点では B）へ A の変更をマージする（[common-experiment-info.reducer.ts:106](../src/app/webapp-common/experiments/reducers/common-experiment-info.reducer.ts#L106)）

`experimentUpdatedSuccessfully` を受ける `getExperimentInfo$`（[同:243](../src/app/webapp-common/experiments/effects/common-experiments-info.effects.ts#L243)）は、表示中のタスクが B でも、action の ID（A）で `getExperiment` を出す（[同:285](../src/app/webapp-common/experiments/effects/common-experiments-info.effects.ts#L285)）。取得した A の詳細で `setExperimentInfoData`・`setExperiment` を出し、Store の詳細が A に置き換わる（[同:339](../src/app/webapp-common/experiments/effects/common-experiments-info.effects.ts#L339)）。

以後、Store と画面の部位で参照するタスクが分かれる。

| 部位 | 参照する値 | タスク |
|---|---|---|
| ヘッダーの名前、各タブの内容 | Store の `infoData` | A |
| セクションの保存（`saveExperimentSection`） | Store の `selectedExperiment`（[同:516](../src/app/webapp-common/experiments/effects/common-experiments-info.effects.ts#L516)） | A |
| ID チップ、ヘッダーの名前の保存 | 詳細画面の部品が、URL の ID と一致する一覧の行から採る `selectedExperiment`（[base-experiment-output.component.ts:179](../src/app/webapp-common/experiments/containers/experiment-ouptut/base-experiment-output.component.ts#L179)） | B |

自動更新の `autoRefreshExperimentInfo` は、一覧の選択（B）と Store の選択（A）が違うと取り直しを捨てる（[同:269](../src/app/webapp-common/experiments/effects/common-experiments-info.effects.ts#L269)）ため、食い違いは別の行を選び直すまで残る。

## 影響範囲と同種箇所

- `experimentUpdatedSuccessfully({id})` を返す保存はすべて同じ経路を通る：名前・説明・タグ（`updateExperimentDetails$`）、各セクションの保存（`saveExperimentSectionData$`）、編集の保存（`saveExperimentData$`）、Hyperparameters・Configuration の保存。セクション側は保存時点の Store の `selectedExperiment.id` を使うため、切り替え後に A を取り直す点は同じ
- 比較画面の名前変更でも A の詳細が読み込まれることはフェーズ2 F で確認済み（比較画面は詳細を表示しないため不具合としなかった）
- 全画面表示（`…/tasks/:id/output/…`）でも、別のタスクへ移る操作（前後の移動など）で同じ経路を通る可能性がある（未確認）

## 対策案

第一案：`getExperimentInfo$` で、action の ID が表示中のタスク（一覧の選択、または URL の ID）と違うときは取り直さない。`experimentUpdatedSuccessfully` の後の取り直しは、保存したタスクを表示しているときだけ意味がある。

第二案：`updateExperimentDetails$` の `updateExperimentInfoData` の判定を、応答の時点の選択で行う（`concatLatestFrom` を応答の後に置く）。あわせて `updateExperimentInfoData` の reducer は `action.id` と `infoData.id` が一致するときだけマージする。

第一案と第二案は両方とも要る。第一案だけでは、応答の時点で `updateExperimentInfoData` が B に A の名前を混ぜる。

## 検証範囲

- 確認したこと：モック API（`tasks.update` を2秒遅らせる）で、応答の後に Store と画面の詳細が A に置き換わること、CONTAINER の保存が A、ヘッダーの名前の保存が B に送られること、応答を待ってから切り替えた対照では B が表示されることを確認した
- 確認していないこと：実バックエンドでの再現（通常の応答は速く、切り替えを間に合わせるには遅延を作る必要がある）。Hyperparameters・Configuration の保存での再現、全画面表示での再現
- 由来：`common-experiments-info.effects.ts`・`common-experiment-info.reducer.ts`・`base-experiment-output.component.ts` は比較資料で実質差分に含まれない
