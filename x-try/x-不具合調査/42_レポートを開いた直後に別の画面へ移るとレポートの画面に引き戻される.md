# レポートを開いた直後に別の画面へ移ると、レポートの画面に引き戻される

| 項目 | 内容 |
|---|---|
| カテゴリー | 状態 |
| 不具合内容 | レポートの本文を表示する部品は、レポートの値が変わるたびに50ms 後の遷移を予約し、部品が破棄されても取り消さない。レポートが届いてから50ms 以内に別の画面へ移ると、移った後にレポートの画面へ戻る。遷移は `skipLocationChange` のため、アドレスバーは移った先の URL のままで、表示だけがレポートになる |
| 期待動作 | 画面を離れた後は、離れた画面の予約した遷移を実行しない |
| 直さないと困ること | 移ったはずの画面がレポートに戻り、アドレスバーと表示が食い違う。再読み込みで直るが、利用者には原因が分からない |
| 修正規模 | 極小 |

| 項目 | 内容 |
|---|---|
| 画面 | レポート > 本文 |
| 観点 | H（ルーティングと画面遷移）、E（タイマーの破棄） |
| 重大度 | S3 |
| 確度 | 再現済み（モック API） |
| 由来 | 上流 |
| 発生条件 | レポートの読み込みが終わってから50ms 以内に、別の画面へ移る（一覧に戻る、サイドナビで別の画面を選ぶ、ブラウザの戻る）。人の操作で50ms に収まることはまれで、読み込みの完了と操作が重なったときに起きる |

## 症状

モック API で、レポートが Store に入った瞬間に、同じ処理の中でレポートの一覧へ遷移させた。

| 時刻（ms） | 出来事 |
|---:|---|
| 2722 | レポート `report-1` への遷移が完了 |
| 2745 | レポートが Store に入る。ここで一覧へ遷移を開始 |
| 2771 | 一覧への遷移が完了 |
| 2804 | `report-1?archive=false` への遷移が完了（予約されていた遷移） |
| 2864 | もう一度 `report-1?archive=false` への遷移が完了 |

1.5秒後の状態は、アドレスバーが `/reports/bug-project/reports`（一覧）、Router の URL が `/reports/bug-project/report-1?archive=false`、画面はレポートの本文（`sm-report`）だった。レポートが届いて1秒後に一覧へ移った対照では、一覧のまま残る。

## 再現手順

人の操作で50ms に合わせるのは難しいため、再現はスクリプトで行う。

1. レポートの一覧を開く
2. レポートを開き、レポートが Store に入った直後（50ms 以内）に一覧へ遷移する
3. 一覧へ移った後、アドレスバーは一覧のまま、表示がレポートに戻る

Playwright の再現は [scripts/p4-report-late-navigate.spec.ts](./scripts/p4-report-late-navigate.spec.ts)。Store の購読でレポートが入った瞬間を捉え、`router.navigateByUrl()` で一覧へ移る。

## 原因

`report.component.ts` の `effect()` は、レポートとアーカイブの状態が変わるたびに `window.setTimeout(…, 50)` を呼び（[report.component.ts:158](../src/app/webapp-common/reports/report/report.component.ts#L158)、[同:168](../src/app/webapp-common/reports/report/report.component.ts#L168)）、50ms 後に `this.route` を基準に `router.navigate(['.'], {skipLocationChange: true, queryParams: {archive}})` を呼ぶ（[同:164](../src/app/webapp-common/reports/report/report.component.ts#L164)）。

- `setTimeout` の戻り値を保持せず、部品の破棄時に取り消さない
- 実行時の判定（[同:159](../src/app/webapp-common/reports/report/report.component.ts#L159)）は、レポートの ID と `this.route.snapshot` の `reportId` を比べる。破棄された部品の `ActivatedRoute` は最後のスナップショットを持ち続け、Store のレポートも画面を離れても消えないため、判定は通る
- `relativeTo` に破棄された部品の `route` を渡しても、Router はそのルートを基準に URL を組み立てるため、レポートの URL へ遷移する

`effect()` は部品の破棄で止まるが、既に予約した `setTimeout` は残る。レポートの値とアーカイブの状態が別々に変わると予約が2つになり、遷移も2回走る（表の 2804 と 2864）。

## 影響範囲と同種箇所

- レポートの読み込み（`getReport` の応答）のほか、アーカイブ・公開・移動などでレポートの値が変わった直後にも予約が入る。移動の後は同じ部品が使い回されるため、画面を離れる操作と重ならない限り症状は出ない
- 観点 E の `setTimeout` の分類（フェーズ2）で、破棄時に clear しない `setTimeout` は大半が描画の調整で実害が無いとした。遷移を行うのはこの箇所だけである

## 対策案

`setTimeout` の ID を保持し、`DestroyRef.onDestroy()` で `clearTimeout()` する。`effect()` の `onCleanup` で前の予約を取り消せば、値が続けて変わったときの二重の遷移も無くなる。

URL の `archive` を Router の状態にだけ載せる目的なら、`setTimeout` を使わずに、レポートの読み込みの Effect か、ルートの `resolve` で扱う方が、画面の破棄と競合しない。

## 検証範囲

- 確認したこと：モック API で、レポートが Store に入った直後に一覧へ移ると、50ms 後にレポートへ引き戻され、アドレスバーと Router の URL・表示が食い違うことを確認した。1秒後に移った対照では起きない
- 確認していないこと：人の操作（クリック、ブラウザの戻る）でのタイミングの一致。実バックエンドでの再現
- 由来：`report.component.ts` は比較資料で実質差分に含まれない
