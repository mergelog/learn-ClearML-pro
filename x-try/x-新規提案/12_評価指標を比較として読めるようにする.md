# 評価指標を比較として読めるようにする

| 項目 | 内容 |
| --- | --- |
| 分類 | ML体験 |
| 領域 | 自作（`features/quality-pipeline`） |
| 直る体験 | 出た数字が良いのか悪いのかを、画面だけで判断できる |
| 規模 | 中〜大 |
| 状態 | 未着手 |

## いま画面で起きていること

評価の画面は、split ごとに4つの数字を並べた表である。

| Split | Accuracy | Precision | Recall | F1 |
| --- | --- | --- | --- | --- |
| validation | 0.812 | 0.704 | 0.591 | 0.643 |
| test | 0.806 | 0.698 | 0.574 | 0.630 |

［[evaluation-scores-table.component.html](../src/app/features/quality-pipeline/components/evaluation-scores-table/evaluation-scores-table.component.html)］

`<caption>` は「Validation decides which model is chosen. Test confirms the choice once.」と、split の役割を説明している。説明しているのはそこまでで、数字そのものについては何も言わない。

言えるだけの材料は、このリポジトリの中にある。

| 判断に要るもの | どこにあるか | 画面に出ているか |
| --- | --- | --- |
| 合格の基準 | [config/model_gate.yaml](../config/model_gate.yaml)（validation の recall ≥ 0.55、f1 ≥ 0.65） | 出ていない |
| 基準に使う指標と使わない指標の別 | 同ファイル（accuracy は基準にしない） | 出ていない。4列が同じ重みで並ぶ |
| いま提供中のモデルの指標 | ClearML 上のモデルに紐づく | 出ていない。[production-model-card](../src/app/features/quality-pipeline/components/production-model-card/production-model-card.component.html) は版と昇格の記録だけ |
| 前回までの実行の指標 | ClearML 上の過去の Task | 出ていない。state が持つ実行は1件（[quality-pipeline.model.ts:102](../src/app/features/quality-pipeline/quality-pipeline.model.ts#L102) の `run: PipelineRun \| null`） |

桁数は `'1.3-3'` の固定である（[evaluation-scores-table.component.ts:27](../src/app/features/quality-pipeline/components/evaluation-scores-table/evaluation-scores-table.component.ts#L27)）。

## なぜ変えるか

`0.643` という数字は、単独では何も意味しない。意味を作るのは3つの比較である。基準との比較、前回との比較、提供中のものとの比較である。3つとも画面に無いので、利用者は `model_gate.yaml` を開くか、ClearML の別画面で過去の実行を探すことになる。

とりわけ、基準に使う指標と使わない指標が同じ見た目で並んでいることは誤読を招く。accuracy は意図的に基準から外されていて、その理由もファイルに書かれている。表はその判断を伝えていない。

## 解決とみなす状態

1. 基準を画面に出す。`model_gate.yaml` の内容（判定する split、指標ごとの下限）を API 経由で読み、表の中で基準との関係を示す。基準に使わない指標は、使わないことが分かる見た目にする
2. 合否を1つの結論として出す。「validation の recall が 0.591 で基準 0.55 を満たす」のような、どの指標がどう効いたかを含む文にする。合格したときも理由を出す
3. 提供中のモデルとの差を出す。同じ split の同じ指標で、差分を符号付きで示す
4. 直近の実行の推移を出す。ここで初めて図が要る。指標ごとの折れ線が数件ぶん見えれば足りる。取り込み領域には [ng2-charts](../src/app/app.config.ts#L58) が登録済みで、追加の依存は要らない
5. 桁数は指標の性質に合わせる。3桁固定でよいかを、値の範囲を見て決める

## 変更の範囲

* 追加：`quality-pipeline-api.service.ts` に、基準を読む経路と、過去の実行の指標を読む経路
* 変更：state に「基準」「提供中のモデルの指標」「直近数件の指標」を足す。実行が1件という前提が変わるため、reducer の書き換えが要る
* 変更：`evaluation-scores-table` と `production-model-card`
* 判断：基準をどこから読むか。`config/model_gate.yaml` はサーバ側のファイルで、ブラウザからは読めない。ClearML のモデルや Task のパラメータとして記録されているなら、そこから読む。記録されていないなら、記録する側（`ml/`）の変更が先に要る

## 確かめ方

* 単体：合否の判定と、その説明の文面。指標が欠けている場合を「不合格」として扱うこと（`gate.py` の判断と揃える。[gate.py:18-19](../ml/model_lifecycle/gate.py#L18) が「報告されなかった指標は不合格」と決めている）
* E2E：基準を満たす／満たさないの2つのモック応答で、結論の文が変わることを確かめる

## 注意

画面が判定をやり直してはいけない。判定は `gate.py` が持っていて、画面はその結果を表示するだけにする。両方で判定すると、基準ファイルを変えたときに片方だけ古い答えを出す。判定の結果が ClearML に記録されていないなら、記録させるのが先である。
