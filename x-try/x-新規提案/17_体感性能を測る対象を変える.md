# 体感性能を測る対象を変える

| 項目 | 内容 |
| --- | --- |
| 分類 | その他の観点 |
| 領域 | 構成（`angular.json`・CI）。削る対象は凍結領域 |
| 直る体験 | 「重い」と感じる箇所を、感想ではなく数字で扱える |
| 規模 | 中 |
| 状態 | 未着手 |

## いま何が測られているか

性能の枠として置かれているのは、バイト数だけである。

| 枠 | 警告 | 失敗 | 場所 |
| --- | --- | --- | --- |
| 初期バンドル | 3.15 MB | 3.30 MB | [angular.json:126-130](../angular.json#L126) |
| 個別のファイル | 560 kB | 620 kB | [同:131-135](../angular.json#L131) |
| component の style | 6 kB | 16 kB | [同:136-139](../angular.json#L136) |

2026-09-12 の実測は 3.10 MB（転送見積 796.21 kB）で、警告まで 0.05 MB、1.6% である（[BL-09](../docs/backlog/09_E2Eと初期束の余裕.md)）。

余裕が無いこと自体は既に把握されていて、削る判断も済んでいる。`@defer` は入れないと決まっていて（[BL-06](../docs/backlog/06_defer.md)）、理由は自作 feature が既に `loadChildren` で完全に遅延しており、初期バンドルへの寄与が0だからである。削る対象は凍結領域にある。

測られていないのは、利用者が待つ時間そのものである。最初の描画までの時間、操作に反応するまでの時間、一覧が入れ替わるまでの時間は、どれも枠になっていない。CI（[.github/workflows/ci.yml](../.github/workflows/ci.yml)）にも、それを測る段は無い。

もう1つ測られていないものがある。動きの量である。テンプレートの `animate.enter` / `animate.leave` が10箇所、scss の `transition:` が135箇所、`@keyframes` が13箇所ある。一方、`prefers-reduced-motion` に応じて止める指定は、自分たちのコードに0件である（唯一の該当は同梱した Plotly の中）。

## なぜ変えるか

バイト数と待ち時間は比例しない。3.10 MB のうち、最初の描画に要る部分がどれだけかは枠が答えない。逆に、バイト数が1バイトも増えない変更で画面が遅くなることもある。5秒ごとの問い合わせ（[10](./10_走っている実行が生きて見えるようにする.md)）や、一覧の読み足し（[05](./05_一覧の続きへ辿り着けるようにする.md)）がそれで、どちらもバンドルには現れない。

余裕が 1.6% しか無い状態でバイト数だけを見ていると、判断が「入れられるか／入れられないか」に寄る。入れたものが速いかどうかは別の話である。

動きを止める指定が無いことは、性能ではなく安全の話に近い。前庭障害のある利用者にとって、止まらない動きは体調に影響する。

## 解決とみなす状態

1. 待ち時間の指標を1つか2つ決めて測る。最初の描画までと、一覧の絞り込みから結果が出るまでで足りる。測るのは開発ビルドではなく本番相当のビルド
2. 測る場所を決める。CI に段を足すなら、実行時間と揺らぎの扱いを先に決める。揺らぎの大きい指標を失敗の条件にすると、無関係の変更で赤になる。最初は記録だけに留め、傾向が見えてから枠にする
3. バイト数の枠は残す。ただし「初期バンドル」の内訳（最初の描画に要る分と、そうでない分）を分けて記録する
4. `prefers-reduced-motion: reduce` のときに、装飾の動きを止める指定を大域に1つ置く。止めるのは装飾だけで、状態の変化を伝える動き（読み込み中の表示など）は残す
5. 問い合わせの回数を記録する。E2E の中で、1画面あたりの要求数を数えて上限を置く。バンドルの枠と同じ性質の枠になる

## 変更の範囲

* 追加：測定の段（CI か、手元で走らせる script か）
* 変更：[reboot.scss](../src/app/webapp-common/styles/reboot.scss) か、自作側の大域 scss に `prefers-reduced-motion` の規則。置き場は [08](./08_フォーカスが見えるようにする.md) の判断と揃える
* 判断：測定を失敗の条件にするか、記録に留めるか

## 注意

E2E の枠は 29/30 で1件しか空いていない（[BL-09](../docs/backlog/09_E2Eと初期束の余裕.md)）。要求数の上限を E2E として足すなら、既存のファイルへの追加にする。新しい観点を足すたびに E2E を1本増やす形は、枠の設計そのものと衝突する。
