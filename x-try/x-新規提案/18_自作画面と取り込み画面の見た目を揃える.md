# 自作画面と取り込み画面の見た目を揃える

| 項目 | 内容 |
| --- | --- |
| 分類 | その他の観点 |
| 領域 | 自作（両 feature）。借りる先は凍結領域 |
| 直る体験 | 画面を移っても、同じ操作が同じ形と同じ手応えで動く |
| 規模 | 中。ただし判断が先 |
| 状態 | 未着手（何を借り、何を持つかの判断が先） |

## いま画面で起きていること

自作の2 feature は、取り込み領域の UI 部品を1つも使っていない。`@common/` からの import は、どちらも `CrumbTypeEnum`（パンくずの種別）の1件だけである。

```
src/app/features/data-catalog/data-catalog.routes.ts:4:    import {CrumbTypeEnum} from '@common/layout/breadcrumbs/breadcrumbs.component';
src/app/features/quality-pipeline/quality-pipeline.routes.ts:4: import {CrumbTypeEnum} from '@common/layout/breadcrumbs/breadcrumbs.component';
```

使われていない部品は揃っている。検索欄、チップ付きの選択、タグ、続きを読む点、コピーの導線、表、確認ダイアログ、自動更新のボタンである（[shared/ui-components/](../src/app/webapp-common/shared/ui-components/)、[shared/components/](../src/app/webapp-common/shared/components/)）。

揃っていないわけでもない部分がある。色はテーマ変数を参照していて、直値を書かない方針が [_data-catalog.mixins.scss:7-9](../src/app/features/data-catalog/styles/_data-catalog.mixins.scss#L7) に明記されている。左のナビの項目も、既存と同じ形で並んでいる（[side-nav.component.html:35-48](../src/app/layout/side-nav/side-nav.component.html#L35)）。

つまり、色と配置は揃っていて、操作の部品だけが揃っていない。利用者から見ると、実験一覧では Material の入力欄と押し心地で操作し、台帳では素の `<input>` と `<button>` で操作することになる。

自作側の中でも揃っていない。`_data-catalog.mixins.scss` と `_quality-pipeline.mixins.scss` は同じ形（表・定義リスト・補足文）を別々に持っていて、[_data-catalog.mixins.scss:11-13](../src/app/features/data-catalog/styles/_data-catalog.mixins.scss#L11) はそれを承知のうえで、まだ寄せないと書いている。

## なぜ変えるか

部品を借りるかどうかは、見た目の統一だけの問題ではない。借りた部品には、キーボード操作・読み上げ・焦点の扱い・IME の扱いが既に入っている。素の要素で組むと、それらを1つずつ足すことになる。この提案書の [03](./03_取り消せない操作に退路を用意する.md)・[04](./04_操作の結果を画面と支援技術の両方へ返す.md)・[06](./06_入力欄を値の形に合わせる.md) は、どれも「借りれば済むもの」を含んでいる。

一方で、借りない判断にも理由がある。凍結領域の部品に依存すると、上流の更新でその部品が変わったときに自作画面が壊れる。`x-不具合調査` に登録された44件のうち、インライン編集・検索欄・表に関わるものは、借りた側にも降ってくる。

判断を先送りしているあいだ、実質的には「借りない」を選び続けている。選んだ結果として、上の3提案で同じ作業を3回することになる。

## 解決とみなす状態

1. 借りる部品と持つ部品の線を1本引く。目安は、上流の不具合の影響を受けても許せるかどうかである。表示だけの部品（タグ、コピー、点）は借りやすく、入力と編集の部品（インライン編集、検索欄）は上流の不具合が多い
2. 引いた線を文書に残す。ADR にするか、[61_アーキテクチャ規約.md](../docs/phase7_チーム開発標準/61_アーキテクチャ規約.md) に足すかを決める
3. 借りない部品については、自作側の `shared/` に1つ置く。いま2つある mixins の重複（チェックリスト P-2）を、この判断と同時に解消する
4. 借りた部品が上流の更新で変わったときに気付く経路を用意する。[web-boundaries.json](../web-boundaries.json) が既に境界を記録しているため、そこへ載せられるかを確かめる
5. 素の要素のまま残すものについては、焦点・読み上げ・キーボードの扱いを自作側の部品として1箇所に持つ

## 変更の範囲

* 判断が主。実装は判断の後
* 影響：[03](./03_取り消せない操作に退路を用意する.md)・[04](./04_操作の結果を画面と支援技術の両方へ返す.md)・[06](./06_入力欄を値の形に合わせる.md)・[09](./09_空の画面に次の行動を置く.md) の実装方法が、この判断で変わる

## 注意

部品を `imports` に足すだけなら、凍結領域のファイルは変わらない。レビュー基準 §4.6 の対象にはならない。ただし依存は増えるので、上流を取り込むときに確認する範囲は広がる。「凍結領域を変更しない」ことと「凍結領域に依存しない」ことは別である。
