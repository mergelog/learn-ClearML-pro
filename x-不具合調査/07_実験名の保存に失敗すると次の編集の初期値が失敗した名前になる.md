# 実験名の保存が API エラーで失敗すると、Store の infoData.name だけが入力値のまま残り、次の編集の初期値が失敗した名前になる

| 項目 | 内容 |

| カテゴリー | 状態 |
| 不具合内容 | 名前の変更が `tasks.update` のエラーで失敗したあと、ヘッダーと一覧は元の名前に戻るが、もう一度編集を開くと入力欄に失敗した名前が入っている。そのまま Enter を押しても「変更なし」として扱われ、保存は再送されない |

## 症状

1. 名前を `Failed name` に変えて確定すると、`tasks.update` が失敗し、「Update task failed」のエラーダイアログが出る
2. ダイアログを閉じると、ヘッダーと一覧は元の名前（`Task A`）のまま
3. もう一度名前をクリックすると、入力欄の初期値は `Failed name` になっている
4. そのまま Enter を押しても `tasks.update` は送られず、編集が閉じる

Store の中では、`info.infoData.name` が `Failed name`、`info.selectedExperiment.name` と一覧の行が `Task A` という食い違いが残る。別の実験を選び直すまで解消しない。

## 再現手順

Playwright（モック API で `tasks.update` を HTTP 400 にする）では [scripts/01-inline-edit-name.spec.ts](./scripts/01-inline-edit-name.spec.ts) の「08 保存失敗後の食い違い」で再現した。

```ts
const api = await mockClearmlApi(page, {
  overrides: {'tasks.update': () => ({status: 400, resultCode: 400, msg: 'Update failed (mock)'})}
});
// 名前を 'Failed name' にして ✓ → エラーダイアログを OK で閉じる
// ヘッダー: 'Task A'、一覧: 'Task A'
// 再度編集を開いた入力欄: 'Failed name'
// Enter → tasks.update は1回目の1件のまま（再送されない）
```

失敗の前後で `tasks.get_by_id_ex` の回数は増えなかった（ページ読み込み時の2回のみ）。失敗後の再取得が行われていない。

## 期待する動作

保存に失敗したら、`infoData.name` もサーバの値（元の名前）に戻る。次の編集は元の名前から始まり、同じ名前でもう一度確定すれば保存が再送される。

## 原因

`infoData` の更新が API より先に行われ、失敗時の再取得が条件次第で行われない。

1. 名前を確定すると `experimentDetailsUpdated` が dispatch され、reducer が API の結果を待たずに `infoData` に `changes` をマージする（[common-experiment-info.reducer.ts:86](../src/app/webapp-common/experiments/reducers/common-experiment-info.reducer.ts#L86)）
2. `updateExperimentDetails$` の `tasks.update` が失敗すると、`catchError` は `requestFailed`・`setServerError`・`getExperimentInfo` を出す（[common-experiments-info.effects.ts:473](../src/app/webapp-common/experiments/effects/common-experiments-info.effects.ts#L473)）。`infoData` を戻す action は無い
3. `getExperimentInfo$` は、一覧で選んでいる実験があればその行の `last_change` を使い（[common-experiments-info.effects.ts:263](../src/app/webapp-common/experiments/effects/common-experiments-info.effects.ts#L263)）、前回取得時より新しくなければ `deactivateLoader` だけを出す（[同:277](../src/app/webapp-common/experiments/effects/common-experiments-info.effects.ts#L277) 付近の条件）。失敗した更新では `last_change` は変わらないため、`getExperiment` による再取得は行われない
4. インライン編集の初期値は `infoData()?.name || experiment()?.name` である（[experiment-info-header.component.html:12](../src/app/webapp-common/experiments/dumb/experiment-info-header/experiment-info-header.component.html#L12)）。`infoData.name` が失敗した名前のため、それが初期値になる。同じ値で確定すると、インライン編集は元の値と同じとみなして取消扱いにする（[inline-edit.component.ts:93](../src/app/webapp-common/shared/ui-components/inputs/inline-edit/inline-edit.component.ts#L93)）

## 影響範囲と同種箇所

`experimentDetailsUpdated` を dispatch する変更はすべて、失敗時に同じ食い違いが残る。名前のほか、GENERAL タブのコメント（[experiment-info-general.component.ts:49](../src/app/webapp-common/experiments/containers/experiment-info-general/experiment-info-general.component.ts#L49)）、データセット版のコメント、アーカイブ・復元の処理（`common-experiments-menu.effects.ts` の2箇所）がこの action を使う。

`experimentDetailsUpdated` は、比較画面の名前変更ダイアログからも dispatch される。このとき reducer は、`info.infoData` がどの実験のものかを確かめずにマージするため、直前に詳細を開いていた別の実験の `infoData.name` が書き換わる可能性がある（コードからの推測。画面では確かめていない）。横断観点 F（フェーズ2）で確かめる。

[x-sequense/01 03-04](../x-sequense/01_実験名の変更と一覧反映/03-04_保存されない分岐.md) の③（詳細のフォームに検証エラーが残っていると `filter` で止まる経路）は、現行コードでは到達しない。`info.errors` に値を書き込む `setExperimentErrors` を dispatch するのは `experiment-info-task-model.component.ts` の `onFormErrorsChanged()` だけで、このメソッドはどのテンプレートからも呼ばれていない。そのため不具合としては登録していない。

## 対策案

第一案は、`updateExperimentDetails$` の `catchError` で `infoData` をサーバの値に戻すことである。`last_change` の比較を経ずに `getExperiment({experimentId: action.id})` を出して再取得するか、`concatLatestFrom` で取得済みの `selectedExperiment` から、変更した項目だけを `updateExperimentInfoData` で戻す。どちらも1ファイルの数行で「小」とした。

第二案は、楽観更新をやめ、reducer で `experimentDetailsUpdated` を受けずに、成功時の `updateExperimentInfoData` だけで `infoData` を更新する方式である。入力から表示までに API の往復分の遅れが出るため、UI の確認が要る。

## 検証範囲

- 確認したこと：Playwright（モック API）で、失敗後のヘッダー・一覧・次の編集の初期値、同じ値の Enter で再送されないこと、失敗後に `tasks.get_by_id_ex` が送られないこと
- 確認していないこと：実バックエンドでの失敗（権限エラーなど）。一覧を経由せず全画面表示で開いた実験の場合（`getExperimentInfo$` は `tasks.get_by_id_ex` で `last_change` を取り直すが、失敗した更新では変わらないため、同じ結果になると推測される）。自動更新が走ったあとの状態（同じく `last_change` の比較で止まると推測される）
- 由来：reducer・Effect・詳細ヘッダーのファイルは、比較資料で上流と一致する
