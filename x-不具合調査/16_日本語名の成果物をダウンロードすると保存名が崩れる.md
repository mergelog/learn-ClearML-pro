# 日本語や空白を含む名前の成果物をダウンロードすると、保存されるファイル名が崩れる

| 項目 | 内容 |
|---|---|
| カテゴリー | 処理値 |
| 不具合内容 | 成果物（ARTIFACTS の DATA AUDIT・OTHER など）のダウンロードボタンで、日本語の名前のファイル（`結果.csv`）が `csv.csv` として保存される。空白を含む名前（`my report.csv`）は `_my report.csv_` になる |
| 期待動作 | サーバにあるファイル名（`結果.csv`、`my report.csv`）で保存される |
| 直さないと困ること | 日本語の名前の成果物を複数ダウンロードすると、どれも同じような名前（`csv.csv`、`csv (1).csv` …）になり、どのファイルがどの成果物か分からなくなる |
| 修正規模 | 小 |

| 項目 | 内容 |
|---|---|
| 画面 | 実験管理 > 詳細 > ARTIFACTS の各成果物のダウンロードボタン（サイズが 500MB 未満のもの） |
| 観点 | B（文字列の値の扱い：ファイル名） |
| 重大度 | S3 |
| 確度 | 再現済み（fileserver の応答のヘッダを、fileserver と同じ形に差し替えて確認） |
| 由来 | 上流 |
| 発生条件 | 成果物のサイズ（`content_size`）が 500MB 未満で、ファイル名に ASCII 以外の文字、空白、`;`・`"` などが含まれる |
| 関連 | なし |

## 症状

| 成果物のファイル名 | fileserver の `Content-Disposition` | 保存名 |
|---|---|---|
| `結果.csv` | `inline; filename=.csv; filename*=UTF-8''%E7%B5%90%E6%9E%9C.csv` | `csv.csv` |
| `my report.csv` | `inline; filename="my report.csv"` | `_my report.csv_` |
| `report.csv` | `inline; filename=report.csv` | `report.csv`（正しい） |

`結果.csv` は、フロントエンドが ASCII の代替名 `.csv` を採り、Chrome が先頭のドットを避けて `csv.csv` にした。`my report.csv` は引用符ごとファイル名にし、Chrome が引用符を `_` に置き換えた。

## 再現手順

実バックエンドの既存タスクの成果物で行う。fileserver（8081）への要求を Playwright で横取りし、ヘッダだけを上の表の形にして返した。表のヘッダの形は、起動中の fileserver コンテナの Werkzeug 3.1.5 の `send_file` を読み、同じ関数で生成して確かめた。

1. 成果物を持つタスクの ARTIFACTS で、成果物（例：OTHER の `evaluation`）を開く
2. ファイルのパスの横のダウンロードボタンを押す
3. 保存名を見る

スクリプトは [scripts/p2b-artifact-download-name.spec.ts](./scripts/p2b-artifact-download-name.spec.ts)。

## 期待する動作

`filename*`（RFC 6266 / RFC 5987 の UTF-8 の名前）があればそれを、無ければ引用符を外した `filename` を保存名にする。

## 原因

[common-experiments-info.effects.ts:422](../src/app/webapp-common/experiments/effects/common-experiments-info.effects.ts#L422) の `downloadArtifact` は、500MB 未満の成果物（[experiment-artifact-item-view.component.ts:47](../src/app/webapp-common/experiments/dumb/experiment-artifact-item-view/experiment-artifact-item-view.component.ts#L47) の `inMemorySize`）を `fetch` でメモリに読み、次の式で保存名を決める。

```ts
const header = res.headers.get('Content-Disposition');
const parts = header!.split(';');
a.download = parts[1].split('=')[1];
```

`;` で区切った2番目の要素の `=` の右をそのまま使うため、次の3点で崩れる。

- fileserver（Flask の `send_from_directory` → Werkzeug の `send_file`）は、ASCII でない名前に対して `filename=<ASCII に落とした代替名>; filename*=UTF-8''<名前>` を返す。2番目の要素は代替名（`結果.csv` なら `.csv`）で、`filename*` は読まれない
- 空白や `;`・`"` を含む名前は、`filename="…"` と引用符で囲まれる。引用符を外していない。名前の中に `;` があると、区切りの位置もずれる
- `Content-Disposition` が無い、または区切りが1つしかない応答では `header!` や `parts[1]` が例外になる（`catchError` で、URL を開き直す経路に落ちる）

500MB 以上の成果物は `fetch` を使わず、`download` を付けた URL を新しいタブで開く。この経路ではブラウザが `Content-Disposition` を解釈するため、`filename*` が使われて正しい名前になる（コードからの判断で、画面では確かめていない）。

## 影響範囲と同種箇所

成果物のダウンロードボタンを持つ画面（ARTIFACTS の DATA AUDIT・OTHER）。ほかにダウンロードのファイル名を決める箇所は次のとおりで、同じ問題は無い。

| 箇所 | 保存名 |
|---|---|
| ログの Download full log | `Log - {タスクID}.txt` |
| グラフの JSON・CSV の書き出し、スカラーの概要の CSV | メトリクス名・タスク名から組み立てる。`download` 属性に日本語をそのまま渡すため問題ない |
| デバッグ画像のダウンロード（`base-image-viewer`） | URL のパスの最後の部分（パーセントエンコードされたまま）を `download` 属性に渡す。fileserver が別オリジンの構成ではブラウザが `download` 属性を無視するため問題ないが、同一オリジンで配信する構成では `%E7%94%BB%E5%83%8F.png` のような名前になるはずである（推測。確かめていない） |

## 対策案

`Content-Disposition` の解析を関数に切り出し、`filename*=UTF-8''…` があれば `decodeURIComponent` した値を、無ければ `filename=` の値の引用符を外したものを使う。どちらも無ければ URL のパスの最後の部分（デコード済み）を使う。1ファイル内の変更で「小」とした。

## 検証範囲

- 確認したこと：Playwright（Chromium、実バックエンドの既存タスク）で、fileserver の応答のヘッダを3通りに差し替えたときの保存名。起動中の fileserver コンテナ（`docker exec` で読み取りだけ）で、`fileserver.py` のダウンロードの処理と、Werkzeug 3.1.5 の `send_file` が返すヘッダの形
- 確認していないこと：実際に日本語の名前の成果物を fileserver に置いたときのダウンロード（成果物のアップロードは書き込みを伴うため行っていない）。500MB 以上の成果物の経路。Safari・Firefox での保存名
- 由来：`common-experiments-info.effects.ts` は比較資料で上流と一致する（§6 の分類4〜10に名前が無い）
