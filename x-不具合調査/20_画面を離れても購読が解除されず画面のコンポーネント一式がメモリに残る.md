# 画面を離れても Store の購読が解除されず、画面のコンポーネント一式がメモリに残る

| 項目 | 内容 |
|---|---|
| カテゴリー | 状態 |
| 不具合内容 | モデル詳細の TASKS タブ、エンドポイントの詳細、比較画面、プロジェクトの OVERVIEW、ダッシュボードのヘッダーで、画面を離れた後も Store の購読が解除されない。購読のコールバックがコンポーネントを参照し続けるため、開いた回数だけ、その画面のコンポーネント（多くは画面の一式と DOM）がメモリに残る |
| 期待動作 | 画面を離れたら購読が解除され、コンポーネントと DOM は GC で回収される |
| 直さないと困ること | 同じタブで画面を行き来するほど、GC で回収されないメモリが増え続ける。モデル詳細の TASKS タブでは、1回開くごとに JS ヒープが約1.7MB 増え、コンポーネント114個と DOM 要素419個が残る。タブを再読み込みせずに長く使う利用者ほど影響が大きい |
| 修正規模 | 小 |

| 項目 | 内容 |
|---|---|
| 画面 | モデル > 詳細 > TASKS、エンドポイント > 詳細 > GENERAL、比較（タスク・モデル）の全タブ、プロジェクト > OVERVIEW、ダッシュボード（ヘッダーの「My work」） |
| 観点 | E（購読の破棄） |
| 重大度 | S4 |
| 確度 | 再現済み |
| 由来 | 上流 |
| 発生条件 | 同じタブで対象の画面を開いて離れる（再読み込みするまで積み上がる）。プロジェクトの OVERVIEW は、そのプロジェクトで指標を選んでいない場合 |
| 関連 | [21](./21_ダッシュボードを開いた後に一覧でMy_Workを選ぶとURLから絞り込みの条件が消える.md)（ダッシュボードのヘッダーの購読が残ることで起きる、URL の絞り込みの消失）、[22](./22_同じ画面で操作を繰り返すと購読やリスナが重なり同じ処理が回数分走る.md)（画面にいるあいだに購読が重なるもの） |

## 症状

実バックエンドで、対象の画面と中立の画面（`/settings/profile`）のあいだをアプリ内の遷移で3往復し、中立の画面に戻るたびに Store の購読数と購読者のコールバックを数えた。あわせて、対象の画面にいるあいだにコンポーネントを `WeakRef` で控え、GC の後も生きていて DOM 上に無いものを数えた。

| 画面 | Store の購読数（開始・1往復・2往復・3往復） | 往復ごとに増えるコールバック | 1・2往復目の分で GC 後も残るもの | 確認 |
|---|---|---|---|---|
| モデル詳細の TASKS タブ | 46・47・48・49 | `(experiments) => { this.tags = uniq(…); this.initTags = false; }` | モデル画面の一式（`ModelsComponent`・表・詳細パネル・TASKS タブの表など、アプリのコンポーネント32種） | 再現（実バックエンド） |
| エンドポイントの詳細の GENERAL タブ | 購読は 1・2・3 と残る | `(id) => this.store.dispatch(ServingActions.getEndpointInfo({id}))` | エンドポイント画面の一式（`ServingComponent`・表・詳細パネル・`ServingGeneralInfoComponent` など16種） | 再現（モック API。実バックエンドにエンドポイントが無い） |
| 比較画面（タスクの `details`・`hyper-params`・`scalars`・`metrics-plots`・`debug-images`、モデルの `models-details`・`network`・`scalars` のすべて） | 58・60・61・62（タスクの `hyper-params/values`） | `(params) => { this.selectedIds = params?.ids; }` | 比較画面の一式（`ExperimentsCompareComponent`・見出し・開いていたタブのコンポーネント） | 再現（実バックエンド） |
| プロジェクトの OVERVIEW | 40・42・43・44 | `() => { this.setMetricsPanel(true); }` | `ProjectInfoComponent`・`MarkdownEditorComponent` | 再現（実バックエンド） |
| ダッシュボード（ヘッダーの「My work」） | 35・36・37・38 | `(params) => { const filters = decodeFilter(params.filter); … }` | `ShowOnlyUserWorkComponent` | 再現（実バックエンド） |

残る量の例として、モデル詳細の TASKS タブと、同じモデルの GENERAL タブ（購読が残らない）を10往復ずつし、往復ごとに GC の後の JS ヒープ（`Runtime.getHeapUsage` の `usedSize`）を取った。

| 画面 | 2往復目から10往復目までの増え方 | 2往復目の分で残るもの |
|---|---|---|
| モデル詳細の TASKS タブ | 1往復あたり約2,064KB | コンポーネント114個、切り離された DOM 要素419個 |
| モデル詳細の GENERAL タブ | 1往復あたり約376KB | なし |

GENERAL タブでも増えているのは、開発ビルドの Store の開発ツールが action と状態の履歴を持つためと考えられる（本番ビルドには入らない）。差の約1.7MB が、TASKS タブの購読が保持している分である。

残った購読のコールバックは、画面を離れた後も Store の値が変わるたびに呼ばれるが、どの箇所も破棄されたコンポーネントのフィールドを書き換えるか、条件で止まるだけで、画面の表示や API 呼び出しには出ない。例外はダッシュボードのヘッダーの購読で、一覧の URL を書き換える（21）。

## 再現手順

1. 同じタブのまま、モデルの詳細を開いて TASKS タブを開き、別の画面（設定など）へ移る。これを何度か繰り返す
2. Chrome の DevTools の Memory で、ヒープのスナップショットを取り、`ModelExperimentsTableComponent`（開発ビルドでは `_ModelExperimentsTableComponent`）を検索する。移った回数だけインスタンスが残っている

スクリプトは次のとおり。

- [scripts/p2e-leak-crawl.spec.ts](./scripts/p2e-leak-crawl.spec.ts)：全ルート（フェーズ0の61ルートと観点 D で足したルート）を3往復して、Store の購読数・コールバック・window/document のリスナ・残るインスタンスを数える。`LEAK_ROUTES` にルートを渡すとそのルートだけを調べる
- [scripts/p2e-serving-general-info.spec.ts](./scripts/p2e-serving-general-info.spec.ts)：エンドポイントの詳細（モック API）
- [scripts/p2e-leak-heap.spec.ts](./scripts/p2e-leak-heap.spec.ts)：TASKS タブと GENERAL タブの JS ヒープの増え方
- 数え方は [scripts/helpers/leak.ts](./scripts/helpers/leak.ts)。Store の購読数は、開発ビルドでは Store の開発ツールが `StateObservable` を差し替えるため、`store.source` から `source` をたどって最初の Subject の `observers` を数える。コールバックは各購読者の `destination` をたどり、`subscribe()` に渡した関数のソースの先頭で区別する

## 期待する動作

画面を離れたら、その画面のコンポーネントが作った購読はすべて解除され、コンポーネントと DOM が回収される。同じ画面を何度開いても、GC の後のメモリの使用量は一定に収まる。

## 原因

どの箇所も、コンポーネントが Store を購読し、破棄のときに解除されない。解除されない理由は箇所ごとに違う。

| 画面 | 箇所 | 解除されない理由 |
|---|---|---|
| モデル詳細の TASKS タブ | [model-experiments-table.component.ts:135](../src/app/webapp-common/models/containers/model-experiments-table/model-experiments-table.component.ts#L135) | `this.experiments$`（`selectExperimentsList`）の購読を保持も解除もしない。同じコンストラクタの `paramsSubscription` は `ngOnDestroy()` で解除している |
| エンドポイントの詳細 | [serving-general-info.component.ts:107](../src/app/webapp-common/serving/serving-general-info/serving-general-info.component.ts#L107) | `takeUntilDestroyed()` の後ろに `combineLatestWith(this.store.select(servingFeature.selectEndpoints))` がある。破棄で外側の `selectRouterParams` は完了するが、`combineLatest` はすべての入力が完了するまで完了しないため、`selectEndpoints` の購読が残る |
| 比較画面 | [experiment-compare-header.component.ts:99](../src/app/webapp-common/experiments-compare/dumbs/experiment-compare-header/experiment-compare-header.component.ts#L99) | コンストラクタで `routerSubscription` に `selectRouterParams` の購読を入れ、`ngOnInit()`（[同 :111](../src/app/webapp-common/experiments-compare/dumbs/experiment-compare-header/experiment-compare-header.component.ts#L111)）で同じフィールドに `selectRouterUrl` の購読を上書きする。`ngOnDestroy()`（[同 :125](../src/app/webapp-common/experiments-compare/dumbs/experiment-compare-header/experiment-compare-header.component.ts#L125)）は後の購読しか解除しない |
| プロジェクトの OVERVIEW | [project-info.component.ts:71](../src/app/webapp-common/project-info/project-info.component.ts#L71) | `filter(data => !!data), take(1)` で、指標が選ばれるまで `take(1)` が完了しない。そのプロジェクトで指標を選ばないまま画面を離れると残る。後でどこかのプロジェクトの指標が Store に入った時点で1回動いて完了する |
| ダッシュボードのヘッダー | [show-only-user-work.component.ts:33](../src/app/webapp-common/shared/components/show-only-user-work/show-only-user-work.component.ts#L33) | `takeUntilDestroyed()` を付けていない。ヘッダーはダッシュボードでだけこの部品を出すため、ダッシュボードを離れるたびに残る（21） |

どこまで残るかは、購読したコンポーネントが何を参照しているかで決まる。比較画面の見出しは `ChangeDetectorRef` を持ち、モデルの TASKS タブの表は `viewChild` で子の表を持つ。これらを通じて画面のビューと DOM がたどれるため、画面の一式が残る。エンドポイントの詳細はビューへの参照を持たないが、観測では画面の一式が残った（どの参照から残るかまでは追っていない）。「My work」の部品は Router と Store しか持たず、部品だけが残る。

## 影響範囲と同種箇所

§3 E の静的な確認（`subscribe` 321件の分類、プラン §8 フェーズ2の結果 E）と、全ルートの巡回で探した。巡回はフェーズ0の61ルートと観点 D で足した11ルートから、重複・中立の画面・存在しないルートを除いた63ルートで、エンドポイントの詳細はモック API で別に確かめた。購読の解除漏れで画面を離れた後に残るものは、上の表の5箇所だった。

`take(1)` や `first()` で止める購読のうち、前に `filter` があって条件を満たす値が来ないと完了しないものも調べた。プロジェクトの OVERVIEW のほかは、値がすぐ届くもの（画面の倍率、署名付き URL、ダイアログの結果など）で、残り続けるものは無かった。

## 対策案

第一案は、箇所ごとに購読を破棄に結び付ける。

- モデル詳細の TASKS タブ：`this.experiments$` の `pipe` に `takeUntilDestroyed()` を足す（コンストラクタの中なので引数は要らない）
- エンドポイントの詳細：`combineLatestWith` を `takeUntilDestroyed()` より前に置くか、`takeUntilDestroyed()` を `pipe` の最後に移す
- 比較画面：コンストラクタの購読を別のフィールドにして `ngOnDestroy()` で解除するか、`takeUntilDestroyed()` を付ける
- プロジェクトの OVERVIEW：`takeUntilDestroyed()` を足す
- ダッシュボードのヘッダー：`takeUntilDestroyed()` を足す（21 の対策と同じ）

5ファイルとも1〜2行の変更で、互いに独立しているため「小」とした。

このコードベースは `takeUntilDestroyed()` を `pipe` の先頭に置く書き方が多い。先頭に置くと、後ろの `switchMap`・`mergeMap`・`combineLatestWith` などの内側の購読は完了せずに残りうる（エンドポイントの詳細がこの型）。lint の `rxjs/no-unsafe-takeuntil` に相当する検査（`takeUntilDestroyed` を最後に置く）を入れると、同じ型の再発を防げる。今回の確認では、先頭に置いたもののうち後ろの内側の購読が残るのはエンドポイントの詳細だけで、ほかは内側が API・ダイアログ・`takeUntil` 付きで完了するか、内側にも `takeUntilDestroyed` がある。

## 検証範囲

- 確認したこと：Playwright（Chromium）と実バックエンド（読み取りだけ）で、全ルートを3往復したときの Store の購読数・コールバック・window/document のリスナ（zone.js が積む配列で数えた）・残るインスタンス。エンドポイントの詳細はモック API で同じことを確かめた。モデル詳細の TASKS タブと GENERAL タブの10往復での JS ヒープの増え方と、残る DOM 要素の数
- 確認していないこと：本番ビルドでの増え方（開発ツールが入らないため、増え方の差はより明確になると考えられる）。画面を長時間使ったときの体感の遅さ。巡回に含めていない画面（ダイアログの中の画面、操作をしてから開く画面など）。巡回は各ルートを開いて3秒待つだけで、画面の中の操作の後にだけ作られる購読は、静的な確認で拾えたものしか確かめていない
- 由来：5つのコンポーネントは比較資料で上流と一致する。購読の解除の仕組み（`takeUntilDestroyed`・`combineLatest` の完了の条件）は Angular 21・rxjs 7 でも同じである
