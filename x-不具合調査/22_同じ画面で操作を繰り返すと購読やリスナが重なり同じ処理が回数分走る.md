# 同じ画面で操作を繰り返すと、購読やリスナが重なり、同じ処理が回数分走る

| 項目 | 内容 |
|---|---|
| カテゴリー | 状態 |
| 不具合内容 | タスクの全画面表示でタブを移るたびに、パンくずを設定する購読が1つずつ増え、選択中のプロジェクトが変わるたびに同じ action（`setBreadcrumbsOptions`）が購読の数だけ dispatch される。比較画面の値の表（SCALARS の VALUES など）では、一覧を取り直すたびに表のスクロール領域へ scroll のリスナが1つずつ増え、1回のスクロールで変更検知（`detectChanges()`）がリスナの数だけ走る |
| 期待動作 | 購読・リスナは画面ごとに1つで、同じ処理は1回だけ走る |
| 直さないと困ること | 画面を開いたまま操作を続けるほど、同じ処理が重なって無駄に走る。比較画面の自動更新（10秒ごと、比較中のタスクが更新されたとき）では、実行中のタスクを比べ続けると1時間で最大360のリスナが積まれ（コードからの見積もり）、スクロールのたびの処理が増えていく |
| 修正規模 | 小 |

| 項目 | 内容 |
|---|---|
| 画面 | 実験管理 > タスクの全画面表示（`/tasks/:id/output/…`）、比較 > SCALARS の VALUES・MAX VALUES・MIN VALUES |
| 観点 | E（購読・イベントリスナの破棄） |
| 重大度 | S4 |
| 確度 | 再現済み |
| 由来 | 上流 |
| 発生条件 | 全画面表示：画面を出ずにタブを移る（URL が変わるたび）。比較画面：更新ボタンを押す、または自動更新で一覧が取り直される |
| 関連 | [20](./20_画面を離れても購読が解除されず画面のコンポーネント一式がメモリに残る.md)（画面を離れた後に残る購読。こちらは画面にいるあいだに重なるもの） |

## 症状

| 箇所 | 操作 | 起きること | 確認 |
|---|---|---|---|
| タスクの全画面表示 | 6つのタブ（EXECUTION・CONFIGURATION・ARTIFACTS・INFO・SCALARS・CONSOLE）を2巡 | パンくずの購読が 1 → 9 → 17 と増える。その後に選択中のプロジェクトを Store に入れ直すと、`setBreadcrumbsOptions` が17回 dispatch される | 再現（実バックエンド） |
| 比較画面の SCALARS の VALUES | 更新ボタンを5回押す | 表のスクロール領域の scroll のリスナが 1 → 6 と増える（同じ要素）。1回のスクロールで `detectChanges()` が6回呼ばれる | 再現（実バックエンド） |

どちらも画面を離れればコンポーネントと一緒に破棄され、画面の外には残らない。画面にいるあいだの処理の重複である。

## 再現手順

全画面表示（実バックエンドの既存タスク、読み取りだけ）：

1. タスクの全画面表示（`…/tasks/{id}/output/execution`）を開く
2. 上のタブで EXECUTION・CONFIGURATION・ARTIFACTS・INFO・SCALARS・CONSOLE を順に開くことを2回繰り返す
3. 選択中のプロジェクトが Store で入れ替わる（プロジェクトの再取得など）と、`setBreadcrumbsOptions` が購読の数だけ続けて dispatch される。Redux DevTools で見える。スクリプトでは同じプロジェクトを `setSelectedProject` で入れ直して起こした

比較画面（実バックエンドの既存タスク2件、読み取りだけ）：

1. 2つのタスクを比較し、SCALARS の VALUES を開く
2. 右上の更新ボタンを5回押す
3. 表のスクロール領域の scroll のリスナが6つになる（zone.js が要素に積む `__zone_symbol__scrollfalse` の配列の長さ）

スクリプトは [scripts/p2e-output-breadcrumbs.spec.ts](./scripts/p2e-output-breadcrumbs.spec.ts) と [scripts/p2e-compare-scroll-listeners.spec.ts](./scripts/p2e-compare-scroll-listeners.spec.ts)。リスナの数え方は [scripts/helpers/leak.ts](./scripts/helpers/leak.ts) の `elementListenerCounts()`。zone.js が `addEventListener` を差し替え、同じ要素・同じ種類のイベントにはブラウザへ1つだけ登録するため、CDP の `DOMDebugger.getEventListeners` では増えたことが分からない。

## 期待する動作

- 全画面表示：パンくずを設定する購読は画面につき1つで、プロジェクトが変わったときに `setBreadcrumbsOptions` を1回だけ dispatch する
- 比較画面：scroll のリスナは表のスクロール領域につき1つで、一覧を取り直しても増えない

## 原因

全画面表示は、[base-experiment-output.component.ts:99](../src/app/webapp-common/experiments/containers/experiment-ouptut/base-experiment-output.component.ts#L99) の `ngOnInit()` が `selectRouterConfig` を購読し、全画面表示のあいだ値が出るたびに `setupBreadcrumbsOptions()` を呼ぶ。`setupBreadcrumbsOptions()`（[同 :201](../src/app/webapp-common/experiments/containers/experiment-ouptut/base-experiment-output.component.ts#L201)）は、呼ばれるたびに `selectedProject$` の購読を `this.subs` に足す。`selectRouterConfig` は画面遷移のたびに新しい配列を返す（`router-reducer.ts` の `setRouterSegments` が `config` を置き換える）ため、タブを移るたびに購読が1つ増える。`this.subs` は `ngOnDestroy()` でまとめて解除されるので、画面を出れば消える。

比較画面は、[experiment-compare-metric-values.component.ts:191](../src/app/webapp-common/experiments-compare/containers/experiment-compare-metric-values/experiment-compare-metric-values.component.ts#L191) の `comparedTasks$` の購読が、一覧の値が変わるたびに `startTableScrollListener()` を呼ぶ（[同 :210](../src/app/webapp-common/experiments-compare/containers/experiment-compare-metric-values/experiment-compare-metric-values.component.ts#L210)）。`startTableScrollListener()`（[同 :249](../src/app/webapp-common/experiments-compare/containers/experiment-compare-metric-values/experiment-compare-metric-values.component.ts#L249)）は `fromEvent(this.scrollContainer, 'scroll')` を購読するが、戻り値を保持も解除もしない。一覧は更新ボタン（`RefreshService.trigger()`）と、比較中のタスクが更新されたときの自動更新（`compare-header-effects.ts` の `refresh.trigger(true)`、`AUTO_REFRESH_INTERVAL` は10秒）で取り直され、そのたびに新しい配列になる。スクロール領域の要素は取り直しで作り直されないため、同じ要素にリスナが積まれる。

## 影響範囲と同種箇所

§3 E の静的な確認で、呼ばれるたびに購読やリスナを足すメソッドを探した（プラン §8 フェーズ2の結果 E）。処理が重なるのはこの2箇所だった。

| 箇所 | 呼ばれる契機 | 重なるもの |
|---|---|---|
| `BaseExperimentOutputComponent.setupBreadcrumbsOptions()`（`ExperimentOutputComponent` が継承） | 全画面表示のあいだの画面遷移ごと | `selectedProject$` の購読と `setBreadcrumbsOptions` の dispatch |
| `ExperimentCompareMetricValuesComponent.startTableScrollListener()` | 比較の値の表の一覧の取り直しごと（`scalars`・`scalars/values`・`scalars/max-values`・`scalars/min-values` の4ルートが同じコンポーネント） | 表のスクロール領域の scroll のリスナと `detectChanges()` |

同じ名前の `setupBreadcrumbsOptions()` を持つほかのコンポーネント（プロジェクト・パイプライン・レポートの一覧、比較画面、モデルの詳細、エンドポイントの詳細など）は、コンストラクタか `ngOnInit()` から1回だけ呼ぶため重ならない。レポートの本文（`report.component.ts`）は `effect()` と `setTimeout` から何度も呼ぶが、中で dispatch するだけで購読を作らないため重ならない。

## 対策案

- 全画面表示：`setupBreadcrumbsOptions()` の購読を `ngOnInit()` で1回だけ作り、`minimized` でないときだけ dispatch するよう処理の中で判断する。または前の購読を保持して、呼ぶ前に解除する
- 比較画面：`startTableScrollListener()` を、スクロール領域の要素が変わったときだけ購読し直すようにする（前の購読を保持して解除する）。`ngAfterViewInit()` で1回だけ購読してもよい

どちらも1ファイル内の数行の変更で、2箇所あわせて「小」とした。

## 検証範囲

- 確認したこと：Playwright（Chromium）と実バックエンド（読み取りだけ）で、全画面表示のタブの移動でパンくずの購読が増えること（Store の購読者のコールバックを数えた。[scripts/helpers/leak.ts](./scripts/helpers/leak.ts) の `storeObserverCallbacks()`）と、選択中のプロジェクトを入れ直したときの `setBreadcrumbsOptions` の回数。比較画面の更新ボタンでスクロールのリスナが増えることと、1回のスクロールでの `detectChanges()` の回数
- 確認していないこと：比較画面の自動更新での増加（実行中のタスクが無く、更新されるタスクを用意していない。自動更新も更新ボタンと同じ `RefreshService.trigger()` を通るため、同じく増えると判断した）。長時間使い続けたときの体感の遅さ
- 由来：2つのコンポーネントは比較資料で上流と一致する。原因は購読の作り方にあり、Angular の版に依存しない
