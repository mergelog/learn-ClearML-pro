# フロントエンドの体験に関する提案

作成：2026-09-23

## この資料は何か

`src/app` のフロントエンドについて、UI・UX の一般的な考え方に照らして、いま欠けているものと、その埋め方を20件に分けたものである。1件1ファイルで、この一覧は索引である。番号は作成順で、重要度の順ではない。

不具合ではない。動かない箇所は [x-不具合調査](../x-不具合調査/00_不具合調査プラン.md) が44件を台帳にしている。こちらが扱うのは、動いてはいるが利用者の判断や操作を支えきれていない箇所である。両者が同じ部品を指すことはあり、その場合は各ファイルの「関連」から辿れる。

読む順番は番号どおりである必要はない。着手の順は §4 を見る。

## 1. 範囲と、範囲外

調べたのは `src/app` のうち、次の2つである。

* 自作の2 feature（`features/data-catalog`・`features/quality-pipeline`）
* アプリ全体に効く構成（大域の scss、経路、通知、自動更新、ビルドの枠、CI）

取り込み領域（`webapp-common/**`・`business-logic/**`）の個別の画面は、網羅していない。

凍結領域のファイルを書き換える提案は1件である（[08](./08_フォーカスが見えるようにする.md)）。加えて、実装の選び方によっては凍結領域へ及ぶものが4件ある。

| # | どこで凍結領域に及びうるか |
| --- | --- |
| [03](./03_取り消せない操作に退路を用意する.md) | 離脱確認の固定文言を変える場合 |
| [04](./04_操作の結果を画面と支援技術の両方へ返す.md) | live region を外枠（`app.component.html`）へ置く場合 |
| [11](./11_実行の終わりを見逃さないようにする.md) | タブの見出しの接頭辞を `BreadcrumbsService` から渡す場合 |
| [17](./17_体感性能を測る対象を変える.md) | 動きを止める規則を大域の scss へ置く場合 |

判断の手順は [62_レビュー基準.md §4.6](../docs/phase7_チーム開発標準/62_レビュー基準.md) に従う。凍結領域の部品を `imports` で借りるだけの場合（[18](./18_自作画面と取り込み画面の見た目を揃える.md)）は、ファイルを書き換えないため §4.6 の対象にはならない。

実機では確かめていない。根拠はすべてリポジトリの中のコードと設定であり、各ファイルは参照した位置を行番号で示している。「実際にそう見える」ことの確認は、着手時に行う。

## 3. 19件に通じている3つのこと

個別に読むと別の話に見えるが、根は3つである。

**持っている情報を渡していない。** `CatalogLineage.origin` は state にありながら component へ渡っていない（[13](./13_来歴を鎖として見せる.md)）。合格の基準は `config/model_gate.yaml` にありながら画面に出ていない（[12](./12_評価指標を比較として読めるようにする.md)）。再現に要る値は ClearML の Task にありながら読み取っていない（[14](./14_再現に要る情報を画面に載せる.md)）。絞り込みの条件は URL にありながら、リンクがそれを引き継がない（[20](./20_画面の状態をURLで渡せるようにする.md)）。どれも新しく作る話ではなく、既にあるものを繋ぐ話である。

**取り込み領域に既にある仕掛けを使っていない。** 通知（`addMessage`）、離脱の確認（`generalLeavingBeforeSaveAlertGuard`）、自動更新（`RefreshService`）、続きを読む部品、チップの入力欄。どれも自作 feature からの参照が0である。使うかどうかの判断が先送りされたまま、使わない側が既定になっている（[18](./18_自作画面と取り込み画面の見た目を揃える.md)）。

**適合の検査が通っていることと、使えることが別である。** axe の違反は自作画面で0件である。その状態で、焦点は全画面で見えず（[08](./08_フォーカスが見えるようにする.md)）、変化は読み上げられない（[04](./04_操作の結果を画面と支援技術の両方へ返す.md)）。検査が見ていないものを一覧にしたのが [19](./19_UXの退行を検出する仕組みを置く.md) である。

## 4. 着手の順

費用と効き目の比で並べると、次のようになる。上から順に、前の結果に依存せず進められる。

| 順 | 件 | 理由 |
| --- | --- | --- |
| 1 | [08](./08_フォーカスが見えるようにする.md) | 変更は数行。効くのは全画面。凍結領域だが範囲が `reboot.scss` の3行に限られる |
| 2 | [20](./20_画面の状態をURLで渡せるようにする.md) の1〜2 | リンク3本の変更。決めてある方針が働いていない状態を直す |

| 4 | [13](./13_来歴を鎖として見せる.md)・[10](./10_走っている実行が生きて見えるようにする.md) | state が既に持っている値を画面へ出す |

## 5. 決めないと進まないこと

次の5つは、実装の前に判断が要る。

| 判断 | どこで扱うか |

| 時刻を UTC と現地時刻のどちらに揃えるか | [07](./07_時刻・数値・言語の表記を揃える.md) |
| 画面の言語を日本語にするか、英語のままにするか | [07](./07_時刻・数値・言語の表記を揃える.md) |
| 取り込み領域の UI 部品をどこまで借りるか | [18](./18_自作画面と取り込み画面の見た目を揃える.md) |
| 画面を離れた後も実行を追跡するか | [11](./11_実行の終わりを見逃さないようにする.md) |
| 画面から本番のモデルを切り替えてよいか、誰が押せるか | [16](./16_昇格と切り戻しを画面から行えるようにする.md) |
| 品質パイプラインが実行を1件だけ持つ前提を変えるか | [20](./20_画面の状態をURLで渡せるようにする.md)・[12](./12_評価指標を比較として読めるようにする.md) |
