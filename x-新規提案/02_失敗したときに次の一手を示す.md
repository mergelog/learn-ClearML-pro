# 失敗したときに次の一手を示す

| 項目 | 内容 |
| --- | --- |
| 分類 | UX体験 |
| 領域 | 自作（`features/data-catalog`・`features/quality-pipeline`） |
| 直る体験 | 失敗した後、画面を再読み込みせずに操作を続けられる |
| 規模 | 中 |
| 状態 | 未着手 |

## いま画面で起きていること

自作画面の失敗表示は、見出しの下に置いた1つの段落である。

* [data-catalog-page.component.html:10-12](../src/app/features/data-catalog/containers/data-catalog-page/data-catalog-page.component.html#L10)
* [catalog-asset-detail-page.component.html:17-19](../src/app/features/data-catalog/containers/catalog-asset-detail-page/catalog-asset-detail-page.component.html#L17)
* [quality-pipeline-page.component.html:10-12](../src/app/features/quality-pipeline/containers/quality-pipeline-page/quality-pipeline-page.component.html#L10)

どれも `<p role="alert">{{ reason }}</p>` で、文面は `describeClearmlFailure()` が作る。この段落には3つのものが無い。再試行の入口、閉じる手段、そして何回目の失敗かの区別である。

一覧の取得が失敗した場合、利用者に残された操作は絞り込みを変えるか、ブラウザを再読み込みするかのどちらかになる。同じ条件でもう一度引く経路が画面に無い。

一方、取り込み領域には仕掛けが揃っている。[layout.actions.ts:90-100](../src/app/webapp-common/core/actions/layout.actions.ts#L90) の `addMessage` は重大度・本文に加えて `userActions`（通知の中に置くボタンと、押したときに流す action）を受け取る。通知の設定は [app.config.ts:47-56](../src/app/app.config.ts#L47) にあり、`autoHide` は既定 5000ms・`error` は消さないと決まっている。`src/app` 全体で `addMessage` は53ファイル・178箇所から呼ばれているが、自作の2 feature からの呼び出しは0である。

## なぜ変えるか

失敗の表示が果たす役割は3つある。何が起きたかを言うこと、誰のせいかを切り分けること、次に何ができるかを示すことである。いまの段落は1つめだけを果たしている。

切り分けが要るのは、ClearML への問い合わせが失敗する原因が一様でないからである。通信が届かない、権限が無い、対象が消えている、要求そのものが不正、の4つは利用者の次の行動が違う。最初の1つだけが「もう一度押す」で解決しうる。

## 解決とみなす状態

1. 失敗の表示に、その失敗を起こした操作をもう一度実行するボタンがある。一覧なら同じ条件での再取得、保存なら同じ値での再保存である
2. `describeClearmlFailure()` の戻り値を、文字列から「種別＋本文」へ変える。種別は通信・権限・不在・要求の4つ。種別ごとに、再試行を出すかどうかと、添える案内を変える
3. 権限と不在では再試行を出さない。代わりに、権限なら誰に依頼するか、不在なら一覧へ戻る導線を出す
4. 操作に伴う失敗（保存・起動・停止）は段落ではなく通知として出し、`userActions` に再試行を置く。画面の読み込みに伴う失敗は、いまの位置の段落のまま、再試行ボタンを足す
5. 失敗の表示は、次に同じ操作が成功した時点で消える。閉じるボタンでも消える

## 変更の範囲

* 変更：[`~/shared/clearml/clearml-failure`](../src/app/shared/clearml/clearml-failure.ts)（戻り値の型）
* 変更：両 feature の reducer が持つ `error` の型と、3つのテンプレート
* 変更：両 feature の Effects。通知として出すものは `addMessage` を dispatch する
* 影響：`describeClearmlFailure()` の戻り値を使っている既存のテストとフィクスチャ（[e2e/fixtures/quality-pipeline.fixture.ts](../e2e/fixtures/quality-pipeline.fixture.ts) の `FAILURE_MESSAGE` を含む）

## 確かめ方

* 単体：HTTP の状態コードと ClearML の `result_subcode` から種別への対応を、応答の実例で確かめる
* E2E：[e2e/accessibility.spec.ts:58](../e2e/accessibility.spec.ts#L58) は失敗の文面が `role="alert"` として読み上げへ届くことを既に見ている。再試行ボタンを足した後もこの検査が通ることを確認する

## 注意

`addMessage` は凍結領域の action である。呼ぶだけなら凍結領域の変更にはあたらない。ただし通知の見た目（[angular-notifier](../src/app/webapp-common/angular-notifier/)）を変える必要が出た場合は、レビュー基準 §4.6 の判断が要る。
