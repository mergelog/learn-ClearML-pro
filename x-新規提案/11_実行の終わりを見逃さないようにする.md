# 実行の終わりを見逃さないようにする

| 項目 | 内容 |
| --- | --- |
| 分類 | ML体験 |
| 領域 | 自作（`features/quality-pipeline`）。通知は凍結領域の action を呼ぶだけ |
| 直る体験 | 実行が終わったこと、失敗したことに気付ける。画面を開きっぱなしにしなくてよい |
| 規模 | 中 |
| 状態 | 未着手（通知をどこまで出すかの判断が先） |

## いま画面で起きていること

実行の追跡は、この画面を開いているあいだだけ続く。

`QualityPipelineEffects` は経路の `providers` に置かれていて（[quality-pipeline.routes.ts:32-36](../src/app/features/quality-pipeline/quality-pipeline.routes.ts#L32)）、経路を離れると state ごと破棄される。追跡は `leavePage` でも止まる（[quality-pipeline.effects.ts:218](../src/app/features/quality-pipeline/state/quality-pipeline.effects.ts#L218)）。

つまり、起動してから別の画面へ移ると、実行が終わったことを知る手段が無い。戻ってくれば `openPage` が最新の実行を読み直すので、結果は見られる。見られるのは戻ってきたときだけである。

タブを別のアプリに切り替えた場合も同じで、ブラウザのタブの見出しは `BreadcrumbsService` が決めた固定の文字のまま変わらない（[breadcrumbs.service.ts:31-37](../src/app/webapp-common/shared/services/breadcrumbs.service.ts#L31)）。

失敗した場合も同じ扱いである。`failed` で終わった実行は、次に画面を開いたときに状態の文字として出る。`statusReason` の行が増えるだけで（[run-summary.component.html:10-13](../src/app/features/quality-pipeline/components/run-summary/run-summary.component.html#L10)）、失敗したことが目立つわけではない。

## なぜ変えるか

学習の実行は、待つあいだに別のことをするのが普通の使い方である。画面を開いたままにしなければ結果に気付けない作りは、その使い方を許していない。

一方で、常時追跡へ倒すのも正しくない。Effects を経路に閉じ込めた判断（[quality-pipeline.routes.ts:18-23](../src/app/features/quality-pipeline/quality-pipeline.routes.ts#L18)）には理由がある。この画面を開かない利用者にとって、この feature は存在しないほうがよい。全体へ移すと、誰も見ていない実行を全員のブラウザが追い続けることになる。

そのため、追跡の範囲を広げるのではなく、終わりを知らせる経路を別に足す。

## 解決とみなす状態

段を分けて決める。1と2だけでも成立する。

1. 実行中はタブの見出しに状態を出す。`Quality pipeline` を `● running — Quality pipeline` のように変え、終わったら戻す。画面を見ていなくても、タブの一覧で分かる
2. 追跡中に終端へ達したら通知を出す。`addMessage` は [layout.effects.ts:77-78](../src/app/webapp-common/core/effects/layout.effects.ts#L77) が受けて `NotifierService` へ渡し、外枠の `notifier-container`（[app.component.html:21](../src/app/app.component.html#L21)）が描く。アプリ全体に登録された Effects なので（[core.providers.ts:32](../src/app/core/core.providers.ts#L32)）、どの画面にいても見える。成功は自動で消える既定、失敗は消さない既定に既になっている（[app.config.ts:50](../src/app/app.config.ts#L50)）
3. 通知に、その実行を開く導線を `userActions` として載せる
4. 経路を離れても追跡を続けるかどうかは、別の判断として切り出す。続けるなら、自分が起動した実行に限る・アプリを開いているあいだに限る・1件だけ、の3条件を置く
5. ブラウザの通知（`Notification` API）は、4を決めてから検討する。許可を求める時機を誤ると、それ自体が嫌われる

## 変更の範囲

* 変更：[quality-pipeline-page.component.ts](../src/app/features/quality-pipeline/containers/quality-pipeline-page/quality-pipeline-page.component.ts)（タブの見出し。`Title` を直接触るか、`BreadcrumbsService` に接頭辞の口を作るか）
* 変更：[quality-pipeline.effects.ts](../src/app/features/quality-pipeline/state/quality-pipeline.effects.ts)。`runRefreshed` が終端に達したときに `addMessage` を流す effect を1本足す
* 判断：4の追跡範囲。決めたら ADR に残す

## 確かめ方

* 単体：終端への到達を1回だけ通知すること。`takeWhile(..., true)` が最後の1件を流す設計（[同:217](../src/app/features/quality-pipeline/state/quality-pipeline.effects.ts#L217)）と組み合わせたときに二重にならないこと
* E2E：[e2e/quality-pipeline.spec.ts](../e2e/quality-pipeline.spec.ts) で、実行の状態を `completed` に変えたモック応答の後に通知が出ることを確かめる

## 注意

`BreadcrumbsService` は凍結領域である。タブの見出しを feature から直接 `Title` で書き換えると、経路が変わったときに `BreadcrumbsService` 側の設定と競合する。どちらが後に書くかは経路の遷移の順序に依存するため、競合を避けるなら接頭辞を渡す口を作るほうが確実である。その場合は凍結領域の変更になる。
