# 再現に要る情報を画面に載せる

| 項目 | 内容 |
| --- | --- |
| 分類 | ML体験 |
| 領域 | 自作（`features/data-catalog`） |
| 直る体験 | 「この結果をもう一度出せるか」を、台帳の画面で判断できる |
| 規模 | 中 |
| 状態 | 未着手 |

## いま画面で起きていること

詳細画面の Facts に並ぶのは、種別ごとに3〜5項目である。

| 種別 | 項目 | 場所 |
| --- | --- | --- |
| Dataset | Version / Registered / Task id | [data-catalog.adapter.ts:136-140](../src/app/features/data-catalog/data-access/data-catalog.adapter.ts#L136) |
| Run | Dataset version / Started / Finished / Task id | [同:147-152](../src/app/features/data-catalog/data-access/data-catalog.adapter.ts#L147) |
| Model | Model version / Dataset version / Framework / Created by run / Model id | [同:159-165](../src/app/features/data-catalog/data-access/data-catalog.adapter.ts#L159) |

実行を再現するために要るもののうち、ここに出ているのは Dataset の版数だけである。出ていないものは、どのコードで走ったか（リポジトリ・ブランチ・コミット）、どの依存関係で走ったか、どの環境で走ったか（コンテナ像・Queue・実行した Worker）、どの設定で走ったか（学習のハイパーパラメータ・乱数の種）である。

これらは ClearML の Task が持っている。読み取っていないだけで、取りに行く経路はある（[data-catalog.adapter.ts:168-175](../src/app/features/data-catalog/data-access/data-catalog.adapter.ts#L168) は既に `hyperparams` と `runtime` から版数を読んでいる）。

値が無い項目は、行ごと消える。[data-catalog.adapter.ts:220-221](../src/app/features/data-catalog/data-access/data-catalog.adapter.ts#L220) の `definedFacts` が空文字の項目を落とすためである。`Dataset version` が読めなかった実行の詳細には、その行が現れない。「記録されていない」と「そもそもこの種別には無い項目」が、画面では同じに見える。

IDの扱いにも問題がある。`Task id`・`Model id`・`Created by run` は32桁の文字列で、[catalog-asset-facts.component.html:39](../src/app/features/data-catalog/components/catalog-asset-facts/catalog-asset-facts.component.html#L39) が素の文字として描く。選択してコピーする以外に使い道が無い。`Created by run` は実行のIDだが、リンクになっていない。取り込み領域には [`CopyClipboardComponent`](../src/app/webapp-common/shared/ui-components/indicators/copy-clipboard/copy-clipboard.component.ts) がある。

## なぜ変えるか

台帳の役割は横断の入口であって、詳細の置き換えではない（[data-catalog.consts.ts](../src/app/features/data-catalog/data-catalog.consts.ts) の `vendorLinkOf` の注釈）。そのため、すべてをここへ出す必要は無い。

ただし「この結果を再現できるか」は、詳細ではなく判断である。判断のためにClearMLの画面へ移り、タブを切り替え、戻ってくるのでは、横断の入口としての役割を果たしていない。判断に要る最小限は台帳に置き、その根拠を見たいときに ClearML へ渡すのが筋である。

再現できないことが分かることにも価値がある。コミットが記録されていない実行、未コミットの変更がある状態で走った実行は、再現できない。それが画面で分かれば、その実行の結果を根拠に使わない判断ができる。

## 解決とみなす状態

1. Run の Facts に、コードの出所（リポジトリ・ブランチ・コミット）と、未コミットの変更があったかどうかを足す。再現の判断に要る項目については、`definedFacts` で落とさず「記録なし」と出す。落としてよいのは、その種別に元から無い項目だけである
2. Run の Facts に、実行した Queue と Worker を足す
3. Model の Facts に、学習に使った主要なハイパーパラメータを足す。全部ではなく、`ml/` 側が「再現に要る」と決めたものに限る。どれを出すかは `ml/` と画面の両方に散らさず、Task のパラメータの節（section）1つに寄せて、その節をまるごと出す
4. IDにコピーの導線を付ける。`Created by run` はその実行の台帳ページへのリンクにする
5. 「再現できるか」を1行の結論として出す。コミットが記録されていて、未コミットの変更が無く、Dataset の版数が分かっているなら再現できる。1つでも欠ければ、欠けているものを名指しする

## 確かめ方

* 単体：記録が欠けている場合の表示。`definedFacts` の対象と対象外を分けたうえで、対象外の項目だけが消えること
* 単体：「再現できるか」の結論を導く純関数
* E2E：a11y 検査を維持する
