# 昇格と切り戻しを画面から行えるようにする

| 項目 | 内容 |
| --- | --- |
| 分類 | ML体験 |
| 領域 | 自作（`features/quality-pipeline`） |
| 直る体験 | どのモデルを提供するかの判断と、その実行が同じ画面で完結する |
| 規模 | 大 |
| 状態 | 未着手（画面から書き込んでよいかの判断が先） |

## いま画面で起きていること

提供中のモデルの欄は、読むだけである。

```
Model version / Dataset version / Promoted by / Promoted at /
Reason / Trained by task / Model id
```

［[production-model-card.component.html:2-17](../src/app/features/quality-pipeline/components/production-model-card/production-model-card.component.html#L2)］

昇格と切り戻しは、コマンドとして別に用意されている。

```
pnpm ml:model promote --model-id <id> --to production --approved-by <who> --reason <why>
pnpm ml:model rollback --approved-by <who> --reason <why>
```

［[ml/model_lifecycle/cli.py:74-97](../ml/model_lifecycle/cli.py#L74)］

`--approved-by` と `--reason` はどちらも必須である。CLI の冒頭がその理由を書いている。「誰も署名していない段階は拒否される」。画面に出ている `Promoted by` と `Reason` は、この2つが記録された結果である。

つまり、判断に要る材料（評価の指標、来歴、提供中のモデル）は画面にあり、判断の実行だけが画面の外にある。切り戻しはとくに問題で、提供中のモデルに問題が見つかったときに、ターミナルを開いて誰が承認したかを打ち込むことになる。

## なぜ変えるか

判断と実行が別の場所にあると、2つのことが起きる。画面で見た値と、コマンドに打ち込むIDが食い違いうること。そして、急ぐときほど記録が雑になることである。

`--approved-by` を手で打つ形は、打った人と承認した人が同じであることを保証しない。画面からであれば、ログイン中の利用者を記録できる。記録の質は、画面から行うほうが上がる。

一方で、画面から本番の切り替えができることには危うさもある。ClearML の権限がそのまま昇格の権限になってよいのかは、別に決める必要がある。

## 解決とみなす状態

段を分ける。1と2だけでも、いまの状態より良い。

1. 切り戻しと昇格のコマンドを、画面から組み立ててコピーできるようにする。IDは画面が埋める。実行はターミナルのまま
2. 昇格できる候補を画面に出す。いま提供中のモデルと、候補のモデルを並べ、指標の差を見せる（[12](./12_評価指標を比較として読めるようにする.md)）
3. 画面から昇格・切り戻しを実行する。理由の入力を必須にし、承認者はログイン中の利用者から取る。確認ダイアログを出す（[03](./03_取り消せない操作に退路を用意する.md)）
4. 切り戻しは、戻す先のモデルを画面に出してから実行する。`rollback` は「production が置き換えたモデルを戻す」動作なので、戻した結果どれが提供されるかを先に見せる
5. 昇格の履歴を出す。いまの画面は現在の1件しか持たない

## 変更の範囲

* 段1：`production-model-card` の変更のみ。コマンドの組み立てと `CopyClipboardComponent`
* 段3以降：`quality-pipeline-api.service.ts` に書き込みの経路。ClearML のモデルのタグ（`PRODUCTION_STAGE_TAG = 'stage:production'`）を付け替える操作になる
* 判断：昇格の判定を画面でやり直さない。`gate.py` と `registry.py` が持つ規則を画面へ写すと、規則を変えたときに片方だけ古くなる。画面から呼ぶ先は、規則を持っている側でなければならない
* 判断：ClearML のモデル更新 API を直接叩くと、`ml/model_lifecycle/registry.py` が行っている検証（宣言された遷移だけを実行する）を迂回する。迂回しないためには、画面が呼べる形で同じ規則を持つ何か（サービス）が要る

## 確かめ方

* 段1：組み立てたコマンドが、実際に通ること
* 段3：`registry.py` の検証を迂回していないこと。宣言されていない遷移（production から candidate へ戻すなど）が画面から起きないこと

## 注意

段3は、この画面を「見るための画面」から「本番を変える画面」へ変える。誰が押せるかを決めないまま入れられない。`ml/model_lifecycle` が承認者を必須にしている設計の意図を、画面側でも保つ必要がある。着手の前に ADR を1本立てる。
